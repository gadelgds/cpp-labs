Задание 1: task1_createthread_vs_beginthreadex.cpp

Полный построчный разбор — ни одна строка не пропущена
Шаг 1 
#include <windows.h>

Подключает Win32 API: CreateThread, WaitForSingleObject, CloseHandle, GetLastError. Без этого заголовка ни одна функция Windows недоступна — это главный API-заголовок для системного программирования.

Шаг 2 
#include <process.h>

Подключает _beginthreadex — CRT-обёртку для создания потоков. Именно ради этой функции нужен заголовок: второй вариант программы без него не скомпилируется.

Шаг 3 
#include <psapi.h>

Подключает GetProcessMemoryInfo и структуру PROCESS_MEMORY_COUNTERS_EX. Эта функция читает потребление памяти процесса — без неё рост было бы видно только в диспетчере задач.

Шаг 4 
#include <iostream>

Подключает std::cout и std::endl для вывода в консоль. Вывод нужен для наблюдения: какой вариант запущен, сколько потоков создано, сколько памяти занято.

Шаг 5 
#include <cstring>

Подключает strtok и strcpy для работы со строками. Функция потока разбирает строку именно через strtok — заголовок даёт её объявление.

Шаг 6 
const int THREAD_COUNT = 10000;

Задаёт число создаваемых потоков — 10 000, как требует задание. Константа вместо «магического числа» в цикле: число легко найти и поменять в одном месте.

Шаг 7 
const int STRTOK_CALLS = 100;

Задаёт, сколько раз один поток разбирает тестовую строку. Один вызов strtok почти ничего не стоит; сто вызовов подряд гарантируют, что поток реально пользуется CRT-функциями.

Шаг 8 
const char* TEST_STRING = "один,два,три;четыре пять:шесть";

Тестовая строка с разными разделителями: запятая, точка с запятой, пробел, двоеточие. Разные разделители показывают, что strtok режет строку по любому символу из набора, а не по одному.

Шаг 9 
DWORD WINAPI WorkerThread(LPVOID param)

Функция потока — код, который выполняет каждый из 10 000 потоков. Такую сигнатуру требует CreateThread: код возврата DWORD, соглашение о вызове WINAPI, один параметр-указатель.

Шаг 10 
char buffer[128];

Локальный буфер потока для копии тестовой строки. У каждого потока свой стек, поэтому свой буфер: потоки не мешают друг другу и не портят общую строку.

Шаг 11 
for (int i = 0; i < STRTOK_CALLS; ++i) {

Повторяет разбор строки 100 раз внутри одного потока. Многократный вызов — условие задания: именно повторение заставляет CRT каждый раз обращаться к своему состоянию потока.

Шаг 12 
strcpy(buffer, TEST_STRING);

Копирует исходную строку в буфер потока перед каждым разбором. strtok портит строку: ставит нули вместо разделителей. Без свежей копии второй разбор уже нечего было бы разбирать.

Шаг 13 
char* token = strtok(buffer, ",;: ");

Первый вызов strtok: начинает разбор буфера и возвращает первое слово. Первый вызов всегда получает указатель на строку, а разделители задаются строкой ",;: " — любой из этих символов режет слово.

Шаг 14 
while (token != nullptr) { token = strtok(nullptr, ",;: "); }

Доразбирает строку до конца: каждый следующий вызов с NULL продолжает с места остановки. Так устроен strtok: NULL означает «продолжай ту же строку». Цикл заканчивается, когда слова кончились и strtok вернул NULL.

Шаг 15 
return 0;

Функция потока возвращает 0 — поток завершается успешно. Возврат из функции потока — нормальный способ его завершить; система освободит его стек и закроет поток.

Шаг 16 
void PrintMemory(const char* label)

Вспомогательная функция: печатает потребление памяти с подписью. Вынесена отдельно, чтобы не дублировать один и тот же код трижды: на старте, каждые 1000 потоков и на финише.

Шаг 17 
PROCESS_MEMORY_COUNTERS_EX pmc;

Объявляет структуру, куда система запишет счётчики памяти процесса. Расширенная версия структуры нужна ради поля PrivateUsage — в обычной PROCESS_MEMORY_COUNTERS его нет.

Шаг 18 
if (GetProcessMemoryInfo(GetCurrentProcess(), ...)) {

Запрашивает у системы счётчики памяти текущего процесса. GetCurrentProcess возвращает псевдодескриптор своего процесса — удобный способ спросить систему о самом себе.

Шаг 19 
std::cout << label << " WorkingSet: " << pmc.WorkingSetSize / 1024 << " КБ" << " PrivateUsage: " << pmc.PrivateUsage / 1024 << " КБ"

Печатает рабочий набор и частную память процесса в килобайтах. Деление на 1024 переводит байты в килобайты — числа получаются короткими и читаемыми. Именно PrivateUsage соответствует столбцу Private Bytes в диспетчере задач.

Шаг 20 
else { std::cout << label << " (не удалось прочитать память..." }

Если чтение памяти не удалось — печатает подпись и код ошибки GetLastError(). Честная диагностика вместо молчания: сбой чтения памяти не должен выглядеть как нулевое потребление.

Шаг 21 
int main(int argc, char* argv[])

Точка входа программы с доступом к аргументам командной строки. Аргументы нужны для выбора варианта: без аргумента или create — CreateThread, begin — _beginthreadex.

Шаг 22 
#if defined(_WIN32) system("chcp 65001 > nul"); #endif

Переключает кодовую страницу консоли на UTF-8 (65001), чтобы русский текст не превращался в кракозябры. Директива препроцессора: команда выполняется только под Windows; на других системах код просто не компилируется в программу.

Шаг 23 
bool useBeginThreadEx = (argc > 1 && strcmp(argv[1], "begin") == 0);

Проверяет первый аргумент: равен ли он слову "begin". Один флаг решает всё поведение программы дальше: какая функция создаёт потоки. Любой другой аргумент (или его отсутствие) означает вариант CreateThread.

Шаг 24 
std::cout << "=== ЗАДАНИЕ 1 ..." / "Вариант: ..." / "Потоков к созданию: ..."

Печатает заголовок, выбранный вариант и число потоков. Сразу видно, какой вариант запущен: при сравнении двух прогонов нельзя перепутать, где какой.

Шаг 25 
PrintMemory("Старт:   ");

Печатает потребление памяти до создания потоков. Базовая точка для сравнения: рост считается от этого значения.

Шаг 26 
for (int i = 0; i < THREAD_COUNT; ++i) {

Главный цикл: 10 000 раз создаёт краткоживущий поток. Это и есть эксперимент задания: много коротких потоков подряд, каждый живёт долю секунды.

Шаг 27 
HANDLE hThread = nullptr;

Объявляет переменную дескриптора потока и обнуляет её. Обе функции создания возвращают дескриптор разного типа, а дальше код общий: одна переменная HANDLE принимает оба результата.

Шаг 28 
if (useBeginThreadEx) { uintptr_t h = _beginthreadex(nullptr, 0, reinterpret_cast<unsigned (__stdcall*)(void*)>(WorkerThread), nullptr, 0, nullptr); hThread = reinterpret_cast<HANDLE>(h); }

Создаёт поток через _beginthreadex — с инициализацией CRT-состояния потока. Это «правильный» вариант для программ на C/C++: _beginthreadex готовит CRT-данные потока до его старта. WorkerThread приводится к нужному типу указателя на функцию — сигнатуры совпадают по соглашению о вызовах, различается только тип возврата.

Шаг 29 
else { hThread = CreateThread(nullptr, 0, WorkerThread, nullptr, 0, nullptr); }

Создаёт поток «голым» вызовом CreateThread — без инициализации CRT. Это «проблемный» вариант задания: система создаёт поток, но CRT о нём ничего не знает и его данные никто не готовит.

Шаг 30 
if (hThread == nullptr) { std::cout << "Ошибка создания потока №" << i ... return 1; }

Проверяет, что поток создан; при ошибке печатает номер потока и код GetLastError() и завершает программу с кодом 1. Без проверки программа ждала бы по нулевому дескриптору. Номер потока показывает, на каком месте цикл сорвался.

Шаг 31 
WaitForSingleObject(hThread, INFINITE); CloseHandle(hThread);

Ждёт завершения потока, затем закрывает его дескриптор. Поток краткоживущий по условию: следующий создаётся только после завершения предыдущего. CloseHandle обязателен — незакрытый дескриптор держит объект потока в ядре.

Шаг 32 
if ((i + 1) % 1000 == 0) { std::cout << "Создано потоков: " << (i + 1) << "  "; PrintMemory(""); }

Каждую тысячу потоков печатает счётчик и текущий срез памяти. По этим строкам видна динамика: растёт ли память равномерно или стоит на месте. Печать на каждой итерации только замусорила бы вывод.

Шаг 33 
std::cout << "Создано потоков всего: " << THREAD_COUNT ... PrintMemory("Финиш:  ");

Печатает итог: всего потоков и финальный срез памяти. Финальная точка для сравнения со стартом: разница «Финиш минус Старт» — и есть результат эксперимента.

Шаг 34 
std::cout << "Сравните PrivateUsage ..." / "С CreateThread ... с _beginthreadex ..."

Подсказывает, как читать результат, и формулирует ожидаемый вывод опыта. На защите не нужно помнить теорию наизусть: программа сама говорит, что должно получиться.

Шаг 35 
return 0;

Успешное завершение программы с кодом 0. Код 0 — общепринятый признак нормального завершения; его видит вызывающая среда.

Задание 2: task2_suspended_hook.cpp

Полный построчный разбор — ни одна строка не пропущена
Шаг 1 
#include <windows.h>

Подключает Win32 API: CreateThread, GetThreadContext, SetThreadContext, ResumeThread, CONTEXT, CREATE_SUSPENDED. Все ключевые функции задания — из этого заголовка; без него не скомпилируется ни один вызов.

Шаг 2 
#include <iostream>

Подключает std::cout и std::endl для вывода в консоль. Вывод — доказательство перехвата: сообщения «ПЕРЕХВАТ» и «ОРИГИНАЛ» видны на экране.

Шаг 3 
const int FIB_N = 40;

Задаёт номер Фибоначчи для расчёта — 40. Константа в одном месте: поменять число для эксперимента можно одной правкой.

Шаг 4 
long long g_result = -1;

Глобальная переменная для результата расчёта, начальное значение −1 («ещё не посчитано»). Поток и main делят эту переменную: поток записывает ответ, main читает его после WaitForSingleObject. Значение −1 сразу показывает, что расчёт не выполнялся.

Шаг 5 
long long FibRecursive(int n) { if (n <= 1) return n; return FibRecursive(n - 1) + FibRecursive(n - 2); }

Рекурсивно вычисляет n-е число Фибоначчи: база — 0 и 1, остальное — сумма двух предыдущих. Выбран именно рекурсивный вариант: он тяжёлый (Fib(40) — около 100 миллионов вызовов, несколько секунд работы), поэтому поток — «настоящая работа», а не мгновенное действие. Итеративный вариант посчитал бы ответ за микросекунды и не показал бы, что поток реально трудился.

Шаг 6 
DWORD WINAPI FibThread(LPVOID param)

Оригинальная функция потока — та, с которой поток должен был стартовать. Её адрес передаётся в CreateThread как точка входа. Если перехват сработал, она не выполнится ни разу — это и есть проверка.

Шаг 7 
std::cout << "ОРИГИНАЛ: поток стартовал со своей функции FibThread."

Печатает сообщение о том, что выполняется оригинальная функция. Маркер-ловушка: если эта строка появилась в выводе — перехват не сработал. При успешном перехвате её не должно быть.

Шаг 8 
g_result = FibRecursive(FIB_N); std::cout << "ОРИГИНАЛ: Fib(" << FIB_N << ") = " << g_result

Считает Fib(40) и печатает результат с пометкой «ОРИГИНАЛ». Показывает, что должна была делать исходная функция, если бы перехват не вмешался.

Шаг 9 
DWORD WINAPI HookThread(LPVOID param)

Функция-перехватчик (хук) — та, с которой поток реально стартует после подмены RIP. Сигнатура такая же, как у функции потока: система запустит её как точку входа потока, передав тот же параметр в регистре RCX.

Шаг 10 
std::cout << "ПЕРЕХВАТ: поток стартовал с хука HookThread, а не с FibThread!"

Печатает сообщение о том, что выполнился именно хук. Главное доказательство перехвата: эта строка появляется только если процессор начал выполнять поток с адреса HookThread.

Шаг 11 
std::cout << "ПЕРЕХВАТ: выполняю расчёт Fib(" << FIB_N << ")..." g_result = FibRecursive(FIB_N); std::cout << "ПЕРЕХВАТ: Fib(" << FIB_N << ") = " << g_result

Хук сам выполняет расчёт и печатает результат с пометкой «ПЕРЕХВАТ». Хук не просто заявляет о себе, а делает работу за оригинал: вызывает ту же FibRecursive и записывает ответ в ту же переменную g_result.

Шаг 12 
int main() {

Точка входа программы. Весь сценарий: создать спящий поток → подменить RIP → оживить → дождаться результата.

Шаг 13 
#if defined(_WIN32) system("chcp 65001 > nul"); #endif

Переключает кодовую страницу консоли на UTF-8 (65001), чтобы русский текст не превращался в кракозябры. Директива препроцессора: команда выполняется только под Windows; на других системах код просто не компилируется в программу.

Шаг 14 
std::cout << "=== ЗАДАНИЕ 2 ..." / "Расчёт: Fib(40) рекурсивно."

Печатает заголовок программы и описание расчёта. Сразу видно, какая программа запущена и что она считает.

Шаг 15 
HANDLE hThread = CreateThread(nullptr, 0, FibThread, nullptr, CREATE_SUSPENDED, nullptr);

Создаёт поток приостановленным: поток создан, но не выполнил ни одной инструкции. Флаг CREATE_SUSPENDED — условие задания: только спящий поток можно безопасно «перехватить», пока он ещё ничего не начал делать.

Шаг 16 
if (hThread == nullptr) { std::cout << "Ошибка CreateThread: " << GetLastError() ... return 1; }

Проверяет создание потока; при ошибке печатает код и выходит с кодом 1. Без потока продолжать нечего: нет ни контекста, ни перехвата. Проверка обязательна.

Шаг 17 
std::cout << "Поток создан с CREATE_SUSPENDED и пока спит."

Подтверждает, что поток создан и приостановлен. В выводе фиксируется состояние «поток спит» — дальше с ним можно делать подмену контекста.

Шаг 18 
CONTEXT ctx; ZeroMemory(&ctx, sizeof(ctx));

Объявляет структуру контекста потока и обнуляет её. В локальной переменной — мусор из стека. Необнулённая структура может передать системе случайные флаги и значения регистров.

Шаг 19 
ctx.ContextFlags = CONTEXT_FULL;

Запрашивает полный набор регистров: все основные регистры, включая RIP. ОБЯЗАТЕЛЬНОЕ условие: без этого флага GetThreadContext не заполнит поле Rip (вернёт структуру с нулями), и подменять будет нечего.

Шаг 20 
if (!GetThreadContext(hThread, &ctx)) { ... return 1; }

Читает контекст приостановленного потока в структуру ctx. При ошибке печатает код и выходит. Это чтение «снимка» регистров потока в момент его сна. На работающем потоке так делать нельзя: регистры меняются каждую инструкцию, и снимок будет бессмысленным.

Шаг 21 
#ifdef _WIN64 std::cout << "Исходный RIP потока: 0x" << std::hex << ctx.Rip

На 64-битной сборке печатает исходное значение регистра RIP в шестнадцатеричном виде. Видно «до»: RIP указывает на начало FibThread. Шестнадцатеричный формат — стандарт для адресов.

Шаг 22 
ctx.Rip = reinterpret_cast<DWORD64>(HookThread);

Подменяет адрес следующей инструкции потока на адрес функции-перехватчика. Центральный шаг задания: процессор начнёт поток не с FibThread, а с HookThread. На x64 регистр называется RIP (на x86 был бы EIP) — поэтому код различает архитектуры.

Шаг 23 
std::cout << "Новый RIP потока: 0x" << std::hex << ctx.Rip << " (адрес HookThread)"

Печатает новое значение RIP после подмены. Видно «после»: адрес изменился на адрес хука — подмена зафиксирована до запуска потока.

Шаг 24 
#else ... ctx.Eip = reinterpret_cast<DWORD>(HookThread); ... #endif

На 32-битной сборке делает то же самое с регистром EIP вместо RIP. На x86 указатель инструкций называется EIP и занимает 32 бита. Ветка нужна для переносимости, хотя задание рассчитано на x64.

Шаг 25 
if (!SetThreadContext(hThread, &ctx)) { ... return 1; }

Записывает изменённый контекст обратно в поток. При ошибке печатает код и выходит. Без этого шага подмена осталась бы только в локальной структуре ctx и ни на что не повлияла бы: система узнаёт о новом RIP только через SetThreadContext.

Шаг 26 
std::cout << "Контекст изменён: поток стартует с хука."

Подтверждает, что контекст записан. В выводе фиксируется момент: подмена завершена, можно будить поток.

Шаг 27 
DWORD prevSuspend = ResumeThread(hThread);

Оживляет поток: уменьшает счётчик приостановки, поток начинает выполняться. Это «пуск»: первая же инструкция потока выполнится по новому адресу RIP — из HookThread. Возвращаемое значение — прежний счётчик приостановки (здесь 1).

Шаг 28 
std::cout << "ResumeThread вызван (счётчик приостановки был " << prevSuspend << "). Поток работает..."

Печатает прежний счётчик приостановки и факт запуска. Счётчик 1 подтверждает, что поток действительно был приостановлен ровно один раз и теперь работает.

Шаг 29 
WaitForSingleObject(hThread, INFINITE); CloseHandle(hThread);

Ждёт завершения потока (окончания расчёта), затем закрывает его дескриптор. Расчёт Fib(40) занимает секунды, main не должен завершиться раньше потока. CloseHandle освобождает объект потока в ядре.

Шаг 30 
std::cout << "Поток завершён. Итог: Fib(" << FIB_N << ") = " << g_result

Печатает итоговый результат расчёта из общей переменной. Main читает g_result только после WaitForSingleObject — значит, поток уже записал туда ответ, гонки нет.

Шаг 31 
if (g_result == 102334155) { std::cout << "Результат верный: Fib(40) = 102334155." }

Проверяет результат по известному значению Fib(40) = 102334155. Независимая проверка правильности: если хук посчитал неверно или вообще не посчитал, это сразу видно.

Шаг 32

задания 1–2

Задание 1. Почему с CreateThread растёт Private Bytes

Поток — это не только код и стек. У каждого потока есть ещё «личное дело» в библиотеке CRT: там хранятся данные функций вроде strtok и asctime. Эти функции не чистые: они запоминают состояние между вызовами. У strtok это указатель на место, где остановился разбор строки. Состояние лежит в TLS — памяти, отдельной для каждого потока.

CreateThread — это «голый» вызов Windows. Система создаёт поток, но CRT о нём ничего не знает: никто не выделил ему «личное дело» и никто его не заведёт. Когда поток первый раз вызывает strtok, CRT замечает отсутствие данных и выделяет их на ходу, в куче процесса. А когда поток завершается, освободить эти данные некому: завершение потока через CreateThread не вызывает код очистки CRT. Блок памяти остаётся в куче — навсегда.

Один поток теряет немного — порядка сотен байт. Но потоков 10 000, и каждый оставляет после себя свой блок. Потеря складывается: Private Bytes (память, принадлежащая только этому процессу) растёт с каждым потоком и после конца программы не возвращается. Это и есть утечка памяти: память выделена, но больше никому не нужна и никто её не освободит.

В диспетчере задач это видно так: запускаете вариант create и смотрите на столбец частной памяти процесса task1.exe — число ползёт вверх всё время работы программы. Программа и сама печатает PrivateUsage на старте, каждые 1000 потоков и на финише, поэтому рост виден и без диспетчера.

Задание 1. Почему с _beginthreadex потребление стабилизируется

_beginthreadex — это обёртка CRT над тем же CreateThread. Разница в том, что делает обёртка до и после работы потока. До старта потока она выделяет и инициализирует CRT-состояние потока: «личное дело» готово заранее, strtok работает с ним с первого вызова. После завершения потока она вызывает код очистки CRT: все данные потока, включая блок для strtok, освобождаются.

Итог: каждый поток прибирает за собой. Куча процесса не растёт от потока к потоку, Private Bytes колеблется около одного уровня — небольшие подъёмы и спады от текущей работы, но без постоянного роста. Поэтому правило простое: в программах на C/C++ потоки создают только через _beginthreadex (или std::thread, который делает то же самое внутри), а «голый» CreateThread оставляют для кода, который вообще не пользуется CRT.

Коротко: CreateThread не готовит и не убирает CRT-данные потока — каждый поток оставляет мусор, память растёт. _beginthreadex готовит данные до старта и освобождает их после финиша — мусора нет, память стоит на месте.

Задание 2. Приостановленный поток и CREATE_SUSPENDED

Обычно поток начинает работу сразу после создания. Флаг CREATE_SUSPENDED меняет это: поток создаётся, но «спит» — процессор не выполняет ни одной его инструкции. У потока есть счётчик приостановки: создание с этим флагом ставит его в 1. Пока счётчик больше нуля, поток не работает. ResumeThread уменьшает счётчик на 1; когда он становится нулём, поток оживает.

Пауза нужна, чтобы успеть что-то сделать с потоком до его старта. В задании это «что-то» — подмена точки входа. Без паузы поток начал бы выполнять свою функцию сразу, и менять было бы поздно.

Задание 2. Контекст потока и регистр RIP

Контекст потока — это снимок всех его регистров: значения, которые процессор держит в регистрах в данный момент. Самый важный здесь регистр — RIP (на x64) или EIP (на x86): указатель инструкций. Процессор всегда выполняет ту инструкцию, адрес которой лежит в RIP, а после её выполнения переходит к следующей.

GetThreadContext копирует регистры приостановленного потока в структуру CONTEXT, а SetThreadContext записывает структуру обратно в поток. Важное условие: перед вызовом GetThreadContext нужно поставить ContextFlags = CONTEXT_FULL — иначе система не знает, какие регистры вам нужны, и поле RIP останется пустым. И второе условие: поток обязан быть приостановлен — у работающего потока регистры меняются каждую инструкцию, снимок будет мусором.

Задание 2. Хук и доказательство перехвата

Хук (перехватчик) — это функция, которая выполняется вместо оригинальной. В задании мы просто меняем адрес в RIP: вместо адреса FibThread пишем адрес HookThread. Когда ResumeThread будит поток, процессор берёт первую инструкцию по новому адресу — и поток начинает работу с хука, даже не зная, что его «перехватили».

Доказательство перехвата — в выводе программы. Хук печатает «ПЕРЕХВАТ», а оригинальная функция печатала бы «ОРИГИНАЛ». Если в выводе есть «ПЕРЕХВАТ» и нет ни одного «ОРИГИНАЛ», значит, FibThread ни разу не выполнилась, а расчёт сделал хук. Дополнительная проверка: результат Fib(40) = 102334155 — известное значение, программа сверяет его сама.

Подмена RIP — приём отладки и исследования, а не обычный способ писать программы. В реальном коде так не делают: это хрупко (нужно точно знать соглашения о вызовах и состояние стека) и антивирусы воспринимают это как подозрительное поведение.

Ответ: CreateThread теряет память, _beginthreadex не теряет память.
