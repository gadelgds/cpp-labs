1. Процессы в Windows: дескрипторы, ядро, таблица хэндлов

Что это. Процесс — это экземпляр выполняющейся программы: собственное виртуальное адресное пространство, набор потоков, открытые ресурсы и блок окружения. Процессы в Windows полностью изолированы друг от друга: один процесс не может напрямую читать или менять память другого. Внутри процесса работает минимум один поток — единица выполнения кода на процессоре.

Зачем это знать. Вся лабораторная работа №6 построена на изоляции процессов: родитель и потомок — отдельные процессы, и именно поэтому изменение переменной у родителя не затрагивает потомка, а завершение родителя не убивает потомка.

Объекты ядра и дескрипторы. Процесс, поток, файл, событие, мьютекс — это объекты ядра (kernel objects): структуры данных, живущие в памяти ядра и недоступные напрямую из пользовательского кода. Программа обращается к ним только через дескриптор (handle, HANDLE) — целое число, индекс в таблице дескрипторов процесса. Дескриптор — это не указатель на объект, а «пропуск» к нему: по нему ядро находит объект и проверяет права доступа.

Таблица дескрипторов. У каждого процесса своя таблица хэндлов. Один и тот же числовой дескриптор в разных процессах означает разные объекты (или ничего). Поэтому дескриптор процесса-потомка, полученный через PROCESS_INFORMATION, действителен только в процессе-родителе, и закрывать его должен тоже родитель.

Счётчик ссылок. У каждого объекта ядра есть счётчик использований: он увеличивается при открытии нового дескриптора и уменьшается при CloseHandle. Объект уничтожается ядром только когда счётчик падает до нуля. Поэтому завершённый процесс продолжает «жить» в ядре как объект до тех пор, пока хоть кто-то держит его дескриптор открытым.

Ключевые правила
  • Процессы изолированы: память, дескрипторы и окружение у каждого свои.
  • Дескриптор — это индекс в таблице процесса, а не адрес объекта.
  • Завершение процесса не уничтожает его объект ядра, пока открыт хоть один дескриптор.
  • Завершение родителя не завершает потомка: у потомка своя жизнь.
Типичные ошибки
  • Считать, что дескриптор из одного процесса можно использовать в другом (без наследования или дублирования через DuplicateHandle).
  • Думать, что после завершения процесса его дескриптор «сам исчезнет» — нет, объект ядра останется до CloseHandle.
  • Путать PID (идентификатор процесса, число) и HANDLE (дескриптор объекта): PID — для поиска процесса, HANDLE — для операций с ним (ожидание, завершение, закрытие).
2. CreateProcess и структуры STARTUPINFO / PROCESS_INFORMATION

Что это. CreateProcess — основная функция Win32 API для создания нового процесса. Она загружает исполняемый файл, создаёт для него адресное пространство, объект процесса, главный поток и запускает его. Возвращает TRUE при успехе и FALSE при ошибке (код — через GetLastError()).

Зачем. Без CreateProcess программа не может запустить другую программу: это единственный штатный путь программного запуска в Win32 API (обёртки вроде system() внутри сами вызывают её же, но без контроля над дескрипторами и окружением).

STARTUPINFO — «как запускать»

Описывает внешний вид и начальные условия нового процесса: заголовок окна, его положение и размер, дескрипторы стандартных потоков ввода/вывода/ошибок, рабочий стол. Обязательные шаги: ZeroMemory(&si, sizeof(si)), затем si.cb = sizeof(si) — по полю cb система определяет версию структуры. В наших программах остальные поля остаются нулевыми — окно показывается обычным образом, потоки наследуются по умолчанию.

PROCESS_INFORMATION — «что получилось»

Сюда система записывает результат запуска — четыре поля:

ПолеЧто этоЗачем нужно
hProcessДескриптор объекта процесса-потомкаОжидание завершения (WaitForSingleObject), получение кода выхода, завершение процесса
hThreadДескриптор главного потока потомкаУправление потоком; закрывается вместе с hProcess
dwProcessIdPID процесса (число)Идентификация процесса, поиск в Диспетчере задач
dwThreadIdID главного потока (число)Идентификация потока
Ключевые правила
  • Всегда обнулять обе структуры через ZeroMemory перед вызовом и ставить si.cb = sizeof(si).
  • Командная строка (lpCommandLine) должна быть в изменяемом буфере (wchar_t cmdLine[]), а не строковым литералом: функция имеет право менять её на месте.
  • Всегда проверять возвращаемое значение: FALSE — процесс не создан, полей pi нет, закрывать нечего.
  • lpApplicationName = NULL — имя программы берётся из командной строки; относительное имя ищется в каталоге приложения, системных каталогах и PATH.
Типичные ошибки
  • Неинициализированная STARTUPINFO (мусор в полях) — непредсказуемые сбои запуска.
  • Передача строкового литерала как lpCommandLine — потенциальное нарушение доступа, так как литерал в памяти только для чтения.
  • Забытая проверка результата: программа продолжает работать с пустым pi и падает на WaitForSingleObject или CloseHandle по мусорному дескриптору.
  • Ожидание, что CreateProcess найдёт exe «где-то»: относительное имя ищется по строгим правилам — exe должен лежать рядом или быть в PATH.
3. Ожидание завершения: WaitForSingleObject

Что это. WaitForSingleObject(hHandle, dwMilliseconds) блокирует вызвавший поток до тех пор, пока указанный объект не перейдёт в сигнальное состояние (signaled), либо пока не истечёт тайм-аут. Дескриптор процесса становится сигнальным ровно в момент завершения процесса.

Зачем. Это способ синхронизации жизненного цикла: родитель узнаёт, что потомок закончил работу, и только потом продолжает свой сценарий (например, читает результаты или освобождает ресурсы). В задании 1 без ожидания программа завершилась бы сразу, не дождавшись закрытия Блокнота.

Возвращаемые значения
КодЗначение
WAIT_OBJECT_0Объект стал сигнальным — процесс завершился (нормальный исход)
WAIT_TIMEOUTИстёк тайм-аут, процесс всё ещё работает (бывает только при конечном тайм-ауте)
WAIT_FAILEDОшибка ожидания (например, неверный дескриптор) — код через GetLastError()
Ключевые правила
  • INFINITE — ждать без ограничения времени; подходит, когда момент завершения заранее неизвестен (пользователь сам закрывает Блокнот).
  • Результат ожидания всегда проверять: WAIT_OBJECT_0 — это единственный признак «процесс завершён».
  • Ждать можно только по действительному дескриптору, полученному от CreateProcess (или открытому через OpenProcess).
Типичные ошибки
  • Ожидание по hThread вместо hProcess: поток может завершиться раньше процесса (или процесс может породить другие потоки), и ожидание даст ложный сигнал.
  • Использование INFINITE там, где процесс может зависнуть навсегда: программа тоже зависнет без возможности отмены. Для таких случаев — конечный тайм-аут в цикле с проверкой.
  • Ожидание завершения потомка, которого родитель уже «отпустил» (закрыл дескриптор): ждать не по чему.
В задании 2 родитель намеренно НЕ вызывает WaitForSingleObject: он завершается мгновенно, а потомок продолжает работу. Это демонстрирует, что ожидание — выбор родителя, а не обязанность, и жизнь потомка от него не зависит.
4. Утечка дескрипторов и зачем нужен CloseHandle

Что это. CloseHandle(h) закрывает дескриптор: удаляет запись из таблицы дескрипторов процесса и уменьшает счётчик ссылок объекта ядра. Когда счётчик падает до нуля, ядро уничтожает объект и освобождает его память.

Зачем. CreateProcess возвращает сразу два дескриптора — процесса и потока. Пока хотя бы один из них открыт, ядро хранит объект завершённого процесса (включая его код завершения) в памяти. Если дескрипторы не закрывать, записи копятся: в короткой программе это незаметно, а в долгоживущем сервисе, запускающем тысячи процессов, таблица дескрипторов переполняется и новые CreateProcess начинают завершаться ошибкой. Это и есть утечка дескрипторов (handle leak) — аналог утечки памяти, но на уровне ядра.

Ключевые правила
  • Закрывать ОБА дескриптора из PROCESS_INFORMATION: и hProcess, и hThread. Забытый hThread — та же утечка.
  • Порядок закрытия значения не имеет.
  • Закрывать нужно даже если родитель не ждал потомка (задание 2): ожидание и закрытие — независимые действия.
  • Закрытие дескриптора НЕ завершает процесс и НЕ убивает поток: оно лишь отпускает ссылку родителя на объект ядра.
  • Закрывать дескриптор нужно ровно один раз: повторный CloseHandle по тому же значению может закрыть уже другой объект, которому система успела выдать тот же номер.
Типичные ошибки
  • Закрыт только hProcess, а hThread забыт (или наоборот).
  • CloseHandle пропущен в ветке ошибки после удачного CreateProcess (например, при ошибке WaitForSingleObject программа выходит, не закрыв дескрипторы).
  • Вера в то, что завершение родителя «само всё закроет»: да, при завершении процесса система закрывает все его дескрипторы, но пока родитель живёт и запускает процессы в цикле, утечка копится при его жизни.
Правило на защиту: «CreateProcess вернул два дескриптора — значит, в программе должно быть два CloseHandle». Если в коде один CloseHandle — это ошибка, даже если программа «работает».
5. Environment Block: как устроен и почему потомок получает копию

Что это. Environment Block (блок окружения) — область памяти процесса, в которой хранятся переменные окружения в виде строк ИМЯ=ЗНАЧЕНИЕ, разделённых нулевыми символами и завершающихся двойным нулём. Блок создаётся для каждого процесса при его запуске и живёт только в его собственном адресном пространстве.

Зачем. Переменные окружения — простейший механизм передачи конфигурации процессу на старте: пути (PATH, TEMP), настройки программ, в нашем случае — STUDENT_ID. Процесс читает их через GetEnvironmentVariable, не зная ничего о том, кто и как их задал.

Копирование при создании процесса. Когда родитель вызывает CreateProcess с lpEnvironment = NULL, система берёт блок окружения родителя, копирует его байт в байт и передаёт копию новому процессу. Копия — это ключевое слово: после этого у родителя и потомка два независимых блока в двух независимых адресных пространствах. Никакой общей памяти между ними нет.

Почему изменение у родителя не влияет на потомка. SetEnvironmentVariable меняет строку только в блоке текущего процесса. Родитель меняет свою копию, потомок свою копию не трогает — он о ней даже не знает. Поэтому порядок операций решает всё: то, что родитель установил ДО CreateProcess, попадёт в снимок потомка; то, что он поменял ПОСЛЕ, — уже нет. Это и демонстрирует задание 2: родитель ставит 19045, запускает потомка, меняет у себя на 99999 — потомок видит 19045.

Ключевые правила
  • Блок окружения принадлежит процессу и копируется при его создании (снимок «на момент старта»).
  • Передача конфигурации через окружение работает только в одну сторону и только в момент запуска: потомок не может «вернуть» значение родителю через окружение.
  • Если передать lpEnvironment не NULL, а собственный блок, потомок получит именно его вместо копии родительского (механизм явного задания окружения).
  • Изменения окружения действуют только на текущий процесс и его будущих потомков, но не на уже запущенные процессы и не на систему в целом.
Типичные ошибки
  • Ожидание, что SetEnvironmentVariable у родителя изменит переменную у уже запущенного потомка («общая память») — нет, это копия.
  • Установка переменной ПОСЛЕ CreateProcess с надеждой, что потомок её увидит, — потомок уже получил снимок без неё.
  • Запуск потомка из среды, где переменная уже задана иначе (например, глобально в системе), и удивление, что потомок видит не то значение.
6. SetEnvironmentVariable и GetEnvironmentVariable: переменная против блока

Что это. SetEnvironmentVariable(имя, значение) — устанавливает, изменяет или удаляет (если значение NULL) переменную окружения в блоке ТЕКУЩЕГО процесса. GetEnvironmentVariable(имя, буфер, размер) — читает переменную из блока текущего процесса в буфер, возвращая длину значения; 0 означает «не найдена» (тогда GetLastError() вернёт ERROR_ENVVAR_NOT_FOUND, код 203) или пустое значение.

Переменная против блока. Переменная — одна строка ИМЯ=ЗНАЧЕНИЕ; блок — весь набор таких строк процесса. SetEnvironmentVariable правит одну строку в своём блоке, CreateProcess с lpEnvironment = NULL копирует весь блок целиком. Поэтому: установить переменную — это про один процесс; запустить потомка — это про передачу всего блока снимком.

Ключевые правила
  • SetEnvironmentVariable влияет только на текущий процесс (и на его будущих потомков через копирование блока).
  • Она не меняет системные переменные и не видна другим уже запущенным программам; чтобы поменять переменную «для всей системы», нужна запись в реестр и рассылка сообщения WM_SETTINGCHANGE — это другой механизм.
  • У GetEnvironmentVariable размер буфера задаётся в символах, а не в байтах: для wchar_t buffer[256] это sizeof(buffer) / sizeof(buffer[0]) = 256.
  • Код ошибки GetLastError() читать сразу после неудачного вызова: следующий вызов API его перезапишет.
  • Если значение не помещается в буфер, GetEnvironmentVariable возвращает требуемую длину — это не ошибка «не найдено», а сигнал дать буфер больше.
Типичные ошибки
  • Путаница SetEnvironmentVariable (локально, в процессе) с системными переменными среды Windows (реестр, «Свойства системы»): первая не видна другим программам.
  • Передача размера буфера в байтах вместо символов для широкой версии функции — буфер «обрезается» в два раза.
  • Игнорирование возврата 0 без проверки GetLastError(): ноль может означать и «переменная не задана», и «значение пустое».
  • Сравнение широких строк через strcmp вместо wcscmp — сравнение пойдёт по байтам и даст неверный результат.
Итог лабораторной: задание 1 показывает, как процесс рождается, ожидается и аккуратно «убирается» из ядра (CreateProcess → WaitForSingleObject → CloseHandle × 2). Задание 2 показывает, что процессы — автономные миры: конфигурация передаётся только снимком блока окружения в момент старта, а дальше каждый живёт своей жизнью.
