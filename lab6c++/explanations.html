Задание 1: Жизненный цикл процесса и очистка ресурсов ядра
task1_createprocess_notepad.cpp
Полный построчный разбор — ни одна строка не пропущена
Шаг 1
#include <windows.h>

Подключает Win32 API: CreateProcess, WaitForSingleObject, CloseHandle, STARTUPINFO, PROCESS_INFORMATION, ZeroMemory, GetLastError. Без этого заголовка ни одна функция Windows недоступна — это главный API-заголовок для системного программирования.

Шаг 2
#include <iostream>

Подключает std::cout / std::endl для вывода в консоль. Вывод нужен для наблюдения за жизненным циклом: запуск, ожидание, закрытие.

Шаг 3
int main() {

Точка входа консольного приложения. Здесь живёт весь сценарий: запуск → ожидание → очистка.

Шаг 4
#if defined(_WIN32) system("chcp 65001 > nul"); #endif

Переключает кодовую страницу консоли на UTF-8 (65001), чтобы русский текст не превращался в кракозябры. Директива препроцессора: команда выполняется только под Windows; на других системах код просто не компилируется в программу.

Шаг 5
std::cout << "=== ЗАДАНИЕ 1 ..."

Печатает заголовок программы. Маркер в выводе: видно, какая программа запущена и что она делает.

Шаг 6
std::cout << "Запускаем Блокнот..."

Сообщает пользователю о начале запуска. Пользователь понимает, что сейчас откроется окно Блокнота — это не случайный процесс.

Шаг 7
STARTUPINFO si;

Объявляет структуру с параметрами запуска: внешний вид окна, дескрипторы стандартных потоков. Без неё CreateProcess не знает, как показать окно нового процесса.

Шаг 8
PROCESS_INFORMATION pi;

Объявляет структуру для результатов: сюда система запишет дескрипторы процесса и потока и их ID. Это наш единственный способ получить дескриптор запущенного процесса — без него нельзя ни ждать его, ни закрыть.

Шаг 9
ZeroMemory(&si, sizeof(si));

Заполняет всю структуру si нулями. В локальных переменных — мусор из стека. Случайный бит во флагах STARTUPINFO может заставить CreateProcess вести себя непредсказуемо.

Шаг 10
ZeroMemory(&pi, sizeof(pi));

То же обнуление для структуры результатов. Защита от мусора: при ошибке CreateProcess поля pi останутся нулями, а не случайными значениями.

Шаг 11
si.cb = sizeof(si);

Записывает в поле cb размер структуры в байтах. CreateProcess по этому полю определяет версию структуры. Если cb равен 0 или мусору — вызов завершится ошибкой ERROR_INVALID_PARAMETER.

Шаг 12
wchar_t cmdLine[] = L"notepad.exe";

Создаёт изменяемый буфер с командной строкой запуска Блокнота (широкие символы, Unicode). Документация требует именно изменяемый буфер: CreateProcess имеет право менять строку на месте. Строковый литерал напрямую передавать нельзя — он в памяти только для чтения.

Шаг 13
BOOL ok = CreateProcess( ... );

Создаёт новый процесс notepad.exe и возвращает TRUE при успехе, FALSE при ошибке. Это центральный вызов задания: только здесь рождается дочерний процесс. Результат обязательно проверяется.

Шаг 14
NULL, // lpApplicationName

Имя исполняемого файла не задано отдельно. Когда первый параметр NULL, система берёт имя программы из командной строки — в нашем случае "notepad.exe".

Шаг 15
cmdLine, // lpCommandLine

Передаёт командную строку с именем программы. Система ищет notepad.exe по правилам поиска исполняемых файлов (каталог приложения, системные каталоги, PATH). Блокнот есть в любой Windows — путь указывать не нужно.

Шаг 16
NULL, // lpProcessAttributes

Атрибуты безопасности процесса — по умолчанию. Дескриптор процесса нельзя будет унаследовать дочерними процессами; для задания это не нужно.

Шаг 17
NULL, // lpThreadAttributes

Атрибуты безопасности главного потока — по умолчанию. То же, что и для процесса: наследование дескриптора потока не требуется.

Шаг 18
FALSE, // bInheritHandles

Запрещает Блокноту наследовать дескрипторы нашей программы. Наследование открыло бы Блокноту доступ к нашим файлам и объектам. Здесь это не нужно и небезопасно.

Шаг 19
0, // dwCreationFlags

Без особых флагов создания. Процесс создаётся обычным образом: не приостановленным, не в отдельной консоли, не с повышенными правами.

Шаг 20
NULL, // lpEnvironment

Блок окружения для потомка не задан явно. NULL означает: потомок получает копию блока окружения родителя. Для Блокнота это нормально; механизм копии подробно разбирается в задании 2.

Шаг 21
NULL, // lpCurrentDirectory

Рабочий каталог потомка не задан явно. NULL означает: потомок наследует текущий каталог родителя. Блокноту каталог не важен.

Шаг 22
&si, // lpStartupInfo

Передаёт заполненную структуру запуска. Система читает отсюда, как показать окно Блокнота (по умолчанию — обычное окно).

Шаг 23
&pi // lpProcessInformation

Передаёт адрес структуры для результатов. Сюда система запишет hProcess, hThread, dwProcessId, dwThreadId — всё, что нужно для ожидания и очистки.

Шаг 24
if (!ok) { ... return 1; }

Если CreateProcess вернул FALSE — печатает код ошибки через GetLastError() и завершает программу с кодом 1. Без этой проверки программа продолжила бы ждать по мусорному дескриптору. Код 1 сигнализирует системе, что запуск не удался.

Шаг 25
std::cout << "Блокнот запущен. PID процесса: " << pi.dwProcessId ...

Выводит ID процесса и ID его главного потока. PID — доказательство, что процесс реально создан; по нему его можно найти в Диспетчере задач.

Шаг 26
std::cout << "Ждём, пока вы закроете Блокнот..."

Объясняет, почему консоль «зависла». Без этой строки ожидание выглядит как зависание программы; пользователь должен знать, что нужно закрыть Блокнот.

Шаг 27
DWORD waitResult = WaitForSingleObject(pi.hProcess, INFINITE);

Блокирует поток до тех пор, пока дескриптор процесса не станет сигнальным, то есть пока Блокнот не завершится. Ждёт без ограничения времени. Это и есть «дождаться закрытия»: дескриптор процесса переходит в сигнальное состояние ровно в момент его завершения. INFINITE — пользователь может держать Блокнот открытым сколь угодно долго.

Шаг 28
if (waitResult == WAIT_OBJECT_0) { ... }

Проверяет, что ожидание завершилось именно завершением процесса, а не ошибкой. WAIT_OBJECT_0 — нормальный исход. Любой другой код означает сбой ожидания, и его надо показать, а не молча идти дальше.

Шаг 29
std::cout << "Блокнот закрыт пользователем."

Подтверждает, что ожидание закончилось. Пользователь видит, что программа заметила закрытие Блокнота.

Шаг 30
else { std::cout << "WaitForSingleObject вернул неожиданный код..." }

Ветка ошибки ожидания: печатает код возврата и GetLastError(). Честная диагностика вместо молчания: если ожидание сорвалось, причина должна быть видна.

Шаг 31
CloseHandle(pi.hProcess);

Закрывает дескриптор процесса Блокнота. КРИТИЧЕСКОЕ УСЛОВИЕ ЗАДАНИЯ. Пока дескриптор открыт, ядро хранит объект процесса и его код завершения в памяти, даже после завершения процесса. Незакрытый дескриптор — утечка ресурса ядра и занятая запись в таблице дескрипторов.

Шаг 32
CloseHandle(pi.hThread);

Закрывает дескриптор главного потока Блокнота. CreateProcess возвращает ДВА дескриптора, и закрыть нужно ОБА. Забытый hThread — та же утечка, что и забытый hProcess. Порядок закрытия значения не имеет.

Шаг 33
std::cout << "Дескрипторы ... закрыты ..."

Подтверждает выполнение очистки. На защите видно, что программа дошла до CloseHandle, а не завершилась раньше.

Шаг 34
return 0;

Успешное завершение программы с кодом 0. Код 0 — общепринятый признак нормального завершения; его видит вызывающая среда.

Переключает консоль на UTF-8 для корректного русского текста. Без этого русские строки в выводе превратятся в кракозябры. Выполняется только под Windows.

Важно: меняется только память этого процесса — ни система, ни другие процессы переменную не увидят. Проверка обязательна: без переменной запускать потомка бессмысленно.

std::cout << "Parent: установлена переменная STUDENT_ID="; std::wcout << valueBefore

Выводит установленное значение на экран. Фиксирует «до»: на защите видно, что переменная была именно 19045 до запуска потомка. std::wcout нужен для широкой строки — обычный cout её не напечатает корректно.

Шаг 10
STARTUPINFO si;

Объявляет структуру параметров запуска потомка. Без неё CreateProcess не вызвать.

ZeroMemory(&si, sizeof(si));

Шаг 13
ZeroMemory(&pi, sizeof(pi));

Обнуляет структуру результатов. При ошибке запуска поля останутся нулями, а не мусором.

Шаг 14
si.cb = sizeof(si);

Указывает размер структуры STARTUPINFO. Без корректного cb CreateProcess вернёт ошибку ERROR_INVALID_PARAMETER.

Шаг 15
wchar_t cmdLine[] = L"Child.exe";

Изменяемый буфер командной строки с относительным именем потомка. Относительное имя — суть условия запуска: Child.exe ищется рядом с Parent.exe. Буфер должен быть изменяемым, потому что CreateProcess может менять строку на месте.

Шаг 16
BOOL ok = CreateProcess( ... );

Создаёт процесс Child.exe, возвращает TRUE при успехе. Центральный вызов: именно в этот момент система копирует блок окружения родителя потомку.

Шаг 17
NULL, // lpApplicationName

Имя программы не задано отдельно. Имя берётся из командной строки — "Child.exe".

Шаг 18
cmdLine, // lpCommandLine

Командная строка запуска потомка. Относительный путь: поиск идёт сначала в каталоге Parent.exe, затем в системных каталогах и PATH.

Шаг 19
NULL, // lpProcessAttributes

Атрибуты безопасности процесса — по умолчанию. Дескриптор потомка не наследуется дальше; для задания это не нужно.

Шаг 20
NULL, // lpThreadAttributes

Атрибуты безопасности потока — по умолчанию. То же: наследование дескриптора потока не требуется.

Шаг 21
FALSE, // bInheritHandles

Потомок не наследует дескрипторы родителя. Потомку не нужны открытые файлы и объекты родителя; наследование только расширило бы поверхность доступа.

Шаг 22
0, // dwCreationFlags

Без особых флагов создания. Потомок стартует сразу, в обычном режиме, в той же консоли неявно (у консольного потомка — своё окно/консоль по правилам системы).

Шаг 23

Явный блок окружения не передан. КЛЮЧЕВОЙ МОМЕНТ ЗАДАНИЯ: NULL означает «передай потомку копию моего блока окружения». Копия делается в момент CreateProcess — позже родитель свою копию меняет, а у потомка остаётся снимок.

Шаг 24
NULL, // lpCurrentDirectory

Рабочий каталог потомка не задан. Потомок наследует текущий каталог родителя — для поиска Child.exe это не влияет, важен каталог Parent.exe.

Шаг 25
&si, // lpStartupInfo

Передаёт параметры запуска. Система читает отсюда настройки окна потомка.

&pi // lpProcessInformation

Передаёт структуру для результатов. Отсюда берём dwProcessId потомка и дескрипторы hProcess/hThread.

if (!ok) { ... return 1; }

Шаг 29
const wchar_t* valueAfter = L"99999";

Новое значение переменной для перезаписи у себя. Любое, отличное от 19045, — чтобы разница была очевидна. Вынесено в константу для наглядности.

if (!SetEnvironmentVariable(varName, valueAfter)) { ... }

Перезаписывает STUDENT_ID на 99999 В СВОЁМ блоке окружения. Ветка else печатает оба факта: у себя стало 99999, а у потомка осталась копия 19045. Это шаг 3 задания — доказательство автономности. Порядок критичен: перезапись идёт СТРОГО ПОСЛЕ CreateProcess. Если бы она была до — потомок получил бы уже 99999, и эксперимент был бы испорчен.

Шаг 31
CloseHandle(pi.hProcess);

Закрывает дескриптор процесса-потомка. Родитель не ждёт потомка, но дескриптор всё равно надо закрыть: иначе объект процесса будет висеть в ядре как утечка (см. задание 1). Закрытие дескриптора НЕ завершает потомка.

Шаг 32
CloseHandle(pi.hThread);

Закрывает дескриптор главного потока потомка. Оба дескриптора из PROCESS_INFORMATION закрываются всегда, даже если ожидание не использовалось.

Шаг 33
std::cout << "Parent: дескрипторы потомка закрыты..."

Сообщает о завершении очистки. Видно, что родитель дошёл до конца сценария и ничего не забыл.

Шаг 34
return 0;

Родитель мгновенно завершается с кодом 0. Это шаг 3 задания: родитель уходит сразу, а потомок продолжает жить сам — завершение родителя потомка не убивает.

Задание 2 (часть 2): Child.exe — потомок
task2_child.cpp
Полный построчный разбор — Child.exe
Шаг 1
#include <windows.h>

Подключает Win32 API: GetEnvironmentVariable, ERROR_ENVVAR_NOT_FOUND. Чтение переменных окружения — функция Windows API.

Шаг 2
#include <iostream>

Подключает std::cout и std::wcout для вывода. Вывод значения переменной и доказательства автономности.

Шаг 3
int main() {

Точка входа программы Child.exe. Сценарий потомка: прочитать переменную → сравнить → доказать → ждать клавишу.

Шаг 4
#if defined(_WIN32) system("chcp 65001 > nul"); #endif

Переключает консоль на UTF-8 для русского текста. Без этого русский вывод станет кракозябрами. Только под Windows.

Шаг 5
std::cout << "=== ЗАДАНИЕ 2: CHILD ..."

Печатает заголовок программы. Различает окна родителя и потомка на экране.

Шаг 6
const wchar_t* varName = L"STUDENT_ID";

Имя искомой переменной окружения. То же имя, что устанавливал родитель; опечатка здесь — и переменная «не найдётся».

Шаг 7
wchar_t buffer[256];

Буфер на стеке для значения переменной (256 широких символов). GetEnvironmentVariable не возвращает строку, а копирует её в буфер, который даёт вызывающий. 256 символов с запасом хватает для короткого значения.

Шаг 8
DWORD len = GetEnvironmentVariable(varName, buffer, sizeof(buffer) / sizeof(buffer[0]));

Читает STUDENT_ID из собственного блока окружения процесса в буфер. Возвращает длину значения без завершающего нуля; 0 — переменная не найдена или пуста. Это шаг 4 задания: потомок читает то, что получил в копии блока при старте. Размер передаётся в символах, а не в байтах, поэтому sizeof делят на sizeof(wchar_t).

Шаг 9
if (len == 0) {

Ветка: переменная не прочитана. Ноль — единственный сигнал проблемы; дальше нужно выяснить причину через GetLastError().

Шаг 10
DWORD err = GetLastError();

Сохраняет код последней ошибки сразу после неудачного вызова. GetLastError() нужно читать немедленно: любой следующий вызов API перезапишет код. Сохранение в переменную — правильный приём.

Шаг 11
if (err == ERROR_ENVVAR_NOT_FOUND) { ... }

Если код равен 203 (ERROR_ENVVAR_NOT_FOUND) — печатает понятное объяснение: переменная не задана, скорее всего Child запущен напрямую без Parent.exe. Это главный диагностический случай: отдельный запуск Child.exe — штатная ситуация, и программа должна объяснить её, а не просто упасть.

Шаг 12
else { std::cout << "Ошибка GetEnvironmentVariable: " << err ... }

Любая другая ошибка — печатается её код. Например, ERROR_ENVVAR_NOT_FOUND — не единственная возможность: слишком маленький буфер даёт другую логику (возврат нужной длины), а прочие коды — редкие сбои API.

Теория: процессы Windows и Environment Block
1. Процессы в Windows: дескрипторы, ядро, таблица хэндлов

Что это. Процесс — это экземпляр выполняющейся программы: собственное виртуальное адресное пространство, набор потоков, открытые ресурсы и блок окружения. Процессы в Windows полностью изолированы друг от друга: один процесс не может напрямую читать или менять память другого. Внутри процесса работает минимум один поток — единица выполнения кода на процессоре.

Зачем это знать. Вся лабораторная работа №6 построена на изоляции процессов: родитель и потомок — отдельные процессы, и именно поэтому изменение переменной у родителя не затрагивает потомка, а завершение родителя не убивает потомка.

Объекты ядра и дескрипторы. Процесс, поток, файл, событие, мьютекс — это объекты ядра (kernel objects): структуры данных, живущие в памяти ядра и недоступные напрямую из пользовательского кода. Программа обращается к ним только через дескриптор (handle, HANDLE) — целое число, индекс в таблице дескрипторов процесса. Дескриптор — это не указатель на объект, а «пропуск» к нему: по нему ядро находит объект и проверяет права доступа.

Таблица дескрипторов. У каждого процесса своя таблица хэндлов. Один и тот же числовой дескриптор в разных процессах означает разные объекты (или ничего). Поэтому дескриптор процесса-потомка, полученный через PROCESS_INFORMATION, действителен только в процессе-родителе, и закрывать его должен тоже родитель.

Счётчик ссылок. У каждого объекта ядра есть счётчик использований: он увеличивается при открытии нового дескриптора и уменьшается при CloseHandle. Объект уничтожается ядром только когда счётчик падает до нуля. Поэтому завершённый процесс продолжает «жить» в ядре как объект до тех пор, пока хоть кто-то держит его дескриптор открытым.

Ключевые правила
  • Процессы изолированы: память, дескрипторы и окружение у каждого свои.
  • Дескриптор — это индекс в таблице процесса, а не адрес объекта.
  • Завершение процесса не уничтожает его объект ядра, пока открыт хоть один дескриптор.
  • Завершение родителя не завершает потомка: у потомка своя жизнь.
Типичные ошибки
  • Считать, что дескриптор из одного процесса можно использовать в другом (без наследования или дублирования через DuplicateHandle).
  • Думать, что после завершения процесса его дескриптор «сам исчезнет» — нет, объект ядра останется до CloseHandle.
  • Путать PID (идентификатор процесса, число) и HANDLE (дескриптор объекта): PID — для поиска процесса, HANDLE — для операций с ним (ожидание, завершение, закрытие).
2. CreateProcess и структуры STARTUPINFO / PROCESS_INFORMATION

Что это. CreateProcess — основная функция Win32 API для создания нового процесса. Она загружает исполняемый файл, создаёт для него адресное пространство, объект процесса, главный поток и запускает его. Возвращает TRUE при успехе и FALSE при ошибке (код — через GetLastError()).

Зачем. Без CreateProcess программа не может запустить другую программу: это единственный штатный путь программного запуска в Win32 API (обёртки вроде system() внутри сами вызывают её же, но без контроля над дескрипторами и окружением).

STARTUPINFO — «как запускать»

Описывает внешний вид и начальные условия нового процесса: заголовок окна, его положение и размер, дескрипторы стандартных потоков ввода/вывода/ошибок, рабочий стол. Обязательные шаги: ZeroMemory(&si, sizeof(si)), затем si.cb = sizeof(si) — по полю cb система определяет версию структуры. В наших программах остальные поля остаются нулевыми — окно показывается обычным образом, потоки наследуются по умолчанию.

PROCESS_INFORMATION — «что получилось»

Сюда система записывает результат запуска — четыре поля:

Ключевые правила
  • Всегда обнулять обе структуры через ZeroMemory перед вызовом и ставить si.cb = sizeof(si).
  • Командная строка (lpCommandLine) должна быть в изменяемом буфере (wchar_t cmdLine[]), а не строковым литералом: функция имеет право менять её на месте.
  • Всегда проверять возвращаемое значение: FALSE — процесс не создан, полей pi нет, закрывать нечего.
  • lpApplicationName = NULL — имя программы берётся из командной строки; относительное имя ищется в каталоге приложения, системных каталогах и PATH.
Типичные ошибки
  • Неинициализированная STARTUPINFO (мусор в полях) — непредсказуемые сбои запуска.
  • Передача строкового литерала как lpCommandLine — потенциальное нарушение доступа, так как литерал в памяти только для чтения.
  • Забытая проверка результата: программа продолжает работать с пустым pi и падает на WaitForSingleObject или CloseHandle по мусорному дескриптору.
  • Ожидание, что CreateProcess найдёт exe «где-то»: относительное имя ищется по строгим правилам — exe должен лежать рядом или быть в PATH.
3. Ожидание завершения: WaitForSingleObject

Что это. WaitForSingleObject(hHandle, dwMilliseconds) блокирует вызвавший поток до тех пор, пока указанный объект не перейдёт в сигнальное состояние (signaled), либо пока не истечёт тайм-аут. Дескриптор процесса становится сигнальным ровно в момент завершения процесса.

Зачем. Это способ синхронизации жизненного цикла: родитель узнаёт, что потомок закончил работу, и только потом продолжает свой сценарий (например, читает результаты или освобождает ресурсы). В задании 1 без ожидания программа завершилась бы сразу, не дождавшись закрытия Блокнота.

Возвращаемые значения

WAIT_TIMEOUTИстёк тайм-аут, процесс всё ещё работает (бывает только при конечном тайм-ауте)

Ключевые правила
  • INFINITE — ждать без ограничения времени; подходит, когда момент завершения заранее неизвестен (пользователь сам закрывает Блокнот).
  • Результат ожидания всегда проверять: WAIT_OBJECT_0 — это единственный признак «процесс завершён».
  • Ждать можно только по действительному дескриптору, полученному от CreateProcess (или открытому через OpenProcess).
Типичные ошибки
  • Ожидание по hThread вместо hProcess: поток может завершиться раньше процесса (или процесс может породить другие потоки), и ожидание даст ложный сигнал.
  • Использование INFINITE там, где процесс может зависнуть навсегда: программа тоже зависнет без возможности отмены. Для таких случаев — конечный тайм-аут в цикле с проверкой.
  • Ожидание завершения потомка, которого родитель уже «отпустил» (закрыл дескриптор): ждать не по чему.
В задании 2 родитель намеренно НЕ вызывает WaitForSingleObject: он завершается мгновенно, а потомок продолжает работу. Это демонстрирует, что ожидание — выбор родителя, а не обязанность, и жизнь потомка от него не зависит.
4. Утечка дескрипторов и зачем нужен CloseHandle

Что это. CloseHandle(h) закрывает дескриптор: удаляет запись из таблицы дескрипторов процесса и уменьшает счётчик ссылок объекта ядра. Когда счётчик падает до нуля, ядро уничтожает объект и освобождает его память.

Зачем. CreateProcess возвращает сразу два дескриптора — процесса и потока. Пока хотя бы один из них открыт, ядро хранит объект завершённого процесса (включая его код завершения) в памяти. Если дескрипторы не закрывать, записи копятся: в короткой программе это незаметно, а в долгоживущем сервисе, запускающем тысячи процессов, таблица дескрипторов переполняется и новые CreateProcess начинают завершаться ошибкой. Это и есть утечка дескрипторов (handle leak) — аналог утечки памяти, но на уровне ядра.

Ключевые правила
  • Закрывать ОБА дескриптора из PROCESS_INFORMATION: и hProcess, и hThread. Забытый hThread — та же утечка.
  • Порядок закрытия значения не имеет.
  • Закрывать нужно даже если родитель не ждал потомка (задание 2): ожидание и закрытие — независимые действия.
  • Закрытие дескриптора НЕ завершает процесс и НЕ убивает поток: оно лишь отпускает ссылку родителя на объект ядра.
  • Закрывать дескриптор нужно ровно один раз: повторный CloseHandle по тому же значению может закрыть уже другой объект, которому система успела выдать тот же номер.
Типичные ошибки
  • Закрыт только hProcess, а hThread забыт (или наоборот).
  • CloseHandle пропущен в ветке ошибки после удачного CreateProcess (например, при ошибке WaitForSingleObject программа выходит, не закрыв дескрипторы).
  • Вера в то, что завершение родителя «само всё закроет»: да, при завершении процесса система закрывает все его дескрипторы, но пока родитель живёт и запускает процессы в цикле, утечка копится при его жизни.
Правило на защиту: «CreateProcess вернул два дескриптора — значит, в программе должно быть два CloseHandle». Если в коде один CloseHandle — это ошибка, даже если программа «работает».
5. Environment Block: как устроен и почему потомок получает копию

Что это. Environment Block (блок окружения) — область памяти процесса, в которой хранятся переменные окружения в виде строк ИМЯ=ЗНАЧЕНИЕ, разделённых нулевыми символами и завершающихся двойным нулём. Блок создаётся для каждого процесса при его запуске и живёт только в его собственном адресном пространстве.

Зачем. Переменные окружения — простейший механизм передачи конфигурации процессу на старте: пути (PATH, TEMP), настройки программ, в нашем случае — STUDENT_ID. Процесс читает их через GetEnvironmentVariable, не зная ничего о том, кто и как их задал.

Копирование при создании процесса. Когда родитель вызывает CreateProcess с lpEnvironment = NULL, система берёт блок окружения родителя, копирует его байт в байт и передаёт копию новому процессу. Копия — это ключевое слово: после этого у родителя и потомка два независимых блока в двух независимых адресных пространствах. Никакой общей памяти между ними нет.

Почему изменение у родителя не влияет на потомка. SetEnvironmentVariable меняет строку только в блоке текущего процесса. Родитель меняет свою копию, потомок свою копию не трогает — он о ней даже не знает. Поэтому порядок операций решает всё: то, что родитель установил ДО CreateProcess, попадёт в снимок потомка; то, что он поменял ПОСЛЕ, — уже нет. Это и демонстрирует задание 2: родитель ставит 19045, запускает потомка, меняет у себя на 99999 — потомок видит 19045.

Ключевые правила
  • Блок окружения принадлежит процессу и копируется при его создании (снимок «на момент старта»).
  • Передача конфигурации через окружение работает только в одну сторону и только в момент запуска: потомок не может «вернуть» значение родителю через окружение.
  • Если передать lpEnvironment не NULL, а собственный блок, потомок получит именно его вместо копии родительского (механизм явного задания окружения).
  • Изменения окружения действуют только на текущий процесс и его будущих потомков, но не на уже запущенные процессы и не на систему в целом.
Типичные ошибки
  • Ожидание, что SetEnvironmentVariable у родителя изменит переменную у уже запущенного потомка («общая память») — нет, это копия.
  • Установка переменной ПОСЛЕ CreateProcess с надеждой, что потомок её увидит, — потомок уже получил снимок без неё.
  • Запуск потомка из среды, где переменная уже задана иначе (например, глобально в системе), и удивление, что потомок видит не то значение.
6. SetEnvironmentVariable и GetEnvironmentVariable: переменная против блока

Что это. SetEnvironmentVariable(имя, значение) — устанавливает, изменяет или удаляет (если значение NULL) переменную окружения в блоке ТЕКУЩЕГО процесса. GetEnvironmentVariable(имя, буфер, размер) — читает переменную из блока текущего процесса в буфер, возвращая длину значения; 0 означает «не найдена» (тогда GetLastError() вернёт ERROR_ENVVAR_NOT_FOUND, код 203) или пустое значение.

Переменная против блока. Переменная — одна строка ИМЯ=ЗНАЧЕНИЕ; блок — весь набор таких строк процесса. SetEnvironmentVariable правит одну строку в своём блоке, CreateProcess с lpEnvironment = NULL копирует весь блок целиком. Поэтому: установить переменную — это про один процесс; запустить потомка — это про передачу всего блока снимком.

Ключевые правила
  • SetEnvironmentVariable влияет только на текущий процесс (и на его будущих потомков через копирование блока).
  • Она не меняет системные переменные и не видна другим уже запущенным программам; чтобы поменять переменную «для всей системы», нужна запись в реестр и рассылка сообщения WM_SETTINGCHANGE — это другой механизм.
  • У GetEnvironmentVariable размер буфера задаётся в символах, а не в байтах: для wchar_t buffer[256] это sizeof(buffer) / sizeof(buffer[0]) = 256.
  • Код ошибки GetLastError() читать сразу после неудачного вызова: следующий вызов API его перезапишет.
  • Если значение не помещается в буфер, GetEnvironmentVariable возвращает требуемую длину — это не ошибка «не найдено», а сигнал дать буфер больше.
Типичные ошибки
  • Путаница SetEnvironmentVariable (локально, в процессе) с системными переменными среды Windows (реестр, «Свойства системы»): первая не видна другим программам.
  • Передача размера буфера в байтах вместо символов для широкой версии функции — буфер «обрезается» в два раза.
  • Игнорирование возврата 0 без проверки GetLastError(): ноль может означать и «переменная не задана», и «значение пустое».
  • Сравнение широких строк через strcmp вместо wcscmp — сравнение пойдёт по байтам и даст неверный результат.
Итог лабораторной: задание 1 показывает, как процесс рождается, ожидается и аккуратно «убирается» из ядра (CreateProcess → WaitForSingleObject → CloseHandle × 2). Задание 2 показывает, что процессы — автономные миры: конфигурация передаётся только снимком блока окружения в момент старта, а дальше каждый живёт своей жизнью.

1. Процессы в Windows: дескрипторы, ядро, таблица хэндлов

Что это. Процесс — экземпляр выполняющейся программы. Процесс имеет собственное виртуальное адресное пространство, набор потоков, открытые ресурсы и блок окружения. Процессы в Windows полностью изолированы друг от друга. Один процесс не читает и не меняет память другого процесса напрямую. Внутри процесса работает минимум один поток. Поток — единица выполнения кода на процессоре.

Зачем это знать. Вся лабораторная работа №6 построена на изоляции процессов. Родитель и потомок — отдельные процессы. Изменение переменной у родителя не затрагивает потомка. Завершение родителя не завершает потомка.

Объекты ядра и дескрипторы. Процесс, поток, файл, событие и мьютекс — объекты ядра (kernel objects). Объекты ядра — структуры данных в памяти ядра. Пользовательский код не обращается к ним напрямую. Программа обращается к объектам только через дескриптор (handle, HANDLE). Дескриптор — целое число. Дескриптор — индекс в таблице дескрипторов процесса. Дескриптор — не указатель на объект. Дескриптор — «пропуск» к объекту. Ядро находит объект по дескриптору. Ядро проверяет права доступа по дескриптору.

Таблица дескрипторов. У каждого процесса своя таблица хэндлов. Один и тот же числовой дескриптор в разных процессах означает разные объекты или ничего. Дескриптор процесса-потомка из структуры PROCESS_INFORMATION действителен только в процессе-родителе. Закрывать дескриптор должен тоже родитель.

Счётчик ссылок. У каждого объекта ядра есть счётчик использований. Счётчик растёт при открытии нового дескриптора. Счётчик падает при вызове CloseHandle. Ядро уничтожает объект только при счётчике, равном нулю. Завершённый процесс продолжает «жить» в ядре как объект, пока хоть кто-то держит его дескриптор открытым.

Ключевые правила
  • Процессы изолированы. Память, дескрипторы и окружение у каждого процесса свои.
  • Дескриптор — это индекс в таблице процесса, а не адрес объекта.
  • Завершение процесса не уничтожает объект ядра. Объект живёт, пока открыт хоть один дескриптор.
  • Завершение родителя не завершает потомка. У потомка своя жизнь.
Типичные ошибки
  • Не используйте дескриптор из одного процесса в другом процессе. Наследование или дублирование через DuplicateHandle — единственные исключения.
  • Не ждите, что дескриптор исчезнет сам после завершения процесса. Объект ядра остаётся до вызова CloseHandle.
  • Не путайте PID и HANDLE. PID — число для поиска процесса. HANDLE — дескриптор для операций с процессом: ожидание, завершение, закрытие.
2. CreateProcess и структуры STARTUPINFO / PROCESS_INFORMATION

Что это. CreateProcess — главная функция Win32 API для создания нового процесса. Функция загружает исполняемый файл. Функция создаёт адресное пространство, объект процесса и главный поток. Функция запускает главный поток. Функция возвращает TRUE при успехе и FALSE при ошибке. Код ошибки даёт функция GetLastError().

Зачем. Без функции CreateProcess программа не запускает другую программу. Это единственный штатный путь программного запуска в Win32 API. Обёртки вроде system() внутри сами вызывают ту же функцию. Обёртки не дают контроля над дескрипторами и окружением.

STARTUPINFO — «как запускать»

Структура описывает внешний вид и начальные условия нового процесса: заголовок окна, его положение и размер, дескрипторы стандартных потоков ввода, вывода и ошибок, рабочий стол. Выполните обязательные шаги: вызовите ZeroMemory(&si, sizeof(si)), затем задайте si.cb = sizeof(si). Система определяет версию структуры по полю cb. В наших программах остальные поля остаются нулевыми. Окно показывается обычным образом. Потоки наследуются по умолчанию.

  • Всегда обнуляйте обе структуры через ZeroMemory перед вызовом. Всегда задавайте si.cb = sizeof(si).
  • Держите командную строку (lpCommandLine) в изменяемом буфере (wchar_t cmdLine[]). Не передавайте строковый литерал. Функция имеет право менять строку на месте.
  • Всегда проверяйте возвращаемое значение. Значение FALSE означает: процесс не создан. Полей pi нет. Закрывать нечего.
  • При lpApplicationName = NULL имя программы берётся из командной строки. Относительное имя ищется в каталоге приложения, в системных каталогах и в PATH.
Типичные ошибки
  • Не оставляйте структуру STARTUPINFO без инициализации. Мусор в полях даёт непредсказуемые сбои запуска.
  • Не передавайте строковый литерал как lpCommandLine. Литерал лежит в памяти только для чтения. Вызов даёт нарушение доступа.
  • Не забывайте проверку результата. Программа продолжает работу с пустым pi. Программа падает на WaitForSingleObject или CloseHandle по мусорному дескриптору.
  • Не ждите, что функция CreateProcess найдёт файл exe «где-то». Относительное имя ищется по строгим правилам. Файл exe лежит рядом или находится в PATH.
3. Ожидание завершения: WaitForSingleObject

Что это. Функция WaitForSingleObject(hHandle, dwMilliseconds) останавливает вызвавший поток. Поток ждёт, пока объект не перейдёт в сигнальное состояние (signaled). Поток ждёт до истечения тайм-аута. Дескриптор процесса становится сигнальным ровно при завершении процесса.

Зачем. Это способ синхронизации жизненного цикла. Родитель узнаёт: потомок закончил работу. Только потом родитель продолжает сценарий. Например, родитель читает результаты или освобождает ресурсы. В задании 1 без ожидания программа завершилась бы сразу. Программа не дождалась бы закрытия Блокнота.

Возвращаемые значения
КодЗначение

WAIT_TIMEOUTТайм-аут истёк. Процесс всё ещё работает. Код бывает только при конечном тайм-ауте.

Ключевые правила
  • INFINITE означает: ждать без ограничения времени. INFINITE подходит, когда момент завершения заранее неизвестен. Пример: пользователь сам закрывает Блокнот.
  • Всегда проверяйте результат ожидания. Только код WAIT_OBJECT_0 означает «процесс завершён».
  • Ждите только по действительному дескриптору. Дескриптор даёт функция CreateProcess или функция OpenProcess.
Типичные ошибки
  • Не ждите по hThread вместо hProcess. Поток завершается раньше процесса. Процесс порождает другие потоки. Ожидание даёт ложный сигнал.
  • Не используйте INFINITE там, где процесс может зависнуть навсегда. Программа тоже зависнет без возможности отмены. Используйте конечный тайм-аут в цикле с проверкой.
  • Не ждите завершения потомка после закрытия дескриптора. Родитель уже «отпустил» потомка. Ждать не по чему.
В задании 2 родитель намеренно не вызывает WaitForSingleObject. Родитель завершается сразу. Потомок продолжает работу. Ожидание — выбор родителя, а не обязанность. Жизнь потомка от ожидания не зависит.
4. Утечка дескрипторов и зачем нужен CloseHandle

Что это. Функция CloseHandle(h) закрывает дескриптор. Функция удаляет запись из таблицы дескрипторов процесса. Функция уменьшает счётчик ссылок объекта ядра. При счётчике, равном нулю, ядро уничтожает объект. Ядро освобождает память объекта.

Зачем. Функция CreateProcess возвращает сразу два дескриптора: дескриптор процесса и дескриптор потока. Пока хоть один дескриптор открыт, ядро хранит объект завершённого процесса в памяти. Ядро хранит и код завершения процесса. Без закрытия дескрипторы копятся. В короткой программе накопление незаметно. В долгоживущем сервисе таблица дескрипторов переполняется. Сервис запускает тысячи процессов. Новые вызовы CreateProcess завершаются ошибкой. Это и есть утечка дескрипторов (handle leak). Утечка дескрипторов — аналог утечки памяти, но на уровне ядра.

Ключевые правила
  • Закрывайте оба дескриптора из структуры PROCESS_INFORMATION: hProcess и hThread. Забытый дескриптор hThread — та же утечка.
  • Порядок закрытия значения не имеет.
  • Закрывайте дескрипторы, даже если родитель не ждал потомка (задание 2). Ожидание и закрытие — независимые действия.
  • Закрытие дескриптора не завершает процесс. Закрытие дескриптора не убивает поток. Закрытие лишь отпускает ссылку родителя на объект ядра.
  • Закрывайте дескриптор ровно один раз. Повторный вызов CloseHandle по тому же значению закрывает уже другой объект. Система успела выдать тот же номер другому объекту.
Типичные ошибки
  • Не закрывайте только hProcess и не забывайте hThread (или наоборот).
  • Не пропускайте вызов CloseHandle в ветке ошибки после удачного вызова CreateProcess. Пример: при ошибке WaitForSingleObject программа выходит без закрытия дескрипторов.
  • Не надейтесь, что завершение родителя «само всё закроет». Да, при завершении процесса система закрывает все его дескрипторы. Но пока родитель живёт и запускает процессы в цикле, утечка копится при его жизни.
Правило на защиту. Функция CreateProcess вернула два дескриптора. Значит, в программе должно быть два вызова CloseHandle. Один вызов CloseHandle в коде — ошибка, даже если программа «работает».
5. Environment Block: как устроен и почему потомок получает копию

Что это. Environment Block (блок окружения) — область памяти процесса. Блок хранит переменные окружения как строки ИМЯ=ЗНАЧЕНИЕ. Строки разделяются нулевыми символами. Блок завершается двойным нулём. Блок создаётся для каждого процесса при его запуске. Блок живёт только в собственном адресном пространстве процесса.

Зачем. Переменные окружения — простейший механизм передачи конфигурации процессу на старте. Примеры: пути PATH и TEMP, настройки программ, в нашем случае — STUDENT_ID. Процесс читает переменные через функцию GetEnvironmentVariable. Процесс не знает, кто и как задал переменные.

Копирование при создании процесса. Родитель вызывает функцию CreateProcess с параметром lpEnvironment = NULL. Система берёт блок окружения родителя. Система копирует блок байт в байт. Система передаёт копию новому процессу. Копия — это главное слово. После копирования у родителя и потомка два независимых блока в двух независимых адресных пространствах. Общей памяти между ними нет.

Почему изменение у родителя не влияет на потомка. Функция SetEnvironmentVariable меняет строку только в блоке текущего процесса. Родитель меняет свою копию. Потомок свою копию не трогает. Потомок о копии родителя даже не знает. Порядок операций решает всё. То, что родитель установил до вызова CreateProcess, попадает в снимок потомка. То, что родитель поменял после вызова, уже не попадает. Задание 2 показывает это: родитель ставит 19045, запускает потомка, меняет у себя на 99999. Потомок видит 19045.

Ключевые правила
  • Блок окружения принадлежит процессу. Блок копируется при создании процесса. Копия — снимок «на момент старта».
  • Передача конфигурации через окружение работает только в одну сторону. Передача работает только в момент запуска. Потомок не возвращает значение родителю через окружение.
  • При lpEnvironment не NULL потомок получает ваш собственный блок. Потомок не получает копию родительского блока. Это механизм явного задания окружения.
  • Изменения окружения действуют только на текущий процесс и его будущих потомков. Изменения не действуют на уже запущенные процессы. Изменения не действуют на систему в целом.
Типичные ошибки
  • Не ждите, что SetEnvironmentVariable у родителя изменит переменную у уже запущенного потомка. Общей памяти нет. Это копия.
  • Не устанавливайте переменную после вызова CreateProcess с надеждой, что потомок её увидит. Потомок уже получил снимок без неё.
  • Не запускайте потомка из среды, где переменная уже задана иначе. Пример: переменная задана глобально в системе. Потомок видит другое значение.
6. SetEnvironmentVariable и GetEnvironmentVariable: переменная против блока

Что это. Функция SetEnvironmentVariable(имя, значение) устанавливает, изменяет или удаляет переменную окружения в блоке текущего процесса. Значение NULL удаляет переменную. Функция GetEnvironmentVariable(имя, буфер, размер) читает переменную из блока текущего процесса в буфер. Функция возвращает длину значения. Значение 0 означает «не найдена» или пустое значение. При коде «не найдена» функция GetLastError() возвращает ERROR_ENVVAR_NOT_FOUND (код 203).

Переменная против блока. Переменная — одна строка ИМЯ=ЗНАЧЕНИЕ. Блок — весь набор таких строк процесса. Функция SetEnvironmentVariable правит одну строку в своём блоке. Функция CreateProcess с параметром lpEnvironment = NULL копирует весь блок целиком. Вывод: установка переменной касается одного процесса. Запуск потомка передаёт весь блок снимком.

Ключевые правила
  • Функция SetEnvironmentVariable влияет только на текущий процесс. Функция влияет и на его будущих потомков через копирование блока.
  • Функция не меняет системные переменные. Функция не видна другим уже запущенным программам. Переменная «для всей системы» требует записи в реестр и рассылки сообщения WM_SETTINGCHANGE. Это другой механизм.
  • Функция GetEnvironmentVariable задаёт размер буфера в символах, а не в байтах. Для wchar_t buffer[256] размер равен sizeof(buffer) / sizeof(buffer[0]) = 256.
  • Читайте код ошибки GetLastError() сразу после неудачного вызова. Следующий вызов API перезаписывает код.
  • Если значение не помещается в буфер, функция GetEnvironmentVariable возвращает требуемую длину. Это не ошибка «не найдено». Это сигнал: дайте буфер больше.
Типичные ошибки
  • Не путайте функцию SetEnvironmentVariable с системными переменными среды Windows. Функция работает локально, в процессе. Системные переменные живут в реестре («Свойства системы»). Функция не видна другим программам.
  • Не передавайте размер буфера в байтах вместо символов для широкой версии функции. Буфер «обрезается» в два раза.
  • Не игнорируйте возврат 0 без проверки GetLastError(). Ноль означает и «переменная не задана», и «значение пустое».
  • Не сравнивайте широкие строки через strcmp. Используйте функцию wcscmp. Функция strcmp сравнивает по байтам и даёт неверный результат.
Итог лабораторной. Задание 1 показывает жизненный цикл процесса. Процесс рождается, ожидается и аккуратно «убирается» из ядра: CreateProcess, затем WaitForSingleObject, затем два вызова CloseHandle. Задание 2 показывает автономность процессов. Конфигурация передаётся только снимком блока окружения в момент старта. Дальше каждый процесс живёт своей жизнью.

PROCESS_INFORMATIONЗадачи 1, 2

PROCESS_INFORMATION — структура, в которую CreateProcess записывает сведения о процессе.

PROCESS_INFORMATION хранит дескриптор процесса, дескриптор потока, номер PID и номер потока.

Пример: PROCESS_INFORMATION похож на свидетельство о рождении: там записаны все данные процесса.
SetEnvironmentVariableЗадача 2

SetEnvironmentVariable — функция, которая задаёт переменную окружения в блоке окружения.

SetEnvironmentVariable меняет переменную окружения только в памяти текущего процесса.

Другие процессы не замечают это изменение.

Пример: SetEnvironmentVariable похож на запись своего имени на своём листке: на листке соседа ничего не изменится.
STARTUPINFOЗадачи 1, 2

STARTUPINFO — структура, в которой родитель описывает вид нового процесса.

Родитель обнуляет STARTUPINFO и указывает её размер в поле cb.

Пример: STARTUPINFO похож на анкету при заселении: анкета описывает, какой должна быть комната.
Правило: Обнуляй STARTUPINFO перед запуском процесса.
WaitForSingleObjectЗадача 1

WaitForSingleObject — функция, которая останавливает поток и ждёт завершения процесса.

WaitForSingleObject ждёт столько, сколько нужно: с INFINITE — без ограничения по времени.

Пример: WaitForSingleObject похож на ожидание у двери: стоишь у двери и ждёшь, пока друг выйдет.
Правило: Вызывай WaitForSingleObject, если нужно дождаться завершения процесса.
