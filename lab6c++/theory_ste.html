1. Процессы в Windows: дескрипторы, ядро, таблица хэндлов

Что это. Процесс — экземпляр выполняющейся программы. Процесс имеет собственное виртуальное адресное пространство, набор потоков, открытые ресурсы и блок окружения. Процессы в Windows полностью изолированы друг от друга. Один процесс не читает и не меняет память другого процесса напрямую. Внутри процесса работает минимум один поток. Поток — единица выполнения кода на процессоре.

Зачем это знать. Вся лабораторная работа №6 построена на изоляции процессов. Родитель и потомок — отдельные процессы. Изменение переменной у родителя не затрагивает потомка. Завершение родителя не завершает потомка.

Объекты ядра и дескрипторы. Процесс, поток, файл, событие и мьютекс — объекты ядра (kernel objects). Объекты ядра — структуры данных в памяти ядра. Пользовательский код не обращается к ним напрямую. Программа обращается к объектам только через дескриптор (handle, HANDLE). Дескриптор — целое число. Дескриптор — индекс в таблице дескрипторов процесса. Дескриптор — не указатель на объект. Дескриптор — «пропуск» к объекту. Ядро находит объект по дескриптору. Ядро проверяет права доступа по дескриптору.

Таблица дескрипторов. У каждого процесса своя таблица хэндлов. Один и тот же числовой дескриптор в разных процессах означает разные объекты или ничего. Дескриптор процесса-потомка из структуры PROCESS_INFORMATION действителен только в процессе-родителе. Закрывать дескриптор должен тоже родитель.

Счётчик ссылок. У каждого объекта ядра есть счётчик использований. Счётчик растёт при открытии нового дескриптора. Счётчик падает при вызове CloseHandle. Ядро уничтожает объект только при счётчике, равном нулю. Завершённый процесс продолжает «жить» в ядре как объект, пока хоть кто-то держит его дескриптор открытым.

Ключевые правила
  • Процессы изолированы. Память, дескрипторы и окружение у каждого процесса свои.
  • Дескриптор — это индекс в таблице процесса, а не адрес объекта.
  • Завершение процесса не уничтожает объект ядра. Объект живёт, пока открыт хоть один дескриптор.
  • Завершение родителя не завершает потомка. У потомка своя жизнь.
Типичные ошибки
  • Не используйте дескриптор из одного процесса в другом процессе. Наследование или дублирование через DuplicateHandle — единственные исключения.
  • Не ждите, что дескриптор исчезнет сам после завершения процесса. Объект ядра остаётся до вызова CloseHandle.
  • Не путайте PID и HANDLE. PID — число для поиска процесса. HANDLE — дескриптор для операций с процессом: ожидание, завершение, закрытие.
2. CreateProcess и структуры STARTUPINFO / PROCESS_INFORMATION

Что это. CreateProcess — главная функция Win32 API для создания нового процесса. Функция загружает исполняемый файл. Функция создаёт адресное пространство, объект процесса и главный поток. Функция запускает главный поток. Функция возвращает TRUE при успехе и FALSE при ошибке. Код ошибки даёт функция GetLastError().

Зачем. Без функции CreateProcess программа не запускает другую программу. Это единственный штатный путь программного запуска в Win32 API. Обёртки вроде system() внутри сами вызывают ту же функцию. Обёртки не дают контроля над дескрипторами и окружением.

STARTUPINFO — «как запускать»

Структура описывает внешний вид и начальные условия нового процесса: заголовок окна, его положение и размер, дескрипторы стандартных потоков ввода, вывода и ошибок, рабочий стол. Выполните обязательные шаги: вызовите ZeroMemory(&si, sizeof(si)), затем задайте si.cb = sizeof(si). Система определяет версию структуры по полю cb. В наших программах остальные поля остаются нулевыми. Окно показывается обычным образом. Потоки наследуются по умолчанию.

PROCESS_INFORMATION — «что получилось»

Система записывает результат запуска сюда. Структура имеет четыре поля:

ПолеЧто этоЗачем нужно
hProcessДескриптор объекта процесса-потомка.Программа ждёт завершение через WaitForSingleObject. Программа получает код выхода. Программа завершает процесс.
hThreadДескриптор главного потока потомка.Программа управляет потоком. Программа закрывает дескриптор вместе с hProcess.
dwProcessIdPID процесса (число).PID идентифицирует процесс. Пользователь находит процесс в Диспетчере задач по PID.
dwThreadIdID главного потока (число).ID идентифицирует поток.
Ключевые правила
  • Всегда обнуляйте обе структуры через ZeroMemory перед вызовом. Всегда задавайте si.cb = sizeof(si).
  • Держите командную строку (lpCommandLine) в изменяемом буфере (wchar_t cmdLine[]). Не передавайте строковый литерал. Функция имеет право менять строку на месте.
  • Всегда проверяйте возвращаемое значение. Значение FALSE означает: процесс не создан. Полей pi нет. Закрывать нечего.
  • При lpApplicationName = NULL имя программы берётся из командной строки. Относительное имя ищется в каталоге приложения, в системных каталогах и в PATH.
Типичные ошибки
  • Не оставляйте структуру STARTUPINFO без инициализации. Мусор в полях даёт непредсказуемые сбои запуска.
  • Не передавайте строковый литерал как lpCommandLine. Литерал лежит в памяти только для чтения. Вызов даёт нарушение доступа.
  • Не забывайте проверку результата. Программа продолжает работу с пустым pi. Программа падает на WaitForSingleObject или CloseHandle по мусорному дескриптору.
  • Не ждите, что функция CreateProcess найдёт файл exe «где-то». Относительное имя ищется по строгим правилам. Файл exe лежит рядом или находится в PATH.
3. Ожидание завершения: WaitForSingleObject

Что это. Функция WaitForSingleObject(hHandle, dwMilliseconds) останавливает вызвавший поток. Поток ждёт, пока объект не перейдёт в сигнальное состояние (signaled). Поток ждёт до истечения тайм-аута. Дескриптор процесса становится сигнальным ровно при завершении процесса.

Зачем. Это способ синхронизации жизненного цикла. Родитель узнаёт: потомок закончил работу. Только потом родитель продолжает сценарий. Например, родитель читает результаты или освобождает ресурсы. В задании 1 без ожидания программа завершилась бы сразу. Программа не дождалась бы закрытия Блокнота.

Возвращаемые значения
КодЗначение
WAIT_OBJECT_0Объект стал сигнальным. Процесс завершился. Это нормальный исход.
WAIT_TIMEOUTТайм-аут истёк. Процесс всё ещё работает. Код бывает только при конечном тайм-ауте.
WAIT_FAILEDОжидание дало ошибку. Пример: неверный дескриптор. Код ошибки даёт функция GetLastError().
Ключевые правила
  • INFINITE означает: ждать без ограничения времени. INFINITE подходит, когда момент завершения заранее неизвестен. Пример: пользователь сам закрывает Блокнот.
  • Всегда проверяйте результат ожидания. Только код WAIT_OBJECT_0 означает «процесс завершён».
  • Ждите только по действительному дескриптору. Дескриптор даёт функция CreateProcess или функция OpenProcess.
Типичные ошибки
  • Не ждите по hThread вместо hProcess. Поток завершается раньше процесса. Процесс порождает другие потоки. Ожидание даёт ложный сигнал.
  • Не используйте INFINITE там, где процесс может зависнуть навсегда. Программа тоже зависнет без возможности отмены. Используйте конечный тайм-аут в цикле с проверкой.
  • Не ждите завершения потомка после закрытия дескриптора. Родитель уже «отпустил» потомка. Ждать не по чему.
В задании 2 родитель намеренно не вызывает WaitForSingleObject. Родитель завершается сразу. Потомок продолжает работу. Ожидание — выбор родителя, а не обязанность. Жизнь потомка от ожидания не зависит.
4. Утечка дескрипторов и зачем нужен CloseHandle

Что это. Функция CloseHandle(h) закрывает дескриптор. Функция удаляет запись из таблицы дескрипторов процесса. Функция уменьшает счётчик ссылок объекта ядра. При счётчике, равном нулю, ядро уничтожает объект. Ядро освобождает память объекта.

Зачем. Функция CreateProcess возвращает сразу два дескриптора: дескриптор процесса и дескриптор потока. Пока хоть один дескриптор открыт, ядро хранит объект завершённого процесса в памяти. Ядро хранит и код завершения процесса. Без закрытия дескрипторы копятся. В короткой программе накопление незаметно. В долгоживущем сервисе таблица дескрипторов переполняется. Сервис запускает тысячи процессов. Новые вызовы CreateProcess завершаются ошибкой. Это и есть утечка дескрипторов (handle leak). Утечка дескрипторов — аналог утечки памяти, но на уровне ядра.

Ключевые правила
  • Закрывайте оба дескриптора из структуры PROCESS_INFORMATION: hProcess и hThread. Забытый дескриптор hThread — та же утечка.
  • Порядок закрытия значения не имеет.
  • Закрывайте дескрипторы, даже если родитель не ждал потомка (задание 2). Ожидание и закрытие — независимые действия.
  • Закрытие дескриптора не завершает процесс. Закрытие дескриптора не убивает поток. Закрытие лишь отпускает ссылку родителя на объект ядра.
  • Закрывайте дескриптор ровно один раз. Повторный вызов CloseHandle по тому же значению закрывает уже другой объект. Система успела выдать тот же номер другому объекту.
Типичные ошибки
  • Не закрывайте только hProcess и не забывайте hThread (или наоборот).
  • Не пропускайте вызов CloseHandle в ветке ошибки после удачного вызова CreateProcess. Пример: при ошибке WaitForSingleObject программа выходит без закрытия дескрипторов.
  • Не надейтесь, что завершение родителя «само всё закроет». Да, при завершении процесса система закрывает все его дескрипторы. Но пока родитель живёт и запускает процессы в цикле, утечка копится при его жизни.
Правило на защиту. Функция CreateProcess вернула два дескриптора. Значит, в программе должно быть два вызова CloseHandle. Один вызов CloseHandle в коде — ошибка, даже если программа «работает».
5. Environment Block: как устроен и почему потомок получает копию

Что это. Environment Block (блок окружения) — область памяти процесса. Блок хранит переменные окружения как строки ИМЯ=ЗНАЧЕНИЕ. Строки разделяются нулевыми символами. Блок завершается двойным нулём. Блок создаётся для каждого процесса при его запуске. Блок живёт только в собственном адресном пространстве процесса.

Зачем. Переменные окружения — простейший механизм передачи конфигурации процессу на старте. Примеры: пути PATH и TEMP, настройки программ, в нашем случае — STUDENT_ID. Процесс читает переменные через функцию GetEnvironmentVariable. Процесс не знает, кто и как задал переменные.

Копирование при создании процесса. Родитель вызывает функцию CreateProcess с параметром lpEnvironment = NULL. Система берёт блок окружения родителя. Система копирует блок байт в байт. Система передаёт копию новому процессу. Копия — это главное слово. После копирования у родителя и потомка два независимых блока в двух независимых адресных пространствах. Общей памяти между ними нет.

Почему изменение у родителя не влияет на потомка. Функция SetEnvironmentVariable меняет строку только в блоке текущего процесса. Родитель меняет свою копию. Потомок свою копию не трогает. Потомок о копии родителя даже не знает. Порядок операций решает всё. То, что родитель установил до вызова CreateProcess, попадает в снимок потомка. То, что родитель поменял после вызова, уже не попадает. Задание 2 показывает это: родитель ставит 19045, запускает потомка, меняет у себя на 99999. Потомок видит 19045.

Ключевые правила
  • Блок окружения принадлежит процессу. Блок копируется при создании процесса. Копия — снимок «на момент старта».
  • Передача конфигурации через окружение работает только в одну сторону. Передача работает только в момент запуска. Потомок не возвращает значение родителю через окружение.
  • При lpEnvironment не NULL потомок получает ваш собственный блок. Потомок не получает копию родительского блока. Это механизм явного задания окружения.
  • Изменения окружения действуют только на текущий процесс и его будущих потомков. Изменения не действуют на уже запущенные процессы. Изменения не действуют на систему в целом.
Типичные ошибки
  • Не ждите, что SetEnvironmentVariable у родителя изменит переменную у уже запущенного потомка. Общей памяти нет. Это копия.
  • Не устанавливайте переменную после вызова CreateProcess с надеждой, что потомок её увидит. Потомок уже получил снимок без неё.
  • Не запускайте потомка из среды, где переменная уже задана иначе. Пример: переменная задана глобально в системе. Потомок видит другое значение.
6. SetEnvironmentVariable и GetEnvironmentVariable: переменная против блока

Что это. Функция SetEnvironmentVariable(имя, значение) устанавливает, изменяет или удаляет переменную окружения в блоке текущего процесса. Значение NULL удаляет переменную. Функция GetEnvironmentVariable(имя, буфер, размер) читает переменную из блока текущего процесса в буфер. Функция возвращает длину значения. Значение 0 означает «не найдена» или пустое значение. При коде «не найдена» функция GetLastError() возвращает ERROR_ENVVAR_NOT_FOUND (код 203).

Переменная против блока. Переменная — одна строка ИМЯ=ЗНАЧЕНИЕ. Блок — весь набор таких строк процесса. Функция SetEnvironmentVariable правит одну строку в своём блоке. Функция CreateProcess с параметром lpEnvironment = NULL копирует весь блок целиком. Вывод: установка переменной касается одного процесса. Запуск потомка передаёт весь блок снимком.

Ключевые правила
  • Функция SetEnvironmentVariable влияет только на текущий процесс. Функция влияет и на его будущих потомков через копирование блока.
  • Функция не меняет системные переменные. Функция не видна другим уже запущенным программам. Переменная «для всей системы» требует записи в реестр и рассылки сообщения WM_SETTINGCHANGE. Это другой механизм.
  • Функция GetEnvironmentVariable задаёт размер буфера в символах, а не в байтах. Для wchar_t buffer[256] размер равен sizeof(buffer) / sizeof(buffer[0]) = 256.
  • Читайте код ошибки GetLastError() сразу после неудачного вызова. Следующий вызов API перезаписывает код.
  • Если значение не помещается в буфер, функция GetEnvironmentVariable возвращает требуемую длину. Это не ошибка «не найдено». Это сигнал: дайте буфер больше.
Типичные ошибки
  • Не путайте функцию SetEnvironmentVariable с системными переменными среды Windows. Функция работает локально, в процессе. Системные переменные живут в реестре («Свойства системы»). Функция не видна другим программам.
  • Не передавайте размер буфера в байтах вместо символов для широкой версии функции. Буфер «обрезается» в два раза.
  • Не игнорируйте возврат 0 без проверки GetLastError(). Ноль означает и «переменная не задана», и «значение пустое».
  • Не сравнивайте широкие строки через strcmp. Используйте функцию wcscmp. Функция strcmp сравнивает по байтам и даёт неверный результат.
Итог лабораторной. Задание 1 показывает жизненный цикл процесса. Процесс рождается, ожидается и аккуратно «убирается» из ядра: CreateProcess, затем WaitForSingleObject, затем два вызова CloseHandle. Задание 2 показывает автономность процессов. Конфигурация передаётся только снимком блока окружения в момент старта. Дальше каждый процесс живёт своей жизнью.
