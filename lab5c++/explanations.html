Шаг 1Строки 1–6
#include <windows.h> и др.

Без windows.h не скомпилируется ни один вызов Win32. io.h/fcntl.h нужны только ради перевода консоли в UTF-8/UTF-16 (строки 58–59).

Шаг 2Строки 8
const DWORD FILE_SIZE_10MB = 10 * 1024 * 1024;

Константа: размер тестового файла — 10 МБ (10 485 760 байт). Одно место правки: размер используется и при создании файла (строка 66), и как предел чтения в бенчмарке (строка 43).

Шаг 3Строки 9
const DWORD SECTOR_SIZE = 4096;

Константа: размер сектора/страницы — 4096 байт (4 КБ). Эталон выравнивания для всего опыта: адрес буфера, смещение в файле и размер чтения должны быть кратны этому числу. Используется в проверке на строке 97.

Шаг 4Строки 11–12
bool GenerateRandomFile(const wchar_t* path, DWORD sizeBytes) {

Объявление функции-генератора тестового файла. Принимает путь (широкая строка UTF-16 для CreateFileW) и размер в байтах, возвращает true при успехе и false при ошибке. Файл создаёт сама программа — заранее готовить его НЕ нужно. bool нужен, чтобы main могла узнать об ошибке (хотя в main результат, к сожалению, игнорируется — см. строку 66).

Шаг 5Строки 13
HANDLE hFile = CreateFileW(path, GENERIC_WRITE, 0, NULL, CREATE_ALWAYS, FILE_ATTRIBUTE_NORMAL, NULL);

Создаёт файл для записи. GENERIC_WRITE — только запись; 0 в третьем параметре — монопольный доступ (никто другой не откроет файл, пока идёт запись); CREATE_ALWAYS — создать новый или обрезать существующий до нуля; FILE_ATTRIBUTE_NORMAL — обычные атрибуты. CREATE_ALWAYS — ключевой момент: при повторном запуске старый файл просто перезаписывается, готовить файл вручную не надо. Монопольный доступ (0) защищает недописанный файл от чтения.

Шаг 6Строки 14
if (hFile == INVALID_HANDLE_VALUE) return false;

Проверка: удалось ли открыть файл. INVALID_HANDLE_VALUE — специальное значение «ошибка» для CreateFile. Без проверки следующий WriteFile получил бы невалидный хендл. Возврат false — единственный сигнал об ошибке наверх.

Шаг 7Строки 16
const DWORD chunkSize = 64 * 1024;

Размер одного куска записи — 64 КБ. 64 КБ кратно 4096, поэтому запись ложится ровно на границы секторов. Писать весь файл одним вызовом (10 МБ) тоже можно, но чанками экономнее память и виден прогресс.

Шаг 8Строки 17
std::vector<char> buffer(chunkSize);

Буфер на 64 КБ в куче (heap). Вектор сам освободит память при выходе из функции — нет утечки и нет риска переполнения стека, как было бы с локальным массивом на 64 КБ.

Шаг 9Строки 18
std::mt19937 rng(42);

Генератор случайных чисел (Mersenne Twister) с фиксированным зерном 42. Зерно фиксировано специально: при каждом запуске файл получается одинаковым — бенчмарк воспроизводим, результаты запусков сравнимы.

Шаг 10Строки 19
for (...) buffer[i] = static_cast<char>('A' + (rng() % 26));

Заполняет чанк случайными латинскими буквами A–Z. Содержимое файла для бенчмарка не важно, но случайные данные честнее нулей: файл из одних нулей файловая система или диск могут сжать или оптимизировать, исказив замер.

Шаг 11Строки 21
DWORD writtenTotal = 0;

Счётчик уже записанных байтов, стартует с нуля. По нему цикл понимает, когда файл дописан до конца.

Шаг 12Строки 22
while (writtenTotal < sizeBytes) {

Цикл записи, пока не набран заданный размер. WriteFile не обязан записать всё за один вызов, поэтому запись идёт порциями до полного объёма.

Шаг 13Строки 23
DWORD toWrite = min(chunkSize, sizeBytes - writtenTotal);

Размер очередного куска: полный чанк или остаток файла, если он меньше. min — макрос из windows.h. Без этого последний кусок вышел бы за границу файла. Для 10 МБ (кратно 64 КБ) остаток равен нулю, но формула делает функцию универсальной для любого размера.

Шаг 14Строки 24
DWORD written = 0;

Переменная, куда WriteFile запишет фактическое число записанных байтов. Фактическое число может быть меньше запрошенного — его надо учитывать, а не верить запрошенному.

Шаг 15Строки 25
WriteFile(hFile, buffer.data(), toWrite, &written, NULL);

Записывает кусок буфера в файл. NULL вместо OVERLAPPED — синхронная запись: вызов ждёт, пока данные уйдут. Синхронный режим проще для учебной программы: после возврата из WriteFile данные уже записаны. Замечание: возвращаемое BOOL здесь не проверяется — при ошибке диска это заметят только по written == 0.

Шаг 16Строки 26
writtenTotal += written;

Продвигает счётчик на реально записанное число байтов. Именно реально записанное, а не запрошенное — иначе при частичной записи файл получился бы короче. Слабое место: если WriteFile вернёт 0 (диск полон), цикл станет бесконечным.

Шаг 17Строки 28
CloseHandle(hFile);

Закрывает хендл файла, сбрасывает буферы на диск. Без закрытия файл остался бы заблокированным (открыт монопольно), и следующие CreateFileW в main упали бы с ошибкой доступа.

Шаг 18Строки 29
return true;

Функция сообщает об успехе. Парный к return false на строке 14: вызывающий код по bool отличает успех от неудачи.

Шаг 19Строки 32–33
double BenchmarkReading(const wchar_t* path, DWORD flags, void* buffer, DWORD readChunkSize) {

Функция замера времени чтения файла. Параметры: путь; flags — режим открытия (с кэшем или без); buffer — заранее выделенный буфер; readChunkSize — размер одного чтения. Возвращает миллисекунды, -1.0 при ошибке открытия. Вся суть сравнения — в одном параметре flags: один и тот же код гоняется дважды, с FILE_ATTRIBUTE_NORMAL и с FILE_FLAG_NO_BUFFERING, поэтому разница времён — чисто эффект флага.

Шаг 20Строки 34
HANDLE hFile = CreateFileW(path, GENERIC_READ, FILE_SHARE_READ, NULL, OPEN_EXISTING, flags, NULL);

Открывает существующий файл на чтение. OPEN_EXISTING — не создавать, а открыть; упадёт, если файла нет. FILE_SHARE_READ — разрешить другим процессам читать файл параллельно. OPEN_EXISTING здесь безопасен, потому что файл только что создан GenerateRandomFile. Но если вызывать эту функцию отдельно без готового файла — вернётся -1.0: вот единственное место, где файл должен существовать заранее.

Шаг 21Строки 35
if (hFile == INVALID_HANDLE_VALUE) return -1.0;

Ошибка открытия → маркер -1.0 вместо времени. -1.0 нельзя спутать с реальным временем (оно всегда ≥ 0), поэтому main могла бы проверить результат — но в коде проверка не делается, и при ошибке на экран выведется «-1 мс».

Шаг 22Строки 37
LARGE_INTEGER freq, start, end;

Три 64-битные переменные: частота таймера, стартовая и финишная отметки. QueryPerformanceCounter работает только с 64-битным счётчиком — int сюда не подойдёт, счётчик тикает миллиарды раз в секунду.

Шаг 23Строки 38
QueryPerformanceFrequency(&freq);

Узнаёт частоту высокоточного таймера (тиков в секунду). Без частоты тики нельзя перевести в секунды: у разных ПК частота разная (обычно ~10 МГц).

Шаг 24Строки 39
QueryPerformanceCounter(&start);

Фиксирует стартовую отметку непосредственно перед чтением. Замеряется только чтение: открытие файла (строка 34) — до старта и в замер не входит.

Шаг 25Строки 41–42
DWORD bytesRead = 0; DWORD totalRead = 0;

bytesRead — прочитано за один вызов ReadFile; totalRead — всего с начала. ReadFile за раз читает не больше readChunkSize, поэтому нужен накопительный счётчик до 10 МБ.

Шаг 26Строки 43
while (totalRead < FILE_SIZE_10MB) {

Цикл чтения, пока не прочитаны все 10 МБ. Файл читается от начала до конца последовательными кусками по 64 КБ — всего 160 чтений.

Шаг 27Строки 44–46
if (!ReadFile(hFile, buffer, readChunkSize, &bytesRead, NULL) || bytesRead == 0) break;

Одно чтение. Выход из цикла при ошибке ReadFile (вернул FALSE) или при конце файла (прочитано 0 байт); строка 46 — закрывающая скобка if. Защита от бесконечного цикла: без break при ошибке цикл крутился бы вечно, ведь totalRead не рос бы.

Шаг 28Строки 47
totalRead += bytesRead;

Добавляет реально прочитанные байты к общему счётчику. Именно реально прочитанные: последнее чтение может быть короче чанка.

Шаг 29Строки 50
QueryPerformanceCounter(&end);

Финишная отметка сразу после цикла чтения. Замер заканчивается ровно на чтении, закрытие файла в замер не входит.

Шаг 30Строки 51
CloseHandle(hFile);

Закрывает файл после замера. Освобождает хендл и сбрасывает кэш чтения; иначе при повторном вызове функции второй CreateFileW мог бы конфликтовать по доступу.

Шаг 31Строки 53
return static_cast<double>(end.QuadPart - start.QuadPart) * 1000.0 / freq.QuadPart;

Переводит разницу тиков в миллисекунды: (end − start) / freq = секунды, × 1000 = мс. Формула замера целиком: тики делятся на частоту, а не на 1000 — частая ошибка новичков. static_cast<double> нужен, чтобы деление было вещественным, а не целочисленным.

Шаг 32Строки 56
int main() {

Точка входа программы. Сюда попадает управление при запуске exe-файла.

Шаг 33Строки 57–60
#if defined(_WIN32) system("chcp 65001 > nul"); _setmode(_fileno(stdout), _O_U8TEXT); #endif

Настройка консоли под Windows: chcp 65001 переключает кодовую страницу на UTF-8; _setmode переводит stdout в режим _O_U8TEXT, чтобы wcout выводил кириллицу как UTF-16. #if — чтобы эти строки компилировались только под Windows. Без этого русские строки в консоли Windows показывались бы кракозябрами. chcp меняет кодировку консоли, а _setmode — режим самого потока вывода; нужны оба шага.

Шаг 34Строки 62
const wchar_t* testFile = L"test_direct_io_10mb.dat";

Имя тестового файла (относительный путь, префикс L — широкая строка). Относительный путь означает: файл создаётся в текущей рабочей папке — там, откуда запущен exe. Именно поэтому запускать надо из папки с программой, а не ярлыком с другой рабочей папкой.

Шаг 35Строки 63
std::wcout << L"=== ПРАКТИКА №1: ..." << std::endl;

Печатает заголовок программы. wcout, а не cout: вывод идёт широкими символами (wchar_t), что сочетается с _O_U8TEXT.

Шаг 36Строки 65–66
std::wcout << L"1. Создание тестового файла..."; GenerateRandomFile(testFile, FILE_SIZE_10MB);

Шаг 1: сообщение и создание файла 10 МБ со случайными данными. Файл создаётся до любых чтений — поэтому OPEN_EXISTING на строках 34 и 70 не падает. Замечание: возвращаемый bool игнорируется — если диск полон или нет прав на запись, программа молча пойдёт дальше, а бенчмарк вернёт -1.

Шаг 37Строки 68–69
// 2. Демонстрация ошибки ... std::wcout << L"\n2. Попытка чтения в невыровненный буфер...";

Анонс шага 2 — демонстрации ошибки 87. Комментарий и вывод делят программу на numbered шаги, чтобы вывод читался как протокол лабораторной.

Шаг 38Строки 70–71
HANDLE hDirect = CreateFileW(testFile, GENERIC_READ, FILE_SHARE_READ, NULL, OPEN_EXISTING, FILE_FLAG_NO_BUFFERING, NULL);

Открывает файл в режиме небуферизированного ввода-вывода: флаг FILE_FLAG_NO_BUFFERING заставляет ядро обойти системный файловый кэш — данные идут DMA напрямую с диска в буфер процесса. Главный флаг всей задачи. Важное следствие: раз кэш обойдён, ядро и контроллер диска требуют строгого выравнивания — именно это и проверяется дальше. Без этого флага ошибка 87 не возникла бы вообще.

Шаг 39Строки 73
if (hDirect != INVALID_HANDLE_VALUE) {

Демонстрация выполняется, только если файл открылся. Защита от падения: если файл не открылся, блок просто пропускается, а программа идёт к шагу 3.

Шаг 40Строки 74
char unalignedBuf[1000]; // Не выровнен по границе 4096 байт, размер не кратен 4096

Локальный буфер на стеке размером 1000 байт. Учебное нарушение сразу двух правил: (1) адрес стекового массива не гарантированно кратен 4096; (2) размер 1000 не кратен 4096 (1000 / 4096 — не целое). Достаточно одного нарушения, чтобы получить ошибку 87.

Шаг 41Строки 75
DWORD bytesRead = 0;

Переменная для числа прочитанных байтов. ReadFile всегда требует указатель, куда положить фактическое число байтов, — даже если чтение упадёт.

Шаг 42Строки 76
BOOL result = ReadFile(hDirect, unalignedBuf, sizeof(unalignedBuf), &bytesRead, NULL);

Попытка прочитать 1000 байт в невыровненный буфер из файла, открытого с FILE_FLAG_NO_BUFFERING. Это и есть «провокация» ошибки: чтение начинается со смещения 0 (оно выровнено), но буфер и размер — нет. ReadFile вернёт FALSE.

Шаг 43Строки 77
if (!result) {

Ветка обработки неудачного чтения. ReadFile при ошибке возвращает FALSE — это единственный признак; число в bytesRead при этом невалидно.

Шаг 44Строки 78
DWORD err = GetLastError();

Сохраняет код ошибки Win32 сразу после неудачного вызова. GetLastError надо вызывать немедленно: любой следующий вызов API (даже wcout) может перезатереть код. Здесь это и есть ожидаемые 87.

Шаг 45Строки 79
std::wcout << L"   [ОШИБКА ПОЛУЧЕНА]: ReadFile вернул FALSE, GetLastError() = " << err << std::endl;

Печатает факт ошибки и её числовой код. Демонстрация для отчёта: код ошибки виден на экране, а не только в отладчике.

Шаг 46Строки 80–82
if (err == ERROR_INVALID_PARAMETER) { std::wcout << L"   -> Код 87 ... буфер не выровнен ..."; }

Проверяет, что код именно 87 (ERROR_INVALID_PARAMETER), и печатает объяснение причины. Программа не просто ловит любую ошибку, а доказывает, что это именно та ошибка, которую требует задание: невыровненный буфер. Если бы код был другим (например, 2 — файл не найден), пояснение не напечаталось бы.

Шаг 47Строки 84
CloseHandle(hDirect);

Закрывает хендл прямого чтения. Хендл больше не нужен: демо ошибки завершено. Закрытие до шага 3 важно — иначе файл остался бы открыт с флагом NO_BUFFERING.

Шаг 48Строки 87–88
// 3. Исправление ошибки ... std::wcout << L"\n3. Выделение выровненного буфера через VirtualAlloc (64 КБ)...";

Анонс шага 3 — правильного решения проблемы выравнивания. Переход от демонстрации ошибки к её исправлению — логика лабораторной: сломали, починили, измерили.

Шаг 49Строки 89
const DWORD alignedChunkSize = 64 * 1024; // 64 КБ (кратно 4096)

Размер будущего буфера — 64 КБ. 65536 / 4096 = 16 ровно: размер кратен сектору, третье правило выполнено. Заодно 64 КБ — удобный размер одного чтения для бенчмарка.

Шаг 50Строки 90
void* alignedBuffer = VirtualAlloc(NULL, alignedChunkSize, MEM_COMMIT | MEM_RESERVE, PAGE_READWRITE);

Выделяет 64 КБ памяти напрямую у ядра: NULL — адрес выбирает ядро; MEM_RESERVE + MEM_COMMIT — зарезервировать диапазон и сразу выделить физические страницы; PAGE_READWRITE — чтение и запись. Ключевое свойство: VirtualAlloc выделяет память целыми страницами, поэтому возвращаемый адрес всегда кратен 64 КБ (гранулярности распределения) — а значит, автоматически кратен и 4096. Это и чинит ошибку 87: первое правило выравнивания выполняется само собой.

Шаг 51Строки 92–95
if (!alignedBuffer) { std::wcout << L"Ошибка VirtualAlloc!" << std::endl; return 1; }

Проверка выделения: при неудаче — сообщение и выход с кодом 1. return 1 (а не 0) — сигнал оболочке и проверяющему, что программа завершилась ошибкой. Без этой проверки дальше был бы ReadFile по NULL.

Шаг 52Строки 96–97
std::wcout << L"   Адрес выровненного буфера: " << alignedBuffer << L" (Адрес % 4096 == " << ((UINT_PTR)alignedBuffer % SECTOR_SIZE) << L")" << std::endl;

Печатает адрес буфера и остаток от его деления на 4096. Наглядное доказательство выравнивания: остаток обязан быть 0. Если там 0 — первое правило выполнено, и чтение с FILE_FLAG_NO_BUFFERING пройдёт. (UINT_PTR) — приведение указателя к числу, чтобы работал оператор %.

Шаг 53Строки 99–100
// 4. Сравнение скорости ... std::wcout << L"\n4. Сравнение производительности чтения 10 МБ ...";

Анонс шага 4 — бенчмарка. Подготовка к главному измерению лабораторной.

Шаг 54Строки 102–103
// Тест А ... double timeCached = BenchmarkReading(testFile, FILE_ATTRIBUTE_NORMAL, alignedBuffer, alignedChunkSize);

Тест А: чтение с обычным системным кэшем. FILE_ATTRIBUTE_NORMAL в параметре flags — обычное открытие без специальных флагов. Тот же файл, тот же выровненный буфер, тот же размер чанка — меняется только флаг. Поэтому разница времён — чистый эффект кэширования, а не разных условий.

Шаг 55Строки 104
std::wcout << L"   А) Стандартное чтение (с системным кэшем):  " << timeCached << L" мс" << std::endl;

Вывод времени теста А в миллисекундах. Первое число для отчёта и сравнения.

Тема 1. Небуферизированный ввод-вывод (FILE_FLAG_NO_BUFFERING)
Задача №1

Что это

Обычное чтение файла в Windows идёт через системный файловый кэш: ядро читает данные с диска в свою память (кэш страниц), а потом копирует их в буфер программы. Получается двойная работа — данные проходят через RAM дважды. Флаг FILE_FLAG_NO_BUFFERING в CreateFileW отключает этот промежуточный кэш: контроллер диска через DMA (прямой доступ к памяти, без участия процессора) пишет данные напрямую в буфер приложения.

Зачем это нужно

  • СУБД (SQL Server, PostgreSQL, Oracle) ведут собственный кэш страниц и не хотят, чтобы ОС держала вторую копию тех же данных — это удваивает расход RAM.
  • Видео и большие файлы: при потоковой обработке гигабайтов кэш ОС бесполезен — данные читаются один раз и больше не понадобятся, а кэш только вытесняет полезные страницы других программ.
  • Предсказуемость: без кэша время чтения — это честное время диска, а не «повезло, что данные уже были в RAM».

Три правила выравнивания — за их нарушение ядро возвращает ошибку 87

Когда кэш обойдён, ядро не может «дочитать» недостающие байты из кэша — контроллер диска работает только целыми секторами. Поэтому все три параметра чтения обязаны быть кратны размеру сектора:

ПравилоЧто должно быть кратно 4096Пример нарушения в задаче 1
1. Адрес буфераБазовый адрес буфера в памятиchar unalignedBuf[1000] на стеке — адрес произвольный, не кратен 4096
2. Смещение в файлеПозиция чтения (файловый указатель)В задаче 1 смещение 0 — кратно, это правило НЕ нарушено
3. Размер чтенияЧисло запрашиваемых байтовsizeof(unalignedBuf) = 1000 — не кратно 4096

Нарушение любого из трёх — ReadFile возвращает FALSE, а GetLastError() — 87 (ERROR_INVALID_PARAMETER). Это не «диск сломался» и не «файл не найден», а именно неверные параметры вызова.

Почему в коде 4096, если сектор диска может быть 512 байт? На современных дисках физический сектор — 4096 байт (Advanced Format), а страница памяти — тоже 4096. Требования Windows формулируются через размер сектора тома, но буфер, выровненный на 4096, удовлетворяет и 512-байтным дискам (4096 кратно 512). Поэтому 4096 — безопасный выбор на любом диске.

Как исправить: VirtualAlloc

VirtualAlloc выделяет память целыми страницами, поэтому возвращаемый адрес всегда кратен 64 КБ (гранулярности распределения) — а значит, автоматически кратен и 4096. В задаче 1 размер буфера 64 КБ тоже кратен 4096 (65536 / 4096 = 16), а чтение идёт с начала файла (смещение 0). Все три правила выполнены — чтение проходит. Проверка в программе — вывод Адрес % 4096 == 0.

Тема 2. Отображение файлов в память и TLB
Задача №2

Что такое file mapping

Проецирование файла в память (file mapping) — это способ работать с файлом как с обычным массивом в памяти, без ReadFile/WriteFile. Шаги: CreateFileW открывает файл → CreateFileMappingW создаёт объект-раздел на файл → MapViewOfFile отображает часть файла в адресное пространство процесса → чтение и запись идут обычными обращениями по указателю → UnmapViewOfFile снимает отображение. За сброс грязных страниц на диск отвечает ядро — лениво, в фоне.

Зачем СУБД используют file mapping

  • Скорость случайного доступа: не нужно позиционировать указатель и вызывать чтение на каждую запись — обращение по указателю, страница подгружается сама по Page Fault.
  • Единый кэш: спроецированные страницы — это те же страницы системного кэша, двойного копирования нет.
  • Совместный доступ: несколько процессов могут спроецировать один файл и видеть изменения друг друга.
  • Пример: SQLite, LMDB и многие встраиваемые СУБД целиком построены на mmap / MapViewOfFile.

Страницы, таблицы страниц и TLB

Память делится на страницы по 4096 байт. Соответствие «виртуальный адрес → физический фрейм» хранится в таблицах страниц (Page Tables) процесса, а процессор кэширует недавние трансляции в TLB (Translation Lookaside Buffer) — маленьком, но очень быстром аппаратном кэше. Пока трансляция в TLB, обращение к памяти идёт без обращения к таблицам страниц.

TLB Flush — сброс этого кэша. Когда ядро меняет таблицы страниц (например, при UnmapViewOfFile), старые трансляции становятся неверными, и процессор обязан их выбросить — инструкцией INVLPG (сброс одной записи) или перезаписью регистра CR3 (сброс всего TLB). После сброса следующее обращение к странице — это TLB Miss + проход по таблицам страниц, а если страница уже не в памяти — ещё и Page Fault с загрузкой страницы с диска.

Гранулярность 64 КБ против страницы 4 КБ

В Windows два разных размера: страница — 4 КБ (единица коммита и защиты), гранулярность распределения — 64 КБ (единица, с которой можно начинать резервирование и проецирование). Поэтому смещение в MapViewOfFile обязано быть кратно 64 КБ — в задаче 2 это делается округлением вниз: (byteOffset / 65536) * 65536, а остаток byteOffset % 65536 — смещение внутри окна. Узнать гранулярность правильно — через GetSystemInfo, а не хардкодом.

Тема 3. Виртуальная память и VirtualAlloc
Задача №3

Что такое виртуальная память

Каждый процесс в 64-битной Windows видит своё приватное виртуальное адресное пространство (~128 ТБ доступно пользователю). Виртуальные адреса не равны физическим: MMU процессора переводит их в физические фреймы RAM через таблицы страниц. Один и тот же виртуальный адрес в двух процессах — это разная физическая память. Физическая RAM выделяется только тогда, когда к странице реально обратились.

Два шага: MEM_RESERVE и MEM_COMMIT

ФлагЧто делаетСтоит ли RAM

Разделение существует не просто так: программа может зарезервировать, например, 1 ГБ адресного пространства «впрок», а коммитить страницы по мере роста данных — так работают кучи, стеки потоков и базы данных.

Правила VirtualAlloc / VirtualFree

  • Выравнивание: базовый адрес всегда кратен 64 КБ (гранулярности). Поэтому память от VirtualAlloc автоматически подходит для FILE_FLAG_NO_BUFFERING.
  • Округление размера: запрошенный размер округляется вверх до целого числа страниц по 4096 байт. 40 000 байт → реально 40 960 (10 страниц). Кратность размера просить не надо.
  • Защита страниц: PAGE_READWRITE — чтение и запись; PAGE_READONLY — только чтение; PAGE_EXECUTE_READWRITE — для JIT-кода. Защита enforced на уровне MMU: неверный доступ — исключение, а не тихая порча.
  • VirtualFree и MEM_RELEASE: при MEM_RELEASE параметр размера обязан быть 0 — освобождается весь блок целиком. Ненулевой размер → ошибка 87. Частично освободить блок нельзя, только целиком.
  • MEM_DECOMMIT: возвращает физические страницы, но диапазон адресов остаётся зарезервированным — его можно закоммитить снова. В задачах 1 и 3 не используется.

Тема 4. Замер времени: QueryPerformanceCounter
Задачи №1 и №2

Обычные часы (clock(), GetTickCount()) слишком грубы для замера миллисекунд. QueryPerformanceCounter — высокоточный таймер Windows с разрешением в доли микросекунды. Схема замера:

  1. QueryPerformanceFrequency(&freq) — узнать, сколько тиков в одной секунде (у разных ПК частота разная, обычно порядка 10 МГц).
  2. QueryPerformanceCounter(&start) — отметка «до».
  3. Замеряемый код.
  4. QueryPerformanceCounter(&end) — отметка «после».
  5. Время в мс = (end − start) × 1000 / freq. Деление именно на частоту, а не на 1000, — частая ошибка.

Важно замерять только интересующий код: открытие файла и создание маппинга в задачах 1–2 вынесены за пределы замера, иначе в результат попал бы посторонний шум. И наоборот: в режиме Б задачи 2 в замер намеренно включены Map/Unmap — потому что их стоимость и есть предмет измерения.

Виртуальная память
Задача №3

Каждая программа видит своё собственное адресное пространство, как будто вся память компьютера принадлежит только ей. На самом деле Windows переводит адреса программы в настоящую физическую память, поэтому две программы могут использовать один и тот же адрес и не мешать друг другу.

Пример: Два человека живут в разных квартирах с одинаковым номером — почтальон (Windows) знает, кому какое письмо нести.
Выравнивание
Задача №1

Буфер считается выровненным, когда его адрес делится на 4096 без остатка. Диск работает только целыми секторами, поэтому программа должна ставить буфер точно на границу сектора.

Пример: Книги на полке ставят с края полки, а не с середины.
Гранулярность распределения
Задача №2

Шаг в 64 КБ, с которым Windows выдаёт адреса: начало любого выделенного участка памяти всегда кратно 64 КБ. Программа не может попросить участок с произвольного адреса.

Пример: Забор ставят только по столбам, расстояние между столбами всегда одинаковое.
Небуферизированный ввод-вывод
Задача №1

Чтение и запись файла напрямую, без системного кэша: данные идут с диска сразу в буфер программы. Так работают базы данных, которым не нужна вторая копия данных в памяти Windows.

Пример: Покупатель забирает товар прямо со склада, а не ждёт, пока его выложат на полку магазина.
Ошибка 87 (ERROR_INVALID_PARAMETER)
Задача №1

Ответ Windows «неверные параметры»: программа попросила прочитать файл, но буфер, смещение в файле или размер чтения не кратны 4096. Чтение не выполняется, программа получает код 87 и должна исправить параметры.

Пример: Ключ не подходит к замку — дверь не открывается, и виноват не замок, а ключ.
Проецирование файла в память
Задача №2

Способ работать с файлом как с обычной памятью: Windows показывает файл в адресном пространстве программы, и программа читает и пишет его обычными действиями с памятью, без отдельных команд чтения и записи файла.

Пример: Книга лежит открытой на столе — читатель сразу берёт любую страницу, а не ходит за ней в библиотеку.
Сброс TLB
Задача №2

Очистка маленького кэша в процессоре, где хранятся переводы адресов в физическую память. Windows очищает этот кэш, когда меняет адреса программы, и после очистки процессор ищет переводы заново, поэтому работа замедляется.

Пример: Учитель стирает шпаргалку с доски, и ученикам приходится писать её заново.
Сектор
Задача №1

Самый маленький кусок диска, который диск читает или пишет за один раз; в этой лабе его размер — 4096 байт. Меньше одного сектора диск прочитать не может, поэтому программа всегда просит целое число секторов.

Пример: Кирпич — самая маленькая часть стены, стену строят только из целых кирпичей.
Системный кэш
Задачи №1, №2

Память, где Windows хранит копии данных из файлов, чтобы второй раз не ходить на диск. Первый раз файл читается с диска, а потом программа берёт данные из кэша — это гораздо быстрее.

Пример: Повар держит нож под рукой, а не ходит за ним на склад каждый раз.
Страница памяти
Задачи №1–№3

Кусок памяти размером 4096 байт; Windows делит всю память на такие куски и выдаёт программе память только целыми страницами.

Пример: Тетрадь состоит из листов, и продавец продаёт только целые листы, а не половинки.
СУБД
Задача №2

Программа для хранения данных и быстрого поиска среди них, например база данных с таблицами. СУБД хранит данные в файлах на диске и сама решает, какие данные держать в памяти.

Пример: Библиотекарь хранит книги и находит нужную книгу, не перебирая все полки.
TLB
Задача №2

Маленький и очень быстрый кэш в процессоре, где хранятся переводы адресов в физическую память. Процессор сначала смотрит в TLB, и только если перевода там нет, ищет адрес дольше.

Пример: Телефонная книга — человек звонит сразу, не вспоминая номер.
VirtualAlloc
Задачи №1, №3

Функция Windows, которая просит память напрямую у ядра Windows. Ядро даёт программе страницы памяти, а адрес начала всегда кратен 64 КБ — поэтому память от VirtualAlloc автоматически подходит для небуферизированного чтения.

Пример: Человек арендует склад напрямую у хозяина, а не через посредника.
FILE_FLAG_NO_BUFFERING
Задача №1

Флаг для открытия файла: говорит Windows не использовать системный кэш и передавать данные напрямую с диска в буфер программы. За это приходится платить строгими правилами: буфер, смещение и размер чтения должны быть кратны 4096, иначе Windows вернёт ошибку 87.

Пример: Курьер везёт посылку прямо покупателю, минуя склад.
MEM_COMMIT
Задачи №1, №3

Флаг для VirtualAlloc: говорит ядру Windows выделить настоящие физические страницы памяти. Без этого флага программа получает только забронированные адреса, а памяти под ними нет.

Пример: Хозяин не только бронирует стол, но и ставит на стол еду.
MEM_RESERVE
Задачи №1, №3

Флаг для VirtualAlloc: говорит ядру Windows забронировать диапазон адресов в адресном пространстве программы, чтобы никто другой его не занял. Физическая память при этом не выделяется — только адреса.

Пример: Человек бронирует стол в кафе, но еда на столе ещё не стоит.
QueryPerformanceCounter
Задачи №1, №2

Функция Windows для точного замера времени: программа вызывает её до и после работы, а потом делит разницу отметок таймера на частоту таймера и получает время в миллисекундах. Обычные часы для таких замеров слишком грубые.

Пример: Судья включает секундомер на старте забега и выключает на финише.

Тема 1. Небуферизированный ввод-вывод (FILE_FLAG_NO_BUFFERING)
Задача №1

Что это

Обычное чтение файла идёт через системный кэш. Ядро читает данные с диска в системный кэш. Ядро копирует данные из системного кэша в буфер программы. Данные проходят через память дважды. Флаг FILE_FLAG_NO_BUFFERING в CreateFileW отключает системный кэш. Контроллер диска пишет данные напрямую в буфер программы через DMA — прямой доступ к памяти без участия процессора.

Зачем это нужно

  • СУБД (SQL Server, PostgreSQL, Oracle) ведут собственный кэш страниц. СУБД не хотят второй копии тех же данных в системном кэше. Вторая копия удваивает расход памяти.
  • Видео и большие файлы: системный кэш бесполезен при потоковой обработке гигабайтов. Программа читает данные один раз. Данные больше не нужны программе. Системный кэш только вытесняет полезные страницы других программ.
  • Предсказуемость: без кэша время чтения равно времени диска. Результат не зависит от того, лежат ли данные уже в памяти.

Три правила выравнивания — за их нарушение ядро возвращает ошибку 87

Небуферизированный ввод-вывод обходит системный кэш. Ядро не дочитывает недостающие байты из системного кэша. Контроллер диска читает только целые секторы. Программа задаёт все три параметра чтения кратными размеру сектора.

2. Смещение в файлеПозиция чтения (файловый указатель)В задаче 1 смещение равно 0. Смещение кратно сектору. Программа не нарушает правило смещения.

Любое нарушение даёт код ошибки 87. ReadFile возвращает FALSE. GetLastError() возвращает 87 (ERROR_INVALID_PARAMETER). Ошибка означает неверные параметры вызова. Ошибка не означает сбой диска. Ошибка не означает отсутствие файла.

Почему в коде 4096, если сектор диска равен 512 байт? Физический сектор современного диска равен 4096 байт (Advanced Format). Страница памяти тоже равна 4096 байт. Windows задаёт требования через размер сектора тома. Буфер с выравниванием 4096 подходит и для дисков с сектором 512 байт, потому что 4096 кратно 512. Поэтому 4096 — безопасный выбор на любом диске.

Как исправить: VirtualAlloc

VirtualAlloc выделяет память целыми страницами. Возвращаемый адрес всегда кратен 64 КБ (гранулярности распределения), поэтому адрес автоматически кратен и 4096. В задаче 1 размер буфера равен 64 КБ, и размер 65536 кратен 4096: 65536 / 4096 = 16. Чтение идёт с начала файла, смещение равно 0. Все три правила выполнены, поэтому чтение проходит. Программа проверяет адрес выводом Адрес % 4096 == 0.

Тема 2. Отображение файлов в память и TLB
Задача №2

Что такое file mapping

Проецирование файла в память (file mapping) работает с файлом как с массивом в памяти. Проецирование не использует ReadFile и WriteFile. Сначала CreateFileW открывает файл, затем CreateFileMappingW создаёт объект-раздел на файл. Затем MapViewOfFile отображает часть файла в адресное пространство процесса. Программа читает и пишет обычными обращениями по указателю, а в конце UnmapViewOfFile снимает отображение. Ядро сбрасывает грязные страницы на диск лениво, в фоне.

Зачем СУБД используют file mapping

  • Скорость случайного доступа: программа не позиционирует указатель для каждой записи. Программа не вызывает чтение для каждой записи. Программа обращается к данным по указателю. Ядро подгружает страницу по Page Fault.
  • Единый кэш: спроецированные страницы — это страницы системного кэша. Программа не копирует данные дважды.
  • Совместный доступ: несколько процессов проецируют один файл. Каждый процесс видит изменения других процессов.
  • Пример: SQLite, LMDB и многие встраиваемые СУБД целиком используют mmap и MapViewOfFile.

Страницы, таблицы страниц и TLB

Память делится на страницы по 4096 байт. Таблица страниц процесса хранит соответствие виртуального адреса физическому фрейму. Процессор кэширует недавние трансляции в TLB (Translation Lookaside Buffer). TLB — маленький, но очень быстрый аппаратный кэш. Пока трансляция лежит в TLB, программа обращается к памяти без таблиц страниц.

Сброс TLB — сброс этого кэша. Ядро меняет таблицы страниц, например при UnmapViewOfFile. Старые трансляции становятся неверными. Процессор выбрасывает старые трансляции инструкцией INVLPG (сброс одной записи) или перезаписью регистра CR3 (сброс всего TLB). После сброса следующее обращение к странице даёт TLB Miss и проход по таблицам страниц. Если страницы нет в памяти, обращение даёт ещё и Page Fault с загрузкой страницы с диска.

Гранулярность 64 КБ против страницы 4 КБ

В Windows есть два разных размера. Страница равна 4 КБ и служит единицей коммита и защиты, а гранулярность распределения равна 64 КБ. Резервирование и проецирование начинаются только с границы 64 КБ, поэтому смещение в MapViewOfFile кратно 64 КБ. Тема 3. Виртуальная память и VirtualAlloc
Задача №3

Что такое виртуальная память

Каждый процесс в 64-битной Windows видит своё приватное виртуальное адресное пространство. Пользователю доступно около 128 ТБ. Виртуальные адреса не равны физическим адресам. MMU процессора переводит виртуальные адреса в физические фреймы памяти через таблицы страниц. Один и тот же виртуальный адрес в двух процессах указывает на разную физическую память. Ядро выделяет физическую память только тогда, когда программа реально обращается к странице.

Правила VirtualAlloc / VirtualFree

  • Выравнивание: базовый адрес всегда кратен 64 КБ (гранулярности распределения). Поэтому память от VirtualAlloc автоматически подходит для FILE_FLAG_NO_BUFFERING.
  • Округление размера: ядро округляет запрошенный размер вверх до целого числа страниц по 4096 байт. Запрос 40 000 байт реально даёт 40 960 байт, то есть 10 страниц. Программа не просит кратность размера.
  • Защита страниц: PAGE_READWRITE разрешает чтение и запись. PAGE_READONLY разрешает только чтение. PAGE_EXECUTE_READWRITE служит для JIT-кода. MMU проверяет защиту страниц. Неверный доступ даёт исключение, а не тихую порчу.
  • VirtualFree и MEM_RELEASE: при MEM_RELEASE размер равен 0. Программа освобождает весь блок целиком. Ненулевой размер даёт ошибку 87. Программа не освобождает блок частично, только целиком.
  • MEM_DECOMMIT: ядро возвращает физические страницы. Диапазон адресов остаётся зарезервированным. Программа снова коммитит этот диапазон. В задачах 1 и 3 программа не использует MEM_DECOMMIT.

Тема 4. Замер времени: QueryPerformanceCounter
Задачи №1 и №2

Обычные часы (clock(), GetTickCount()) слишком грубы для замера миллисекунд. QueryPerformanceCounter — высокоточный таймер Windows с разрешением в доли микросекунды. Программа измеряет время по такой схеме:

  1. QueryPerformanceFrequency(&freq) узнаёт, сколько тиков в одной секунде. У разных ПК частота разная, обычно порядка 10 МГц.
  2. QueryPerformanceCounter(&start) ставит отметку «до».
  3. Программа выполняет замеряемый код.
  4. QueryPerformanceCounter(&end) ставит отметку «после».
  5. Время в мс равно (end − start) × 1000 / freq. Программа делит именно на частоту, а не на 1000. Деление на 1000 — частая ошибка.

Программа измеряет только интересующий код. Программа выносит открытие файла и создание проецирования в задачах 1–2 за пределы замера. Иначе в результат попадает посторонний шум. В режиме Б задачи 2 замер намеренно включает Map/Unmap. Их стоимость и есть предмет измерения.

Виртуальная память
Задача №3

Виртуальная память — это адресное пространство программы. Windows даёт каждой программе отдельное адресное пространство. Программа работает только со своим адресным пространством. Windows переводит адреса из адресного пространства в физическую память. Пример: две программы пишут по одному адресу, но Windows даёт каждой свою физическую память.

Выравнивание
Задача №1

Выравнивание — это положение буфера на границе, кратной 4096 байтам. Буфер начинается там, где начинается кусок диска размером 4096 байт. Диск читает и пишет только целые куски по 4096 байт. Программа ставит буфер так, чтобы начало буфера совпадало с началом куска. Пример: книга начинается с новой страницы, а не с середины страницы.

Гранулярность распределения
Задача №2

Гранулярность распределения — это шаг, с которым Windows даёт адреса. Шаг равен 64 КБ. Windows даёт начало участка только на границе этого шага. Программа не может начать участок в середине шага. Пример: забор ставят только по столбам, а не между столбами.

Небуферизированный ввод-вывод
Задача №1

Небуферизированный ввод-вывод — это чтение и запись файла мимо системного кэша. Диск передаёт данные прямо в буфер программы. Диск не кладёт данные в системный кэш. Windows не хранит копию данных в системном кэше. Пример: покупатель берёт товар прямо со склада, а не с полки магазина.

Ошибка 87 (ERROR_INVALID_PARAMETER)
Задача №1

Ошибка 87 — это ответ Windows: параметры вызова неверны. Windows возвращает ошибку 87, когда буфер, смещение или размер не кратны 4096. Программа получает ошибку 87 и не читает данные. Программа исправляет параметры и повторяет чтение. Пример: замок не открывается, потому что ключ не подходит к замку.

Проецирование файла в память
Задача №2

Проецирование файла в память — это способ работать с файлом как со страницами памяти. Windows показывает файл как часть адресного пространства программы. Программа читает файл и пишет в файл, как в страницы памяти. Программа не просит Windows читать файл и писать файл. Пример: книга лежит открытой на столе, и читатель берёт любую страницу сразу.

Сброс TLB
Задача №2

Сброс TLB — это очистка маленького кэша в процессоре. Этот кэш хранит переводы адресов в физическую память. Процессор использует переводы адресов, чтобы быстро находить физическую память. Windows очищает этот кэш, когда меняет адреса программы. После очистки процессор ищет переводы адресов заново, и работа замедляется. Пример: учитель стирает шпаргалку с доски, и ученики пишут её заново.

Сектор
Задача №1

Сектор — это самый маленький кусок диска, который диск читает за один раз. Размер сектора равен 4096 байтам. Диск не читает меньше одного сектора. Программа просит у диска целое число секторов. Пример: кирпич — самая маленькая часть стены, и стену строят только из целых кирпичей.

Системный кэш
Задачи №1, №2

Системный кэш — это физическая память, где Windows хранит копии данных из файлов. Windows читает файл с диска один раз и кладёт копию в системный кэш. Программа берёт данные из системного кэша, а не с диска. Второе чтение файла идёт быстрее первого чтения. Пример: повар держит нож под рукой, а не ходит за ним на склад.

Страница памяти
Задачи №1–№3

Страница памяти — это кусок физической памяти размером 4096 байт. Windows делит физическую память на страницы памяти. Windows даёт программе физическую память только целыми страницами памяти. Программа не получает меньше одной страницы памяти. Пример: тетрадь состоит из листов, и продавец продаёт только целые листы.

СУБД
Задача №2

СУБД — это программа для хранения данных и поиска данных. СУБД хранит данные в файлах на диске. СУБД читает из файлов только нужные данные. СУБД сама решает, какие данные держать в физической памяти. Пример: библиотекарь хранит книги и находит нужную книгу без перебора всех книг.

TLB
Задача №2

TLB — это маленький кэш в процессоре для переводов адресов. TLB хранит переводы адресов в физическую память. Процессор берёт перевод адресов из TLB и сразу находит физическую память. Без перевода адресов процессор ищет адрес дольше. Пример: телефонная книга хранит номера, и человек звонит сразу, без поиска номера.

VirtualAlloc
Задачи №1, №3

VirtualAlloc — это функция Windows, которая просит страницы памяти у ядра Windows. Программа вызывает VirtualAlloc, и ядро Windows даёт ей страницы памяти. Ядро Windows даёт адрес, кратный 64 КБ. Программа возвращает страницы памяти ядру Windows, когда они больше не нужны. Пример: человек берёт в аренду склад, а потом возвращает склад хозяину.

FILE_FLAG_NO_BUFFERING
Задача №1

FILE_FLAG_NO_BUFFERING — это флаг для открытия файла без системного кэша. Программа передаёт флаг, когда открывает файл. Флаг говорит Windows: не клади данные в системный кэш. Флаг требует выравнивания буфера, смещения и размера на 4096. Пример: курьер везёт посылку прямо покупателю, а не на склад.

MEM_COMMIT
Задачи №1, №3

MEM_COMMIT — это флаг для выделения страниц памяти. Программа передаёт флаг функции VirtualAlloc. Флаг говорит ядру Windows: дай страницы памяти. Без флага программа получает только адреса, а не страницы памяти. Пример: хозяин не только бронирует стол, но и ставит на стол еду.

MEM_RESERVE
Задачи №1, №3

MEM_RESERVE — это флаг для бронирования адресного пространства. Программа передаёт флаг функции VirtualAlloc. Флаг говорит ядру Windows: сохрани эти адреса за мной. Флаг не даёт страницы памяти, только адреса. Пример: человек бронирует стол в кафе, но еда на столе ещё не стоит.

QueryPerformanceCounter
Задачи №1, №2

QueryPerformanceCounter — это функция Windows для точного замера времени. Программа вызывает функцию до работы и после работы. Функция возвращает число отметок точного таймера Windows. Программа делит разницу отметок на частоту таймера и получает время в миллисекундах. Пример: судья включает секундомер на старте и выключает секундомер на финише.
