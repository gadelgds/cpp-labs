Тема 1. Небуферизированный ввод-вывод (FILE_FLAG_NO_BUFFERING)
Задача №1

Что это

Обычное чтение файла в Windows идёт через системный файловый кэш: ядро читает данные с диска в свою память (кэш страниц), а потом копирует их в буфер программы. Получается двойная работа — данные проходят через RAM дважды. Флаг FILE_FLAG_NO_BUFFERING в CreateFileW отключает этот промежуточный кэш: контроллер диска через DMA (прямой доступ к памяти, без участия процессора) пишет данные напрямую в буфер приложения.

Зачем это нужно

  • СУБД (SQL Server, PostgreSQL, Oracle) ведут собственный кэш страниц и не хотят, чтобы ОС держала вторую копию тех же данных — это удваивает расход RAM.
  • Видео и большие файлы: при потоковой обработке гигабайтов кэш ОС бесполезен — данные читаются один раз и больше не понадобятся, а кэш только вытесняет полезные страницы других программ.
  • Предсказуемость: без кэша время чтения — это честное время диска, а не «повезло, что данные уже были в RAM».

Три правила выравнивания — за их нарушение ядро возвращает ошибку 87

Когда кэш обойдён, ядро не может «дочитать» недостающие байты из кэша — контроллер диска работает только целыми секторами. Поэтому все три параметра чтения обязаны быть кратны размеру сектора:

ПравилоЧто должно быть кратно 4096Пример нарушения в задаче 1
1. Адрес буфераБазовый адрес буфера в памятиchar unalignedBuf[1000] на стеке — адрес произвольный, не кратен 4096
2. Смещение в файлеПозиция чтения (файловый указатель)В задаче 1 смещение 0 — кратно, это правило НЕ нарушено
3. Размер чтенияЧисло запрашиваемых байтовsizeof(unalignedBuf) = 1000 — не кратно 4096

Нарушение любого из трёх — ReadFile возвращает FALSE, а GetLastError() — 87 (ERROR_INVALID_PARAMETER). Это не «диск сломался» и не «файл не найден», а именно неверные параметры вызова.

Почему в коде 4096, если сектор диска может быть 512 байт? На современных дисках физический сектор — 4096 байт (Advanced Format), а страница памяти — тоже 4096. Требования Windows формулируются через размер сектора тома, но буфер, выровненный на 4096, удовлетворяет и 512-байтным дискам (4096 кратно 512). Поэтому 4096 — безопасный выбор на любом диске.

Как исправить: VirtualAlloc

VirtualAlloc выделяет память целыми страницами, поэтому возвращаемый адрес всегда кратен 64 КБ (гранулярности распределения) — а значит, автоматически кратен и 4096. В задаче 1 размер буфера 64 КБ тоже кратен 4096 (65536 / 4096 = 16), а чтение идёт с начала файла (смещение 0). Все три правила выполнены — чтение проходит. Проверка в программе — вывод Адрес % 4096 == 0.

Тема 2. Отображение файлов в память и TLB
Задача №2

Что такое file mapping

Проецирование файла в память (file mapping) — это способ работать с файлом как с обычным массивом в памяти, без ReadFile/WriteFile. Шаги: CreateFileW открывает файл → CreateFileMappingW создаёт объект-раздел на файл → MapViewOfFile отображает часть файла в адресное пространство процесса → чтение и запись идут обычными обращениями по указателю → UnmapViewOfFile снимает отображение. За сброс грязных страниц на диск отвечает ядро — лениво, в фоне.

Зачем СУБД используют file mapping

  • Скорость случайного доступа: не нужно позиционировать указатель и вызывать чтение на каждую запись — обращение по указателю, страница подгружается сама по Page Fault.
  • Единый кэш: спроецированные страницы — это те же страницы системного кэша, двойного копирования нет.
  • Совместный доступ: несколько процессов могут спроецировать один файл и видеть изменения друг друга.
  • Пример: SQLite, LMDB и многие встраиваемые СУБД целиком построены на mmap / MapViewOfFile.

Страницы, таблицы страниц и TLB

Память делится на страницы по 4096 байт. Соответствие «виртуальный адрес → физический фрейм» хранится в таблицах страниц (Page Tables) процесса, а процессор кэширует недавние трансляции в TLB (Translation Lookaside Buffer) — маленьком, но очень быстром аппаратном кэше. Пока трансляция в TLB, обращение к памяти идёт без обращения к таблицам страниц.

TLB Flush — сброс этого кэша. Когда ядро меняет таблицы страниц (например, при UnmapViewOfFile), старые трансляции становятся неверными, и процессор обязан их выбросить — инструкцией INVLPG (сброс одной записи) или перезаписью регистра CR3 (сброс всего TLB). После сброса следующее обращение к странице — это TLB Miss + проход по таблицам страниц, а если страница уже не в памяти — ещё и Page Fault с загрузкой страницы с диска.

Гранулярность 64 КБ против страницы 4 КБ

В Windows два разных размера: страница — 4 КБ (единица коммита и защиты), гранулярность распределения — 64 КБ (единица, с которой можно начинать резервирование и проецирование). Поэтому смещение в MapViewOfFile обязано быть кратно 64 КБ — в задаче 2 это делается округлением вниз: (byteOffset / 65536) * 65536, а остаток byteOffset % 65536 — смещение внутри окна. Узнать гранулярность правильно — через GetSystemInfo, а не хардкодом.

Тема 3. Виртуальная память и VirtualAlloc
Задача №3

Что такое виртуальная память

Каждый процесс в 64-битной Windows видит своё приватное виртуальное адресное пространство (~128 ТБ доступно пользователю). Виртуальные адреса не равны физическим: MMU процессора переводит их в физические фреймы RAM через таблицы страниц. Один и тот же виртуальный адрес в двух процессах — это разная физическая память. Физическая RAM выделяется только тогда, когда к странице реально обратились.

Два шага: MEM_RESERVE и MEM_COMMIT

ФлагЧто делаетСтоит ли RAM
MEM_RESERVEРезервирует непрерывный диапазон виртуальных адресов, чтобы никто другой его не занялНет — только адреса
MEM_COMMITПривязывает к зарезервированным адресам физические страницы (RAM или файл подкачки)Да — страницы реально выделяются
MEM_RESERVE | MEM_COMMITОба шага сразу — самый частый случай (как в задачах 1 и 3)Да

Разделение существует не просто так: программа может зарезервировать, например, 1 ГБ адресного пространства «впрок», а коммитить страницы по мере роста данных — так работают кучи, стеки потоков и базы данных.

Правила VirtualAlloc / VirtualFree

  • Выравнивание: базовый адрес всегда кратен 64 КБ (гранулярности). Поэтому память от VirtualAlloc автоматически подходит для FILE_FLAG_NO_BUFFERING.
  • Округление размера: запрошенный размер округляется вверх до целого числа страниц по 4096 байт. 40 000 байт → реально 40 960 (10 страниц). Кратность размера просить не надо.
  • Защита страниц: PAGE_READWRITE — чтение и запись; PAGE_READONLY — только чтение; PAGE_EXECUTE_READWRITE — для JIT-кода. Защита enforced на уровне MMU: неверный доступ — исключение, а не тихая порча.
  • VirtualFree и MEM_RELEASE: при MEM_RELEASE параметр размера обязан быть 0 — освобождается весь блок целиком. Ненулевой размер → ошибка 87. Частично освободить блок нельзя, только целиком.
  • MEM_DECOMMIT: возвращает физические страницы, но диапазон адресов остаётся зарезервированным — его можно закоммитить снова. В задачах 1 и 3 не используется.

Тема 4. Замер времени: QueryPerformanceCounter
Задачи №1 и №2

Обычные часы (clock(), GetTickCount()) слишком грубы для замера миллисекунд. QueryPerformanceCounter — высокоточный таймер Windows с разрешением в доли микросекунды. Схема замера:

  1. QueryPerformanceFrequency(&freq) — узнать, сколько тиков в одной секунде (у разных ПК частота разная, обычно порядка 10 МГц).
  2. QueryPerformanceCounter(&start) — отметка «до».
  3. Замеряемый код.
  4. QueryPerformanceCounter(&end) — отметка «после».
  5. Время в мс = (end − start) × 1000 / freq. Деление именно на частоту, а не на 1000, — частая ошибка.

Важно замерять только интересующий код: открытие файла и создание маппинга в задачах 1–2 вынесены за пределы замера, иначе в результат попал бы посторонний шум. И наоборот: в режиме Б задачи 2 в замер намеренно включены Map/Unmap — потому что их стоимость и есть предмет измерения.

Задача №3 — память ядра

Как вводить размер: после приглашения введите число и нажмите Enter. Примеры: 10000 (по умолчанию), 1000, 500000. Чтобы получить значение по умолчанию, введите 0 или любую букву — просто нажать Enter не выйдет: оператор >> пропускает пустые строки и ждёт число.

Память успешно возвращена ядру Windows (VirtualFree MEM_RELEASE).

Ограничения ввода: при count больше 46 341 значения i*i перестают влезать в int (переполнение) — для учебного запуска берите count ≤ 46 341. Гигантские значения (например, больше свободной оперативной памяти) дадут «Ошибка выделения памяти у ядра» и завершение с кодом 1 — это честная проверка из программы, а не падение. Реально выделяемый объём всегда округляется ядром вверх до целого числа страниц по 4096 байт.

Главный вывод про «заранее создать файл»: ни для одной программы файл заранее создавать не надо — обе программы, которым нужен файл, создают его сами при запуске (CREATE_ALWAYS). Поэтому инструкция «создайте непустой файл и укажите путь» к этой лабе не относится: путь уже указан в коде относительным именем, а файл появляется сам в рабочей папке.
