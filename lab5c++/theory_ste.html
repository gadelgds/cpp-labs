Тема 1. Небуферизированный ввод-вывод (FILE_FLAG_NO_BUFFERING)
Задача №1

Что это

Обычное чтение файла идёт через системный кэш. Ядро читает данные с диска в системный кэш. Ядро копирует данные из системного кэша в буфер программы. Данные проходят через память дважды. Флаг FILE_FLAG_NO_BUFFERING в CreateFileW отключает системный кэш. Контроллер диска пишет данные напрямую в буфер программы через DMA — прямой доступ к памяти без участия процессора.

Зачем это нужно

  • СУБД (SQL Server, PostgreSQL, Oracle) ведут собственный кэш страниц. СУБД не хотят второй копии тех же данных в системном кэше. Вторая копия удваивает расход памяти.
  • Видео и большие файлы: системный кэш бесполезен при потоковой обработке гигабайтов. Программа читает данные один раз. Данные больше не нужны программе. Системный кэш только вытесняет полезные страницы других программ.
  • Предсказуемость: без кэша время чтения равно времени диска. Результат не зависит от того, лежат ли данные уже в памяти.

Три правила выравнивания — за их нарушение ядро возвращает ошибку 87

Небуферизированный ввод-вывод обходит системный кэш. Ядро не дочитывает недостающие байты из системного кэша. Контроллер диска читает только целые секторы. Программа задаёт все три параметра чтения кратными размеру сектора.

ПравилоЧто должно быть кратно 4096Пример нарушения в задаче 1
1. Адрес буфераБазовый адрес буфера в памятиchar unalignedBuf[1000] лежит на стеке. Адрес буфера произвольный. Адрес не кратен 4096.
2. Смещение в файлеПозиция чтения (файловый указатель)В задаче 1 смещение равно 0. Смещение кратно сектору. Программа не нарушает правило смещения.
3. Размер чтенияЧисло запрашиваемых байтовsizeof(unalignedBuf) равно 1000. Размер не кратен 4096.

Любое нарушение даёт код ошибки 87. ReadFile возвращает FALSE. GetLastError() возвращает 87 (ERROR_INVALID_PARAMETER). Ошибка означает неверные параметры вызова. Ошибка не означает сбой диска. Ошибка не означает отсутствие файла.

Почему в коде 4096, если сектор диска равен 512 байт? Физический сектор современного диска равен 4096 байт (Advanced Format). Страница памяти тоже равна 4096 байт. Windows задаёт требования через размер сектора тома. Буфер с выравниванием 4096 подходит и для дисков с сектором 512 байт, потому что 4096 кратно 512. Поэтому 4096 — безопасный выбор на любом диске.

Как исправить: VirtualAlloc

VirtualAlloc выделяет память целыми страницами. Возвращаемый адрес всегда кратен 64 КБ (гранулярности распределения), поэтому адрес автоматически кратен и 4096. В задаче 1 размер буфера равен 64 КБ, и размер 65536 кратен 4096: 65536 / 4096 = 16. Чтение идёт с начала файла, смещение равно 0. Все три правила выполнены, поэтому чтение проходит. Программа проверяет адрес выводом Адрес % 4096 == 0.

Тема 2. Отображение файлов в память и TLB
Задача №2

Что такое file mapping

Проецирование файла в память (file mapping) работает с файлом как с массивом в памяти. Проецирование не использует ReadFile и WriteFile. Сначала CreateFileW открывает файл, затем CreateFileMappingW создаёт объект-раздел на файл. Затем MapViewOfFile отображает часть файла в адресное пространство процесса. Программа читает и пишет обычными обращениями по указателю, а в конце UnmapViewOfFile снимает отображение. Ядро сбрасывает грязные страницы на диск лениво, в фоне.

Зачем СУБД используют file mapping

  • Скорость случайного доступа: программа не позиционирует указатель для каждой записи. Программа не вызывает чтение для каждой записи. Программа обращается к данным по указателю. Ядро подгружает страницу по Page Fault.
  • Единый кэш: спроецированные страницы — это страницы системного кэша. Программа не копирует данные дважды.
  • Совместный доступ: несколько процессов проецируют один файл. Каждый процесс видит изменения других процессов.
  • Пример: SQLite, LMDB и многие встраиваемые СУБД целиком используют mmap и MapViewOfFile.

Страницы, таблицы страниц и TLB

Память делится на страницы по 4096 байт. Таблица страниц процесса хранит соответствие виртуального адреса физическому фрейму. Процессор кэширует недавние трансляции в TLB (Translation Lookaside Buffer). TLB — маленький, но очень быстрый аппаратный кэш. Пока трансляция лежит в TLB, программа обращается к памяти без таблиц страниц.

Сброс TLB — сброс этого кэша. Ядро меняет таблицы страниц, например при UnmapViewOfFile. Старые трансляции становятся неверными. Процессор выбрасывает старые трансляции инструкцией INVLPG (сброс одной записи) или перезаписью регистра CR3 (сброс всего TLB). После сброса следующее обращение к странице даёт TLB Miss и проход по таблицам страниц. Если страницы нет в памяти, обращение даёт ещё и Page Fault с загрузкой страницы с диска.

Гранулярность 64 КБ против страницы 4 КБ

В Windows есть два разных размера. Страница равна 4 КБ и служит единицей коммита и защиты, а гранулярность распределения равна 64 КБ. Резервирование и проецирование начинаются только с границы 64 КБ, поэтому смещение в MapViewOfFile кратно 64 КБ. В задаче 2 программа округляет смещение вниз: (byteOffset / 65536) * 65536, а остаток byteOffset % 65536 — смещение внутри окна. Программа узнаёт гранулярность через GetSystemInfo, а не хардкодом.

Тема 3. Виртуальная память и VirtualAlloc
Задача №3

Что такое виртуальная память

Каждый процесс в 64-битной Windows видит своё приватное виртуальное адресное пространство. Пользователю доступно около 128 ТБ. Виртуальные адреса не равны физическим адресам. MMU процессора переводит виртуальные адреса в физические фреймы памяти через таблицы страниц. Один и тот же виртуальный адрес в двух процессах указывает на разную физическую память. Ядро выделяет физическую память только тогда, когда программа реально обращается к странице.

Два шага: MEM_RESERVE и MEM_COMMIT

ФлагЧто делаетСтоит ли RAM

MEM_COMMITMEM_COMMIT привязывает к зарезервированным адресам физические страницы. Страницы лежат в памяти или в файле подкачки.Да — страницы реально выделяются

Программа резервирует адресное пространство впрок, а коммитит страницы по мере роста данных. Программа резервирует, например, 1 ГБ адресного пространства. Так работают кучи, стеки потоков и базы данных.

Правила VirtualAlloc / VirtualFree

  • Выравнивание: базовый адрес всегда кратен 64 КБ (гранулярности распределения). Поэтому память от VirtualAlloc автоматически подходит для FILE_FLAG_NO_BUFFERING.
  • Округление размера: ядро округляет запрошенный размер вверх до целого числа страниц по 4096 байт. Запрос 40 000 байт реально даёт 40 960 байт, то есть 10 страниц. Программа не просит кратность размера.
  • Защита страниц: PAGE_READWRITE разрешает чтение и запись. PAGE_READONLY разрешает только чтение. PAGE_EXECUTE_READWRITE служит для JIT-кода. MMU проверяет защиту страниц. Неверный доступ даёт исключение, а не тихую порчу.
  • VirtualFree и MEM_RELEASE: при MEM_RELEASE размер равен 0. Программа освобождает весь блок целиком. Ненулевой размер даёт ошибку 87. Программа не освобождает блок частично, только целиком.
  • MEM_DECOMMIT: ядро возвращает физические страницы. Диапазон адресов остаётся зарезервированным. Программа снова коммитит этот диапазон. В задачах 1 и 3 программа не использует MEM_DECOMMIT.

Тема 4. Замер времени: QueryPerformanceCounter
Задачи №1 и №2

Обычные часы (clock(), GetTickCount()) слишком грубы для замера миллисекунд. QueryPerformanceCounter — высокоточный таймер Windows с разрешением в доли микросекунды. Программа измеряет время по такой схеме:

  1. QueryPerformanceFrequency(&freq) узнаёт, сколько тиков в одной секунде. У разных ПК частота разная, обычно порядка 10 МГц.
  2. QueryPerformanceCounter(&start) ставит отметку «до».
  3. Программа выполняет замеряемый код.
  4. QueryPerformanceCounter(&end) ставит отметку «после».
  5. Время в мс равно (end − start) × 1000 / freq. Программа делит именно на частоту, а не на 1000. Деление на 1000 — частая ошибка.

Программа измеряет только интересующий код. Программа выносит открытие файла и создание проецирования в задачах 1–2 за пределы замера. Иначе в результат попадает посторонний шум. В режиме Б задачи 2 замер намеренно включает Map/Unmap. Их стоимость и есть предмет измерения.

Задача №2 — симуляция СУБД

Файл готовить заранее не нужно. Программа сама создаёт database_16mb.bin (16 МБ, 4 194 304 значения int) в рабочей папке при запуске. Файл создаёт функция CreateDbBinaryFile с флагом CREATE_ALWAYS. Нужно только около 16 МБ свободного места и право на запись в папку с exe. После прогона пользователь удаляет файл. При следующем запуске программа пересоздаёт файл.

Ожидаемый вывод:

=== ПРАКТИКА №2: СИМУЛЯЦИЯ СУБД (СТАНДАРТНЫЙ I/O vs FILE MAPPING & TLB FLUSH) ===
1. Создание бинарного файла 16 МБ с массивом целых чисел (int)...

2. Запуск Режима А (Стандартный I/O со системным кэшем): 10 000 операций...
   -> Время выполнения Режима А: X мс

3. Запуск Режима Б (Ручное проецирование с UnmapViewOfFile): 10 000 операций...
   -> Время выполнения Режима Б: Y мс

--- АНАЛИЗ НАКЛАДНЫХ РАСХОДОВ TLB FLUSH ---
1. При частых вызовах UnmapViewOfFile ядро ОС Windows вынуждено:
   - Изменять таблицы страниц (Page Tables) процесса;
   - Выполнять аппаратную инструкцию сброса буфера ассоциативной трансляции (TLB Flush / INVLPG);
   - Обрабатывать Page Fault при следующем MapViewOfFile.
2. В Режиме А системный файловый кэш держит страницы непрерывно в ОЗУ без переключения маппингов.

Что должно получиться: время режима Б заметно больше времени режима А, обычно в разы, и это измеряемый эффект сброса TLB. Если режим Б оказался быстрее, диск и кэш прогреты первым режимом, поэтому второй прогон подряд даёт другую картину, и пользователь перезапускает программу. Настоящие ошибки: «Время -1 мс» не предусмотрено в этой программе, потому что программа считает время всегда. Если программа не создала файл, оба режима читают несуществующий файл и молча работают с ошибками ReadFile и WriteFile. Пользователь проверяет, что database_16mb.bin появился и его размер равен ровно 16 777 216 байт.

Задача №3 — память ядра

Файлы не нужны вообще. Программа не открывает и не создаёт файлов, только память и консоль. Единственное условие запуска — консоль (cmd или PowerShell). Программа ждёт ввода числа с клавиатуры.

Как вводить размер: после приглашения пользователь вводит число и нажимает Enter. Примеры: 10000 (по умолчанию), 1000, 500000. Чтобы получить значение по умолчанию, пользователь вводит 0 или любую букву. Просто нажать Enter не выйдет. Оператор >> пропускает пустые строки и ждёт число.

Ожидаемый вывод (для 10000):

=== ПРАКТИКА №3: ВЫДЕЛЕНИЕ ПАМЯТИ НАПРЯМУЮ У ЯДРА WINDOWS (VirtualAlloc) ===
Введите размер массива целых чисел (по умолчанию 10000): 10000
Запрошено элементов: 10000 (40000 байт / ~39 КБ)
Память успешно выделена ядром по адресу: 0x000001...

Первые 10 элементов массива (квадраты индексов):
  pArray[0] = 0
  pArray[1] = 1
  pArray[2] = 4
  pArray[3] = 9
  pArray[4] = 16
  pArray[5] = 25
  pArray[6] = 36
  pArray[7] = 49
  pArray[8] = 64
  pArray[9] = 81

Память успешно возвращена ядру Windows (VirtualFree MEM_RELEASE).

Ограничения ввода: при count больше 46 341 значения i*i перестают влезать в int. Это переполнение. Для учебного запуска пользователь берёт count ≤ 46 341. Гигантские значения, например больше свободной памяти, дают «Ошибка выделения памяти у ядра» и завершение с кодом 1. Это честная проверка из программы, а не падение. Ядро округляет реально выделяемый объём вверх до целого числа страниц по 4096 байт.
