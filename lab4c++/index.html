Задача 1 (Наизусть): Явное приведение типов через static_cast

#include <iostream>
#include <iomanip>

int main() {
    #if defined(_WIN32)
    system("chcp 65001 > nul");
    #endif

    std::cout << "=== НАИЗУСТЬ: ЯВНОЕ ПРИВЕДЕНИЕ ТИПОВ ЧЕРЕЗ static_cast ===" << std::endl;

    // ЧАСТЬ 1: Вычитание int из long с явным приведением к long
    long valLong = 100000L;
    int valInt = 25000;

    // Вычитание с явным приведением static_cast<long>()
    long resultLong = valLong - static_cast<long>(valInt);

    std::cout << "\n[Целочисленное вычитание]:" << std::endl;
    std::cout << "  Переменная long:                 " << valLong << std::endl;
    std::cout << "  Переменная int:                  " << valInt << std::endl;
    std::cout << "  Результат (long - static_cast<long>(int)): " << resultLong << std::endl;

    // ЧАСТЬ 2: Вычитание float из double с явным приведением к double
    double valDouble = 125.75;
    float valFloat = 25.25f;

    // Вычитание с явным приведением static_cast<double>()
    double resultDouble = valDouble - static_cast<double>(valFloat);

    std::cout << "\n[Вещественное вычитание с плавающей точкой]:" << std::endl;
    std::cout << std::fixed << std::setprecision(4);
    std::cout << "  Переменная double:               " << valDouble << std::endl;
    std::cout << "  Переменная float:                " << valFloat << std::endl;
    std::cout << "  Результат (double - static_cast<double>(float)): " << resultDouble << std::endl;

    return 0;
}

// Вычитание с явным приведением static_cast<long>()Комментарий к ключевой строке задания.Фиксирует, что приведение выполняется именно оператором static_cast, а не C-style кастом (long)valInt.
long resultLong = valLong - static_cast<long>(valInt);Приводит valInt к типу long во время компиляции, затем вычитает: 100000 − 25000 = 75000. Без static_cast компилятор сам неявно расширил бы int до long — результат был бы тем же, но требование задания («явно») не выполнялось бы, а намерение программиста не было бы видно в коде.

std::cout << " Переменная int: ..." << valInt << std::endl;Выводит значение valInt — 25000.То же: фиксация второго операнда в выводе.
std::cout << " Результат (long - static_cast<long>(int)): " << resultLong << std::endl;Выводит результат — 75000, а в самой подписи повторяет формулу вычисления.Подпись содержит формулу, поэтому вывод самодокументирован: проверяющий видит не просто число, а то, как оно получено.
// ЧАСТЬ 2: ...Комментарий: дальше вещественная часть задания.Структурирует программу на две симметричные части, как в условии.
double valDouble = 125.75;Объявляет переменную двойной точности (64 бита по IEEE 754) со значением 125.75.«Старший» вещественный тип в паре; литерал с точкой по умолчанию и так имеет тип double, суффикс не нужен.
float valFloat = 25.25f;Объявляет переменную одинарной точности (32 бита) со значением 25.25. Суффикс f делает литерал типом float.Без суффикса литерал 25.25 имел бы тип double, и присваивание в float было бы СУЖАЮЩИМ преобразованием — компилятор выдал бы предупреждение, а значение могло бы потерять точность. Суффикс f убирает сужение.
// Вычитание с явным приведением static_cast<double>()Комментарий к ключевой строке второй части.Аналогично части 1: фиксирует использование именно static_cast.
double resultDouble = valDouble - static_cast<double>(valFloat);Расширяет float до double и вычитает: 125.75 − 25.25 = 100.5.Расширяющее приведение (32 → 64 бита) безопасно: значение сохраняется точно, новой точности не появляется — double просто хранит то же самое число, которое было во float. Здесь результат ровно 100.5, потому что 25.25 = 25 + 1/4 точно представимо в двоичной системе. С числами вроде 0.1 так не было бы: float хранит 0.1 лишь приближённо, и расширение до double показало бы «хвост» (0.100000001490116...).

Поэтому три следующие строки напечатают числа как 125.7500, 25.2500, 100.5000. Без fixed по умолчанию выводилось бы до 6 значащих цифр (125.75, 25.25, 100.5).

std::cout << " Переменная float: ..." << valFloat << std::endl;Выводит 25.2500. Обратите внимание: значение float при выводе неявно расширяется до double, но формат задают манипуляторы, поэтому печатается 4 знака.Фиксация второго операнда; формат вывода единый для всего блока.
std::cout << " Результат (double - static_cast<double>(float)): " << resultDouble << std::endl;Выводит результат — 100.5000.Итог второй части; подпись снова содержит формулу.

Итог: оба приведения в задаче — РАСШИРЯЮЩИЕ (int → long, float → double), поэтому данные не теряются. Обратное направление (long → int, double → float) было бы СУЖАЮЩИМ и могло бы потерять значение — именно поэтому в теории разбирается разница между ними.

Типичные ошибки:

  • Кракозябры вместо кириллицы — запустили exe не из консоли, а двойным кликом, либо консоль не в UTF-8. Лечится запуском из терминала Windows; строка chcp 65001 в коде уже решает это при запуске из cmd/PowerShell.

Задача 2 (Самостоятельно): Указатели void* и разрядность x64
task2_void_pointers_x64.cpp
task2_void_pointers_x64.cpp — полный код (38 строк) 
#include <iostream>

int main() {
    #if defined(_WIN32)
    system("chcp 65001 > nul");
    #endif

    std::cout << "=== САМОСТОЯТЕЛЬНО 1: УКАЗАТЕЛИ void* И РАЗМЕРЫ В x64 ===" << std::endl;

    // 1. Создание переменных типов int и long со значениями
    int numInt = 42;
    long numLong = 123456L;

    // 2. Создание независимых универсальных указателей типа void*
    void* ptrVoid1 = &numInt;
    void* ptrVoid2 = &numLong;

    // 3. Обратное преобразование указателей void* в исходные типы int* и long*
    int* ptrInt = static_cast<int*>(ptrVoid1);
    long* ptrLong = static_cast<long*>(ptrVoid2);

    // 4. Извлечение значений из памяти (разыменование) и вывод на экран
    std::cout << "\n[Извлеченные значения]:" << std::endl;
    std::cout << "  Значение из ptrInt:  " << *ptrInt << " (адрес: " << ptrInt << ")" << std::endl;
    std::cout << "  Значение из ptrLong: " << *ptrLong << " (адрес: " << ptrLong << ")" << std::endl;

    // 5. Определение размеров указателей и типов в архитектуре сборки (x64)
    std::cout << "\n[Размеры типов и указателей в текущей системе]:" << std::endl;
    std::cout << "  Разрядность сборки:    " << (sizeof(void*) * 8) << "-бит" << std::endl;
    std::cout << "  sizeof(int):           " << sizeof(int) << " байт (" << sizeof(int) * 8 << " бит)" << std::endl;
    std::cout << "  sizeof(long):          " << sizeof(long) << " байт (" << sizeof(long) * 8 << " бит)" << std::endl;
    std::cout << "  sizeof(long long):     " << sizeof(long long) << " байт (" << sizeof(long long) * 8 << " бит)" << std::endl;
    std::cout << "  sizeof(void*):         " << sizeof(void*) << " байт (" << sizeof(void*) * 8 << " бит)" << std::endl;
    std::cout << "  sizeof(int*):          " << sizeof(int*) << " байт (" << sizeof(int*) * 8 << " бит)" << std::endl;
    std::cout << "  sizeof(long*):         " << sizeof(long*) << " байт (" << sizeof(long*) * 8 << " бит)" << std::endl;

    return 0;
}

Нужен именно static_cast: программист берёт на себя ответственность, что по этому адресу действительно лежит int. Если бы там лежал long или double, компилятор не остановил бы, а значение прочиталось бы неверно — это главный риск void*.
long* ptrLong = static_cast<long*>(ptrVoid2);То же: void* → long*.Симметричная операция для второй переменной. Тип приведения должен совпадать с исходным типом переменной, иначе разыменование даст мусор.

Адрес при каждом запуске разный (ASLR), поэтому в выводе он будет отличаться от примера — это нормально.

Итог: все указатели в x64 — по 8 байт, независимо от типа данных. А вот сами типы различаются: int и long в Windows — по 4 байта, long long — 8 байт.

#include <windows.h>
#include <iostream>
#include <string>

int main() {
    #if defined(_WIN32)
    system("chcp 65001 > nul");
    #endif

    std::cout << "=== САМОСТОЯТЕЛЬНО 2: ПРОЕЦИРОВАНИЕ ФАЙЛА С ФИКСИРОВАННЫМ СМЕЩЕНИЕМ ===" << std::endl;

    const wchar_t* filename = L"mapped_large_test.txt";

    // 1. Получаем информацию об архитектуре и гранулярности распределения памяти Windows
    SYSTEM_INFO sysInfo;
    GetSystemInfo(&sysInfo);
    DWORD allocGranularity = sysInfo.dwAllocationGranularity; // Обычно 65536 байт (64 КБ)

    std::cout << "Системная гранулярность выделения памяти (Allocation Granularity): "
              << allocGranularity << " байт (" << (allocGranularity / 1024) << " КБ)" << std::endl;

    // 2. Создаем тестовый файл достаточного размера (например, 256 КБ = 4 * 64 КБ)
    HANDLE hFile = CreateFileW(
        filename,
        GENERIC_READ | GENERIC_WRITE,
        FILE_SHARE_READ,
        NULL,
        CREATE_ALWAYS,
        FILE_ATTRIBUTE_NORMAL,
        NULL
    );

    if (hFile == INVALID_HANDLE_VALUE) {
        std::cout << "Ошибка создания файла: " << GetLastError() << std::endl;
        return 1;
    }

    // Заполняем файл данными: 4 блока по 64 КБ с уникальными маркерами
    const DWORD totalFileSize = 4 * allocGranularity; // 256 КБ
    std::string fillData(totalFileSize, '.');

    // Размещаем маркер во 2-м блоке (смещение 2 * allocGranularity = 128 КБ)
    std::string secretMessage = "[СЕКРЕТНЫЙ ТЕКСТ НА СМЕЩЕНИИ 128 КБ]";
    size_t targetOffset = 2 * allocGranularity;
    memcpy(&fillData[targetOffset], secretMessage.c_str(), secretMessage.length());

    DWORD bytesWritten = 0;
    WriteFile(hFile, fillData.data(), totalFileSize, &bytesWritten, NULL);

    // 3. Создаем объект проекции файла (File Mapping Object)
    HANDLE hMapping = CreateFileMappingW(
        hFile,
        NULL,
        PAGE_READONLY,
        0,
        0,
        NULL
    );

    if (hMapping == NULL) {
        std::cout << "Ошибка CreateFileMapping: " << GetLastError() << std::endl;
        CloseHandle(hFile);
        return 1;
    }

    // 4. Смещение для MapViewOfFile ОБЯЗАНО быть строго кратным allocGranularity!
    // Демонстрируем расчет смещения:
    DWORD offsetLow = (DWORD)(targetOffset & 0xFFFFFFFF);
    DWORD offsetHigh = (DWORD)(((ULONGLONG)targetOffset >> 32) & 0xFFFFFFFF);
    SIZE_T viewSize = 1024; // Отображаем окно размером 1024 байта

    std::cout << "\nЗапрос проецирования участка файла:" << std::endl;
    std::cout << "  Смещение: " << targetOffset << " байт (кратно " << allocGranularity << ")" << std::endl;
    std::cout << "  Размер проецируемого окна: " << viewSize << " байт" << std::endl;

    // 5. Проецируем срез файла в виртуальную память процесса
    const char* pView = static_cast<const char*>(MapViewOfFile(
        hMapping,
        FILE_MAP_READ,
        offsetHigh,
        offsetLow,
        viewSize
    ));

    if (pView == NULL) {
        std::cout << "Ошибка MapViewOfFile: " << GetLastError() << std::endl;
    } else {
        std::cout << "  Успешно спроецировано по виртуальному адресу: " << (void*)pView << std::endl;

        // Читаем данные из памяти спроецированного окна
        std::string readChunk(pView, secretMessage.length());
        std::cout << "  Прочитанные данные: \"" << readChunk << "\"" << std::endl;

        // Отмонтируем проекцию
        UnmapViewOfFile(pView);
        std::cout << "Окно проекции успешно размонтировано (UnmapViewOfFile)." << std::endl;
    }

    // 6. Закрытие дескрипторов
    CloseHandle(hMapping);
    CloseHandle(hFile);

    return 0;
}

Замечание для защиты: результат WriteFile и равенство bytesWritten == totalFileSize здесь НЕ проверяются — при нехватке места на диске файл мог бы оказаться короче, а программа этого не заметила бы.
// 3. Создаем объект проекции файла (File Mapping Object)Комментарий: шаг 3 — создать секцию (объект ядра для проецирования).Проецирование идёт в два этапа: сначала создаётся объект отображения, потом из него — представление (view). Пропустить первый этап нельзя.
HANDLE hMapping = CreateFileMappingW( hFile, NULL, PAGE_READONLY, 0, 0, NULL );Создаёт объект проекции файла. Аргументы: дескриптор файла; NULL — безопасность по умолчанию; PAGE_READONLY — страницы отображения только для чтения; размер отображения 0, 0 — ВЕСЬ файл (верхние и нижние 32 бита размера равны 0, что означает «размер файла»); NULL — безымянная секция.Размер 0, 0 — удобный приём: не нужно заранее знать размер файла, секция покрывает его целиком. PAGE_READONLY сочетается с GENERIC_READ у файла; страницы будут только на чтение — запись через указатель pView вызвала бы нарушение доступа. Если бы нужен был и запись, потребовались бы PAGE_READWRITE и FILE_MAP_WRITE.
if (hMapping == NULL) {Проверяет, создалась ли проекция. Для CreateFileMappingW признак ошибки — именно NULL (в отличие от CreateFileW, где признак — INVALID_HANDLE_VALUE).Разные функции — разные коды ошибки, путать их нельзя: проверка hMapping == INVALID_HANDLE_VALUE здесь была бы неверной.
std::cout << "Ошибка CreateFileMapping: " << GetLastError() << std::endl;Печатает код ошибки создания проекции.Диагностика: без кода непонятно, что именно не так (например, несовместимые флаги защиты).
CloseHandle(hFile);Закрывает дескриптор файла перед выходом по ошибке.Важно: даже на ветке ошибки нельзя «бросить» открытый дескриптор — это утечка ресурса. Файл уже создан на диске, дескриптор надо закрыть.
return 1;Завершает программу с кодом ошибки 1.Без объекта проекции проецировать нечего — продолжать бессмысленно.
}Закрывает блок if проверки проекции.Дальше — код, работающий только при успешном создании секции.
// 4. Смещение для MapViewOfFile ОБЯЗАНО быть строго кратным allocGranularity!Комментарий-предупреждение: главное правило задачи.Это то, что проверяется в лабораторной: смещение, не кратное 64 КБ, MapViewOfFile отвергнет.
// Демонстрируем расчет смещения:Комментарий: дальше идёт демонстрационный расчёт младшей/старшей частей смещения.Подчёркивает, что расчёт делается вручную, а не «магическими числами», — так видно механику Win32 API.
DWORD offsetLow = (DWORD)(targetOffset & 0xFFFFFFFF);Выделяет младшие 32 бита смещения: битовая маска 0xFFFFFFFF оставляет только нижние 32 бита 64-битного числа. Для 131072 это просто 131072.MapViewOfFile принимает смещение не одним 64-битным числом, а двумя 32-битными параметрами (dwFileOffsetHigh, dwFileOffsetLow) — наследие 32-битного API. Поэтому 64-битное смещение приходится «разрезать» пополам вручную.
DWORD offsetHigh = (DWORD)(((ULONGLONG)targetOffset >> 32) & 0xFFFFFFFF);Выделяет старшие 32 бита смещения: сдвиг вправо на 32 бита, затем маска. Для 131072 старшая часть равна 0.Приведение к ULONGLONG перед сдвигом важно: сдвиг 32-битного значения на 32 бита дал бы неопределённый результат. Пример для больших файлов: смещение 5 ГБ (0x1_40000000) дало бы offsetHigh = 1, offsetLow = 0x40000000 — вместе они снова собираются как high × 2³² + low.
SIZE_T viewSize = 1024; // Отображаем окно размером 1024 байтаЗадаёт размер проецируемого окна — 1024 байта (1 КБ).Проецируется не весь файл, а только «окно» в 1 КБ начиная со смещения 128 КБ — это и есть «чтение огромного файла порциями» из условия. Окна в 1 КБ достаточно: маркер занимает всего несколько десятков байт. Читать за пределами окна (дальше 1024 байт от его начала) НЕЛЬЗЯ — будет нарушение доступа.
std::cout << "\nЗапрос проецирования участка файла:" << std::endl;Печатает подзаголовок блока с пустой строкой-отступом.Отделяет в выводе параметры проецирования от предыдущих шагов.
std::cout << " Смещение: " << targetOffset << " байт (кратно " << allocGranularity << ")" << std::endl;Печатает «Смещение: 131072 байт (кратно 65536)».Демонстрирует проверяющему, что смещение действительно кратно гранулярности — условие задачи выполнено явно, а не на словах.
std::cout << " Размер проецируемого окна: " << viewSize << " байт" << std::endl;Печатает «Размер проецируемого окна: 1024 байт».Фиксирует размер окна в выводе.
// 5. Проецируем срез файла в виртуальную память процессаКомментарий: шаг 5 — собственно отображение.Центральный вызов программы.
const char* pView = static_cast<const char*>(MapViewOfFile( hMapping, FILE_MAP_READ, offsetHigh, offsetLow, viewSize ));Отображает 1024 байта файла, начиная со смещения 131072, в виртуальное адресное пространство процесса и возвращает указатель на начало окна. Аргументы: дескриптор секции; FILE_MAP_READ — доступ только на чтение; старшая и младшая части смещения; размер окна. MapViewOfFile возвращает void*, поэтому результат явно приводится к const char*.После этого вызова байты файла читаются как обычная память: pView[0] — первый байт маркера. const char* выбран потому, что данные — текст, а const запрещает запись (отображение всё равно только для чтения). static_cast здесь обязателен: неявное приведение void* → const char* в C++ запрещено.
if (pView == NULL) {Проверяет, удалось ли спроецировать окно.Если смещение не кратно 64 КБ, MapViewOfFile вернёт NULL, а GetLastError() — 1132 (ERROR_MAPPED_ALIGNMENT). Если смещение + размер окна выходят за конец файла — тоже NULL с другим кодом.
std::cout << "Ошибка MapViewOfFile: " << GetLastError() << std::endl;Печатает код ошибки проецирования.По коду различают причину: 1132 — неверное выравнивание смещения, другие коды — выход за конец файла или нехватка виртуальной памяти.
} else {Ветка успеха: проекция создана.Разделение на «ошибка» и «успех» — стандартный паттерн Win32: дальше код, который работает только с живым отображением.
std::cout << " Успешно спроецировано по виртуальному адресу: " << (void*)pView << std::endl;Печатает виртуальный адрес начала окна. Приведение (void*)pView нужно, чтобы cout напечатал АДРЕС, а не содержимое: для const char* оператор << по умолчанию печатает строку до '\0'.Без приведения к void* вывод показал бы текст маркера вместо адреса — классическая ловушка char* в потоках. Адрес при каждом запуске разный (ASLR) — это нормально.
// Читаем данные из памяти спроецированного окнаКомментарий: дальше чтение из отображения.Показывает, что чтение идёт из ПАМЯТИ, а не через ReadFile — в этом и смысл проецирования.
std::string readChunk(pView, secretMessage.length());Создаёт строку из ровно secretMessage.length() байт, начиная с адреса pView. Используется конструктор string(const char*, size_t) — чтение по длине, а не до нулевого байта.Так читается именно маркер: он начинается на смещении 128 КБ, а его длина известна заранее. Конструктор по длине важен: в спроецированной памяти после маркера идут точки '.', а не '\0', поэтому чтение «до нуля» прочитало бы лишнее.
std::cout << " Прочитанные данные: \"" << readChunk << "\"" << std::endl;Печатает прочитанный маркер в кавычках: «[СЕКРЕТНЫЙ ТЕКСТ НА СМЕЩЕНИИ 128 КБ]».Главное доказательство работы программы: текст, записанный в файл на шаге 2, прочитан обратно через спроецированную память на шаге 5. Если бы смещение было неверным, здесь был бы другой текст или ошибка.
// Отмонтируем проекциюКомментарий: дальше освобождение отображения.Структурирует завершение работы.
UnmapViewOfFile(pView);Отмонтирует (unmap) представление: освобождает виртуальный адресный диапазон окна. Функция возвращает BOOL, здесь результат не проверяется.Каждое MapViewOfFile обязано завершаться парным UnmapViewOfFile — иначе диапазон виртуальной памяти останется занятым до конца процесса. После этого вызова указатель pView становится недействительным, обращаться к нему нельзя.
std::cout << "Окно проекции успешно размонтировано (UnmapViewOfFile)." << std::endl;Печатает подтверждение размонтирования.Фиксирует в выводе, что ресурс освобождён корректно.
}Закрывает блок else (ветку успеха).Синтаксическая граница ветки.
// 6. Закрытие дескрипторовКомментарий: шаг 6 — финальная очистка.Последний шаг программы.
CloseHandle(hMapping);Закрывает дескриптор объекта проекции (секции).Порядок важен: сначала закрывается секция, потом файл. Объект ядра уничтожается, когда закрыт последний его дескриптор. Здесь закрытие идёт после UnmapViewOfFile, поэтому к этому моменту отображение уже снято.
CloseHandle(hFile);Закрывает дескриптор файла.После закрытия файл можно открывать другими программами без ограничений, а дескриптор не утекает. Файл mapped_large_test.txt остаётся на диске — его можно открыть и убедиться, что маркер действительно на смещении 128 КБ.
return 0;Возвращает ОС код 0 — успешное завершение.Выполняется, даже если MapViewOfFile не удался: в той ветке программа лишь печатает ошибку, но всё равно доходит сюда и возвращает 0. Строго говоря, это слабое место — по коду возврата нельзя отличить «проекция не удалась» от успеха; для учебного кода допустимо.
}Закрывающая скобка main.Конец программы; все локальные объекты (sysInfo, строки, счётчики) уничтожаются.
Почему смещение ОБЯЗАНО быть кратно 64 КБ: диспетчер виртуальной памяти Windows отображает файл страницами, привязанными к гранулярности распределения (Allocation Granularity = 65 536 байт). Смещение 131072 = 2 × 65536 — допустимо. Смещение 131073 или 100000 — нет: MapViewOfFile вернёт NULL, а GetLastError() даст 1132 (ERROR_MAPPED_ALIGNMENT).
Итог: программа сама создаёт файл 256 КБ, кладёт маркер ровно на 128 КБ, проецирует окно 1 КБ с этого смещения и читает маркер из памяти — без единого вызова ReadFile.
Как запустить — задача 3

Только Windows. Программа использует Win32 API (windows.h, CreateFileW, MapViewOfFile) — под Linux/macOS она не соберётся.

Файл заранее создавать НЕ нужно. Это важно: программа сама создаёт mapped_large_test.txt в рабочей папке (флаг CREATE_ALWAYS в CreateFileW), записывает в него 256 КБ данных (4 × 64 КБ) и кладёт маркер на смещение 128 КБ. При каждом запуске файл перезаписывается заново. Если в папке уже лежит старый mapped_large_test.txt — он будет обнулён и создан заново, это нормальное поведение, а не ошибка.

Единственное условие к папке запуска: право на запись в рабочую папку (туда, откуда запускается exe). Если прав нет — программа напечатает «Ошибка создания файла: 5» (код 5 = отказано в доступе) и завершится с кодом 1.

Компиляция (Windows):

:: MSVC — в Developer Command Prompt for VS: cl /EHsc /std:c++17 task3_memory_mapped_offset.cpp :: MinGW-w64 (g++) — в PowerShell / cmd: g++ -std=c++17 -o task3.exe task3_memory_mapped_offset.cpp

Запуск: из папки, где лежит exe (файл mapped_large_test.txt появится рядом с exe):

.\task3.exe

Ожидаемый вывод (виртуальный адрес при каждом запуске разный — это нормально):

=== САМОСТОЯТЕЛЬНО 2: ПРОЕЦИРОВАНИЕ ФАЙЛА С ФИКСИРОВАННЫМ СМЕЩЕНИЕМ === Системная гранулярность выделения памяти (Allocation Granularity): 65536 байт (64 КБ) Запрос проецирования участка файла: Смещение: 131072 байт (кратно 65536) Размер проецируемого окна: 1024 байт Успешно спроецировано по виртуальному адресу: 0x0000021A3B4C5000 Прочитанные данные: "[СЕКРЕТНЫЙ ТЕКСТ НА СМЕЩЕНИИ 128 КБ]" Окно проекции успешно размонтировано (UnmapViewOfFile).

Проверка файла после запуска: рядом с exe появится mapped_large_test.txt размером 262144 байта; маркер можно найти поиском по файлу или командой PowerShell:

:: Размер файла и проверка маркера на смещении 128 КБ: powershell -c "(Get-Item mapped_large_test.txt).Length" powershell -c "$b=[System.IO.File]::ReadAllBytes('mapped_large_test.txt'); [System.Text.Encoding]::UTF8.GetString($b[131072..131120])"

Типичные ошибки:

  • «Ошибка MapViewOfFile: 1132» — смещение не кратно 64 КБ. В коде смещение 131072 = 2 × 65536, поэтому при неизменённом коде этой ошибки не будет; она появится, если поменять targetOffset на некруглое число (например, 100000).
  • «Ошибка создания файла: 5» — нет прав на запись в папку запуска (например, exe лежит в C:\Program Files). Запустите из обычной папки, например из папки проекта или Desktop.
  • «Ошибка MapViewOfFile» с другим кодом — смещение + размер окна выходят за конец файла. В коде файл 256 КБ, а окно 128 КБ + 1 КБ = 129 КБ < 256 КБ, поэтому при неизменённом коде не возникает; появится, если уменьшить totalFileSize или увеличить targetOffset.
  • Нарушение доступа (падение) при чтении дальше 1024 байт от pView — окно спроецировано только на 1 КБ; байты за его пределами недоступны. Читайте только внутри viewSize.
  • Если в старой версии шпаргалки вы видели код с OPEN_EXISTING — это была сокращённая версия: в реальном файле task3_memory_mapped_offset.cpp стоит CREATE_ALWAYS, и файл создаётся самой программой. Для режима OPEN_EXISTING файл действительно пришлось бы создавать заранее (например, fsutil file createnew mapped_large_test.txt 262144), но к актуальному коду это не относится.
