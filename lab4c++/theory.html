Тема 1. Приведение типов: неявное, явное, static_cast
к задаче 1 • task1_explicit_casting.cpp

Что это

Приведение типов (type cast, преобразование типа) — это смена типа значения: один и тот же набор бит начинает интерпретироваться по правилам другого типа. Например, целое число 25000 типа int после приведения к long остаётся числом 25000, но занимает «старший» целочисленный тип и может участвовать в операциях с long без дополнительных преобразований.

Зачем это нужно

В C++ у каждой переменной строгий тип, а у каждой операции — требования к типам операндов. Приведение типов нужно, чтобы: (1) выполнить операцию между значениями разных типов по заданным правилам; (2) показать компилятору и читающему код, что преобразование сделано намеренно, а не случайно; (3) подавить предупреждения компилятора о потере данных там, где программист проверил, что потери нет.

Неявное и явное приведение

ВидКак выглядитКто решаетПример
Неявное (implicit)Никак не пишется — компилятор вставляет самКомпилятор, по правилам языкаlong x = 25000; — int неявно расширяется до long
Явное (explicit)Оператор приведения в кодеПрограммистlong x = static_cast<long>(25000);

Неявное приведение происходит при присваивании, передаче аргумента в функцию, возврате из функции и в смешанных арифметических выражениях. Оно всегда «безопасно» с точки зрения компилятора: язык разрешает неявно только те преобразования, которые не могут потерять значение (расширяющие). Сужающие преобразования неявно тоже разрешены, но компилятор обычно выдаёт предупреждение — это сигнал «проверь, ты точно этого хотел?».

static_cast — главный оператор явного приведения

static_cast<НовыйТип>(выражение) — приведение, проверяемое во время компиляции. «Static» означает, что проверка и само преобразование происходят на этапе сборки, а не во время выполнения: никакого кода проверки в программу не добавляется, поэтому static_cast бесплатен по времени работы. Что он умеет:

  • Числовые преобразования: int ↔ long, float ↔ double, целое ↔ вещественное, знаковое ↔ беззнаковое.
  • Приведения указателей: void* → типизированный указатель и обратно (тема 2), приведения в иерархии классов вверх/вниз (в этой лабе не используется).
  • Явный вызов конструктора преобразования: static_cast<std::string>(…) и подобные.

Чего static_cast НЕ делает: он не снимает const (для этого есть const_cast), не приводит несвязанные типы (например, int* → double* напрямую — ошибка компиляции) и не проверяет во время выполнения, что по указателю действительно лежит объект нужного типа (для этого есть dynamic_cast, только для классов с виртуальными функциями). Старый C-style каст (long)valInt делает всё это «молча» и без проверок, поэтому в современном C++ его избегают: static_cast видно в коде, его легко найти поиском, и он запрещает опасные преобразования.

Расширяющие и сужающие преобразования

НаправлениеПримерыПотеря данных
Расширяющее (widening)int → long, float → double, int → doubleНет: значение сохраняется точно
Сужающее (narrowing)long → int, double → float, double → intВозможна: старшие биты отбрасываются, дробная часть отбрасывается, точность теряется

Оба приведения в задаче 1 — расширяющие, поэтому результат точный. Обратные примеры: static_cast<int>(100000L) в 32-битном int ещё влезает, а static_cast<int>(5000000000L) уже даст неверное число (переполнение); static_cast<int>(3.99) даст 3 — дробная часть просто отбрасывается, без округления.

Размеры целых типов в Windows (модель LLP64)

В Linux x64 модель данных другая — LP64, и там long равен 8 байтам. Поэтому sizeof(long) зависит от системы, и программа задачи 2 честно измеряет его через sizeof, а не полагается на память.

Вещественные числа: IEEE 754, float и double

Числа с плавающей точкой хранятся по стандарту IEEE 754: знак (1 бит), порядок-экспонента и мантисса (значащие цифры в двоичной системе).

ТипРазмерЗнак / экспонента / мантиссаТочных десятичных цифрПримерный диапазон
float4 байта (32 бита)1 / 8 / 23 бита≈ 7±3,4 × 10³⁸
double8 байт (64 бита)1 / 11 / 52 бита≈ 15–16±1,8 × 10³⁰⁸

Главное следствие: большинство десятичных дробей (0.1, 0.2, 25.25 — нет, 25.25 исключение) нельзя точно записать в двоичной системе, поэтому float и double хранят лишь приближение. Примеры:

Пример: потеря точности
float f = 0.1f;              // хранится как 0.100000001490116...
double d = static_cast<double>(f); // станет 0.10000000149011612 —
// расширение НЕ добавляет точности, оно показывает
// то значение, которое уже было во float
double x = 0.1 + 0.2;        // 0.30000000000000004, а не 0.3

В задаче 1 этого эффекта нет: 25.25 = 25 + 1/4, а 1/4 — точная степень двойки, поэтому float хранит 25.25 точно и результат 100.5 точен. Суффикс f у литерала 25.25f обязателен: без него литерал имеет тип double, и присваивание в float было бы сужающим преобразованием с предупреждением компилятора.

Типичные ошибки

  • Путать static_cast с C-style кастом (тип)значение: результат тот же, но C-style каст скрывает опасные преобразования и его нельзя найти поиском по коду.
  • Считать, что static_cast<double>(float) повышает точность: нет, оно лишь сохраняет уже имеющееся (приближённое) значение float в более широком формате.
  • Сравнивать вещественные числа через == после вычислений: из-за накопления ошибки округления 0.1 + 0.2 == 0.3 даёт false; сравнивают с допуском (эпсилон).
  • Забывать суффикс f у float-литералов и суффикс L у long-литералов — компилятор выдаёт предупреждения о сужении.
  • Сужающее приведение больших значений: static_cast<int>(5000000000L) — переполнение, значение искажается молча, без ошибки времени выполнения.
Тема 2. Указатели void* и разрядность x64
к задаче 2 • task2_void_pointers_x64.cpp

Что это

Указатель — переменная, хранящая адрес ячейки памяти. int* p = &x; означает: «p хранит адрес переменной x, а по этому адресу лежит значение типа int». Тип указателя говорит компилятору, сколько байт читать при разыменовании (*p) и на сколько байт сдвигаться при p + 1.

void* — универсальный (нетипизированный) указатель. Он хранит адрес, но не знает, данные какого типа лежат по этому адресу. «Void» буквально означает «пустота»: у типа void нет размера, поэтому компилятор не знает, сколько байт читать и как их интерпретировать.

Зачем нужен void*

  • Обобщённые функции: memcpy, malloc, qsort работают с «сырой» памятью любого типа — они принимают void*.
  • Системные API: Win32-функции вроде MapViewOfFile (тема 3) возвращают void*, потому что отображаемая память может содержать что угодно — текст, структуры, картинки.
  • Хранение «чужого» адреса: когда тип данных заранее неизвестен и выясняется позже (например, по коду типа, переданному рядом).

Правила работы с void*

ОперацияРазрешена?Пояснение
Любой указатель → void*Да, неявноvoid* p = &numInt; — безопасно, адрес просто копируется
void* → типизированный указательТолько явно, через static_castint* p = static_cast<int*>(ptrVoid); — программист отвечает за правильность типа
Разыменование *ptrVoidНет — ошибка компиляцииНеизвестно, сколько байт читать: у void нет размера
Арифметика ptrVoid + 1Нет (в стандартном C++)Неизвестен шаг: на сколько байт сдвигаться — на 1, 4 или 8?
sizeof(void*)ДаРазмер самого указателя известен всегда — 8 байт в x64
Сравнение указателей ==ДаСравниваются адреса как числа

Главный риск void*: компилятор не проверяет, что тип при обратном приведении совпадает с реальным типом данных. Если в void* лежит адрес double, а привести его к int* и разыменовать — получится мусор: первые 4 байта double будут прочитаны как целое число. Ошибки компиляции не будет, программа просто выдаст неверный результат. Поэтому рядом с void* всегда должен быть отдельный признак типа (перечисление, флаг, знание из контекста).

Разрядность x64 и размеры типов

«64-битная архитектура» означает, что адресное пространство — 64 бита: указатель может адресовать 2⁶⁴ байт, а сам занимает 8 байт. Размер указателя зависит ТОЛЬКО от архитектуры, а не от типа данных:

ВыражениеWindows x64 (LLP64)Linux x64 (LP64)Windows/Linux x86
sizeof(void*)884
sizeof(int*), sizeof(long*)884
sizeof(int)444
sizeof(long)484
sizeof(long long)888

Модель данных Windows называется LLP64: long long и указатели — 64-битные, а long остаётся 32-битным (для совместимости со старым кодом). Модель Linux — LP64: long тоже 64-битный. Поэтому программа задачи 2 на Linux напечатала бы sizeof(long) = 8 — это не ошибка, а другая модель данных. Приём sizeof(void*) * 8 — способ «спросить» разрядность у компилятора: в x64 получится 64, в x86 — 32.

Адреса в выводе: почему они каждый раз разные

Адреса переменных на стеке (0x000000A1B2C3D4E5 в примере) при каждом запуске разные из-за ASLR (рандомизации размещения адресного пространства) — защитного механизма Windows. Сравнивать адреса между запусками бессмысленно; важно лишь, что адрес из ptrInt совпадает с адресом переменной numInt, а значения извлекаются верно.

Типичные ошибки

  • Попытка разыменовать void* напрямую (*ptrVoid) — ошибка компиляции; сначала static_cast.
  • Неявное приведение void* → int* (int* p = ptrVoid;) — ошибка компиляции в C++ (в C это разрешено, в C++ — нет).
  • Обратное приведение к НЕВЕРНОМУ типу: компилятор промолчит, а значение будет мусором.
  • Разыменование указателя после уничтожения переменной (висячий указатель): void* не продлевает жизнь объекту.
  • Путать размер указателя и размер данных: sizeof(int*) = 8, а sizeof(int) = 4 — это разные вещи.
  • Сборка в 32-битном режиме при задаче про x64: sizeof(void*) станет 4 — проверяйте целевую платформу (x64) в настройках проекта.
Тема 3. Проецирование файлов в память: CreateFileMapping и MapViewOfFile
к задаче 3 • task3_memory_mapped_offset.cpp

Что это

Проецирование файла в память (memory-mapped file) — механизм, при котором содержимое файла отображается в виртуальное адресное пространство процесса: байты файла становятся доступны как обычная память, через указатель. Чтение файла превращается в чтение из памяти (pView[i]), а запись в память — в запись в файл (если отображение открыто на запись). Диспетчер виртуальной памяти Windows сам подгружает нужные страницы с диска и сбрасывает изменённые обратно.

Зачем это нужно

  • Большие файлы: файл в гигабайты не нужно целиком грузить в RAM — отображается только нужное «окно», а система подкачивает страницы по мере обращения.
  • Скорость: нет буферов и лишних копирований, как при ReadFile; данные читаются напрямую из страничного кэша системы.
  • Общий доступ к памяти: одна и та же секция может быть спроецирована в несколько процессов — это способ межпроцессного взаимодействия (shared memory).
  • Произвольный доступ: к любому смещению файла можно обратиться напрямую, без seek и последовательного чтения.

Цепочка вызовов: от файла к указателю

Проецирование всегда делается в три шага, и у каждого шага — свой дескриптор, который потом надо закрыть:

ШагФункцияЧто создаётЧто вернуть / закрыть
1CreateFileWОткрывает файл, возвращает HANDLE hFileОшибка — INVALID_HANDLE_VALUE; закрыть — CloseHandle(hFile)
2CreateFileMappingWСоздаёт объект ядра «секция» (File Mapping Object), возвращает HANDLE hMappingОшибка — NULL; закрыть — CloseHandle(hMapping)
3MapViewOfFileОтображает окно секции в адресное пространство, возвращает void* pViewОшибка — NULL; снять — UnmapViewOfFile(pView)

Порядок освобождения — обратный порядку создания: сначала UnmapViewOfFile(pView), потом CloseHandle(hMapping), потом CloseHandle(hFile). Закрытие дескриптора файла раньше времени отображение не разрушает (секция держит файл), но правильный порядок — часть дисциплины работы с ресурсами: каждый открытый дескриптор должен быть закрыт ровно один раз.

CreateFileMapping: параметры

CreateFileMappingW(hFile, NULL, PAGE_READONLY, 0, 0, NULL) — аргументы по порядку: дескриптор файла; атрибуты безопасности (NULL — по умолчанию); защита страниц (PAGE_READONLY — только чтение, PAGE_READWRITE — чтение и запись, PAGE_WRITECOPY — копирование при записи); старший и младший DWORD размера секции — 0, 0 означает «размер всего файла»; имя секции (NULL — безымянная, только для этого процесса). Защита секции и права доступа к файлу должны согласовываться: PAGE_READONLY требует GENERIC_READ у файла, PAGE_READWRITE — GENERIC_READ | GENERIC_WRITE.

MapViewOfFile: параметры

MapViewOfFile(hMapping, FILE_MAP_READ, offsetHigh, offsetLow, viewSize) — аргументы: дескриптор секции; желаемый доступ (FILE_MAP_READ — чтение, FILE_MAP_WRITE — запись, FILE_MAP_ALL_ACCESS — всё); старшая и младшая части смещения начала окна; размер окна в байтах (0 — до конца секции). Возвращает void* — указатель на начало окна, который приводят к нужному типу (const char* для текста).

Allocation Granularity — почему смещение не может быть случайным

Диспетчер виртуальной памяти Windows работает не с отдельными байтами, а с блоками. Есть два разных размера, и их нельзя путать:

ВеличинаЗначение (x86/x64)На что влияет
Размер страницы (dwPageSize)4 КБ (4096 байт)Минимальная единица подкачки с диска и защиты памяти
Гранулярность распределения (dwAllocationGranularity)64 КБ (65 536 байт)Выравнивание начальных адресов резервируемых областей виртуальной памяти — и смещений в MapViewOfFile

Смещение окна в файле должно быть кратно именно гранулярности — 64 КБ. Причина аппаратно-системная: виртуальные адреса областей, которые резервирует менеджер памяти, выравниваются по 64 КБ, и начало отображаемого окна привязано к этим границам. Смещение 131072 = 2 × 65536 — допустимо. Смещение 100000, 131073 или 65537 — нет: MapViewOfFile немедленно вернёт NULL, а GetLastError() даст код 1132 — ERROR_MAPPED_ALIGNMENT («базовый адрес или смещение файла не имеют требуемого выравнивания»).

При этом РАЗМЕР окна может быть любым (в задаче — 1024 байта): выравнивание требуется только для начала окна, а не для его конца. И читать внутри окна можно с любой точностью: если нужно прочитать данные с «некратного» смещения 100000, проецируют окно с кратного смещения 65536, а потом просто берут pView[100000 − 65536] — то есть добавляют разницу внутри окна.

Как узнать гранулярность правильно: не хардкодить 65536, а спросить у системы через GetSystemInfo(&sysInfo) и поле dwAllocationGranularity. На всех современных Windows x86/x64 это 64 КБ, но код, который спрашивает, а не угадывает, — переносимый и правильный.

Разбиение смещения на offsetHigh / offsetLow

MapViewOfFile — функция из 32-битной эпохи: 64-битное смещение она принимает двумя 32-битными параметрами. Поэтому смещение «разрезают» пополам:

Разбиение 64-битного смещения
DWORD offsetLow  = (DWORD)(targetOffset & 0xFFFFFFFF);
DWORD offsetHigh = (DWORD)(((ULONGLONG)targetOffset >> 32) & 0xFFFFFFFF);
// Обратная сборка: смещение = offsetHigh * 2^32 + offsetLow
СмещениеoffsetHighoffsetLow
131072 (128 КБ, задача)0131072
5 368 709 120 (5 ГБ)11 073 741 824 (0x40000000)
0 (начало файла)00

Приведение к ULONGLONG перед сдвигом обязательно: сдвиг 32-битного значения на 32 бита — неопределённое поведение. Для смещений меньше 4 ГБ старшая часть всегда 0, но код пишется общим — для файлов любого размера.

Чтение порциями: идея задачи

Файл в задаче — 256 КБ, а окно — всего 1 КБ. Это модель работы с огромным файлом: вместо загрузки всего файла в память программа отображает окно на нужном смещении, читает его, снимает отображение и отображает следующее окно (например, 131072 + 1024, если 1024 кратно… — нет: следующее окно тоже должно начинаться с кратного 64 КБ смещения, поэтому «порции» при проецировании обычно делают размером, кратным гранулярности, а внутри окна двигаются указателем). В задаче демонстрируется один шаг этого цикла: окно на 128 КБ, чтение маркера, снятие отображения.

Типичные ошибки

  • Смещение не кратно 64 КБ → NULL и ошибка 1132 (ERROR_MAPPED_ALIGNMENT).
  • Смещение + размер окна выходят за конец файла → MapViewOfFile возвращает NULL (файл должен быть не меньше, чем offset + viewSize).
  • Забыть UnmapViewOfFile или CloseHandle — утечка виртуального адресного диапазона и дескрипторов.
  • Чтение/запись за пределами окна (дальше viewSize байт от pView) — нарушение доступа, падение программы.
  • Запись через отображение, открытое как PAGE_READONLY / FILE_MAP_READ, — нарушение доступа; для записи нужны PAGE_READWRITE и FILE_MAP_WRITE.
  • Путать коды ошибок: у CreateFileW признак неудачи — INVALID_HANDLE_VALUE, а у CreateFileMappingW и MapViewOfFile — NULL.
  • Выводить const char* через cout без приведения к void* — напечатается строка, а не адрес.
  • Проверять GetLastError() не сразу после неудачного вызова — следующий вызов API может перезаписать код ошибки.

Чем компилировать

Подходят два компилятора (нужен стандарт C++17 или новее):

Компиляция всех трёх задач
:: MSVC — в Developer Command Prompt for VS (цель x64):
cl /EHsc /std:c++17 task1_explicit_casting.cpp
cl /EHsc /std:c++17 task2_void_pointers_x64.cpp
cl /EHsc /std:c++17 task3_memory_mapped_offset.cpp

:: MinGW-w64 (g++) — в PowerShell / cmd:
g++ -std=c++17 -o task1.exe task1_explicit_casting.cpp
g++ -std=c++17 -o task2.exe task2_void_pointers_x64.cpp
g++ -std=c++17 -o task3.exe task3_memory_mapped_offset.cpp

Флаг /EHsc у MSVC включает обработку исключений C++ (нужен для корректной работы стандартной библиотеки), -std=c++17 задаёт стандарт языка. Имя выходного exe у MSVC совпадает с именем cpp-файла (task1_explicit_casting.exe), у g++ задаётся флагом -o. Запускать — из той же папки, где лежит exe: .\task1.exe, .\task2.exe, .\task3.exe.

Задача 3: откуда берётся файл

В актуальном коде task3_memory_mapped_offset.cpp файл создаётся самой программой: CreateFileW вызван с флагом CREATE_ALWAYS — «создать новый файл или обнулить существующий». Поэтому заранее создавать mapped_large_test.txt НЕ нужно, и его размер заранее не важен: программа сама записывает в него 256 КБ (4 блока по 64 КБ) и кладёт маркер на смещение 128 КБ. После запуска файл остаётся рядом с exe, его размер — 262144 байта. Если запустить программу ещё раз, файл будет перезаписан заново — это нормально.

Если бы в коде вместо CREATE_ALWAYS стоял OPEN_EXISTING (так было в сокращённой версии кода из старой шпаргалки), файл пришлось бы создавать заранее, и он должен был бы быть не меньше 128 КБ + 1 КБ (смещение + окно). Для такого случая файл создаётся одной из команд (выполнять в папке запуска, от имени пользователя с правами на запись):

Создание тестового файла вручную — только для режима OPEN_EXISTING
:: cmd (256 КБ = 262144 байта):
fsutil file createnew mapped_large_test.txt 262144

:: PowerShell (тот же результат):
[System.IO.File]::WriteAllBytes('mapped_large_test.txt', [byte[]]::new(262144))

К актуальному коду задачи 3 эти команды не относятся — они приведены здесь только чтобы было понятно, откуда взялось требование «файл не меньше 128 КБ» и как его выполнить, если преподаватель попросит вариант программы с OPEN_EXISTING.

Проверка результата

  • Задача 1: в выводе должны быть 75000 и 100.5000. Любое другое число — ошибка в значениях или в приведении.
  • Задача 2: значения 42 и 123456 извлечены верно; все sizeof(...*) равны 8, разрядность — 64-бит. Адреса при каждом запуске разные — это нормально (ASLR).
  • Задача 3: в выводе — «Системная гранулярность: 65536 байт (64 КБ)», «Смещение: 131072 байт», прочитанный маркер «[СЕКРЕТНЫЙ ТЕКСТ НА СМЕЩЕНИИ 128 КБ]» и строка об успешном размонтировании. Рядом с exe должен появиться файл mapped_large_test.txt размером 262144 байта.
Если программа запускается двойным кликом по exe, а не из терминала, консольное окно закроется сразу после завершения — вывод не успеть прочитать. Запускайте из cmd или PowerShell либо добавьте паузу в конце (например, system("pause") перед return 0 — только для отладки, в сдаваемый код лучше не включать).
