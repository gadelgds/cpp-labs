Шаг 3

Точка входа программы. Возвращаемое значение int — код завершения для операционной системы. Так требует стандарт C++: выполнение всегда начинается с main, а код возврата сообщает ОС, успешно ли завершилась программа.

Шаг 4

Директива условной компиляции: следующий код попадёт в сборку, только если компилятор определил макрос _WIN32, то есть идёт сборка под Windows. Команда chcp существует только в Windows. На Linux/macOS этот блок просто исчезнет на этапе препроцессора, и программа останется переносимой.

Шаг 5

Выполняет консольную команду Windows chcp 65001 — переводит кодовую страницу консоли на UTF-8. Перенаправление > nul прячет служебный вывод самой команды («Active code page: 65001»). Иначе кириллица в заголовках («НАИЗУСТЬ», «Целочисленное вычитание») в консоли Windows показала бы кракозябры. Строго по стандарту функция system объявлена в <cstdlib> — здесь она доступна через транзитивное включение из <iostream>, но для чистоты кода #include <cstdlib> стоило бы добавить явно.

Шаг 6

Закрывает условный блок, начатый #if defined(_WIN32). Без него препроцессор считал бы весь остаток файла частью условия — ошибка компиляции.

Печатает баннер-заголовок программы и переводит курсор на новую строку (endl заодно сбрасывает буфер вывода). Маркирует начало вывода задачи 1, чтобы при запуске трёх программ подряд было видно, где чья работа.

Комментарий: поясняет, что дальше идёт целочисленная часть задания. Комментарии не влияют на выполнение, но на защите нужно уметь объяснить структуру программы по частям.

Шаг 9
long valLong = 100000L;

Объявляет переменную типа long со значением 100000. Суффикс L явно указывает, что литерал имеет тип long, а не int. В Windows (модель данных LLP64) long — 4 байта, как и int, но по заданию нужен именно тип long: это «старший» целочисленный тип в паре. Без суффикса литерал 100000 всё равно влез бы в int и был бы неявно преобразован, суффикс делает намерение явным.

Шаг 10
int valInt = 25000;

Объявляет переменную типа int со значением 25000. Второй операнд вычитания — «младший» тип, который по заданию надо явно привести к long.

Шаг 11
// Вычитание с явным приведением static_cast<long>()

Комментарий к ключевой строке задания. Фиксирует, что приведение выполняется именно оператором static_cast, а не C-style кастом (long)valInt.

Шаг 12
long resultLong = valLong - static_cast<long>(valInt);

Приводит valInt к типу long во время компиляции, затем вычитает: 100000 − 25000 = 75000. Результат имеет тип long. Это и есть суть задания: приведение делается ЯВНО, до операции, поэтому оба операнда вычитания уже одного типа и компилятор не выполняет никаких скрытых неявных преобразований. Без static_cast компилятор сам неявно расширил бы int до long — результат был бы тем же, но требование задания («явно») не выполнялось бы, а намерение программиста не было бы видно в коде.

Шаг 14

Выводит значение valLong — 100000. Показывает исходные данные до операции: на защите по выводу должно быть видно, из чего получился результат.

Шаг 15

Выводит значение valInt — 25000. То же: фиксация второго операнда в выводе.

Шаг 16
std::cout << "  Результат (long - static_cast<long>(int)): " << resultLong << std::endl;

Выводит результат — 75000, а в самой подписи повторяет формулу вычисления. Подпись содержит формулу, поэтому вывод самодокументирован: проверяющий видит не просто число, а то, как оно получено.

Шаг 18
double valDouble = 125.75;

Объявляет переменную двойной точности (64 бита по IEEE 754) со значением 125.75. «Старший» вещественный тип в паре; литерал с точкой по умолчанию и так имеет тип double, суффикс не нужен.

Шаг 19

Объявляет переменную одинарной точности (32 бита) со значением 25.25. Суффикс f делает литерал типом float. Без суффикса литерал 25.25 имел бы тип double, и присваивание в float было бы СУЖАЮЩИМ преобразованием — компилятор выдал бы предупреждение, а значение могло бы потерять точность. Суффикс f убирает сужение.

Шаг 20
// Вычитание с явным приведением static_cast<double>()

Комментарий к ключевой строке второй части. Аналогично части 1: фиксирует использование именно static_cast.

Шаг 21
double resultDouble = valDouble - static_cast<double>(valFloat);

Расширяет float до double и вычитает: 125.75 − 25.25 = 100.5. Расширяющее приведение (32 → 64 бита) безопасно: значение сохраняется точно, новой точности не появляется — double просто хранит то же самое число, которое было во float. Здесь результат ровно 100.5, потому что 25.25 = 25 + 1/4 точно представимо в двоичной системе. С числами вроде 0.1 так не было бы: float хранит 0.1 лишь приближённо, и расширение до double показало бы «хвост» (0.100000001490116...).

Шаг 22
std::cout << "\n[Вещественное вычитание ...]:" << std::endl;

Печатает подзаголовок второй части с пустой строкой-отступом перед ним. Отделяет вещественный блок от целочисленного в выводе.

Шаг 23
std::cout << std::fixed << std::setprecision(4);

Включает режим фиксированной записи (fixed) и задаёт 4 знака после запятой для всех последующих вещественных выводов. Эта строка сама ничего не печатает. Манипуляторы «липкие»: один раз установленные, они действуют на все дальнейшие выводы в этот поток. Поэтому три следующие строки напечатают числа как 125.7500, 25.2500, 100.5000. Без fixed по умолчанию выводилось бы до 6 значащих цифр (125.75, 25.25, 100.5).

Шаг 24
std::cout << "  Переменная double: ..." << valDouble << std::endl;

Выводит 125.7500 (уже с 4 знаками после запятой из-за fixed). Фиксация первого операнда вещественного вычитания.

Шаг 25
std::cout << "  Переменная float: ..." << valFloat << std::endl;

Выводит 25.2500. Обратите внимание: значение float при выводе неявно расширяется до double, но формат задают манипуляторы, поэтому печатается 4 знака. Фиксация второго операнда; формат вывода единый для всего блока.

Шаг 26
std::cout << "  Результат (double - static_cast<double>(float)): " << resultDouble << std::endl;

Выводит результат — 100.5000. Итог второй части; подпись снова содержит формулу.

Шаг 27
return 0;

Возвращает операционной системе код 0 — «программа завершилась успешно». По соглашению код 0 означает успех, любое ненулевое значение — ошибку. В main return 0 можно опустить (компилятор подставит сам), но явный возврат нагляднее.

}

Закрывающая фигурная скобка тела main. Конец программы; все локальные переменные (valLong, valInt, resultLong и т.д.) уничтожаются при выходе из функции.

Итог: оба приведения в задаче — РАСШИРЯЮЩИЕ (int → long, float → double), поэтому данные не теряются. Обратное направление (long → int, double → float) было бы СУЖАЮЩИМ и могло бы потерять значение — именно поэтому в теории разбирается разница между ними.

Печатает баннер-заголовок программы. Отделяет вывод этой задачи от других при последовательном запуске всех трёх программ.

Шаг 7
// 1. Создание переменных типов int и long со значениями

Комментарий: шаг 1 по условию задачи. Номера шагов (1–5) повторяют пункты условия — на защите удобно сверять код с заданием пункт в пункт.

Шаг 8
int numInt = 42;

Создаёт на стеке переменную int (4 байта) со значением 42. Первый «подопытный» объект: у него берут адрес, кладут в void*, потом возвращают значение обратно. Значение 42 — произвольное, легко узнать в выводе.

Шаг 9
long numLong = 123456L;

Создаёт на стеке переменную long со значением 123456. Суффикс L — литерал типа long. Второй объект другого типа, чтобы показать: один и тот же void* может хранить адрес и int, и long. В Windows long — тоже 4 байта (модель LLP64), но тип у переменной другой, и это важно для приведения обратно.

Шаг 10
// 2. Создание независимых универсальных указателей типа void*

Комментарий: шаг 2 по условию. Структурирует код по пунктам задания.

Шаг 11
void* ptrVoid1 = &numInt;

Создаёт универсальный указатель и записывает в него адрес numInt. Оператор & берёт адрес переменной. Преобразование «любой указатель → void*» в C++ выполняется НЕЯВНО и безопасно: адрес просто копируется, информация о типе «забывается». Поэтому здесь нет static_cast — он не нужен. После этого ptrVoid1 знает, ГДЕ лежит значение, но не знает, ЧТО там лежит и сколько байт читать.

Шаг 12
void* ptrVoid2 = &numLong;

То же для адреса numLong. Два независимых указателя — по одному на каждую переменную, как требует условие («независимые указатели»).

Шаг 13
// 3. Обратное преобразование указателей void* в исходные типы int* и long*

Комментарий: шаг 3 по условию. Ключевой шаг задачи: без обратного приведения значения из void* не извлечь.

Шаг 14
int* ptrInt = static_cast<int*>(ptrVoid1);

Явно приводит void* обратно к int*. Адрес не меняется — меняется только «взгляд» компилятора на память по этому адресу. Обратное направление «void* → типизированный указатель» НЕЯВНО запрещено: компилятор не позволит написать int* p = ptrVoid1; — это ошибка. Нужен именно static_cast: программист берёт на себя ответственность, что по этому адресу действительно лежит int. Если бы там лежал long или double, компилятор не остановил бы, а значение прочиталось бы неверно — это главный риск void*.

Шаг 15
long* ptrLong = static_cast<long*>(ptrVoid2);

То же: void* → long*. Симметричная операция для второй переменной. Тип приведения должен совпадать с исходным типом переменной, иначе разыменование даст мусор.

Шаг 16
// 4. Извлечение значений из памяти (разыменование) и вывод на экран

Комментарий: шаг 4 по условию. Структурирует код по пунктам задания.

Шаг 17

Печатает подзаголовок блока результатов с пустой строкой-отступом (\n). Отделяет блок значений от баннера программы.

Шаг 18

Разыменовывает ptrInt (*ptrInt — прочитать 4 байта по адресу и истолковать как int) и печатает значение 42 вместе с самим адресом. Демонстрирует два разных смысла указателя в одной строке: *ptrInt — значение ПО адресу, ptrInt без звёздочки — сам адрес. Адрес при каждом запуске разный (ASLR), поэтому в выводе он будет отличаться от примера — это нормально.

Шаг 19

// 5. Определение размеров указателей и типов в архитектуре сборки (x64)

Печатает sizeof(long long) — 8 байт (64 бита). В Windows именно long long — 64-битный целый тип, а не long. Строка добавлена для контраста с предыдущей.

Печатает sizeof(void*) — 8 байт (64 бита) в x64. Главный вывод задачи: размер указателя зависит только от архитектуры, а не от типа, на который он указывает. void* занимает столько же, сколько любой другой указатель.

Шаг 27

Печатает sizeof(int*) — 8 байт (64 бита). Подтверждение: указатель на 4-байтный int сам занимает 8 байт — размер указателя НЕ равен размеру данных, на которые он указывает.

Шаг 28
std::cout << "  sizeof(long*): ..." << sizeof(long*) << " байт (" << sizeof(long*) * 8 << " бит)" << std::endl;

Печатает sizeof(long*) — 8 байт (64 бита). Третье подтверждение того же правила на другом типе указателя.

return 0;

}

Комментарий: дальше идёт демонстрационный расчёт младшей/старшей частей смещения. Подчёркивает, что расчёт делается вручную, а не «магическими числами», — так видно механику Win32 API.

Шаг 39

Выделяет младшие 32 бита смещения: битовая маска 0xFFFFFFFF оставляет только нижние 32 бита 64-битного числа. Для 131072 это просто 131072. MapViewOfFile принимает смещение не одним 64-битным числом, а двумя 32-битными параметрами (dwFileOffsetHigh, dwFileOffsetLow) — наследие 32-битного API. Поэтому 64-битное смещение приходится «разрезать» пополам вручную.

Шаг 40

Выделяет старшие 32 бита смещения: сдвиг вправо на 32 бита, затем маска. Для 131072 старшая часть равна 0. Приведение к ULONGLONG перед сдвигом важно: сдвиг 32-битного значения на 32 бита дал бы неопределённый результат. Пример для больших файлов: смещение 5 ГБ (0x1_40000000) дало бы offsetHigh = 1, offsetLow = 0x40000000 — вместе они снова собираются как high × 2³² + low.

Тема 1. Приведение типов: неявное, явное, static_cast
к задаче 1 • task1_explicit_casting.cpp

Что это

Приведение типов (type cast, преобразование типа) — это смена типа значения: один и тот же набор бит начинает интерпретироваться по правилам другого типа. Например, целое число 25000 типа int после приведения к long остаётся числом 25000, но занимает «старший» целочисленный тип и может участвовать в операциях с long без дополнительных преобразований.

Зачем это нужно

В C++ у каждой переменной строгий тип, а у каждой операции — требования к типам операндов. Приведение типов нужно, чтобы: (1) выполнить операцию между значениями разных типов по заданным правилам; (2) показать компилятору и читающему код, что преобразование сделано намеренно, а не случайно; (3) подавить предупреждения компилятора о потере данных там, где программист проверил, что потери нет.

Неявное и явное приведение

ВидКак выглядитКто решаетПример
Неявное (implicit)Никак не пишется — компилятор вставляет самКомпилятор, по правилам языкаlong x = 25000; — int неявно расширяется до long
Явное (explicit)Оператор приведения в кодеПрограммистlong x = static_cast<long>(25000);

Неявное приведение происходит при присваивании, передаче аргумента в функцию, возврате из функции и в смешанных арифметических выражениях. Оно всегда «безопасно» с точки зрения компилятора: язык разрешает неявно только те преобразования, которые не могут потерять значение (расширяющие). Сужающие преобразования неявно тоже разрешены, но компилятор обычно выдаёт предупреждение — это сигнал «проверь, ты точно этого хотел?».

static_cast — главный оператор явного приведения

static_cast<НовыйТип>(выражение) — приведение, проверяемое во время компиляции. «Static» означает, что проверка и само преобразование происходят на этапе сборки, а не во время выполнения: никакого кода проверки в программу не добавляется, поэтому static_cast бесплатен по времени работы. Что он умеет:

  • Числовые преобразования: int ↔ long, float ↔ double, целое ↔ вещественное, знаковое ↔ беззнаковое.
  • Приведения указателей: void* → типизированный указатель и обратно (тема 2), приведения в иерархии классов вверх/вниз (в этой лабе не используется).
  • Явный вызов конструктора преобразования: static_cast<std::string>(…) и подобные.

Чего static_cast НЕ делает: он не снимает const (для этого есть const_cast), не приводит несвязанные типы (например, int* → double* напрямую — ошибка компиляции) и не проверяет во время выполнения, что по указателю действительно лежит объект нужного типа (для этого есть dynamic_cast, только для классов с виртуальными функциями). Старый C-style каст (long)valInt делает всё это «молча» и без проверок, поэтому в современном C++ его избегают: static_cast видно в коде, его легко найти поиском, и он запрещает опасные преобразования.

Оба приведения в задаче 1 — расширяющие, поэтому результат точный. Обратные примеры: static_cast<int>(100000L) в 32-битном int ещё влезает, а static_cast<int>(5000000000L) уже даст неверное число (переполнение); static_cast<int>(3.99) даст 3 — дробная часть просто отбрасывается, без округления.

Вещественные числа: IEEE 754, float и double

Числа с плавающей точкой хранятся по стандарту IEEE 754: знак (1 бит), порядок-экспонента и мантисса (значащие цифры в двоичной системе).

Главное следствие: большинство десятичных дробей (0.1, 0.2, 25.25 — нет, 25.25 исключение) нельзя точно записать в двоичной системе, поэтому float и double хранят лишь приближение. Примеры:

Типичные ошибки

  • Путать static_cast с C-style кастом (тип)значение: результат тот же, но C-style каст скрывает опасные преобразования и его нельзя найти поиском по коду.
  • Считать, что static_cast<double>(float) повышает точность: нет, оно лишь сохраняет уже имеющееся (приближённое) значение float в более широком формате.
  • Сравнивать вещественные числа через == после вычислений: из-за накопления ошибки округления 0.1 + 0.2 == 0.3 даёт false; сравнивают с допуском (эпсилон).
  • Забывать суффикс f у float-литералов и суффикс L у long-литералов — компилятор выдаёт предупреждения о сужении.
  • Сужающее приведение больших значений: static_cast<int>(5000000000L) — переполнение, значение искажается молча, без ошибки времени выполнения.
Тема 2. Указатели void* и разрядность x64
к задаче 2 • task2_void_pointers_x64.cpp

Что это

Указатель — переменная, хранящая адрес ячейки памяти. int* p = &x; означает: «p хранит адрес переменной x, а по этому адресу лежит значение типа int». Тип указателя говорит компилятору, сколько байт читать при разыменовании (*p) и на сколько байт сдвигаться при p + 1.

void* — универсальный (нетипизированный) указатель. Он хранит адрес, но не знает, данные какого типа лежат по этому адресу. «Void» буквально означает «пустота»: у типа void нет размера, поэтому компилятор не знает, сколько байт читать и как их интерпретировать.

Зачем нужен void*

  • Обобщённые функции: memcpy, malloc, qsort работают с «сырой» памятью любого типа — они принимают void*.
  • Системные API: Win32-функции вроде MapViewOfFile (тема 3) возвращают void*, потому что отображаемая память может содержать что угодно — текст, структуры, картинки.
  • Хранение «чужого» адреса: когда тип данных заранее неизвестен и выясняется позже (например, по коду типа, переданному рядом).

Правила работы с void*

Арифметика ptrVoid + 1Нет (в стандартном C++)Неизвестен шаг: на сколько байт сдвигаться — на 1, 4 или 8?

Главный риск void*: компилятор не проверяет, что тип при обратном приведении совпадает с реальным типом данных. Если в void* лежит адрес double, а привести его к int* и разыменовать — получится мусор: первые 4 байта double будут прочитаны как целое число. Ошибки компиляции не будет, программа просто выдаст неверный результат. Поэтому рядом с void* всегда должен быть отдельный признак типа (перечисление, флаг, знание из контекста).

Разрядность x64 и размеры типов

«64-битная архитектура» означает, что адресное пространство — 64 бита: указатель может адресовать 2⁶⁴ байт, а сам занимает 8 байт. Размер указателя зависит ТОЛЬКО от архитектуры, а не от типа данных:

Модель данных Windows называется LLP64: long long и указатели — 64-битные, а long остаётся 32-битным (для совместимости со старым кодом). Модель Linux — LP64: long тоже 64-битный. Поэтому программа задачи 2 на Linux напечатала бы sizeof(long) = 8 — это не ошибка, а другая модель данных. Приём sizeof(void*) * 8 — способ «спросить» разрядность у компилятора: в x64 получится 64, в x86 — 32.

Адреса в выводе: почему они каждый раз разные

Адреса переменных на стеке (0x000000A1B2C3D4E5 в примере) при каждом запуске разные из-за ASLR (рандомизации размещения адресного пространства) — защитного механизма Windows. Сравнивать адреса между запусками бессмысленно; важно лишь, что адрес из ptrInt совпадает с адресом переменной numInt, а значения извлекаются верно.

Типичные ошибки

  • Попытка разыменовать void* напрямую (*ptrVoid) — ошибка компиляции; сначала static_cast.
  • Неявное приведение void* → int* (int* p = ptrVoid;) — ошибка компиляции в C++ (в C это разрешено, в C++ — нет).
  • Обратное приведение к НЕВЕРНОМУ типу: компилятор промолчит, а значение будет мусором.
  • Разыменование указателя после уничтожения переменной (висячий указатель): void* не продлевает жизнь объекту.
  • Путать размер указателя и размер данных: sizeof(int*) = 8, а sizeof(int) = 4 — это разные вещи.
  • Сборка в 32-битном режиме при задаче про x64: sizeof(void*) станет 4 — проверяйте целевую платформу (x64) в настройках проекта.
Тема 3. Проецирование файлов в память: CreateFileMapping и MapViewOfFile
к задаче 3 • task3_memory_mapped_offset.cpp

Что это

Проецирование файла в память (memory-mapped file) — механизм, при котором содержимое файла отображается в виртуальное адресное пространство процесса: байты файла становятся доступны как обычная память, через указатель. Чтение файла превращается в чтение из памяти (pView[i]), а запись в память — в запись в файл (если отображение открыто на запись). Диспетчер виртуальной памяти Windows сам подгружает нужные страницы с диска и сбрасывает изменённые обратно.

Зачем это нужно

  • Большие файлы: файл в гигабайты не нужно целиком грузить в RAM — отображается только нужное «окно», а система подкачивает страницы по мере обращения.
  • Скорость: нет буферов и лишних копирований, как при ReadFile; данные читаются напрямую из страничного кэша системы.
  • Общий доступ к памяти: одна и та же секция может быть спроецирована в несколько процессов — это способ межпроцессного взаимодействия (shared memory).
  • Произвольный доступ: к любому смещению файла можно обратиться напрямую, без seek и последовательного чтения.

Цепочка вызовов: от файла к указателю

Проецирование всегда делается в три шага, и у каждого шага — свой дескриптор, который потом надо закрыть:

ШагФункцияЧто создаётЧто вернуть / закрыть
1CreateFileWОткрывает файл, возвращает HANDLE hFileОшибка — INVALID_HANDLE_VALUE; закрыть — CloseHandle(hFile)
2CreateFileMappingWСоздаёт объект ядра «секция» (File Mapping Object), возвращает HANDLE hMappingОшибка — NULL; закрыть — CloseHandle(hMapping)
3MapViewOfFileОтображает окно секции в адресное пространство, возвращает void* pViewОшибка — NULL; снять — UnmapViewOfFile(pView)

Порядок освобождения — обратный порядку создания: сначала UnmapViewOfFile(pView), потом CloseHandle(hMapping), потом CloseHandle(hFile). Закрытие дескриптора файла раньше времени отображение не разрушает (секция держит файл), но правильный порядок — часть дисциплины работы с ресурсами: каждый открытый дескриптор должен быть закрыт ровно один раз.

CreateFileMapping: параметры

CreateFileMappingW(hFile, NULL, PAGE_READONLY, 0, 0, NULL) — аргументы по порядку: дескриптор файла; атрибуты безопасности (NULL — по умолчанию); защита страниц (PAGE_READONLY — только чтение, PAGE_READWRITE — чтение и запись, PAGE_WRITECOPY — копирование при записи); старший и младший DWORD размера секции — 0, 0 означает «размер всего файла»; имя секции (NULL — безымянная, только для этого процесса). Защита секции и права доступа к файлу должны согласовываться: PAGE_READONLY требует GENERIC_READ у файла, PAGE_READWRITE — GENERIC_READ | GENERIC_WRITE.

MapViewOfFile: параметры

MapViewOfFile(hMapping, FILE_MAP_READ, offsetHigh, offsetLow, viewSize) — аргументы: дескриптор секции; желаемый доступ (FILE_MAP_READ — чтение, FILE_MAP_WRITE — запись, FILE_MAP_ALL_ACCESS — всё); старшая и младшая части смещения начала окна; размер окна в байтах (0 — до конца секции). Возвращает void* — указатель на начало окна, который приводят к нужному типу (const char* для текста).

Allocation Granularity — почему смещение не может быть случайным

Диспетчер виртуальной памяти Windows работает не с отдельными байтами, а с блоками. Есть два разных размера, и их нельзя путать:

ВеличинаЗначение (x86/x64)На что влияет
Размер страницы (dwPageSize)4 КБ (4096 байт)Минимальная единица подкачки с диска и защиты памяти
Гранулярность распределения (dwAllocationGranularity)64 КБ (65 536 байт)Выравнивание начальных адресов резервируемых областей виртуальной памяти — и смещений в MapViewOfFile

Смещение окна в файле должно быть кратно именно гранулярности — 64 КБ. Причина аппаратно-системная: виртуальные адреса областей, которые резервирует менеджер памяти, выравниваются по 64 КБ, и начало отображаемого окна привязано к этим границам. Смещение 131072 = 2 × 65536 — допустимо. Смещение 100000, 131073 или 65537 — нет: MapViewOfFile немедленно вернёт NULL, а GetLastError() даст код 1132 — ERROR_MAPPED_ALIGNMENT («базовый адрес или смещение файла не имеют требуемого выравнивания»).

При этом РАЗМЕР окна может быть любым (в задаче — 1024 байта): выравнивание требуется только для начала окна, а не для его конца. И читать внутри окна можно с любой точностью: если нужно прочитать данные с «некратного» смещения 100000, проецируют окно с кратного смещения 65536, а потом просто берут pView[100000 − 65536] — то есть добавляют разницу внутри окна.

Как узнать гранулярность правильно: не хардкодить 65536, а спросить у системы через GetSystemInfo(&sysInfo) и поле dwAllocationGranularity. На всех современных Windows x86/x64 это 64 КБ, но код, который спрашивает, а не угадывает, — переносимый и правильный.

Приведение к ULONGLONG перед сдвигом обязательно: сдвиг 32-битного значения на 32 бита — неопределённое поведение. Для смещений меньше 4 ГБ старшая часть всегда 0, но код пишется общим — для файлов любого размера.

Чтение порциями: идея задачи

Файл в задаче — 256 КБ, а окно — всего 1 КБ. Это модель работы с огромным файлом: вместо загрузки всего файла в память программа отображает окно на нужном смещении, читает его, снимает отображение и отображает следующее окно (например, 131072 + 1024, если 1024 кратно… — нет: следующее окно тоже должно начинаться с кратного 64 КБ смещения, поэтому «порции» при проецировании обычно делают размером, кратным гранулярности, а внутри окна двигаются указателем). В задаче демонстрируется один шаг этого цикла: окно на 128 КБ, чтение маркера, снятие отображения.

Типичные ошибки

  • Смещение не кратно 64 КБ → NULL и ошибка 1132 (ERROR_MAPPED_ALIGNMENT).
  • Смещение + размер окна выходят за конец файла → MapViewOfFile возвращает NULL (файл должен быть не меньше, чем offset + viewSize).
  • Забыть UnmapViewOfFile или CloseHandle — утечка виртуального адресного диапазона и дескрипторов.
  • Чтение/запись за пределами окна (дальше viewSize байт от pView) — нарушение доступа, падение программы.
  • Запись через отображение, открытое как PAGE_READONLY / FILE_MAP_READ, — нарушение доступа; для записи нужны PAGE_READWRITE и FILE_MAP_WRITE.
  • Путать коды ошибок: у CreateFileW признак неудачи — INVALID_HANDLE_VALUE, а у CreateFileMappingW и MapViewOfFile — NULL.
  • Выводить const char* через cout без приведения к void* — напечатается строка, а не адрес.
  • Проверять GetLastError() не сразу после неудачного вызова — следующий вызов API может перезаписать код ошибки.

Проверка результата

Что это

Приведение типов — это смена типа значения. Один и тот же набор бит получает правила другого типа. Пример: число 25000 имеет тип int. После приведения к long число остаётся 25000. Но теперь оно принадлежит старшему целочисленному типу. Теперь оно участвует в операциях с long без лишних преобразований.

Зачем это нужно

У каждой переменной строгий тип. У каждой операции свои требования к типам операндов. Приведение типов нужно для трёх целей. Цель 1: выполнить операцию между значениями разных типов по заданным правилам. Цель 2: показать компилятору и читателю, что преобразование сделано намеренно. Цель 3: убрать предупреждения компилятора там, где программист проверил отсутствие потерь.

Неявное и явное приведение

ВидКак выглядитКто решаетПример
Неявное (implicit)Компилятор вставляет сам. В коде ничего не пишется.Компилятор решает по правилам языка.long x = 25000; — int неявно расширяется до long.
Явное (explicit)Программист пишет оператор приведения в коде.Программист решает сам.long x = static_cast<long>(25000);

Неявное приведение происходит в четырёх местах. Место 1: присваивание. Место 2: передача аргумента в функцию. Место 3: возврат из функции. Место 4: смешанные арифметические выражения. Язык разрешает неявно только безопасные преобразования. Безопасные преобразования не теряют значение. Сужающие преобразования неявно тоже разрешены. Но компилятор выдаёт предупреждение. Предупреждение спрашивает: проверь, ты точно этого хотел?

static_cast — главный оператор явного приведения

static_cast<НовыйТип>(выражение) — приведение с проверкой во время компиляции. Слово static означает: проверка происходит на этапе сборки. Код проверки в программу не добавляется. Поэтому static_cast бесплатен по времени работы. Что он умеет:

  • Числовые преобразования: int ↔ long, float ↔ double, целое ↔ вещественное, знаковое ↔ беззнаковое.
  • Приведения указателей: void* → типизированный указатель и обратно (тема 2). Приведения в иерархии классов вверх и вниз. В этой лабе они не используются.
  • Явный вызов конструктора преобразования: static_cast<std::string>(…) и подобные.

Чего static_cast не делает. Он не снимает const. Для этого есть const_cast. Он не приводит несвязанные типы. Пример: int* → double* напрямую вызывает ошибку компиляции. Он не проверяет во время выполнения, что по указателю лежит объект нужного типа. Для этого есть dynamic_cast. Он работает только для классов с виртуальными функциями. Старый C-style каст (long)valInt делает всё это молча и без проверок. Поэтому в современном C++ его избегают. static_cast виден в коде. Его легко найти поиском. Он запрещает опасные преобразования.

Расширяющие и сужающие преобразования

Расширяющее (widening)int → long, float → double, int → doubleНет: значение сохраняется точно.
Сужающее (narrowing)long → int, double → float, double → intВозможна: старшие биты отбрасываются. Дробная часть отбрасывается. Точность теряется.

Оба приведения в задаче 1 — расширяющие. Поэтому результат точный. Обратные примеры: static_cast<int>(100000L) ещё влезает в 32-битный int. Но static_cast<int>(5000000000L) даёт неверное число: происходит переполнение. static_cast<int>(3.99) даёт 3: дробная часть отбрасывается без округления.

Вещественные числа: IEEE 754, float и double

Числа с плавающей точкой хранятся по стандарту IEEE 754. Число состоит из трёх частей. Часть 1: знак (1 бит). Часть 2: порядок-экспонента. Часть 3: мантисса — значащие цифры в двоичной системе.

ТипРазмерЗнак / экспонента / мантиссаТочных десятичных цифрПримерный диапазон

double8 байт (64 бита)1 / 11 / 52 бита≈ 15–16±1,8 × 10³⁰⁸

Главное следствие: большинство десятичных дробей нельзя точно записать в двоичной системе. Примеры: 0.1 и 0.2. Число 25.25 — исключение: оно записывается точно. Поэтому float и double хранят лишь приближение. Примеры кода:

Пример: потеря точности
float f = 0.1f;              // хранится как 0.100000001490116...
double d = static_cast<double>(f); // станет 0.10000000149011612 —
// расширение НЕ добавляет точности, оно показывает
// то значение, которое уже было во float
double x = 0.1 + 0.2;        // 0.30000000000000004, а не 0.3

В задаче 1 этого эффекта нет. Число 25.25 равно 25 + 1/4. Дробь 1/4 — точная степень двойки. Поэтому float хранит 25.25 точно. Результат 100.5 точен. Суффикс f у литерала 25.25f обязателен. Без него литерал имеет тип double. Присваивание в float стало бы сужающим преобразованием. Компилятор выдал бы предупреждение.

Типичные ошибки

  • Путать static_cast с C-style кастом (тип)значение: результат тот же. Но C-style каст скрывает опасные преобразования. Его нельзя найти поиском по коду.
  • Считать, что static_cast<double>(float) повышает точность: нет. Он лишь сохраняет уже имеющееся значение float в более широком формате.
  • Сравнивать вещественные числа через == после вычислений: ошибка округления накапливается. Выражение 0.1 + 0.2 == 0.3 даёт false. Сравнивай с допуском (эпсилон).
  • Забывать суффикс f у float-литералов и суффикс L у long-литералов: компилятор выдаёт предупреждения о сужении.
  • Сужающее приведение больших значений: static_cast<int>(5000000000L) вызывает переполнение. Значение искажается молча. Ошибки времени выполнения нет.
Тема 2. Указатели void* и разрядность x64
к задаче 2 • task2_void_pointers_x64.cpp

Что это

Указатель — переменная. Она хранит адрес ячейки памяти. Пример: int* p = &x;. Переменная p хранит адрес переменной x. По этому адресу лежит значение типа int. Тип указателя говорит компилятору две вещи. Вещь 1: сколько байт читать при разыменовании (*p). Вещь 2: на сколько байт сдвигаться при p + 1.

void* — универсальный указатель. Он не имеет типа. Он хранит адрес. Он не знает, данные какого типа лежат по этому адресу. Слово void буквально означает «пустота». У типа void нет размера. Поэтому компилятор не знает, сколько байт читать и как их толковать.

Зачем нужен void*

  • Обобщённые функции: memcpy, malloc, qsort работают с сырой памятью любого типа. Они принимают void*.
  • Системные API: Win32-функции принимают и возвращают void*. Пример: MapViewOfFile (тема 3). Отображаемая память может содержать что угодно: текст, структуры, картинки.
  • Хранение чужого адреса: тип данных заранее неизвестен. Тип выясняется позже. Например, по коду типа, переданному рядом.

Правила работы с void*

ОперацияРазрешена?Пояснение

Главный риск void*: компилятор не проверяет тип при обратном приведении. Пример: в void* лежит адрес double. Программа приводит его к int* и разыменовывает. Результат — мусор: первые 4 байта double читаются как целое число. Ошибки компиляции нет. Программа просто выдаёт неверный результат. Поэтому рядом с void* всегда держи отдельный признак типа. Признак — перечисление, флаг или знание из контекста.

Разрядность x64 и размеры типов

64-битная архитектура означает: адресное пространство — 64 бита. Указатель адресует 2⁶⁴ байт. Сам указатель занимает 8 байт. Размер указателя зависит только от архитектуры. Тип данных не влияет на него.

Модель данных Windows называется LLP64. В ней long long и указатели — 64-битные. А long остаётся 32-битным. Причина: совместимость со старым кодом. Модель Linux называется LP64. В ней long тоже 64-битный. Поэтому программа задачи 2 на Linux печатает sizeof(long) = 8. Это не ошибка. Это другая модель данных. Приём sizeof(void*) * 8 спрашивает разрядность у компилятора. В x64 получается 64. В x86 получается 32.

Адреса в выводе: почему они каждый раз разные

Адреса переменных на стеке при каждом запуске разные. Пример: 0x000000A1B2C3D4E5. Причина: ASLR. ASLR — рандомизация размещения адресного пространства. Это защитный механизм Windows. Сравнивать адреса между запусками бессмысленно. Важно лишь одно: адрес из ptrInt совпадает с адресом numInt. Значения извлекаются верно.

Типичные ошибки

  • Разыменование void* напрямую (*ptrVoid): ошибка компиляции. Сначала сделай static_cast.
  • Неявное приведение void* → int* (int* p = ptrVoid;): ошибка компиляции в C++. В C это разрешено. В C++ — нет.
  • Обратное приведение к неверному типу: компилятор промолчит. Значение будет мусором.
  • Разыменование указателя после уничтожения переменной: указатель становится висячим. void* не продлевает жизнь объекту.
  • Путать размер указателя и размер данных: sizeof(int*) = 8. А sizeof(int) = 4. Это разные вещи.
  • Сборка в 32-битном режиме при задаче про x64: sizeof(void*) станет 4. Проверяй целевую платформу x64 в настройках проекта.
Тема 3. Проецирование файлов в память: CreateFileMapping и MapViewOfFile
к задаче 3 • task3_memory_mapped_offset.cpp

Что это

Проецирование файла в память — механизм Windows. Содержимое файла отображается в виртуальное адресное пространство процесса. Байты файла становятся обычной памятью. Программа читает их через указатель. Чтение файла превращается в чтение из памяти (pView[i]). Запись в память превращается в запись в файл. Это работает, если отображение открыто на запись. Диспетчер виртуальной памяти Windows сам подгружает страницы с диска. Он сам сбрасывает изменённые страницы обратно.

Зачем это нужно

  • Большие файлы: файл в гигабайты не нужно целиком грузить в RAM. Программа отображает только нужное окно. Система подкачивает страницы по мере обращения.
  • Скорость: нет буферов и лишних копирований, как при ReadFile. Данные читаются напрямую из страничного кэша системы.
  • Общий доступ к памяти: одна секция проецируется в несколько процессов. Это способ межпроцессного взаимодействия (shared memory).
  • Произвольный доступ: программа обращается к любому смещению файла напрямую. Функции seek и последовательное чтение не нужны.

Цепочка вызовов: от файла к указателю

Проецирование всегда делается в три шага. У каждого шага свой дескриптор. Каждый дескриптор потом надо закрыть.

ШагФункцияЧто создаётЧто вернуть / закрыть
1CreateFileWОткрывает файл. Возвращает HANDLE hFile.Ошибка: INVALID_HANDLE_VALUE. Закрытие: CloseHandle(hFile).
2CreateFileMappingWСоздаёт объект ядра «секция». Возвращает HANDLE hMapping.Ошибка: NULL. Закрытие: CloseHandle(hMapping).
3MapViewOfFileОтображает окно секции в память. Возвращает void* pView.Ошибка: NULL. Снятие: UnmapViewOfFile(pView).

Порядок освобождения обратен порядку создания. Шаг 1: UnmapViewOfFile(pView). Шаг 2: CloseHandle(hMapping). Шаг 3: CloseHandle(hFile). Закрытие дескриптора файла раньше времени отображение не разрушает: секция держит файл. Но правильный порядок — часть дисциплины. Каждый открытый дескриптор закрывается ровно один раз.

CreateFileMapping: параметры

CreateFileMappingW(hFile, NULL, PAGE_READONLY, 0, 0, NULL). Аргументы по порядку. Аргумент 1: дескриптор файла. Аргумент 2: атрибуты безопасности. NULL означает значения по умолчанию. Аргумент 3: защита страниц. PAGE_READONLY означает только чтение. PAGE_READWRITE означает чтение и запись. PAGE_WRITECOPY означает копирование при записи. Аргументы 4 и 5: старший и младший DWORD размера секции. Значения 0, 0 означают размер всего файла. Аргумент 6: имя секции. NULL означает безымянную секцию только для этого процесса. Защита секции и права доступа к файлу обязаны согласовываться. PAGE_READONLY требует GENERIC_READ у файла. PAGE_READWRITE требует GENERIC_READ | GENERIC_WRITE.

MapViewOfFile: параметры

MapViewOfFile(hMapping, FILE_MAP_READ, offsetHigh, offsetLow, viewSize). Аргументы по порядку. Аргумент 1: дескриптор секции. Аргумент 2: желаемый доступ. FILE_MAP_READ означает чтение. FILE_MAP_WRITE означает запись. FILE_MAP_ALL_ACCESS означает полный доступ. Аргументы 3 и 4: старшая и младшая части смещения начала окна. Аргумент 5: размер окна в байтах. Значение 0 означает: до конца секции. Функция возвращает void* — указатель на начало окна. Программист приводит его к нужному типу. Для текста это const char*.

Allocation Granularity — почему смещение не может быть случайным

Диспетчер виртуальной памяти Windows работает не с отдельными байтами, а с блоками. Есть два разных размера. Их нельзя путать.

ВеличинаЗначение (x86/x64)На что влияет
Размер страницы (dwPageSize)4 КБ (4096 байт)Минимальная единица подкачки с диска и защиты памяти.
Гранулярность распределения (dwAllocationGranularity)64 КБ (65 536 байт)Выравнивание начальных адресов областей памяти — и смещений в MapViewOfFile.

Смещение окна обязано быть кратно именно гранулярности — 64 КБ. Причина: виртуальные адреса областей выравниваются по 64 КБ. Начало окна привязано к этим границам. Смещение 131072 = 2 × 65536: оно допустимо. Смещение 100000, 131073 или 65537: недопустимо. MapViewOfFile немедленно возвращает NULL. GetLastError даёт код 1132 — ERROR_MAPPED_ALIGNMENT. Код означает: базовый адрес или смещение файла не имеют требуемого выравнивания.

При этом размер окна может быть любым. В задаче он равен 1024 байтам. Выравнивание требуется только для начала окна, а не для его конца. Читать внутри окна можно с любой точностью. Пример: нужны данные со смещения 100000. Программа проецирует окно со смещения 65536. Потом программа берёт pView[100000 − 65536]. Разница добавляется внутри окна.

Как узнать гранулярность правильно: не хардкодь 65536. Спроси у системы через GetSystemInfo(&sysInfo). Возьми поле dwAllocationGranularity. На всех современных Windows x86/x64 это 64 КБ. Но код, который спрашивает, а не угадывает, — переносимый и правильный.

MapViewOfFile — функция из 32-битной эпохи. Она принимает 64-битное смещение двумя 32-битными параметрами. Поэтому смещение разрезают пополам.

Чтение порциями: идея задачи

Файл в задаче — 256 КБ. Окно — всего 1 КБ. Это модель работы с огромным файлом. Программа не грузит весь файл в память. Программа отображает окно на нужном смещении. Программа читает окно. Программа снимает отображение. Потом программа отображает следующее окно. Следующее окно тоже начинается с кратного 64 КБ смещения. Поэтому порции при проецировании обычно делают размером, кратным гранулярности. Внутри окна программа двигается указателем. Задача показывает один шаг этого цикла: окно на 128 КБ, чтение маркера, снятие отображения.

Типичные ошибки

  • Смещение не кратно 64 КБ: MapViewOfFile возвращает NULL. Ошибка 1132 (ERROR_MAPPED_ALIGNMENT).
  • Смещение и окно выходят за конец файла: MapViewOfFile возвращает NULL. Файл обязан быть не меньше, чем offset + viewSize.
  • Забыть UnmapViewOfFile или CloseHandle: утечка диапазона адресов и дескрипторов.
  • Чтение или запись за пределами окна: нарушение доступа. Программа падает.
  • Запись через отображение PAGE_READONLY / FILE_MAP_READ: нарушение доступа. Для записи нужны PAGE_READWRITE и FILE_MAP_WRITE.
  • Путать коды ошибок: у CreateFileW признак неудачи — INVALID_HANDLE_VALUE. У CreateFileMappingW и MapViewOfFile — NULL.
  • Вывод const char* через cout без приведения к void*: печатается строка, а не адрес.
  • Проверка GetLastError() не сразу после неудачного вызова: следующий вызов API перезаписывает код ошибки.

STE-версия: словарь терминов

Как написан этот словарь (стиль STE)

Эта версия написана по правилам ASD-STE100, упрощённого технического английского, перенесённым на русский. Правила применены примерно на 60%: они действуют на сами определения. Вступление, примечания и подписи написаны обычным стилем.

Правила, которые действуют в определениях:

  • Одна мысль — одно предложение.
  • Инструкция — не больше 20 слов. Описание — не больше 25 слов.
  • Действительный залог: предложение называет, кто что делает («Windows показывает», «программа меняет»).
  • Одно понятие — всегда одно и то же слово: файл, программа, Windows, значение, тип, смещение, указатель, память, адрес, байт, число, ошибка, команда. Без синонимов. Падежные формы одного слова допускаются.
  • Сначала ответ, потом подробности: первое предложение — само определение, дальше только детали или пример.
  • Один абзац — одна тема, не больше шести предложений.

Что не применено полностью: русский язык требует падежей, поэтому одно и то же слово встречается в разных падежных формах (файл, файла, файлу) — это считается тем же словом. Английские имена из кода (static_cast, MapViewOfFile, void*) оставлены как есть: это имена, а не слова для замены.
