Тема 1. Приведение типов: неявное, явное, static_cast
к задаче 1 • task1_explicit_casting.cpp

Что это

Приведение типов — это смена типа значения. Один и тот же набор бит получает правила другого типа. Пример: число 25000 имеет тип int. После приведения к long число остаётся 25000. Но теперь оно принадлежит старшему целочисленному типу. Теперь оно участвует в операциях с long без лишних преобразований.

Зачем это нужно

У каждой переменной строгий тип. У каждой операции свои требования к типам операндов. Приведение типов нужно для трёх целей. Цель 1: выполнить операцию между значениями разных типов по заданным правилам. Цель 2: показать компилятору и читателю, что преобразование сделано намеренно. Цель 3: убрать предупреждения компилятора там, где программист проверил отсутствие потерь.

Неявное и явное приведение

ВидКак выглядитКто решаетПример
Неявное (implicit)Компилятор вставляет сам. В коде ничего не пишется.Компилятор решает по правилам языка.long x = 25000; — int неявно расширяется до long.
Явное (explicit)Программист пишет оператор приведения в коде.Программист решает сам.long x = static_cast<long>(25000);

Неявное приведение происходит в четырёх местах. Место 1: присваивание. Место 2: передача аргумента в функцию. Место 3: возврат из функции. Место 4: смешанные арифметические выражения. Язык разрешает неявно только безопасные преобразования. Безопасные преобразования не теряют значение. Сужающие преобразования неявно тоже разрешены. Но компилятор выдаёт предупреждение. Предупреждение спрашивает: проверь, ты точно этого хотел?

static_cast — главный оператор явного приведения

static_cast<НовыйТип>(выражение) — приведение с проверкой во время компиляции. Слово static означает: проверка происходит на этапе сборки. Код проверки в программу не добавляется. Поэтому static_cast бесплатен по времени работы. Что он умеет:

  • Числовые преобразования: int ↔ long, float ↔ double, целое ↔ вещественное, знаковое ↔ беззнаковое.
  • Приведения указателей: void* → типизированный указатель и обратно (тема 2). Приведения в иерархии классов вверх и вниз. В этой лабе они не используются.
  • Явный вызов конструктора преобразования: static_cast<std::string>(…) и подобные.

Чего static_cast не делает. Он не снимает const. Для этого есть const_cast. Он не приводит несвязанные типы. Пример: int* → double* напрямую вызывает ошибку компиляции. Он не проверяет во время выполнения, что по указателю лежит объект нужного типа. Для этого есть dynamic_cast. Он работает только для классов с виртуальными функциями. Старый C-style каст (long)valInt делает всё это молча и без проверок. Поэтому в современном C++ его избегают. static_cast виден в коде. Его легко найти поиском. Он запрещает опасные преобразования.

Расширяющие и сужающие преобразования

НаправлениеПримерыПотеря данных
Расширяющее (widening)int → long, float → double, int → doubleНет: значение сохраняется точно.
Сужающее (narrowing)long → int, double → float, double → intВозможна: старшие биты отбрасываются. Дробная часть отбрасывается. Точность теряется.

Оба приведения в задаче 1 — расширяющие. Поэтому результат точный. Обратные примеры: static_cast<int>(100000L) ещё влезает в 32-битный int. Но static_cast<int>(5000000000L) даёт неверное число: происходит переполнение. static_cast<int>(3.99) даёт 3: дробная часть отбрасывается без округления.

В Linux x64 модель данных другая: LP64. Там long равен 8 байтам. Поэтому sizeof(long) зависит от системы. Программа задачи 2 измеряет его через sizeof. Программа не полагается на память.

Вещественные числа: IEEE 754, float и double

Числа с плавающей точкой хранятся по стандарту IEEE 754. Число состоит из трёх частей. Часть 1: знак (1 бит). Часть 2: порядок-экспонента. Часть 3: мантисса — значащие цифры в двоичной системе.

ТипРазмерЗнак / экспонента / мантиссаТочных десятичных цифрПримерный диапазон
float4 байта (32 бита)1 / 8 / 23 бита≈ 7±3,4 × 10³⁸
double8 байт (64 бита)1 / 11 / 52 бита≈ 15–16±1,8 × 10³⁰⁸

Главное следствие: большинство десятичных дробей нельзя точно записать в двоичной системе. Примеры: 0.1 и 0.2. Число 25.25 — исключение: оно записывается точно. Поэтому float и double хранят лишь приближение. Примеры кода:

Пример: потеря точности
float f = 0.1f;              // хранится как 0.100000001490116...
double d = static_cast<double>(f); // станет 0.10000000149011612 —
// расширение НЕ добавляет точности, оно показывает
// то значение, которое уже было во float
double x = 0.1 + 0.2;        // 0.30000000000000004, а не 0.3

В задаче 1 этого эффекта нет. Число 25.25 равно 25 + 1/4. Дробь 1/4 — точная степень двойки. Поэтому float хранит 25.25 точно. Результат 100.5 точен. Суффикс f у литерала 25.25f обязателен. Без него литерал имеет тип double. Присваивание в float стало бы сужающим преобразованием. Компилятор выдал бы предупреждение.

Типичные ошибки

  • Путать static_cast с C-style кастом (тип)значение: результат тот же. Но C-style каст скрывает опасные преобразования. Его нельзя найти поиском по коду.
  • Считать, что static_cast<double>(float) повышает точность: нет. Он лишь сохраняет уже имеющееся значение float в более широком формате.
  • Сравнивать вещественные числа через == после вычислений: ошибка округления накапливается. Выражение 0.1 + 0.2 == 0.3 даёт false. Сравнивай с допуском (эпсилон).
  • Забывать суффикс f у float-литералов и суффикс L у long-литералов: компилятор выдаёт предупреждения о сужении.
  • Сужающее приведение больших значений: static_cast<int>(5000000000L) вызывает переполнение. Значение искажается молча. Ошибки времени выполнения нет.
Тема 2. Указатели void* и разрядность x64
к задаче 2 • task2_void_pointers_x64.cpp

Что это

Указатель — переменная. Она хранит адрес ячейки памяти. Пример: int* p = &x;. Переменная p хранит адрес переменной x. По этому адресу лежит значение типа int. Тип указателя говорит компилятору две вещи. Вещь 1: сколько байт читать при разыменовании (*p). Вещь 2: на сколько байт сдвигаться при p + 1.

void* — универсальный указатель. Он не имеет типа. Он хранит адрес. Он не знает, данные какого типа лежат по этому адресу. Слово void буквально означает «пустота». У типа void нет размера. Поэтому компилятор не знает, сколько байт читать и как их толковать.

Зачем нужен void*

  • Обобщённые функции: memcpy, malloc, qsort работают с сырой памятью любого типа. Они принимают void*.
  • Системные API: Win32-функции принимают и возвращают void*. Пример: MapViewOfFile (тема 3). Отображаемая память может содержать что угодно: текст, структуры, картинки.
  • Хранение чужого адреса: тип данных заранее неизвестен. Тип выясняется позже. Например, по коду типа, переданному рядом.

Правила работы с void*

ОперацияРазрешена?Пояснение
Любой указатель → void*Да, неявноvoid* p = &numInt;. Адрес просто копируется. Это безопасно.
void* → типизированный указательТолько явно, через static_castint* p = static_cast<int*>(ptrVoid);. Программист отвечает за правильность типа.
Разыменование *ptrVoidНет — ошибка компиляцииНеизвестно, сколько байт читать. У void нет размера.
Арифметика ptrVoid + 1Нет (в стандартном C++)Неизвестен шаг: сдвигаться на 1, 4 или 8 байт?
sizeof(void*)ДаРазмер самого указателя известен всегда: 8 байт в x64.
Сравнение указателей ==ДаАдреса сравниваются как числа.

Главный риск void*: компилятор не проверяет тип при обратном приведении. Пример: в void* лежит адрес double. Программа приводит его к int* и разыменовывает. Результат — мусор: первые 4 байта double читаются как целое число. Ошибки компиляции нет. Программа просто выдаёт неверный результат. Поэтому рядом с void* всегда держи отдельный признак типа. Признак — перечисление, флаг или знание из контекста.

Разрядность x64 и размеры типов

64-битная архитектура означает: адресное пространство — 64 бита. Указатель адресует 2⁶⁴ байт. Сам указатель занимает 8 байт. Размер указателя зависит только от архитектуры. Тип данных не влияет на него.

ВыражениеWindows x64 (LLP64)Linux x64 (LP64)Windows/Linux x86
sizeof(void*)884
sizeof(int*), sizeof(long*)884
sizeof(int)444
sizeof(long)484
sizeof(long long)888

Модель данных Windows называется LLP64. В ней long long и указатели — 64-битные. А long остаётся 32-битным. Причина: совместимость со старым кодом. Модель Linux называется LP64. В ней long тоже 64-битный. Поэтому программа задачи 2 на Linux печатает sizeof(long) = 8. Это не ошибка. Это другая модель данных. Приём sizeof(void*) * 8 спрашивает разрядность у компилятора. В x64 получается 64. В x86 получается 32.

Адреса в выводе: почему они каждый раз разные

Адреса переменных на стеке при каждом запуске разные. Пример: 0x000000A1B2C3D4E5. Причина: ASLR. ASLR — рандомизация размещения адресного пространства. Это защитный механизм Windows. Сравнивать адреса между запусками бессмысленно. Важно лишь одно: адрес из ptrInt совпадает с адресом numInt. Значения извлекаются верно.

Типичные ошибки

  • Разыменование void* напрямую (*ptrVoid): ошибка компиляции. Сначала сделай static_cast.
  • Неявное приведение void* → int* (int* p = ptrVoid;): ошибка компиляции в C++. В C это разрешено. В C++ — нет.
  • Обратное приведение к неверному типу: компилятор промолчит. Значение будет мусором.
  • Разыменование указателя после уничтожения переменной: указатель становится висячим. void* не продлевает жизнь объекту.
  • Путать размер указателя и размер данных: sizeof(int*) = 8. А sizeof(int) = 4. Это разные вещи.
  • Сборка в 32-битном режиме при задаче про x64: sizeof(void*) станет 4. Проверяй целевую платформу x64 в настройках проекта.
Тема 3. Проецирование файлов в память: CreateFileMapping и MapViewOfFile
к задаче 3 • task3_memory_mapped_offset.cpp

Что это

Проецирование файла в память — механизм Windows. Содержимое файла отображается в виртуальное адресное пространство процесса. Байты файла становятся обычной памятью. Программа читает их через указатель. Чтение файла превращается в чтение из памяти (pView[i]). Запись в память превращается в запись в файл. Это работает, если отображение открыто на запись. Диспетчер виртуальной памяти Windows сам подгружает страницы с диска. Он сам сбрасывает изменённые страницы обратно.

Зачем это нужно

  • Большие файлы: файл в гигабайты не нужно целиком грузить в RAM. Программа отображает только нужное окно. Система подкачивает страницы по мере обращения.
  • Скорость: нет буферов и лишних копирований, как при ReadFile. Данные читаются напрямую из страничного кэша системы.
  • Общий доступ к памяти: одна секция проецируется в несколько процессов. Это способ межпроцессного взаимодействия (shared memory).
  • Произвольный доступ: программа обращается к любому смещению файла напрямую. Функции seek и последовательное чтение не нужны.

Цепочка вызовов: от файла к указателю

Проецирование всегда делается в три шага. У каждого шага свой дескриптор. Каждый дескриптор потом надо закрыть.

ШагФункцияЧто создаётЧто вернуть / закрыть
1CreateFileWОткрывает файл. Возвращает HANDLE hFile.Ошибка: INVALID_HANDLE_VALUE. Закрытие: CloseHandle(hFile).
2CreateFileMappingWСоздаёт объект ядра «секция». Возвращает HANDLE hMapping.Ошибка: NULL. Закрытие: CloseHandle(hMapping).
3MapViewOfFileОтображает окно секции в память. Возвращает void* pView.Ошибка: NULL. Снятие: UnmapViewOfFile(pView).

Порядок освобождения обратен порядку создания. Шаг 1: UnmapViewOfFile(pView). Шаг 2: CloseHandle(hMapping). Шаг 3: CloseHandle(hFile). Закрытие дескриптора файла раньше времени отображение не разрушает: секция держит файл. Но правильный порядок — часть дисциплины. Каждый открытый дескриптор закрывается ровно один раз.

CreateFileMapping: параметры

CreateFileMappingW(hFile, NULL, PAGE_READONLY, 0, 0, NULL). Аргументы по порядку. Аргумент 1: дескриптор файла. Аргумент 2: атрибуты безопасности. NULL означает значения по умолчанию. Аргумент 3: защита страниц. PAGE_READONLY означает только чтение. PAGE_READWRITE означает чтение и запись. PAGE_WRITECOPY означает копирование при записи. Аргументы 4 и 5: старший и младший DWORD размера секции. Значения 0, 0 означают размер всего файла. Аргумент 6: имя секции. NULL означает безымянную секцию только для этого процесса. Защита секции и права доступа к файлу обязаны согласовываться. PAGE_READONLY требует GENERIC_READ у файла. PAGE_READWRITE требует GENERIC_READ | GENERIC_WRITE.

MapViewOfFile: параметры

MapViewOfFile(hMapping, FILE_MAP_READ, offsetHigh, offsetLow, viewSize). Аргументы по порядку. Аргумент 1: дескриптор секции. Аргумент 2: желаемый доступ. FILE_MAP_READ означает чтение. FILE_MAP_WRITE означает запись. FILE_MAP_ALL_ACCESS означает полный доступ. Аргументы 3 и 4: старшая и младшая части смещения начала окна. Аргумент 5: размер окна в байтах. Значение 0 означает: до конца секции. Функция возвращает void* — указатель на начало окна. Программист приводит его к нужному типу. Для текста это const char*.

Allocation Granularity — почему смещение не может быть случайным

Диспетчер виртуальной памяти Windows работает не с отдельными байтами, а с блоками. Есть два разных размера. Их нельзя путать.

ВеличинаЗначение (x86/x64)На что влияет
Размер страницы (dwPageSize)4 КБ (4096 байт)Минимальная единица подкачки с диска и защиты памяти.
Гранулярность распределения (dwAllocationGranularity)64 КБ (65 536 байт)Выравнивание начальных адресов областей памяти — и смещений в MapViewOfFile.

Смещение окна обязано быть кратно именно гранулярности — 64 КБ. Причина: виртуальные адреса областей выравниваются по 64 КБ. Начало окна привязано к этим границам. Смещение 131072 = 2 × 65536: оно допустимо. Смещение 100000, 131073 или 65537: недопустимо. MapViewOfFile немедленно возвращает NULL. GetLastError даёт код 1132 — ERROR_MAPPED_ALIGNMENT. Код означает: базовый адрес или смещение файла не имеют требуемого выравнивания.

При этом размер окна может быть любым. В задаче он равен 1024 байтам. Выравнивание требуется только для начала окна, а не для его конца. Читать внутри окна можно с любой точностью. Пример: нужны данные со смещения 100000. Программа проецирует окно со смещения 65536. Потом программа берёт pView[100000 − 65536]. Разница добавляется внутри окна.

Как узнать гранулярность правильно: не хардкодь 65536. Спроси у системы через GetSystemInfo(&sysInfo). Возьми поле dwAllocationGranularity. На всех современных Windows x86/x64 это 64 КБ. Но код, который спрашивает, а не угадывает, — переносимый и правильный.

Разбиение смещения на offsetHigh / offsetLow

MapViewOfFile — функция из 32-битной эпохи. Она принимает 64-битное смещение двумя 32-битными параметрами. Поэтому смещение разрезают пополам.

Разбиение 64-битного смещения
DWORD offsetLow  = (DWORD)(targetOffset & 0xFFFFFFFF);
DWORD offsetHigh = (DWORD)(((ULONGLONG)targetOffset >> 32) & 0xFFFFFFFF);
// Обратная сборка: смещение = offsetHigh * 2^32 + offsetLow
СмещениеoffsetHighoffsetLow
131072 (128 КБ, задача)0131072
5 368 709 120 (5 ГБ)11 073 741 824 (0x40000000)

Приведение к ULONGLONG перед сдвигом обязательно. Сдвиг 32-битного значения на 32 бита — неопределённое поведение. Для смещений меньше 4 ГБ старшая часть всегда равна 0. Но код пишется общим: для файлов любого размера.

Чтение порциями: идея задачи

Файл в задаче — 256 КБ. Окно — всего 1 КБ. Это модель работы с огромным файлом. Программа не грузит весь файл в память. Программа отображает окно на нужном смещении. Программа читает окно. Программа снимает отображение. Потом программа отображает следующее окно. Следующее окно тоже начинается с кратного 64 КБ смещения. Поэтому порции при проецировании обычно делают размером, кратным гранулярности. Внутри окна программа двигается указателем. Задача показывает один шаг этого цикла: окно на 128 КБ, чтение маркера, снятие отображения.

Типичные ошибки

  • Смещение не кратно 64 КБ: MapViewOfFile возвращает NULL. Ошибка 1132 (ERROR_MAPPED_ALIGNMENT).
  • Смещение и окно выходят за конец файла: MapViewOfFile возвращает NULL. Файл обязан быть не меньше, чем offset + viewSize.
  • Забыть UnmapViewOfFile или CloseHandle: утечка диапазона адресов и дескрипторов.
  • Чтение или запись за пределами окна: нарушение доступа. Программа падает.
  • Запись через отображение PAGE_READONLY / FILE_MAP_READ: нарушение доступа. Для записи нужны PAGE_READWRITE и FILE_MAP_WRITE.
  • Путать коды ошибок: у CreateFileW признак неудачи — INVALID_HANDLE_VALUE. У CreateFileMappingW и MapViewOfFile — NULL.
  • Вывод const char* через cout без приведения к void*: печатается строка, а не адрес.
  • Проверка GetLastError() не сразу после неудачного вызова: следующий вызов API перезаписывает код ошибки.

Чем компилировать

Подходят два компилятора. Нужен стандарт C++17 или новее.

Компиляция всех трёх задач
:: MSVC — в Developer Command Prompt for VS (цель x64):
cl /EHsc /std:c++17 task1_explicit_casting.cpp
cl /EHsc /std:c++17 task2_void_pointers_x64.cpp
cl /EHsc /std:c++17 task3_memory_mapped_offset.cpp

:: MinGW-w64 (g++) — в PowerShell / cmd:
g++ -std=c++17 -o task1.exe task1_explicit_casting.cpp
g++ -std=c++17 -o task2.exe task2_void_pointers_x64.cpp
g++ -std=c++17 -o task3.exe task3_memory_mapped_offset.cpp

Флаг /EHsc у MSVC включает обработку исключений C++. Он нужен для работы стандартной библиотеки. Флаг -std=c++17 задаёт стандарт языка. Имя выходного exe у MSVC совпадает с именем cpp-файла: task1_explicit_casting.exe. У g++ имя задаёт флаг -o. Запускай из той же папки, где лежит exe: .\task1.exe, .\task2.exe, .\task3.exe.

Задача 3: откуда берётся файл

В актуальном коде файл создаётся самой программой. CreateFileW вызван с флагом CREATE_ALWAYS. Флаг означает: создать новый файл или обнулить существующий. Поэтому заранее создавать mapped_large_test.txt не нужно. Размер заранее не важен: программа сама записывает 256 КБ (4 блока по 64 КБ). Программа кладёт маркер на смещение 128 КБ. После запуска файл остаётся рядом с exe. Его размер — 262144 байта. Повторный запуск перезаписывает файл заново. Это нормально.

Если бы в коде стоял OPEN_EXISTING, файл пришлось бы создавать заранее. Так было в сокращённой версии кода из старой шпаргалки. Файл обязан был бы быть не меньше 128 КБ + 1 КБ: смещение плюс окно. Для такого случая файл создаётся одной из команд. Выполняй команду в папке запуска. Нужны права на запись.

Создание тестового файла вручную — только для режима OPEN_EXISTING
:: cmd (256 КБ = 262144 байта):
fsutil file createnew mapped_large_test.txt 262144

:: PowerShell (тот же результат):
[System.IO.File]::WriteAllBytes('mapped_large_test.txt', [byte[]]::new(262144))

К актуальному коду задачи 3 эти команды не относятся. Они приведены только для ясности. Они объясняют, откуда взялось требование «файл не меньше 128 КБ». Они показывают, как выполнить требование, если преподаватель попросит вариант с OPEN_EXISTING.

Проверка результата

  • Задача 1: в выводе обязаны быть 75000 и 100.5000. Любое другое число означает ошибку в значениях или в приведении.
  • Задача 2: значения 42 и 123456 извлечены верно. Все sizeof(...*) равны 8. Разрядность — 64 бита. Адреса при каждом запуске разные. Это нормально (ASLR).
  • Задача 3: в выводе — гранулярность 65536 байт (64 КБ). В выводе — смещение 131072 байта. В выводе — прочитанный маркер «[СЕКРЕТНЫЙ ТЕКСТ НА СМЕЩЕНИИ 128 КБ]». В выводе — строка об успешном размонтировании. Рядом с exe лежит файл mapped_large_test.txt размером 262144 байта.
Двойной клик по exe закрывает консоль сразу после завершения. Вывод прочитать не успеть. Запускай из cmd или PowerShell. Или добавь паузу в конце. Например, system("pause") перед return 0. Пауза нужна только для отладки. В сдаваемый код её лучше не включать.
