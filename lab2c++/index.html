Теория ОС и Win32

Ответы на экзаменационные вопросы

В1
Что произойдет, если запустить ReadFile асинхронно, но сразу же закрыть хэндл файла через CloseHandle, не дожидаясь окончания операции?
Краткий итог: Память объекта файла сразу не освободится, но операция прервется/отменится, а передача буфера на стеке может вызвать порчу памяти (Memory Corruption) или падение приложения!

Подробная физика процесса:

  • Создание IRP: При вызове ReadFile с флагом OVERLAPPED подсистема ввода-вывода Windows создает I/O Request Packet (IRP) и направляет его драйверу накопителя. Функция сразу возвращает управление со статусом ERROR_IO_PENDING.
  • Счетчик ссылок ядра: Объект файла ядра (File Object) имеет счетчик ссылок (Reference Count). CloseHandle удаляет дескриптор из таблицы процесса и уменьшает счетчик. Однако драйвер, обрабатывающий запрос, держит свою ссылку на File Object, поэтому сам объект ядра останется жив до фактического завершения пакета.
  • Отмена запроса: Закрытие дескриптора обычно отправляет драйверу команду очистки (IRP_MJ_CLEANUP), приводя к попытке отмены операции (I/O Cancellation).
  • Критическая опасность для буфера: Если буфер данных (lpBuffer) или структура OVERLAPPED были объявлены локально в функции, поток выйдет из нее, стек будет перезаписан, а DMA-контроллер или драйвер затем попытается записать прочитанные с диска данные по старому адресу. Это классическое повреждение памяти.
  • Потеря статуса: Функция GetOverlappedResult вернет ошибку ERROR_INVALID_HANDLE, так как дескриптор файла закрыт.
В2
Почему для структуры OVERLAPPED критически важно обнулять её поля (например, через = {0} или memset) перед передачей в системный вызов?
Главная причина: Неинициализированная структура содержит случайный стек-мусор, который ОС примет за файловое смещение и дескриптор события!

Структура OVERLAPPED имеет вид:

typedef struct _OVERLAPPED {
    ULONG_PTR Internal;     // [OUT] Код возврата NTSTATUS
    ULONG_PTR InternalHigh; // [OUT] Число переданных байт
    union {
        struct {
            DWORD Offset;     // [IN] Младшие 32 бита файлового смещения
            DWORD OffsetHigh; // [IN] Старшие 32 бита файлового смещения
        };
        PVOID Pointer;
    };
    HANDLE hEvent;          // [IN] Дескриптор события для ожидания
} OVERLAPPED;
  • Смещение (Offset / OffsetHigh): В асинхронных операциях ОС не использует неявный файловый указатель! Смещение, откуда читать или куда писать, считывается исключительно из полей Offset. Мусорные байты заставят ОС читать файл с случайного адреса (например, 3 терабайта), вернув ERROR_HANDLE_EOF.
  • Хэндл события (hEvent): Драйвер проверяет hEvent != NULL. Если в поле окажется мусорное число, ядро воспримет его как валидный хэндл и попытается вызвать для него SetEvent(), что приведет к непредсказуемым ошибкам в работе других объектов.
В3
Маленький файл (10 байт) сохранен в NTFS как резидентный. Будет ли при его чтении через ReadFile с флагом OVERLAPPED происходить реальная асинхронная задержка ввода-вывода?
Ответ: НЕТ, реальной асинхронной задержки не будет! Операция завершится синхронно и мгновенно.

Почему это происходит:

  • В файловой системе NTFS файлы размером до ~700–800 байт помещаются прямо внутрь 1-килобайтной записи таблицы MFT (Master File Table) в качестве резидентного атрибута $DATA.
  • При открытии файла запись MFT уже находится в оперативной памяти (в пуле ядра / системном кэше метаданных NTFS).
  • Поскольку данные уже лежат в ОЗУ, драйверу NTFS не требуется формировать запросы к физическому контроллеру диска, позиционировать головки или ждать завершения DMA.
  • ReadFile мгновенно копирует 10 байт из памяти MFT в буфер вызывающей программы и возвращает TRUE (операция завершена синхронно без ERROR_IO_PENDING).
В4
Как можно открыть файлы с именем $MFT?

Файл $MFT — это главная таблица метаданных тома NTFS. Стандартный путь C:\$MFT заблокирован драйвером файловой системы (возвращает ERROR_ACCESS_DENIED).

Способы получить к нему доступ:

  • Способ 1 (Низкоуровневый доступ к тому — Raw Volume Access):
    С правами Администратора открыть том как блочное устройство: CreateFileW(L"\\\\.\\C:", GENERIC_READ, FILE_SHARE_READ | FILE_SHARE_WRITE, NULL, OPEN_EXISTING, 0, NULL);
    Затем через функцию DeviceIoControl() с управляющими кодами:
    • FSCTL_GET_NTFS_FILE_RECORD — чтение конкретных записей MFT (например, запись 0 — это $MFT).
    • FSCTL_GET_RETRIEVAL_POINTERS — получение экстентов (LCN/VCN цепочек) размещения MFT на диске.
  • Способ 2 (Журнал изменений USN): Использование официального API FSCTL_READ_USN_JOURNAL для потокового чтения истории записей MFT.
  • Способ 3 (Теневые копии тома VSS): Создание Volume Shadow Copy (теневой копии) через службу VSS. В теневой копии драйвер NTFS часто позволяет читать $MFT напрямую.
В5
Почему в Windows файлы ИМЯ.txt и имя.txt — это один и тот же файл?
Архитектурный факт: Ядро Windows NT и файловая система NTFS поддерживают регистрозависимость, но подсистема Win32 API принудительно игнорирует регистр!
  • Наследие MS-DOS: Исторически пользовательская среда DOS/Windows создавалась так, чтобы пользователи не путались из-за регистра букв при вводе команд.
  • Win32 Subsystem: При вызове Win32 функций (CreateFile, FindFirstFile) библиотека kernel32.dll транслирует вызов в Native API ядру (NtCreateFile), передавая системный флаг OBJ_CASE_INSENSITIVE.
  • Нормализация: Имена файлов приводятся к верхнему регистру по системной таблице Unicode Uppercase Table перед поиском записи в каталоге. При этом регистр сохраняется для отображения (Case-Preserving).
  • Примечание: В Windows 10/11 для каталогов WSL чувствительность к регистру можно включить командой fsutil.exe file setCaseSensitiveInfo <папка> enable.
В6
Как ОС узнает свободен ли сектор на диске?

Операционная система работает с диском на уровне кластеров (Cluster, обычно 4 КБ = 8 секторов по 512 байт).

  • Битовая карта тома в NTFS ($Bitmap): В корне любого раздела NTFS хранится специальный метафайл $Bitmap (запись 6 в MFT). Он представляет собой непрерывный битовый массив:
    • Бит = 0: кластер свободен для записи;
    • Бит = 1: кластер занят данными файла или метаданными.
    При создании файла ОС сканирует $Bitmap в поисках нулевых бит, резервирует их (устанавливает в 1) и записывает данные.
  • В файловых системах FAT/FAT32: Статус определяется таблицей FAT: свободный кластер содержит число 0x00000000.
  • На уровне физического SSD (команда TRIM): Когда кластер освобождается, драйвер ОС отправляет контроллеру твердотельного накопителя команду TRIM (ATA) или Deallocate (NVMe), уведомляя, что физические ячейки памяти можно очистить.

Сравнение размеров типов в x86 и x64
Модель ILP32 (x86) против LLP64 (x64 в Windows)
Тип данных x86 (32-бит) x64 (64-бит) Изменяется? Назначение
int 4 байта 4 байта Нет Базовое целое со знаком
long 4 байта 4 байта Нет В Windows LLP64 всегда 32 бита!
long long 8 байт 8 байт Нет 64-битное целое число
void* 4 байта 8 байт ДА Указатель на память
DWORD 4 байта 4 байта Нет 32-битное беззнаковое целое
LONG 4 байта 4 байта Нет 32-битное знаковое целое
ULONG_PTR 4 байта 8 байт ДА Целое число точности указателя
DWORD_PTR 4 байта 8 байт ДА Беззнаковое целое точности указателя
INT_PTR 4 байта 8 байт ДА Знаковое целое точности указателя
Почему так устроен Windows: Windows на 64-битных процессорах использует модель LLP64 (а не LP64 как в Linux). В ней long и int остаются 32-битными, чтобы сохранить работоспособность старого Win32 кода. Для хранения адресов памяти в целых числах Microsoft ввела семейство полиморфных типов *_PTR, которые расширяются до 8 байт на x64.

Задание 3: Ошибка усечения указателя в x64

Исходник: task8_ptr_truncation_fix.cpp
Проблема каста (DWORD)lpContext и ее устранение
Ошибка в оригинальном коде: DWORD TRUNCATED_PTR = (DWORD)lpContext;
В 64-битной сборке указатель lpContext имеет размер 8 байт, а DWORD — 4 байта. Происходит Pointer Truncation: старшие 32 бита адреса стираются. При обратном касте в указатель получается поврежденный адрес и происходит падение 0xC0000005 (Access Violation)!
Исправленное решение: Использовать DWORD_PTR вместо DWORD! 
// БЫЛО (с ошибкой в x64):
void ProcessData(DWORD dataStylePointer) {
    int* pNumber = (int*)dataStylePointer; // Авария в x64!
    ...
}

// СТАЛО (исправлено для x86 и x64):
void ProcessData(DWORD_PTR dataStylePointer) {
    int* pNumber = reinterpret_cast<int*>(dataStylePointer);
    if (pNumber != nullptr) {
        std::cout << "Value: " << *pNumber << std::endl;
    }
}

int main() {
    int criticalValue = 2026;
    int* lpContext = &criticalValue;
    // Безопасное приведение без потери битов:
    DWORD_PTR SAFE_PTR = (DWORD_PTR)lpContext;
    ProcessData(SAFE_PTR);
    return 0;
}

Задание 4: Хэндлы объектов ядра Windows

Исходник: task9_kernel_handles.cpp
CreateFile, CreateEvent, GetCurrentProcess
1
Почему хэндлы кратны 4 и малы? Хэндл — это не адрес в памяти ядра, а индекс (смещение) в таблице дескрипторов процесса (Process Handle Table). Записи идут с шагом, кратным 4, а младшие 2 бита зарезервированы ядром под служебные флаги (например, запрет наследования). Поэтому значения равны 4, 8, 12, 16...
2
Почему GetCurrentProcess возвращает -1 (0xFFFFFFFF)? Это константа-маркер (псевдо-дескриптор / pseudo-handle). Она не расходует запись в таблице дескрипторов. Ядро, видя -1, сразу обращается к текущему процессу. Его не нужно закрывать через CloseHandle()!

Результат вывода программы: 30 40
1

5
*p = 40; — разыменовываем p и записываем 40 в ячейку b. Теперь b = 40.
6
cout << a << " " << b; — печатает "30 40".
Исходник: task2_strings_memory.cpp
Задача 2: Строки и массивы в памяти
Код задачи: char str[] = "Hello"; const char* p = "Hello"; std::cout << sizeof(str) << " " << sizeof(p);
Результат вывода в 64-битной системе: 6 8 (в 32-битной было бы 6 4)
1
sizeof(str) == 6 байт 'str' — локальный массив на стеке. Слово "Hello" содержит 5 букв + 1 нуль-терминатор '\0'. Размер: 5 + 1 = 6 байт.
2
sizeof(p) == 8 байт 'p' — переменная-указатель. Оператор sizeof(p) вычисляет размер самого указателя, а не строки! В x64 любой адрес занимает 8 байт.
