Подробное объяснение различий моделей памяти

1. В Windows x64 используется модель LLP64: типы int и long остаются 32-битными (4 байта), чтобы старый 32-битный код продолжал работать без изменений.

2. Указатели (void*) в x64 увеличиваются до 8 байт (64 бита адреса).

3. Типы ULONG_PTR, DWORD_PTR, INT_PTR — это целые числа с точностью до указателя. В x86 они равны 4 байтам, а в x64 — 8 байтам, что делает их безопасными для сохранения адресов.

Задание 3: Исправление усечения указателя в x64

#include <iostream>

// Исправлено: замена DWORD на DWORD_PTR для предотвращения усечения адреса в x64
void ProcessData(DWORD_PTR dataStylePointer) {
    int* pNumber = reinterpret_cast<int*>(dataStylePointer);
    if (pNumber != nullptr) {
        std::cout << "Value: " << *pNumber << std::endl;
    }
}

int main() {
    #if defined(_WIN32)
    system("chcp 65001 > nul");
    #endif

    int criticalValue = 2026;
    int* lpContext = &criticalValue;

    // Исправлено: каст указателя в 64-битный тип DWORD_PTR вместо 32-битного DWORD
    DWORD_PTR SAFE_PTR = (DWORD_PTR)lpContext;

    ProcessData(SAFE_PTR);

    return 0;
}

Разбор ошибки и решения

В чем была ошибка: (DWORD)lpContext отбрасывает старшие 32 бита указателя в 64-битной сборке. Внутри ProcessData обратный каст в int* получает битый адрес. Разыменование *pNumber приводит к мгновенному падению программы с кодом 0xC0000005 (Access Violation).

Как исправлено: Заменой DWORD на DWORD_PTR. В x86 он 32-битный, а в x64 — 64-битный, поэтому ни один бит адреса не теряется.

Задание 4: Хэндлы объектов ядра Windows

task3_kernel_handles.cpp 
#include <windows.h>
#include <iostream>
#include <iomanip>

int main() {
    #if defined(_WIN32)
    system("chcp 65001 > nul");
    #endif

    // 1. Создание/открытие файла (объект ядра File)
    HANDLE hFile = CreateFileW(
        L"temp_kernel_demo.tmp",
        GENERIC_READ | GENERIC_WRITE,
        FILE_SHARE_READ,
        NULL,
        CREATE_ALWAYS,
        FILE_ATTRIBUTE_TEMPORARY | FILE_FLAG_DELETE_ON_CLOSE,
        NULL
    );

    // 2. Создание события (объект ядра Event)
    HANDLE hEvent = CreateEventW(NULL, TRUE, FALSE, NULL);

    // 3. Получение дескриптора текущего процесса (псевдо-хэндл)
    HANDLE hProcess = GetCurrentProcess();

    std::cout << "=== Объекты ядра Windows и их дескрипторы ===" << std::endl;
    std::cout << "1. File Handle (CreateFile):          " << (void*)hFile    << " (UINT_PTR: " << (UINT_PTR)hFile    << ")" << std::endl;
    std::cout << "2. Event Handle (CreateEvent):        " << (void*)hEvent   << " (UINT_PTR: " << (UINT_PTR)hEvent   << ")" << std::endl;
    std::cout << "3. Current Process (GetCurrentProcess): " << (void*)hProcess << " (UINT_PTR: " << (UINT_PTR)hProcess << ")" << std::endl;

    // Закрытие реальных дескрипторов
    if (hFile != INVALID_HANDLE_VALUE) {
        CloseHandle(hFile);
    }
    if (hEvent != NULL) {
        CloseHandle(hEvent);
    }
    // Псевдо-дескриптор hProcess закрывать через CloseHandle не нужно!

    return 0;
}

Ответы на вопросы задания

1. Почему хэндлы кратны 4 и малы? Хэндл — это индекс (смещение) в таблице дескрипторов процесса (Process Handle Table). Записи идут с шагом, кратным 4, а 2 младших бита зарезервированы ядром под флаги (например, защиту от закрытия). Поэтому значения — 4, 8, 12, 16...

2. Почему GetCurrentProcess возвращает -1 (0xFFFFFFFF)? Это системный псевдо-дескриптор (константа). Он не занимает запись в таблице. Системные функции видят -1 и сразу обращаются к текущему процессу. Его не нужно закрывать через CloseHandle.

6 экзаменационных вопросов по ОС (Фото 3)

В1
Что произойдет, если запустить ReadFile асинхронно, но сразу же закрыть хэндл файла через CloseHandle, не дожидаясь окончания операции?
Итог: Объект файла сразу не удалится (драйвер держит ссылку), но операция будет отменена. Если буфер был на стеке, произойдет порча памяти!
  • Драйвер держит собственную ссылку на File Object до завершения пакета IRP.
  • Закрытие хэндла инициирует IRP_MJ_CLEANUP (отмену I/O).
  • Если буфер на стеке был освобожден выходом из функции, DMA-контроллер запишет данные по старому адресу, вызвав повреждение памяти или падение.
  • GetOverlappedResult вернет ERROR_INVALID_HANDLE.
В2
Почему для структуры OVERLAPPED критически важно обнулять её поля (например, через = {0} или memset)?
  • Поля смещения (Offset / OffsetHigh): В асинхронных вызовах Windows берет смещение для чтения исключительно из этих полей. Мусорные байты заставят ядро пытаться читать файл со случайного терабайтного смещения, вызвав ERROR_HANDLE_EOF.
  • Дескриптор события (hEvent): Мусорное значение ядро примет за валидный хэндл и попытается вызвать SetEvent(), что приведет к ложным срабатываниям в чужих объектах.
В3
Маленький файл (10 байт) сохранен в NTFS как резидентный. Будет ли при его чтении через ReadFile с флагом OVERLAPPED происходить реальная асинхронная задержка ввода-вывода?
Ответ: НЕТ, реальной задержки ввода-вывода не будет!

Файлы до ~700 байт в NTFS хранятся прямо внутри 1024-байтной записи MFT как резидентный атрибут $DATA. Запись MFT уже находится в оперативной памяти (в кэше ядра). Функция ReadFile мгновенно копирует 10 байт из памяти в буфер и синхронно возвращает TRUE.

В4
Как можно открыть файлы с именем $MFT?

Прямой путь C:\$MFT защищен файловой системой (ERROR_ACCESS_DENIED).

  • Raw Volume Access: Открыть физический том с правами Администратора: CreateFileW(L"\\\\.\\C:", ...) и читать записи через DeviceIoControl(FSCTL_GET_NTFS_FILE_RECORD).
  • USN Journal: Чтение записей через API журнала изменений FSCTL_READ_USN_JOURNAL.
  • Теневые копии (VSS): Чтение напрямую из Volume Shadow Copy.
В5
Почему в Windows файлы ИМЯ.txt и имя.txt — это один и тот же файл?
  • Подсистема Win32 регистронезависима: Для совместимости с DOS подсистема Win32 принудительно передает ядру флаг OBJ_CASE_INSENSITIVE и приводит имена к верхнему регистру.
  • Ядро NT и NTFS поддерживают регистрозависимость: Сама файловая система NTFS сохраняет регистр букв (Case-Preserving) и поддерживает регистрозависимость ядра при вызове Native API (NtCreateFile без флага). В Windows 10/11 регистрозависимость папки можно включить через fsutil.exe file setCaseSensitiveInfo <папка> enable.
В6
Как ОС узнает свободен ли сектор на диске?
  • ОС оперирует кластерами (обычно 4 КБ = группа секторов).
  • Метафайл $Bitmap в NTFS: В корне тома находится битовая карта $Bitmap (запись 6 в MFT), где каждый бит соответствует кластеру: 0 — свободен, 1 — занят.
  • В FAT32: Статус хранится в таблице FAT (свободный кластер равен 0x00000000).
  • На уровне SSD: ОС сообщает контроллеру об освобожденных секторах командой TRIM / Deallocate.

Задача 4б: Перенос буквы «н» в начало (исходная строка не меняется)
3_practice_hw/task4b_move_letter_n.cpp
task4b_move_letter_n.cpp 
#define _CRT_SECURE_NO_WARNINGS
#include <iostream>
#include <cstdio>
#include <cstring>

int main() {
    #if defined(_WIN32)
    system("chcp 65001 > nul");
    #endif

    // Исходная переменная объявлена const — её НИКТО не меняет
    const char clientStr[] = "Клиент";
    int ID = 245;

    // Число -> строка
    char idStr[32];
    sprintf(idStr, "%d", ID);

    // Буква 'н' (в UTF-8 это два байта)
    const char letterN[] = "н";

    // НОВАЯ строка-результат, исходную переменную не трогаем
    char result[128] = "";

    // 1. Кладём букву 'н' в НАЧАЛО результата
    strcat(result, letterN);

    // 2. Ищем букву 'н' в исходном слове
    const char* posN = strstr(clientStr, letterN);
    if (posN != nullptr) {
        int before = (int)(posN - clientStr);      // байт до буквы 'н'

        // 3. Копируем начало слова ("Клие") — уже без буквы 'н'
        strncat(result, clientStr, before);

        // 4. Копируем остаток после буквы 'н' ("т")
        strcat(result, posN + strlen(letterN));
    }

    // 5. Приклеиваем число
    strcat(result, idStr);

    std::cout << "Исходная строка (не изменена): " << clientStr << std::endl;
    std::cout << "Результат:                     " << result << std::endl;

    return 0;
}
