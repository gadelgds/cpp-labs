## Задание 1. Префиксы венгерской нотации и реальные типы Win32

### Условие
Расшифровать префиксы и определить реальный тип данных для переменных:
`LPCSTR pszName, LPVOID lpBuffer, HMODULE hMod, DWORD cbSize`

### Подробный разбор

| Переменная | Префикс | Расшифровка префикса | Тип Win32 | Реальный тип C/C++ | Назначение |
| :--- | :---: | :--- | :--- | :--- | :--- |
| `pszName` | `psz` | `p` — pointer (указатель), `sz` — zero-terminated string (строка с `\0`) | `LPCSTR` | `const char*` | Указатель на константную ANSI-строку |
| `lpBuffer` | `lp` | `lp` — long pointer (исторический 32-битный указатель Windows) | `LPVOID` | `void*` | Нетипизированный указатель на буфер памяти |
| `hMod` | `h` | `h` — handle (дескриптор объекта ядра/модуля) | `HMODULE` | `HINSTANCE` $\to$ `HANDLE` $\to$ `void*` | Дескриптор загруженного модуля (`.exe` или `.dll`), базовый адрес в памяти |
| `cbSize` | `cb` | `cb` — count of bytes (количество байт) | `DWORD` | `unsigned long` | 32-битное беззнаковое целое число для размера |

## Задание 2. Исследование моделей данных C++ и Win32 (`sizeof`)

* **Исходный файл для копирования:** [`task1_types_sizeof.cpp`](task1_types_sizeof.cpp)

### Сводная таблица размеров типов (x86 vs x64)

| Тип данных | Размер в x86 (32-бит) | Размер в x64 (64-бит) | Меняет размер? | Описание |
| :--- | :---: | :---: | :---: | :--- |
| `int` | 4 байта | 4 байта | Нет | Базовый знаковый integer |
| `long` | 4 байта | 4 байта | Нет | В модели Windows LLP64 всегда 32 бита |
| `long long` | 8 байт | 8 байт | Нет | 64-битное целое число |
| `void*` | 4 байта | **8 байт** | **ДА** | Указатель на адрес памяти |
| `DWORD` | 4 байта | 4 байта | Нет | `unsigned long` (32 бита) |
| `LONG` | 4 байта | 4 байта | Нет | `long` (32 бита) |
| `ULONG_PTR` | 4 байта | **8 байт** | **ДА** | Полиморфное беззнаковое целое размера указателя |
| `DWORD_PTR` | 4 байта | **8 байт** | **ДА** | Полиморфное беззнаковое целое размера указателя |
| `INT_PTR` | 4 байта | **8 байт** | **ДА** | Полиморфное знаковое целое размера указателя |

### Подробное объяснение различий
1. **Модели памяти (ILP32 vs LLP64):**
   * В 32-битной Windows действует модель **ILP32** (Integer, Long, Pointer — 32 бита).
   * В 64-битной Windows принята модель **LLP64** (Long Long, Pointer — 64 бита; а `int` и `long` остаются 32-битными). Это решение Microsoft позволило без переписывания исполнять миллионы строк 32-битного кода. В отличие от Windows, в 64-битном Linux (модель LP64) тип `long` равен 8 байтам.
2. **Семейство типов `*_PTR`:**
   * Типы `ULONG_PTR`, `DWORD_PTR`, `INT_PTR` — это **не указатели**, а целочисленные типы (integers), способные безопасно вместить значение указателя без потери бит. На x86 они 32-битные, на x64 — 64-битные.

## Задание 3. Исправление ошибки усечения указателя (Pointer Truncation)

* **Исходный файл для копирования:** [`task2_ptr_truncation_fix.cpp`](task2_ptr_truncation_fix.cpp)

### В чем заключалась ошибка
В исходном коде присутствовала строка:
```cpp
DWORD TRUNCATED_PTR = (DWORD)lpContext;
ProcessData(TRUNCATED_PTR);
```
* **В x86 (32-бит)**: `sizeof(lpContext) == 4` и `sizeof(DWORD) == 4`. Преобразование проходит без потери информации.
* **В x64 (64-бит)**: `sizeof(lpContext) == 8`, а `sizeof(DWORD) == 4`. Происходит усечение адреса: компилятор выдает предупреждение `C4311: 'type cast': pointer truncation from 'int *' to 'DWORD'`, а старшие 32 бита 64-битного адреса стираются.
* **Результат работы ошибки**: внутри `ProcessData` обратное приведение `(int*)dataStylePointer` восстанавливает невалидный адрес вида `0x00000000...` вместо `0x00007FF7...`. Попытка разыменования `*pNumber` вызывает немедленное аварийное завершение программы — **Access Violation (0xC0000005)**.

### Исправление
Заменить устаревший тип `DWORD` на полиморфный `DWORD_PTR` (или `uintptr_t`):
```cpp
void ProcessData(DWORD_PTR dataStylePointer) {
    int* pNumber = reinterpret_cast<int*>(dataStylePointer);
    if (pNumber != nullptr) {
        std::cout << "Value: " << *pNumber << std::endl;
    }
}
```
И в точке вызова:
```cpp
DWORD_PTR SAFE_PTR = (DWORD_PTR)lpContext;
ProcessData(SAFE_PTR);
```

## Задание 4. Объекты ядра Windows и исследование дескрипторов (HANDLE)

* **Исходный файл для копирования:** [`task3_kernel_handles.cpp`](task3_kernel_handles.cpp)

### Вопросы и ответы

#### 1. Почему значения хэндлов часто кратны 4 и похожи на малые числа?
* Хэндл (`HANDLE`) в Windows — это **не прямой адрес** структуры в памяти ядра (Kernel Space), так как передача прямых адресов ядра в пользовательский режим (User Mode) создала бы огромную уязвимость в безопасности.
* Дескриптор является индексом (смещением) в системной таблице дескрипторов процесса (**Process Handle Table**), управляемой ядром ОС.
* Таблица устроена как массив записей. Смещение каждой записи кратно 4 байтам, а младшие 2 бита дескриптора зарезервированы ядром под служебные флаги (например, запрет закрытия или флаг наследования дескриптора дочерними процессами).
* Поэтому реальные дескрипторы представляют собой числа 4, 8, 12, 16, 20... (шестнадцатеричные: `0x4`, `0x8`, `0xC`, `0x10`...), то есть малые положительные целые числа, строго кратные 4.

#### 2. Почему `GetCurrentProcess()` возвращает псевдо-хэндл `-1` (`0xFFFFFFFF`)?
* Функция `GetCurrentProcess()` возвращает специальную константу `((HANDLE)(LONG_PTR)-1)` — так называемый **псевдо-дескриптор** (pseudo-handle).
* Он не создает запись в таблице дескрипторов процесса и не увеличивает счетчик ссылок.
* Когда системная функция Windows (например, `WaitForSingleObject`) видит значение `-1`, она мгновенно понимает, что вызов адресован к текущему процессу, без необходимости поиска в таблице.
* **Важно**: Псевдо-дескриптор **не нужно** закрывать с помощью `CloseHandle()`.
* Если процессу требуется *настоящий* дескриптор самого себя (например, для передачи другому процессу), он создается через функцию `DuplicateHandle()`.
