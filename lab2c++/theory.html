Тема 1 • Задание 1 из Word

Венгерская нотация и типы Win32

Что это

Венгерская нотация — соглашение об именах переменных в Win32 API: имя начинается с префикса из строчных букв, который подсказывает тип или назначение переменной. Префикс — это не часть типа, а только подсказка для читающего код; компилятор на него не смотрит.

Нотация появилась во времена C без строгой типизации, когда перепутать указатель и число было легко. В современном C++ её роль меньше, но весь Win32 API написан именно так, поэтому префиксы надо уметь читать.

Типы Win32 из задания 1

LPCSTR = const char* — указатель на константную ANSI-строку (L — long pointer, P — pointer, C — const, STR — string). Буква C означает «только чтение»: через такой указатель строку менять нельзя.

LPVOID = void* — нетипизированный указатель на любой буфер. Его нельзя разыменовать напрямую: сначала надо привести к конкретному типу.

HMODULE — дескриптор загруженного модуля (.exe или .dll); по сути базовый адрес модуля в памяти, в Win32 равен HINSTANCE, а тот — HANDLE.

DWORD = unsigned long — 32-битное беззнаковое целое. Всегда 4 байта и в x86, и в x64 — это важно для темы усечения ниже.

Типичная ошибка: читать префикс как тип. cbSize — это не «тип cb», а обычное 32-битное число, у которого имя подсказывает, что в нём хранится размер в байтах. И наоборот: переменная без префикса может иметь любой тип — префикс ни к чему не обязывает компилятор.

Тема 2 • task1_types_sizeof.cpp

Модели данных и sizeof: x86 / x64, LLP64

Что это

Модель данных — это правило, какой размер в байтах имеет каждый базовый тип на данной платформе. Стандарт C++ фиксирует только соотношения (например, sizeof(char) == 1, sizeof(long) >= sizeof(int)), а точные размеры выбирает платформа. Поэтому одна и та же программа на разных системах может видеть разные размеры типов.

sizeof — оператор, который возвращает размер типа или переменной в байтах. Он вычисляется во время компиляции (для обычных типов) и не выполняет свой операнд: sizeof(a++) не увеличит a.

МодельГде действуетintlonglong longуказатель
ILP32Windows x86, Linux x864484
LLP64Windows x644488
LP64Linux / macOS x644888
Ключевые правила

1. В Windows x64 действует LLP64: long остаётся 4 байта, а растут только long long и указатели. Microsoft сделала так, чтобы миллионы строк 32-битного кода продолжали компилироваться без правок.

2. В Linux x64 — LP64: long равен 8 байтам. Тот же код, скомпилированный под Linux, даст другой sizeof(long). Размеры типов нельзя заучивать «вообще» — только для конкретной платформы.

3. Типы ULONG_PTR, DWORD_PTR, INT_PTR — это целые числа «шириной с указатель»: 4 байта в x86 и 8 байт в x64. Они существуют именно для безопасного хранения адресов в целых числах (см. следующую тему).

4. DWORD и LONG — всегда 4 байта, в обеих архитектурах. Поэтому их нельзя использовать для хранения указателей.

Типичная ошибка: считать, что long — это «длинное, значит 8 байт». В Windows это неверно: sizeof(long) == 4 и в x86, и в x64. Для гарантированных 8 байт нужен long long или int64_t.

Применяется в: 1_lab2_word/task1_types_sizeof.cpp — программа печатает реальные размеры на машине, где запущена; запустите её в x86- и x64-сборках и сравните вывод.

Тема 3 • task2_ptr_truncation_fix.cpp

Усечение указателя (pointer truncation)

Что это

Указатель в x64 занимает 8 байт (64 бита адреса, например 0x00007FF7A1B2C3D4). Если записать такой адрес в 32-битное целое (DWORD, 4 байта), старшие 32 бита просто отбрасываются — адрес «усекается» до 0xA1B2C3D4. Обратное преобразование даёт уже другой, мусорный адрес.

В x86 проблемы нет: указатель и DWORD оба по 4 байта. Поэтому ошибка проявляется только при переходе на 64 бита — классический баг портирования старого кода.

ШагЧто происходитРезультат
Ошибочный кодDWORD t = (DWORD)lpContext; в x64Старшие 32 бита адреса потеряны; компилятор: предупреждение C4311
Обратный кастint* p = (int*)t; внутри функцииВосстановлен чужой адрес вида 0x00000000A1B2C3D4
Разыменование*p — чтение по битому адресуПадение: Access Violation, код 0xC0000005
ИсправлениеDWORD_PTR t = (DWORD_PTR)lpContext;В x64 — 8 байт, адрес цел; в x86 — 4 байта, тоже цел
Ключевые правила

1. Адрес храните только в указателе или в целом «шириной с указатель»: DWORD_PTR / ULONG_PTR / INT_PTR (Win32) или стандартном uintptr_t / intptr_t. Никогда — в DWORD, int или long.

2. reinterpret_cast<int*>(x) — явное низкоуровневое преобразование целого в указатель. Компилятор доверяет программисту и не проверяет, валиден ли адрес: проверка if (pNumber != nullptr) ловит только ноль, но не битый ненулевой адрес.

3. Предупреждение компилятора C4311 («pointer truncation») — это не косметика, а сигнал о потере данных. Сборка с /W4 и отношение к предупреждениям как к ошибкам (/WX) ловят такие баги до запуска.

Типичная ошибка: «на моём компьютере работает». Усечённый адрес может случайно указывать на доступную память, и программа проработает, пока не получит другой адрес (например, после перезапуска из-за ASLR — случайного базового адреса). Баг плавающий, поэтому его ловят по предупреждению компилятора, а не по тестам.

Применяется в: 1_lab2_word/task2_ptr_truncation_fix.cpp — исправленная версия: параметр ProcessData и переменная SAFE_PTR имеют тип DWORD_PTR.

Тема 4 • task3_kernel_handles.cpp

Хэндлы объектов ядра Windows (HANDLE)

Что это

Ядро Windows не даёт программам прямых указателей на свои внутренние структуры — это дыра в безопасности. Вместо этого программа получает хэндл (HANDLE) — небольшое число, индекс в таблице дескрипторов процесса. По этому индексу ядро само находит объект (файл, событие, процесс, поток и т.д.).

Хэндл — не адрес и не «магическое число»: его нельзя разыменовать, с ним нельзя делать арифметику. Это просто «пропуск», который предъявляют системным функциям.

ФункцияЧто создаёт / возвращаетОшибкаЗакрывать?
CreateFileWХэндл файла (объект ядра File)INVALID_HANDLE_VALUE (−1)Да, CloseHandle
CreateEventWХэндл события (объект ядра Event)NULL (0)Да, CloseHandle
GetCurrentProcessПсевдо-хэндл текущего процесса (−1)Не бываетНет, никогда
Ключевые правила

1. Почему хэндлы малы и кратны 4. Записи таблицы дескрипторов идут с шагом 4 байта, а 2 младших бита хэндла зарезервированы ядром под служебные флаги. Поэтому реальные хэндлы — 4, 8, 12, 16… (0x4, 0x8, 0xC, 0x10…). Это индекс, а не адрес.

2. Псевдо-хэндл −1. GetCurrentProcess() возвращает константу ((HANDLE)(LONG_PTR)-1). Записи в таблице под неё нет, счётчик ссылок не растёт. Функции Windows, увидев −1, понимают: речь о текущем процессе. Закрывать его через CloseHandle нельзя. Настоящий хэндл самого себя получают через DuplicateHandle.

3. Разные коды ошибок. CreateFileW при ошибке возвращает INVALID_HANDLE_VALUE, а большинство других функций создания (включая CreateEventW) — NULL. Проверять надо именно тот код, который документирован для конкретной функции.

4. Каждый открытый хэндл надо закрыть. Незакрытые хэндлы — утечка: объект ядра живёт, пока есть хоть один хэндл. Исключение — только псевдо-хэндлы.

5. Флаги из программы. FILE_ATTRIBUTE_TEMPORARY | FILE_FLAG_DELETE_ON_CLOSE — файл временный и удалится сам при закрытии хэндла; CREATE_ALWAYS — создать заново (или обнулить существующий); TRUE в CreateEventW — событие с ручным сбросом (manual-reset), FALSE — начальное состояние «не сигнальное».

Типичная ошибка: закрыть псевдо-хэндл (CloseHandle(GetCurrentProcess())) или проверить CreateFileW на NULL вместо INVALID_HANDLE_VALUE. Вторая ошибка опасна: при неудаче CreateFileW вернёт −1, проверка на NULL её пропустит, и программа дальше будет работать с невалидным хэндлом.

Применяется в: 1_lab2_word/task3_kernel_handles.cpp — файл temp_kernel_demo.tmp создаётся в рабочей папке и сам удаляется при закрытии хэндла.

Тема 5 • 2_lecture_hw/task1_pointers.cpp

Указатели и разыменование

Что это

Указатель — переменная, которая хранит адрес другой переменной в памяти. Указатель имеет тип: int* означает «адрес ячейки с целым числом». Сам указатель тоже занимает память: 4 байта в x86 и 8 байт в x64.

Три оператора, которые надо не путать: & — «взять адрес», * в объявлении — «это указатель», * в выражении — «разыменовать», то есть обратиться к памяти по адресу.

ВыражениеЧто делаетПример
int* p;Объявляет указатель на intСама переменная p хранит адрес
p = &a;Записывает в p адрес переменной aТеперь p «указывает на» a
*p = 30;Записывает 30 в память, на которую указывает pМеняется a, сам p не меняется
p = &b;Перенаправляет указатель на bМеняется сам p, значения a и b не меняются
int x = *p;Читает значение по адресу из pКопирует значение, на которое указывает p
Состояния памяти в лекционной задаче

Начало: a = 10, b = 20. После int* p = &a; указатель смотрит на a. После *p = 30; — a = 30, b = 20. После p = &b; указатель смотрит уже на b, а значения не меняются. После *p = 40; — a = 30, b = 40. Вывод: 30 40.

Главный вывод задачи: *p = ... меняет переменную, на которую указывает указатель, а p = ... меняет сам указатель. Это две разные операции, хотя в обеих участвует p.

Типичные ошибки: (1) разыменовать неинициализированный указатель (int* p; *p = 5; — адрес мусорный, падение); (2) перепутать p = &b и *p = b — первое перенаправляет указатель, второе копирует значение; (3) разыменовать nullptr — мгновенное падение с Access Violation.

Применяется в: 2_lecture_hw/task1_pointers.cpp, а также в 1_lab2_word/task2_ptr_truncation_fix.cpp (обратный каст и разыменование *pNumber).

Тема 6 • 2_lecture_hw/task2_strings_memory.cpp

Память строк и нуль-терминатор

Что это

Строка в C — это массив символов char, который заканчивается невидимым символом '\0' (нуль-терминатор, код 0). Именно по нему функции вроде strlen и strcat понимают, где строка кончается. Без '\0' строка — просто набор байтов неизвестной длины.

Строковый литерал "Hello" — это 6 байт в памяти: 5 букв + '\0'. Компилятор добавляет нуль автоматически.

ОбъявлениеЧто создаётсяГде лежитsizeofМожно менять?
char str[] = "Hello";Массив из 6 char (копия литерала)Стек6Да, str[0] = 'h';
const char* p = "Hello";Указатель на литералУказатель — на стеке; сам литерал — в секции констант (.rdata)8 (x64) / 4 (x86)Нет — только чтение; запись — UB
Ключевые правила

1. sizeof(массив) — размер всего массива в байтах (6). sizeof(указатель) — размер самого указателя (8 в x64), а не строки. Длину строки даёт strlen() — 5 для "Hello".

2. char str[] копирует литерал в свою память: у программы появляется своя изменяемая строка. const char* p только указывает на общий неизменяемый литерал.

3. const у указателя — это обещание не менять символы через него. Попытка записи через неконстантный указатель на литерал — неопределённое поведение (обычно падение, так как .rdata только для чтения).

Типичная ошибка: думать, что sizeof(p) — это длина строки. Нет: длина строки — strlen(p), а sizeof(p) — всегда 8 (x64) для любого указателя, хоть на строку из 5 символов, хоть из 5000.

Применяется в: 2_lecture_hw/task2_strings_memory.cpp (вывод 6 8 в x64, 6 4 в x86), а также во всех задачах практики с char[].

Тема 7 • task1_vars_discount.cpp, task2_type_casting.cpp

Переменные и приведение типов

Что это

Переменная — именованная ячейка памяти с типом. Тип решает три вещи: сколько байт занимает значение, какие операции с ним допустимы и как компилятор преобразует его при смешивании с другими типами. int — целое (4 байта), double — вещественное двойной точности (8 байт).

Приведение типов (cast) — явное или неявное преобразование значения из одного типа в другой. Явное пишется программистом (static_cast<double>(a)), неявное компилятор делает сам по правилам языка.

Выражение (a = 7, b = 3)Тип операцииРезультатПочему
a / bЦелочисленное деление2 (тип int)Оба операнда int — дробная часть отбрасывается, остаток 1 теряется
static_cast<double>(a) / bВещественное деление2.333333… (тип double)Один операнд double — второй неявно приводится к double (usual arithmetic conversions)
(double)a / bТо же, C-style каст2.333333…Эквивалентно, но static_cast виднее и безопаснее
price * (1.0 - discount)Смешанная арифметика297.5 (тип double)int приводится к double, потому что второй операнд — double
Ключевые правила

1. Целочисленное деление отбрасывает дробь, а не округляет. 7 / 3 == 2, а не 2.33 и не 2.5. Если нужен остаток — оператор % (7 % 3 == 1).

2. Достаточно привести один операнд. Как только один операнд деления стал double, второй приводится автоматически. Кастовать оба не нужно.

3. static_cast<double>(a) лучше C-style (double)a: его видно в коде, его ищет поиск, и он не делает неожиданных низкоуровневых преобразований (в отличие от reinterpret_cast).

4. Форматирование вывода. std::fixed + std::setprecision(n) из <iomanip> задают ровно n знаков после запятой. Манипуляторы «липкие»: действуют на все последующие выводы вещественных чисел, пока их не изменят. Сами значения они не округляют — только отображение.

5. Деньги и double. В учебных задачах скидка в double допустима, но в реальных расчётах деньги в вещественных числах не хранят (0.1 + 0.2 ≠ 0.3 из-за двоичных дробей) — хранят копейки в int и делят на 100 только при выводе.

Типичная ошибка: double x = a / b; при a = 7, b = 3 даст 2.0, а не 2.333: деление выполняется до присваивания, пока оба операнда ещё int. Приводить надо операнды деления, а не его результат.

Применяется в: 3_practice_hw/task1_vars_discount.cpp (сдача, скидка 15%, вывод с 2 знаками), 3_practice_hw/task2_type_casting.cpp (деление 7/3 и вывод с 3 знаками).

Тема 8 • task3_char_reading.cpp

getchar и посимвольный ввод

Что это

getchar() (из <cstdio>) читает из стандартного ввода stdin ровно один символ и возвращает его код. Это самый низкий уровень символьного ввода в C: никакого разбора чисел или слов — только байты один за другим.

Цикл while ((ch = getchar()) != '\n' && ch != EOF) — классический идиом: читать, пока не встретится конец строки (нажатие Enter даёт '\n') или конец ввода.

ВопросОтвет
Почему ch — int, а не char?getchar() должен вернуть любое значение символа (0–255) плюс особое значение EOF (обычно −1) для конца ввода. В char эти значения не помещаются одновременно: −1 совпал бы с символом 0xFF. Поэтому тип возвращаемого значения — int.
Что такое EOF?Константа «конец файла/ввода» (обычно −1). В консоли Windows её посылают клавишами Ctrl+Z, затем Enter; в Linux/macOS — Ctrl+D.
Зачем скобки вокруг присваивания?Присваивание = имеет низкий приоритет: без скобок ch = getchar() != '\n' прочиталось бы как ch = (getchar() != '\n') и в ch попал бы 0 или 1. Скобки заставляют сначала присвоить символ, потом сравнить.
Почему символы приходят только после Enter?Консоль Windows буферизует ввод построчно: программа получает символы, только когда пользователь нажал Enter. Это свойство терминала, а не getchar(). Для чтения клавиш без Enter нужны другие функции (_getch()).
Что делает if (ch == ' ')?Сравнивает код символа с кодом пробела (ASCII 32) и увеличивает счётчик. Табуляция ('\t') и другие пробельные символы пробелом не считаются.
Типичные ошибки: (1) char ch; вместо int ch; — тогда EOF (−1) неотличим от символа с кодом 255, и цикл может не завершиться или завершиться раньше времени; (2) забытые скобки в while (ch = getchar() != '\n') — присваивается результат сравнения, а не символ; (3) смешивание getchar() и std::cin без синхронизации — потоки C и C++ могут конфликтовать.

Применяется в: 3_practice_hw/task3_char_reading.cpp — программа интерактивная: ждёт ввода строки и считает в ней пробелы.

Тема 9 • task4_num_to_string.cpp, task4b_move_letter_n.cpp

sprintf, strcat и безопасность строк

Что это

В C нет встроенного типа «строка»: строка — это массив char с нулём на конце, а работа с ней — это функции из <cstring> и <cstdio>. Две главные здесь: sprintf (форматированный вывод в массив вместо экрана) и strcat (дописывание одной строки в конец другой).

ФункцияЧто делаетЧто важно знать
sprintf(buf, "%d", ID)Пишет число ID как текст в массив buf и добавляет '\0'"%d" — формат десятичного целого; результат для 245 — символы '2','4','5','\0'
strcat(dst, src)Ищет '\0' в dst и копирует туда src вместе с её '\0'В dst должно быть достаточно места, иначе — переполнение буфера
strncat(dst, src, n)Как strcat, но копирует не более n символовВ задаче 4b — копирование начала слова без буквы «н»
strstr(haystack, needle)Ищет подстроку, возвращает указатель на неё или nullptrВ задаче 4b — поиск буквы «н» в слове «Клиент»
strlen(s)Длина строки в байтах (без '\0')Для «н» в UTF-8 вернёт 2 — это байты, а не символы
Ключевые правила

1. Запас памяти обязателен. char clientStr[128] = "Клиент №"; — массив в разы больше строки, чтобы strcat было куда дописывать. Массив «впритык» под исходную фразу дал бы переполнение буфера (Buffer Overflow) и падение или порчу соседних данных.

2. _CRT_SECURE_NO_WARNINGS — до всех #include. MSVC считает sprintf/strcat небезопасными и выдаёт предупреждение C4996. Макрос отключает его. Строка должна стоять самой первой в файле — иначе не сработает. В MinGW (g++) макрос ни на что не влияет и безвреден.

3. Безопасные аналоги. В современном коде вместо sprintf используют snprintf (с лимитом размера), вместо strcat — strcat_s (MSVC) или вообще std::string и std::to_string(ID). В учебных задачах старые функции допустимы, но про их опасность надо знать.

4. Байты ≠ символы в UTF-8. Русские буквы в UTF-8 занимают по 2 байта: «н» — это байты 0xD0 0xBD. Поэтому strlen("н") == 2, арифметика указателей (posN - clientStr) считает байты, и strncat(result, clientStr, 8) копирует 4 буквы «Клие» (8 байт). Задача 4b целиком построена на этом: «н» вырезается по байтовым смещениям, а не по номерам символов.

5. const char[] не меняется. В задаче 4b исходная строка объявлена const и собирается новая строка result — это и есть требование задачи («исходную переменную не трогаем»).

Типичные ошибки: (1) strcat в массив без запаса — переполнение; (2) забытый '\0' в массиве, заполненном вручную, — функции строк читают дальше по памяти; (3) считать strlen числом символов для русского текста — это байты; (4) sprintf без проверки размера буфера — число может не влезть (для int достаточно 12 байт, в задачах взят запас 32).

Применяется в: 3_practice_hw/task4_num_to_string.cpp («Клиент №245»), 3_practice_hw/task4b_move_letter_n.cpp («нКлиет245», исходная строка не изменена).

Общий раздел

Условия запуска: компиляторы, команды, требования

Чем компилировать

MSVC (Visual Studio, Windows): открыть «Developer Command Prompt for VS», перейти в папку с файлом и собрать командой cl /EHsc /W4 имя.cpp. Флаг /W4 включает предупреждения (ловит, например, C4311 про усечение указателя). Получится имя.exe в той же папке.

MinGW-w64 (g++, Windows): g++ -Wall -Wextra -o имя.exe имя.cpp. windows.h и Win32 API в MinGW-w64 есть, поэтому задачи 1–3 из лабы собираются и там.

Запуск: в cmd — имя.exe, в PowerShell — .\имя.exe. Запускать из папки с исходником, чтобы видеть файлы, которые создаёт программа (задача с хэндлами).

Кодировка: во всех Win32-программах лабы стоит system("chcp 65001 > nul") — консоль переключается на UTF-8, чтобы русский текст выводился правильно. Исходники должны быть сохранены в UTF-8. Если в консоли вместо букв знаки вопроса — проверьте кодировку файла и шрифт консоли.

Что сломается, если что-то не так

— «windows.h: No such file» — задача собирается не под Windows (или в MinGW не установлен пакет win32). Переносимые задачи (лекция, практика) собираются везде, Win32-задачи — только под Windows.

— Предупреждение C4996 про sprintf/strcat — в MSVC без первой строки #define _CRT_SECURE_NO_WARNINGS сборка задач 4 и 4b даст предупреждение (с /WX — ошибку). Макрос уже стоит в файлах, не удаляйте его.

— Кракозябры вместо русского текста — исходник сохранён не в UTF-8 или консоль не в UTF-8. Сохраните файл в UTF-8 и убедитесь, что выполняется chcp 65001.

— Задача 3 (хэндлы): CreateFile вернул ошибку — нет прав на запись в рабочей папке. Запустите из папки, куда разрешена запись (например, папки с исходником), а не из системного каталога.

— Задача 3 (getchar): программа «висит» — она ждёт ввода. Введите текст и нажмите Enter; завершить ввод без Enter нельзя (консоль буферизует построчно).
