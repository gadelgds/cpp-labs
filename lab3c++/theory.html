1. Асинхронный I/O, OVERLAPPED и события (hEvent)

Что это

Обычный (синхронный) вызов ReadFile возвращает управление только после того, как данные уже в памяти. Асинхронный вызов возвращает управление сразу, а данные дочитываются в фоне контроллером диска по DMA. Поток в это время свободен: может делать другую работу или спать в ожидании события.

В Win32 асинхронность включается на уровне дескриптора — флагом FILE_FLAG_OVERLAPPED в CreateFileW. Без него OVERLAPPED игнорируется, и все операции синхронные. Включать флаг надо при открытии, позже его добавить нельзя.

Структура OVERLAPPED — поля

ПолеНазначение
Offset / OffsetHigh64-битное смещение операции в файле (младшие и старшие 32 бита). В асинхронном режиме у файла нет «текущего указателя» — смещение задаётся каждый раз явно.
hEventСобытие ядра, которое драйвер переведёт в сигнальное состояние по завершении операции. Может быть NULL — тогда о завершении узнают только через GetOverlappedResult.
Internal / InternalHighСлужебные поля ядра: код завершения и число переданных байт. Программой не заполняются — их пишет драйвер.
PointerЗарезервировано системой, не используется.

Как узнать, что операция завершена

СпособКак работаетКогда удобен
WaitForSingleObject(hEvent, INFINITE)Поток засыпает до сигнала события, CPU не тратится (0%).Одна операция, простое ожидание — как в задаче 1.
GetOverlappedResult(hFile, &ov, &bytes, TRUE)Сам ждёт завершения (последний аргумент TRUE) и возвращает число байт.Когда событие не создавалось вовсе.
GetOverlappedResult(…, FALSE)Не ждёт: возвращает результат уже завершённой операции.После WaitForSingleObject — как в задаче 1.
WaitForMultipleObjectsЖдёт сразу несколько событий.Много параллельных операций.
Completion Port (IOCP)Ядро само складывает завершённые операции в очередь.Серверы с тысячами операций, высшая производительность.

События: ручной и автоматический сброс

CreateEventW(NULL, TRUE, FALSE, NULL) — событие с ручным сбросом (manual-reset): после срабатывания оно остаётся сигнальным, пока его явно не погасит ResetEvent. Именно поэтому в задаче 1 перед каждым чтением и записью вызывается ResetEvent — иначе WaitForSingleObject сразу вернулся бы по старому сигналу. Событие с автоматическим сбросом (FALSE вторым аргументом) гаснет само, когда один ожидающий поток проснулся.

Ключевые правила

  • Всегда обнуляйте OVERLAPPED (memset) перед первым использованием: мусор в полях смещения — чтение не оттуда или сбой.
  • FALSE от асинхронного ReadFile/WriteFile — норма. Ошибка — только если GetLastError() != ERROR_IO_PENDING (997). Код ошибки читайте сразу после вызова.
  • Буфер нельзя трогать до завершения операции. Пока драйвер пишет в буфер по DMA, чтение из него или повторная запись дадут гонку данных. В задаче 1 поэтому чтение и запись идут строго по очереди.
  • Четвёртый аргумент ReadFile/WriteFile — NULL при OVERLAPPED: число байт забирается только через GetOverlappedResult.
  • Один OVERLAPPED — одна операция. Нельзя переиспользовать структуру, пока операция не завершена.

Типичные ошибки

  • Забыли FILE_FLAG_OVERLAPPED при открытии — операции стали синхронными, а ERROR_IO_PENDING никогда не возникает.
  • Забыли ResetEvent перед операцией — ожидание мгновенно «проходит», а данные ещё не готовы.
  • Забыли задать Offset/OffsetHigh — чтение идёт с нулевого или мусорного смещения.
  • Проверили только readRet == FALSE и решили, что это ошибка, — программа «падает» на первом же нормальном чтении.
  • Не проверили возвращаемое значение GetOverlappedResult — как в задаче 1: при сбое чтения bytesTransferred может содержать старое значение, и программа этого не заметит.

Мини-пример: чтение одного блока

HANDLE hEvent = CreateEventW(NULL, TRUE, FALSE, NULL); OVERLAPPED ov = {}; ov.hEvent = hEvent; ov.Offset = 0; ReadFile(h, buf, 4096, NULL, &ov); // FALSE + ERROR_IO_PENDING — нормально. WaitForSingleObject(hEvent, INFINITE); DWORD n = 0; GetOverlappedResult(h, &ov, &n, FALSE); // n — реально прочитано

2. NTFS MFT и атрибуты $DATA: резидентные и нерезидентные

Что это

MFT (Master File Table) — главная таблица файлов NTFS: массив записей фиксированного размера 1024 байта (1 КБ), по одной записи на каждый файл и каталог тома. Запись MFT — не сами данные, а «паспорт» файла: заголовок и набор атрибутов.

Основные атрибуты записи MFT

АтрибутЧто хранит
$STANDARD_INFORMATIONВремя создания/изменения, атрибуты файла (скрытый, системный и т.д.).
$FILE_NAMEИмя файла, ссылка на родительский каталог.
$DATAСодержимое файла — резидентно или нерезидентно (см. ниже).
$SECURITY_DESCRIPTORПрава доступа (ACL).
$ATTRIBUTE_LISTСписок продолжений, если атрибуты не влезли в одну запись MFT.

Резидентный и нерезидентный $DATA

Резидентный (Resident)Нерезидентный (Non-Resident)
Где данныеПрямо внутри 1024-байтной записи MFT.В отдельных кластерах тома, вне MFT.
Что в MFTСами байты файла.Список Data Runs — цепочек кластеров (экстентов).
КогдаФайл маленький: после заголовка и служебных атрибутов остаётся свободное место. На практике порог около 700 байт (зависит от длины имени и других атрибутов).Файл не помещается в свободное место записи.

Пример из задачи 2200 байт.2500 байт и 500 КБ.

Важно: порог резидентности — не ровно 1024 и не ровно 700 байт. Запись MFT занята заголовком, $STANDARD_INFORMATION, $FILE_NAME и заголовком самого $DATA, поэтому свободного места обычно около 700 байт, и точное значение зависит от длины имени файла и наличия других атрибутов. Поэтому 200 байт — заведомо резидентно, а 2500 — заведомо нет.

Data Runs и экстенты: VCN и LCN

Нерезидентный файл описывается цепочками непрерывных кластеров — экстентами (Data Runs). У каждого экстента два номера: LCN (Logical Cluster Number — номер первого физического кластера цепочки на томе) и NextVCN (Virtual Cluster Number — логический номер кластера внутри файла, с которого начинается следующая цепочка). Один экстент — файл лежит подряд; много экстентов — файл фрагментирован.

Как это проверяется в задаче 2

DeviceIoControl(hFile, FSCTL_GET_RETRIEVAL_POINTERS, …) просит драйвер NTFS вернуть карту кластеров файла в структуру RETRIEVAL_POINTERS_BUFFER (поля ExtentCount и массив Extents[] с Lcn и NextVcn). Для резидентного файла карты нет — драйвер возвращает ошибку ERROR_HANDLE_EOF (код 38). Программа использует этот код как признак резидентности: это не сбой, а диагностический сигнал.

Типичные ошибки и заблуждения

  • Считать порог резидентности ровно 1024 байта. Нет: часть записи занята служебными данными, порог ниже и плавает.
  • Считать ERROR_HANDLE_EOF сбоем программы. В этом контексте это ожидаемый ответ «кластеров нет».
  • Запускать на FAT32/exFAT и ждать того же поведения: там нет MFT и нет резидентных атрибутов, коды ошибок будут другими.
  • Думать, что резидентный файл «не занимает места вообще»: он занимает место в самой MFT (запись 1 КБ выделяется под файл в любом случае).
  • Выходной буфер outBuf[1024] в задаче 2 вмещает лишь несколько экстентов; у сильно фрагментированного файла DeviceIoControl вернёт ERROR_MORE_DATA — код это не обрабатывает.
3. Физический размер файла: кластеры и slack

Что это

У файла два размера. Логический размер — сколько байт данных записано (то, что показывает GetFileSizeEx и проводник в графе «Размер»). Физический размер («размер на диске») — сколько байт реально выделено на томе под данные файла вне MFT (то, что показывает проводник в графе «Размер на диске» и возвращает AllocationSize из FILE_STANDARD_INFO). Они почти никогда не равны.

Кластер — минимальная единица выделения

NTFS выделяет место кластерами — блоками обычно по 4096 байт (4 КБ) при стандартном форматировании. Файл занимает целое число кластеров, даже если его данные меньше одного кластера. Неиспользованный остаток последнего кластера называется slack (хвост): он принадлежит файлу, но данных в нём нет.

Логический размерРезидентностьФизический размер (кластер 4 КБ)Пояснение
200 байтРезидентный0 байтДанные внутри записи MFT, кластеры не выделялись (кейс 1 задачи 3).
2000 байтНерезидентный4096 байтОдин кластер 4 КБ, slack = 2096 байт (кейс 2 задачи 3).
4096 байтНерезидентный4096 байтРовно один кластер, slack = 0.
4097 байтНерезидентный8192 байтДва кластера: один байт переполнил первый, slack = 4095 байт.
0 байт (пустой файл)Резидентный0 байтДанных нет, кластеры не нужны.

Ловушка GetCompressedFileSizeW — почему старый код врал

Несмотря на слово Compressed в имени, для обычного (несжатого, не разреженного) файла функция возвращает логический размер, как GetFileSize. Так написано в самой документации Microsoft: «If the file is not compressed or a sparse file, the value obtained is the actual file size, the same as the value returned by a call to GetFileSize». Реальный размер на диске она даёт только для сжатых и разреженных файлов. Поэтому старый вариант задачи 3 печатал 200 и 2000 вместо правильных 0 и 4096 — это не баг Windows, а задокументированное поведение функции с вводящим в заблуждение именем. Проводник поступает так же: GetCompressedFileSize он вызывает только для сжатых и разреженных файлов, а для обычных округляет логический размер вверх до кластера (так описано у Raymond Chen в статье «Just What Is \'Size on Disk?\'»).

Прямой путь: AllocationSize

Правильный замер — спросить у самой NTFS, сколько места выделено: GetFileInformationByHandleEx(hFile, FileStandardInfo, &stdInfo, sizeof(stdInfo)), поле FILE_STANDARD_INFO.AllocationSize. Для резидентного файла оно равно 0, для нерезидентного — числу кластеров × размер кластера (2000 байт → 4096 при кластере 4 КБ). Запрос делается по открытому хэндлу, до CloseHandle. Альтернативный прямой путь — как у проводника: GetDiskFreeSpace (размер кластера) + округление логического размера вверх до кластера, а резидентность проверять через FSCTL_GET_RETRIEVAL_POINTERS, как в задаче 2 (ошибка ERROR_HANDLE_EOF означает «резидентный», то есть 0 байт). Возвращает функция младшие 32 бита; старшие 32 бита — через второй параметр (highSize). При ошибке возвращается INVALID_FILE_SIZE (0xFFFFFFFF), и тогда надо проверять GetLastError() — в задаче 3 эта проверка теперь есть.

Почему «размер на диске» зависит от тома

  • Размер кластера задаётся при форматировании: 4 КБ — стандарт, но бывает 512 байт, 8 КБ, 64 КБ. Файл 2000 байт на томе с кластером 8 КБ займёт 8192 байта.
  • Сжатие NTFS: на сжатом томе физический размер меньше логического.
  • Разреженные файлы (sparse): нулевые области не занимают кластеры, физический размер может быть много меньше логического.
  • Резидентность: маленькие файлы на NTFS занимают 0 байт вне MFT, а на FAT32 — целый кластер.

Типичные ошибки

  • Путать логический и физический размеры: «файл 2000 байт» не означает «2000 байт на диске».
  • Верить имени GetCompressedFileSizeW: для обычных файлов она возвращает логический размер, а не размер на диске.
  • Забывать про старшую часть размера (highSize): для файлов больше 4 ГБ младших 32 бит недостаточно.
  • Сравнивать «размер на диске» между разными томами без учёта размера кластера.
  • Ожидать 0 байт для маленького файла на любом диске: это свойство только NTFS.
4. Синхронный и асинхронный вызовы, блокировка потока

Что это

Синхронный вызов (ReadFile без FILE_FLAG_OVERLAPPED) не возвращает управление, пока операция не завершена. Асинхронный — возвращает сразу, завершение отслеживается отдельно (событие, GetOverlappedResult, IOCP).

Что происходит с потоком при синхронном чтении

  1. Поток вызывает ReadFile и уходит в ядро (системный вызов).
  2. Ядро формирует пакет IRP (I/O Request Packet) и передаёт его драйверу диска.
  3. Драйвер ставит запрос в очередь устройства; данных ещё нет — ждать надо.
  4. Планировщик переводит поток из состояния Running в Waiting (Blocked): поток не получает квантов CPU и не выполняет ни одной инструкции.
  5. Контроллер диска по DMA кладёт данные в память и генерирует прерывание.
  6. Драйвер завершает IRP, планировщик переводит поток в Ready, затем в Running — ReadFile возвращает управление.

Таблица состояний потока

СостояниеЧто делает потокПример из задачи 4
RunningВыполняется на ядре CPU.Печать тиков 1–4.
ReadyГотов к выполнению, ждёт свободного ядра.Краткий переход после завершения чтения.
Waiting (Blocked)Спит, не получает CPU, пока не наступит событие.Пауза между тиком 5 и сообщением о завершении ReadFile.

Почему зависает GUI

Классическое однопоточное GUI-приложение обрабатывает сообщения (клики, перерисовка, таймеры) в том же потоке, где вызывается чтение. Пока поток в Waiting, очередь сообщений не разбирается: окно не перерисовывается, кнопки не нажимаются, Windows помечает окно как «Не отвечает». Именно это имитирует задача 4: тики — это «пульс» потока интерфейса, а замер тиков на 5-м шаге — момент зависания.

Как решают проблему блокировки на практике

  • Асинхронный I/O (задача 1): тот же поток не блокируется чтением.
  • Отдельный рабочий поток: тяжёлое чтение уходит в фоновый поток, GUI-поток остаётся свободным.
  • Пул потоков / IOCP: много операций без привязки потока к каждой.
  • Чтение порциями: вместо одного ReadFile на 64 МБ — цикл по маленьким блокам с проверкой «не пора ли обработать сообщения» между блоками.

Типичные ошибки

  • Думать, что «поток завис» означает «программа сломалась»: поток в Waiting — нормальное состояние, он проснётся сам, когда данные будут готовы.
  • Делать синхронное чтение в потоке GUI «на чуть-чуть»: на HDD или при холодном кэше «чуть-чуть» превращается в секунды зависания.
  • Не проверять возвращаемое значение ReadFile: в задаче 4 при ошибке чтения bytesRead останется 0, а программа напечатает «Прочитано 0 МБ» как успех.
  • Ожидать видимую паузу на любом диске: на NVMe SSD с тёплым кэшем чтение 64 МБ нулей занимает миллисекунды, пауза почти незаметна.
5. Общие условия запуска всех программ

Что нужно для запуска любой из четырёх программ

  • Только Windows (Windows 10/11, x64): все программы используют Win32 API (windows.h). На Linux/macOS не компилируются.
  • Компилятор: MSVC (cl /EHsc /W4 файл.cpp в Developer Command Prompt for VS) или MinGW-w64 (g++ -O2 -o файл.exe файл.cpp). Флаги и библиотеки по умолчанию: дополнительных .lib не требуется, все вызовы — из kernel32.
  • Рабочая папка: все пути в программах относительные — файлы создаются в текущей папке, откуда запущен exe. Запускайте из папки с exe (в cmd/PowerShell), а не двойным кликом: при двойном клике окно консоли закроется сразу после завершения, и вывод не прочитать.
  • Том NTFS: обязателен для задач 2 и 3 (MFT, резидентные атрибуты). Задачи 1 и 4 работают на любом томе, но файлы разумно держать на NTFS.
  • Русский вывод: программы сами переключают консоль в UTF-8 (chcp 65001 + _setmode); шрифт консоли должен поддерживать кириллицу (обычно Consolas).
