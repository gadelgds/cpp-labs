Шаг 1Строки 1–5
#include <windows.h> … <iomanip>

Подключают заголовки: <windows.h> — весь Win32 API (HANDLE, CreateFileW, OVERLAPPED); <iostream> — std::wcout; <io.h> и <fcntl.h> — _fileno и _setmode для UTF-8; <iomanip> — std::fixed и std::setprecision для вывода прогресса с одним знаком после запятой. Без windows.h нет ни одного вызова из программы. _setmode нужен, потому что программа выводит русский текст через wcout, а консоль Windows по умолчанию не в UTF-8.

Шаг 2Строки 6–7
const DWORD CHUNK_SIZE = 64 * 1024; // 64 КБ

Константа: один блок копирования — 65 536 байт (64 КБ). Используется и как размер буфера, и как размер одной операции чтения/записи. 64 КБ — удобный размер: кратен странице памяти (4 КБ) и кластеру диска, буфер помещается в кэш, а операций на 1 ГБ получается 16 384 — не слишком много и не слишком мало.

Шаг 3Строки 8–11
bool CreateDummyFile(const wchar_t* path, DWORD sizeMB) { HANDLE hFile = CreateFileW(…)

Функция создаёт тестовый файл заданного размера в мегабайтах. Открывает (создаёт заново) файл по широкому пути path только на запись, без совместного доступа (третий аргумент 0), с флагом CREATE_ALWAYS. Вынесена в отдельную функцию, чтобы main не загромождать созданием файла. CREATE_ALWAYS означает: если файл уже есть — его содержимое стирается. 0 в совместном доступе — пока файл создаётся, никто другой его не откроет.

Шаг 4Строки 12
if (hFile == INVALID_HANDLE_VALUE) return false;

Проверка: если CreateFileW не смог создать файл (нет прав, неверный путь, диск переполнен), функция сразу возвращает false. HANDLE при ошибке равен INVALID_HANDLE_VALUE, а не NULL. Без проверки следующие вызовы работали бы с битым дескриптором.

Шаг 5Строки 13–16
LARGE_INTEGER liSize; liSize.QuadPart = (LONGLONG)sizeMB * 1024 * 1024;

Считает размер файла в байтах: мегабайты × 1024 × 1024. Результат кладётся в 64-битное поле QuadPart структуры LARGE_INTEGER. Размер 1024 МБ = 1 073 741 824 байт — не влезает в 32-битный DWORD (максимум ~4 ГБ, но здесь важен именно 64-битный тип для SetFilePointerEx). Приведение к LONGLONG защищает от переполнения при умножении в 32 битах.

Шаг 6Строки 17–18
if (!SetFilePointerEx(hFile, liSize, NULL, FILE_BEGIN) || !SetEndOfFile(hFile)) {

Ключевой приём: указатель файла переставляется на позицию liSize от начала (FILE_BEGIN), а SetEndOfFile обрезает/расширяет файл до текущей позиции. Файл мгновенно становится нужного размера. Так файл на 1 ГБ создаётся за доли секунды: байты не записываются по одному, NTFS просто помечает размер в MFT, а содержимое — нули. Писать 1 ГБ нулей циклом было бы в сотни раз дольше.

Шаг 7Строки 19–21
CloseHandle(hFile); return false; }

Ветка ошибки: если переставить указатель или задать конец файла не удалось, дескриптор закрывается и возвращается false. Открытый дескриптор нельзя бросать: незакрытый HANDLE — утечка ресурса ядра, а файл останется заблокированным.

Шаг 8Строки 22–24
CloseHandle(hFile); return true; }

Успешный путь: дескриптор закрывается, функция возвращает true — файл создан. Файл создаётся и тут же закрывается: дальше его откроет main уже на чтение. Разделение «создал — закрыл — открыл заново» упрощает логику.

Шаг 9Строки 25–26
int main() {

Точка входа консольной программы. Возвращаемое int станет кодом завершения процесса: 0 — успех, 1 — ошибка (см. return 1 ниже).

Шаг 10Строки 27–30
#if defined(_WIN32) system("chcp 65001 > nul"); _setmode(_fileno(stdout), _O_U8TEXT); #endif

Настройка UTF-8 для консоли: chcp 65001 переключает кодовую страницу консоли в UTF-8, а _setmode переводит stdout в текстовый UTF-8-режим, чтобы wcout печатал русские буквы, а не кракозябры. Весь вывод программы — через std::wcout с широкими строками L"…". Без этих двух строк русский текст в консоли Windows отобразился бы неверно. #if defined(_WIN32) — защита: на другой системе эти вызовы не компилируются.

Шаг 11Строки 31–35
const wchar_t* srcPath = L"source_large.dat"; const wchar_t* dstPath = L"destination_copy.dat"; std::wcout << L"=== АСИНХРОННОЕ КОПИРОВАНИЕ…" …

Имена файлов — относительные (без пути): оба файла лежат в текущей рабочей папке, откуда запущен exe. Затем печатается заголовок программы. Относительный путь означает: результат зависит от того, из какой папки запустили программу. Запуск из другой папки создаст файлы там, а не рядом с exe.

Шаг 12Строки 36–40
WIN32_FIND_DATAW findData; HANDLE hFind = FindFirstFileW(srcPath, &findData); if (hFind == INVALID_HANDLE_VALUE) {

Проверка существования исходника: FindFirstFileW ищет файл source_large.dat. Если дескриптор поиска равен INVALID_HANDLE_VALUE — файла нет, заходим в ветку создания. Файл на 1 ГБ создаётся только при первом запуске. При повторном запуске готовый файл переиспользуется, и программа не тратит время и место заново. WIN32_FIND_DATAW — структура, куда поиск кладёт данные о найденном файле (здесь её содержимое не используется).

Шаг 13Строки 41–46
std::wcout << L"Создание тестового файла на 1024 МБ…"; if (!CreateDummyFile(srcPath, 1024)) { … return 1; } std::wcout << L"Тестовый файл успешно создан.";

Если исходника не было: сообщение, вызов CreateDummyFile на 1024 МБ. При неудаче — печать кода ошибки GetLastError() и выход с кодом 1. При успехе — подтверждение. return 1 — сигнал оболочке/скрипту, что программа завершилась ошибкой. GetLastError() сразу после неудачного вызова даёт код Win32-ошибки (например, 112 — нет места на диске).

Шаг 14Строки 47–49
} else { FindClose(hFind); }

Ветка «файл уже есть»: закрывается дескриптор поиска FindFirstFileW. FindClose обязателен: иначе дескриптор поиска останется открытым до конца процесса. Содержимое найденного файла не проверяется — файл любого размера и содержимого будет просто скопирован.

Шаг 15Строки 50–52
// 1. Открытие исходного файла … HANDLE hSrc = CreateFileW(

Начало открытия исходника на чтение. Комментарий «1.» нумерует шаги алгоритма. Порядок важен: сначала источник, потом приёмник — если источник не откроется, приёмник создавать бессмысленно.

Шаг 16Строки 53–60
srcPath, GENERIC_READ, FILE_SHARE_READ, NULL, OPEN_EXISTING, FILE_FLAG_OVERLAPPED, NULL

Аргументы CreateFileW: путь; только чтение; разрешён совместный доступ на чтение другим процессам; без атрибутов безопасности (NULL); открыть существующий файл (OPEN_EXISTING — не создавать); главный флаг FILE_FLAG_OVERLAPPED — асинхронный режим; без шаблона (NULL). FILE_FLAG_OVERLAPPED — суть задачи: без него ReadFile/WriteFile на этом дескрипторе всегда синхронные, и весь OVERLAPPED-механизм ниже не сработает. OPEN_EXISTING гарантирует, что случайно не создастся пустой файл вместо настоящего исходника. FILE_SHARE_READ позволяет, например, антивирусу параллельно читать файл.

Шаг 17Строки 61–64
if (hSrc == INVALID_HANDLE_VALUE) { … return 1; }

Проверка открытия исходника: при ошибке — сообщение с кодом GetLastError() и выход 1. Сюда попадём, например, если файл удалили между проверкой FindFirstFileW и открытием, или нет прав на чтение.

Шаг 18Строки 65–67
// 2. Создание целевого файла … HANDLE hDst = CreateFileW(

Начало создания файла-приёмника на запись. Шаг «2.» после открытия источника — симметрично, оба дескриптора нужны до начала копирования.

Шаг 19Строки 68–75
dstPath, GENERIC_WRITE, 0, NULL, CREATE_ALWAYS, FILE_FLAG_OVERLAPPED, NULL

Аргументы: путь приёмника; только запись; совместный доступ запрещён (0 — никто не откроет файл, пока идёт запись); CREATE_ALWAYS — создать новый или стереть существующий; тот же FILE_FLAG_OVERLAPPED. CREATE_ALWAYS означает потерю старого destination_copy.dat при каждом запуске — это задумано: копия всегда свежая. Запрет совместного доступа защищает недописанную копию от чтения извне.

Шаг 20Строки 76–80
if (hDst == INVALID_HANDLE_VALUE) { … CloseHandle(hSrc); return 1; }

При ошибке создания приёмника — сообщение, закрытие уже открытого исходника и выход 1. Здесь впервые видно аккуратное освобождение: hSrc уже открыт, и его нельзя бросать при выходе по ошибке. Это единственный return, где закрывается ранее открытый дескриптор.

Шаг 21Строки 81–85
LARGE_INTEGER fileSize; GetFileSizeEx(hSrc, &fileSize); std::wcout << L"Размер исходного файла: " << (fileSize.QuadPart / (1024 * 1024)) << L" МБ" …

Узнаёт точный 64-битный размер исходника и печатает его в мегабайтах (деление на 1024×1024, целочисленное — дробная часть отбрасывается). Размер нужен циклу копирования как условие остановки. GetFileSizeEx возвращает размер через структуру, а не через DWORD, поэтому корректен для файлов больше 4 ГБ.

Шаг 22Строки 86–89
HANDLE hReadEvent = CreateEventW(NULL, TRUE, FALSE, NULL); HANDLE hWriteEvent = CreateEventW(NULL, TRUE, FALSE, NULL);

Создаются два события ядра: одно для чтения, одно для записи. Аргументы: без атрибутов безопасности; TRUE — событие с ручным сбросом (manual-reset); FALSE — начальное состояние несигнальное; без имени. Событие — это флажок в ядре: драйвер диска переводит его в сигнальное состояние, когда операция завершена. Ручной сброс (TRUE) означает, что событие само не гаснет после срабатывания — его гасит только явный ResetEvent перед следующей операцией. Два отдельных события нужны, чтобы чтение и запись не путали сигналы друг друга.

Шаг 23Строки 90–91
char* buffer = new char[CHUNK_SIZE];

Выделяется буфер на 64 КБ — один на чтение и на запись по очереди. Один общий буфер — причина, почему чтение и запись идут строго по очереди: пока идёт запись, читать в тот же буфер нельзя, иначе данные перезапишутся. Для параллелизма понадобились бы два буфера (конвейер).

Шаг 24Строки 92–96
OVERLAPPED ovRead; OVERLAPPED ovWrite; memset(&ovRead, 0, sizeof(ovRead)); memset(&ovWrite, 0, sizeof(ovWrite));

Две структуры OVERLAPPED (для чтения и для записи) и их обнуление через memset. Обнуление критично: в OVERLAPPED есть служебные поля Internal/InternalHigh, которые ядро заполняет само, и поля смещения Offset/OffsetHigh. Мусор со стека в этих полях — чтение с неверного смещения или сбой операции. Обнуляют всегда, до первого использования.

Шаг 25Строки 97–99
ovRead.hEvent = hReadEvent; ovWrite.hEvent = hWriteEvent;

Каждой структуре OVERLAPPED привязывается своё событие. Именно поле hEvent связывает операцию и событие: когда драйвер завершит чтение, он просигналит hReadEvent, а когда запись — hWriteEvent. Без привязки WaitForSingleObject не узнал бы о завершении.

Шаг 26Строки 100–102
ULONGLONG currentOffset = 0; DWORD bytesTransferred = 0;

currentOffset — 64-битное смещение текущего блока от начала файла (начинаем с 0). bytesTransferred — сюда GetOverlappedResult запишет, сколько байт реально передано за операцию. 64-битное смещение обязательно: файл 1 ГБ не влезает в 32 бита смещения с запасом на будущее, а структура OVERLAPPED хранит смещение двумя DWORD (Offset + OffsetHigh).

Шаг 27Строки 103–104
std::wcout << L"Запуск асинхронного копирования блоками по " << (CHUNK_SIZE / 1024) << L" КБ..." …

Печать начала копирования с размером блока (64 КБ). Информационный вывод: пользователь видит, что программа перешла к работе, а не зависла на создании файла.

Шаг 28Строки 105–106
while (currentOffset < (ULONGLONG)fileSize.QuadPart) {

Главный цикл: повторять, пока скопировано меньше размера файла. Цикл идёт по смещению, а не по счётчику блоков: так последний неполный блок (хвост файла) обрабатывается тем же кодом.

Шаг 29Строки 107–110
DWORD bytesToRead = CHUNK_SIZE; if (currentOffset + bytesToRead > (ULONGLONG)fileSize.QuadPart) { bytesToRead = (DWORD)(fileSize.QuadPart - currentOffset); }

Размер очередного чтения: обычно полный блок 64 КБ, но если до конца файла осталось меньше — берётся только остаток. Без этой проверки последний ReadFile запросил бы байты за концом файла. Приведение к DWORD безопасно: остаток здесь заведомо меньше CHUNK_SIZE.

Шаг 30Строки 111–115
ovRead.Offset = (DWORD)(currentOffset & 0xFFFFFFFF); ovRead.OffsetHigh = (DWORD)(currentOffset >> 32); ResetEvent(hReadEvent);

Разбор 64-битного смещения на младшие 32 бита (Offset) и старшие 32 бита (OffsetHigh) и запись в ovRead. Затем событие чтения переводится в несигнальное состояние. В асинхронном режиме у файла нет текущего указателя: каждая операция читает строго по смещению из OVERLAPPED. Маска 0xFFFFFFFF отрезает младшие биты, сдвиг >> 32 даёт старшие. ResetEvent обязателен перед операцией: событие с ручным сбросом само не гаснет, и без сброса WaitForSingleObject сразу «подумал» бы, что чтение уже готово (по старому сигналу).

Шаг 31Строки 116–119
BOOL readRet = ReadFile(hSrc, buffer, bytesToRead, NULL, &ovRead);

Асинхронный вызов чтения: прочитать bytesToRead байт из hSrc по смещению из ovRead в buffer. Четвёртый аргумент NULL — при OVERLAPPED сюда нельзя передавать указатель на счётчик байт, результат будет в GetOverlappedResult. Вызов возвращает управление почти сразу, не дожидаясь диска: данные копируются в фоне контроллером по DMA, а поток свободен. Это и есть асинхронность.

Шаг 32Строки 120–122
if (!readRet && GetLastError() != ERROR_IO_PENDING) { … break; }

Проверка: ReadFile при асинхронном запуске почти всегда возвращает FALSE, но это не ошибка, а код ERROR_IO_PENDING (997) — «операция принята и выполняется». Ошибка — только любой другой код: тогда печать и выход из цикла через break. Главная ловушка для новичка: FALSE от асинхронного ReadFile — норма. Проверять надо именно GetLastError() == ERROR_IO_PENDING. Вызывать GetLastError() нужно сразу: любой следующий вызов Win32 API перезапишет код.

Шаг 33Строки 123–126
WaitForSingleObject(hReadEvent, INFINITE); GetOverlappedResult(hSrc, &ovRead, &bytesTransferred, FALSE);

Ожидание завершения чтения: поток засыпает до сигнала hReadEvent (INFINITE — без таймаута), затем GetOverlappedResult забирает у ядра фактическое число прочитанных байт в bytesTransferred. Последний аргумент FALSE — не ждать повторно, операция уже завершена. Пока поток спит в WaitForSingleObject, он не тратит CPU (0% загрузки). GetOverlappedResult — обязательный шаг: только он даёт точное число байт; для последнего блока оно меньше CHUNK_SIZE. Возвращаемое значение GetOverlappedResult здесь не проверяется — это слабое место программы (см. теорию).

Шаг 34Строки 127–128
if (bytesTransferred == 0) break;

Если прочитано 0 байт — конец файла (или сбой), цикл прерывается. Защита от бесконечного цикла: если диск вернул 0 байт, currentOffset не продвинется, и без break цикл крутился бы вечно.

Шаг 35Строки 129–133
ovWrite.Offset = ovRead.Offset; ovWrite.OffsetHigh = ovRead.OffsetHigh; ResetEvent(hWriteEvent);

Смещение для записи берётся из только что выполненного чтения (тот же блок файла), событие записи сбрасывается в несигнальное состояние. Копия пишется ровно на то же смещение, что и читалась, — иначе файл-приёмник получился бы перемешанным. Копирование полей из ovRead, а не пересчёт из currentOffset, гарантирует совпадение.

Шаг 36Строки 134–136
BOOL writeRet = WriteFile(hDst, buffer, bytesTransferred, NULL, &ovWrite);

Асинхронная запись прочитанных байт в приёмник по тому же смещению. Пишется именно bytesTransferred, а не bytesToRead. Писать надо столько, сколько реально прочитано: в последнем блоке это меньше 64 КБ, и запись лишних байт из буфера испортила бы хвост файла мусором.

Шаг 37Строки 137–140
if (!writeRet && GetLastError() != ERROR_IO_PENDING) { … break; }

Та же проверка, что и у чтения: FALSE + не ERROR_IO_PENDING — настоящая ошибка записи (например, кончилось место на диске), печать и выход из цикла. Ошибка записи чаще всего — нехватка места под destination_copy.dat: приёмнику нужен ещё 1 ГБ рядом с исходником.

Шаг 38Строки 141–144
WaitForSingleObject(hWriteEvent, INFINITE); GetOverlappedResult(hDst, &ovWrite, &bytesTransferred, FALSE);

Ожидание завершения записи и получение числа реально записанных байт. Только после этого буфер можно перезаписывать следующим чтением: запись в фоне ещё могла бы идти, и раннее чтение испортило бы данные. Здесь программа сознательно последовательна: чтение → ожидание → запись → ожидание.

Шаг 39Строки 145–146
currentOffset += bytesTransferred;

Смещение продвигается на число записанных байт. Продвижение именно на записанное (а не запрошенное) количество защищает от потери данных при короткой записи: следующий блок начнётся ровно там, где закончился предыдущий.

1. Асинхронный I/O, OVERLAPPED и события (hEvent)

Что это

Обычный (синхронный) вызов ReadFile возвращает управление только после того, как данные уже в памяти. Асинхронный вызов возвращает управление сразу, а данные дочитываются в фоне контроллером диска по DMA. Поток в это время свободен: может делать другую работу или спать в ожидании события.

В Win32 асинхронность включается на уровне дескриптора — флагом FILE_FLAG_OVERLAPPED в CreateFileW. Без него OVERLAPPED игнорируется, и все операции синхронные. Включать флаг надо при открытии, позже его добавить нельзя.

Структура OVERLAPPED — поля

ПолеНазначение
Offset / OffsetHigh64-битное смещение операции в файле (младшие и старшие 32 бита). В асинхронном режиме у файла нет «текущего указателя» — смещение задаётся каждый раз явно.
hEventСобытие ядра, которое драйвер переведёт в сигнальное состояние по завершении операции. Может быть NULL — тогда о завершении узнают только через GetOverlappedResult.
Internal / InternalHighСлужебные поля ядра: код завершения и число переданных байт. Программой не заполняются — их пишет драйвер.
PointerЗарезервировано системой, не используется.

Как узнать, что операция завершена

СпособКак работаетКогда удобен
WaitForSingleObject(hEvent, INFINITE)Поток засыпает до сигнала события, CPU не тратится (0%).Одна операция, простое ожидание — как в задаче 1.
GetOverlappedResult(hFile, &ov, &bytes, TRUE)Сам ждёт завершения (последний аргумент TRUE) и возвращает число байт.Когда событие не создавалось вовсе.

События: ручной и автоматический сброс

CreateEventW(NULL, TRUE, FALSE, NULL) — событие с ручным сбросом (manual-reset): после срабатывания оно остаётся сигнальным, пока его явно не погасит ResetEvent. Именно поэтому в задаче 1 перед каждым чтением и записью вызывается ResetEvent — иначе WaitForSingleObject сразу вернулся бы по старому сигналу. Событие с автоматическим сбросом (FALSE вторым аргументом) гаснет само, когда один ожидающий поток проснулся.

Ключевые правила

  • Всегда обнуляйте OVERLAPPED (memset) перед первым использованием: мусор в полях смещения — чтение не оттуда или сбой.
  • FALSE от асинхронного ReadFile/WriteFile — норма. Ошибка — только если GetLastError() != ERROR_IO_PENDING (997). Код ошибки читайте сразу после вызова.
  • Буфер нельзя трогать до завершения операции. Пока драйвер пишет в буфер по DMA, чтение из него или повторная запись дадут гонку данных. В задаче 1 поэтому чтение и запись идут строго по очереди.
  • Четвёртый аргумент ReadFile/WriteFile — NULL при OVERLAPPED: число байт забирается только через GetOverlappedResult.
  • Один OVERLAPPED — одна операция. Нельзя переиспользовать структуру, пока операция не завершена.

Типичные ошибки

  • Забыли FILE_FLAG_OVERLAPPED при открытии — операции стали синхронными, а ERROR_IO_PENDING никогда не возникает.
  • Забыли ResetEvent перед операцией — ожидание мгновенно «проходит», а данные ещё не готовы.
  • Забыли задать Offset/OffsetHigh — чтение идёт с нулевого или мусорного смещения.
  • Проверили только readRet == FALSE и решили, что это ошибка, — программа «падает» на первом же нормальном чтении.
  • Не проверили возвращаемое значение GetOverlappedResult — как в задаче 1: при сбое чтения bytesTransferred может содержать старое значение, и программа этого не заметит.

2. NTFS MFT и атрибуты $DATA: резидентные и нерезидентные

Что это

MFT (Master File Table) — главная таблица файлов NTFS: массив записей фиксированного размера 1024 байта (1 КБ), по одной записи на каждый файл и каталог тома. Запись MFT — не сами данные, а «паспорт» файла: заголовок и набор атрибутов.

Основные атрибуты записи MFT

АтрибутЧто хранит

$FILE_NAMEИмя файла, ссылка на родительский каталог.
$DATAСодержимое файла — резидентно или нерезидентно (см. ниже).
$SECURITY_DESCRIPTORПрава доступа (ACL).

Важно: порог резидентности — не ровно 1024 и не ровно 700 байт. Запись MFT занята заголовком, $STANDARD_INFORMATION, $FILE_NAME и заголовком самого $DATA, поэтому свободного места обычно около 700 байт, и точное значение зависит от длины имени файла и наличия других атрибутов. Поэтому 200 байт — заведомо резидентно, а 2500 — заведомо нет.

Data Runs и экстенты: VCN и LCN

Нерезидентный файл описывается цепочками непрерывных кластеров — экстентами (Data Runs). У каждого экстента два номера: LCN (Logical Cluster Number — номер первого физического кластера цепочки на томе) и NextVCN (Virtual Cluster Number — логический номер кластера внутри файла, с которого начинается следующая цепочка). Один экстент — файл лежит подряд; много экстентов — файл фрагментирован.

Как это проверяется в задаче 2

DeviceIoControl(hFile, FSCTL_GET_RETRIEVAL_POINTERS, …) просит драйвер NTFS вернуть карту кластеров файла в структуру RETRIEVAL_POINTERS_BUFFER (поля ExtentCount и массив Extents[] с Lcn и NextVcn). Для резидентного файла карты нет — драйвер возвращает ошибку ERROR_HANDLE_EOF (код 38). Программа использует этот код как признак резидентности: это не сбой, а диагностический сигнал.

Типичные ошибки и заблуждения

  • Считать порог резидентности ровно 1024 байта. Нет: часть записи занята служебными данными, порог ниже и плавает.
  • Считать ERROR_HANDLE_EOF сбоем программы. В этом контексте это ожидаемый ответ «кластеров нет».
  • Запускать на FAT32/exFAT и ждать того же поведения: там нет MFT и нет резидентных атрибутов, коды ошибок будут другими.
  • Думать, что резидентный файл «не занимает места вообще»: он занимает место в самой MFT (запись 1 КБ выделяется под файл в любом случае).
  • Выходной буфер outBuf[1024] в задаче 2 вмещает лишь несколько экстентов; у сильно фрагментированного файла DeviceIoControl вернёт ERROR_MORE_DATA — код это не обрабатывает.
3. Физический размер файла: кластеры и slack

Что это

У файла два размера. Логический размер — сколько байт данных записано (то, что показывает GetFileSizeEx и проводник в графе «Размер»). Физический размер («размер на диске») — сколько байт реально выделено на томе под данные файла вне MFT (то, что показывает проводник в графе «Размер на диске» и возвращает AllocationSize из FILE_STANDARD_INFO). Они почти никогда не равны.

Кластер — минимальная единица выделения

NTFS выделяет место кластерами — блоками обычно по 4096 байт (4 КБ) при стандартном форматировании. Файл занимает целое число кластеров, даже если его данные меньше одного кластера. Неиспользованный остаток последнего кластера называется slack (хвост): он принадлежит файлу, но данных в нём нет.

Ловушка GetCompressedFileSizeW — почему старый код врал

Несмотря на слово Compressed в имени, для обычного (несжатого, не разреженного) файла функция возвращает логический размер, как GetFileSize. Так написано в самой документации Microsoft: «If the file is not compressed or a sparse file, the value obtained is the actual file size, the same as the value returned by a call to GetFileSize». Реальный размер на диске она даёт только для сжатых и разреженных файлов. Поэтому старый вариант задачи 3 печатал 200 и 2000 вместо правильных 0 и 4096 — это не баг Windows, а задокументированное поведение функции с вводящим в заблуждение именем. Проводник поступает так же: GetCompressedFileSize он вызывает только для сжатых и разреженных файлов, а для обычных округляет логический размер вверх до кластера (так описано у Raymond Chen в статье «Just What Is \'Size on Disk?\'»).

Прямой путь: AllocationSize

Правильный замер — спросить у самой NTFS, сколько места выделено: GetFileInformationByHandleEx(hFile, FileStandardInfo, &stdInfo, sizeof(stdInfo)), поле FILE_STANDARD_INFO.AllocationSize. Для резидентного файла оно равно 0, для нерезидентного — числу кластеров × размер кластера (2000 байт → 4096 при кластере 4 КБ). Запрос делается по открытому хэндлу, до CloseHandle. Альтернативный прямой путь — как у проводника: GetDiskFreeSpace (размер кластера) + округление логического размера вверх до кластера, а резидентность проверять через FSCTL_GET_RETRIEVAL_POINTERS, как в задаче 2 (ошибка ERROR_HANDLE_EOF означает «резидентный», то есть 0 байт). Возвращает функция младшие 32 бита; старшие 32 бита — через второй параметр (highSize). При ошибке возвращается INVALID_FILE_SIZE (0xFFFFFFFF), и тогда надо проверять GetLastError() — в задаче 3 эта проверка теперь есть.

Почему «размер на диске» зависит от тома

  • Размер кластера задаётся при форматировании: 4 КБ — стандарт, но бывает 512 байт, 8 КБ, 64 КБ. Файл 2000 байт на томе с кластером 8 КБ займёт 8192 байта.
  • Сжатие NTFS: на сжатом томе физический размер меньше логического.
  • Разреженные файлы (sparse): нулевые области не занимают кластеры, физический размер может быть много меньше логического.
  • Резидентность: маленькие файлы на NTFS занимают 0 байт вне MFT, а на FAT32 — целый кластер.

Типичные ошибки

  • Путать логический и физический размеры: «файл 2000 байт» не означает «2000 байт на диске».
  • Верить имени GetCompressedFileSizeW: для обычных файлов она возвращает логический размер, а не размер на диске.
  • Забывать про старшую часть размера (highSize): для файлов больше 4 ГБ младших 32 бит недостаточно.
  • Сравнивать «размер на диске» между разными томами без учёта размера кластера.
  • Ожидать 0 байт для маленького файла на любом диске: это свойство только NTFS.
4. Синхронный и асинхронный вызовы, блокировка потока

Что это

Синхронный вызов (ReadFile без FILE_FLAG_OVERLAPPED) не возвращает управление, пока операция не завершена. Асинхронный — возвращает сразу, завершение отслеживается отдельно (событие, GetOverlappedResult, IOCP).

Что происходит с потоком при синхронном чтении

  1. Поток вызывает ReadFile и уходит в ядро (системный вызов).
  2. Ядро формирует пакет IRP (I/O Request Packet) и передаёт его драйверу диска.
  3. Драйвер ставит запрос в очередь устройства; данных ещё нет — ждать надо.
  4. Планировщик переводит поток из состояния Running в Waiting (Blocked): поток не получает квантов CPU и не выполняет ни одной инструкции.
  5. Контроллер диска по DMA кладёт данные в память и генерирует прерывание.
  6. Драйвер завершает IRP, планировщик переводит поток в Ready, затем в Running — ReadFile возвращает управление.

Почему зависает GUI

Классическое однопоточное GUI-приложение обрабатывает сообщения (клики, перерисовка, таймеры) в том же потоке, где вызывается чтение. Пока поток в Waiting, очередь сообщений не разбирается: окно не перерисовывается, кнопки не нажимаются, Windows помечает окно как «Не отвечает». Именно это имитирует задача 4: тики — это «пульс» потока интерфейса, а замер тиков на 5-м шаге — момент зависания.

Как решают проблему блокировки на практике

  • Асинхронный I/O (задача 1): тот же поток не блокируется чтением.
  • Отдельный рабочий поток: тяжёлое чтение уходит в фоновый поток, GUI-поток остаётся свободным.
  • Пул потоков / IOCP: много операций без привязки потока к каждой.
  • Чтение порциями: вместо одного ReadFile на 64 МБ — цикл по маленьким блокам с проверкой «не пора ли обработать сообщения» между блоками.

Типичные ошибки

  • Думать, что «поток завис» означает «программа сломалась»: поток в Waiting — нормальное состояние, он проснётся сам, когда данные будут готовы.
  • Делать синхронное чтение в потоке GUI «на чуть-чуть»: на HDD или при холодном кэше «чуть-чуть» превращается в секунды зависания.
  • Не проверять возвращаемое значение ReadFile: в задаче 4 при ошибке чтения bytesRead останется 0, а программа напечатает «Прочитано 0 МБ» как успех.
  • Ожидать видимую паузу на любом диске: на NVMe SSD с тёплым кэшем чтение 64 МБ нулей занимает миллисекунды, пауза почти незаметна.
5. Общие условия запуска всех программ

Что нужно для запуска любой из четырёх программ

  • Только Windows (Windows 10/11, x64): все программы используют Win32 API (windows.h). На Linux/macOS не компилируются.
  • Компилятор: MSVC (cl /EHsc /W4 файл.cpp в Developer Command Prompt for VS) или MinGW-w64 (g++ -O2 -o файл.exe файл.cpp). Флаги и библиотеки по умолчанию: дополнительных .lib не требуется, все вызовы — из kernel32.
  • Рабочая папка: все пути в программах относительные — файлы создаются в текущей папке, откуда запущен exe. Запускайте из папки с exe (в cmd/PowerShell), а не двойным кликом: при двойном клике окно консоли закроется сразу после завершения, и вывод не прочитать.

IRPЗадача 4

IRP (I/O Request Packet) — пакет, в котором Windows описывает одну операцию с диском. Когда программа читает файл, Windows создаёт IRP, передаёт его диску, а диск возвращает IRP с результатом.

LCNЗадача 2

LCN (Logical Cluster Number) — номер кластера на диске. Windows нумерует все кластеры тома подряд с нуля, и LCN говорит, где именно на диске лежит кусок файла.

MFTЗадачи 2, 3

MFT (Master File Table) — главная таблица NTFS, в ней по одной записи на каждый файл и папку. Запись хранит имя файла и его размеры, а также либо сами данные (у маленького файла), либо карту кластеров (у большого).

OVERLAPPEDЗадача 1

OVERLAPPED — структура, которую программа передаёт в ReadFile или WriteFile для асинхронного вызова. В ней лежат номер байта, с которого читать или писать, и событие hEvent, по которому Windows сообщает об окончании операции.

SlackЗадача 3

Slack — пустой хвост последнего кластера файла. Файл занимает кластер целиком, даже если его данные меньше кластера, поэтому остаток кластера принадлежит файлу, но данных в нём нет.

VCNЗадача 2

VCN (Virtual Cluster Number) — номер кластера внутри файла: первый кусок файла имеет VCN 0, второй — VCN 1, и так далее. VCN говорит, в каком порядке идут куски файла, а LCN — где каждый кусок лежит на диске.

Асинхронный вызовЗадача 1

Асинхронный вызов — вызов, после которого программа не ждёт, а сразу продолжает работу. Программа отдаёт операцию Windows и занимается своими делами, а Windows сообщает о готовности через событие hEvent. Пример из жизни: ты отправил письмо и пошёл дальше, а не стоишь у почтового ящика и не ждёшь ответа.

Блокировка потокаЗадача 4

Блокировка потока — остановка потока, пока не закончится операция. Поток — это одна линия выполнения программы: если поток читает большой файл синхронным вызовом, он стоит и ждёт, а программа на это время замирает.

КластерЗадачи 2, 3

Кластер — самый маленький кусок диска, который Windows выдаёт файлу, обычно 4096 байт. Файл всегда занимает целое число кластеров, даже если его данные меньше одного кластера. Пример: один кластер — это как одна полка: книгу тоньше полки всё равно кладут на целую полку.

Логический размерЗадача 3

Логический размер — сколько байт данных записано в файл. Это число показывает проводник в графе «Размер»: для файла из 2000 байт логический размер равен 2000.

Нерезидентный атрибутЗадача 2

Нерезидентный атрибут — часть записи MFT, которая не хранит сами данные файла, а хранит карту его кластеров. Так бывает у больших файлов: данные не помещаются в запись MFT и лежат на диске в кластерах.

Резидентный атрибутЗадача 2

Резидентный атрибут — часть записи MFT, в которой лежат сами данные файла. Так бывает у маленьких файлов: данные помещаются в запись MFT, и файл не занимает кластеров на диске.

Синхронный вызовЗадачи 1, 4

Синхронный вызов — вызов, после которого программа ждёт, пока операция закончится. Программа вызывает ReadFile и стоит, пока Windows не прочитает данные, и только потом идёт дальше. Пример из жизни: ты стоишь у кассы и ждёшь, пока кассир пробьёт товар, — уйти нельзя, пока он не закончит.

СмещениеЗадача 1

Смещение — номер байта в файле, с которого начинается чтение или запись. Смещение 0 — это самое начало файла, а смещение 4096 — байт номер 4096. Пример: как страница в книге — смещение говорит, с какого места читать.

Событие (hEvent)Задача 1

Событие (hEvent) — сигнал, которым Windows сообщает программе, что операция закончилась. Программа создаёт событие и кладёт его в OVERLAPPED, а когда Windows заканчивает чтение, она включает событие, и программа узнаёт, что данные готовы.

Физический размерЗадача 3

Физический размер (размер на диске) — сколько байт реально занято на диске под данные файла. Это число показывает проводник в графе «Размер на диске»: для файла из 2000 байт физический размер равен 4096, потому что файл занял один кластер.

Экстент (Data Run)Задача 2

Экстент (Data Run) — один непрерывный кусок файла на диске. У файла может быть несколько экстентов, если его кластеры лежат в разных местах диска, и каждый экстент описывается двумя числами: LCN, где кусок начинается, и VCN, какой это кусок по порядку.

1. Асинхронный I/O, OVERLAPPED и события (hEvent)

Что это

Синхронный вызов ReadFile возвращает управление только после того, как данные уже лежат в памяти. Асинхронный вызов возвращает управление сразу. Данные дочитываются в фоне: контроллер диска передаёт их по DMA. Поток в это время свободен. Поток делает другую работу или спит в ожидании события.

В Win32 программа включает асинхронность на уровне дескриптора. Программа передаёт флаг FILE_FLAG_OVERLAPPED в CreateFileW. Без флага Windows игнорирует OVERLAPPED, и все операции идут синхронно. Программа включает флаг при открытии файла. Позже добавить флаг нельзя.

Структура OVERLAPPED — поля

ПолеНазначение
Offset / OffsetHighДва поля задают 64-битное смещение операции в файле. Первое поле хранит младшие 32 бита. Второе поле хранит старшие 32 бита. В асинхронном режиме файл не имеет текущего указателя. Программа задаёт смещение явно при каждой операции.
hEventСобытие ядра — это hEvent. Драйвер переводит событие в сигнальное состояние, когда операция завершается. Событие может быть NULL. Тогда программа узнаёт о завершении только через GetOverlappedResult.
Internal / InternalHighПоля Internal и InternalHigh — служебные поля ядра. Internal хранит код завершения операции. InternalHigh хранит число переданных байт. Программа не заполняет эти поля. Их пишет драйвер.
PointerСистема резервирует это поле. Программа не использует это поле.

События: ручной и автоматический сброс

CreateEventW(NULL, TRUE, FALSE, NULL) создаёт событие с ручным сбросом (manual-reset). После срабатывания событие остаётся сигнальным до явного вызова ResetEvent. Поэтому задача 1 вызывает ResetEvent перед каждым чтением и записью. Без сброса WaitForSingleObject сразу вернулся бы по старому сигналу. Событие с автоматическим сбросом гаснет само, когда один ожидающий поток просыпается. Автоматический сброс включает FALSE вторым аргументом.

Ключевые правила

  • Всегда обнуляйте OVERLAPPED (memset) перед первым использованием. Мусор в полях смещения даёт чтение не оттуда или сбой.
  • FALSE от асинхронного ReadFile/WriteFile — норма. Ошибка возникает только при GetLastError() != ERROR_IO_PENDING (997). Читайте код ошибки сразу после вызова.
  • Буфер нельзя трогать до завершения операции. Пока драйвер пишет в буфер по DMA, чтение из буфера или повторная запись дают гонку данных. Поэтому задача 1 выполняет чтение и запись строго по очереди.
  • Четвёртый аргумент ReadFile/WriteFile — NULL при OVERLAPPED. Программа забирает число байт только через GetOverlappedResult.
  • Один OVERLAPPED — одна операция. Не переиспользуйте структуру, пока операция не завершена.

Типичные ошибки

  • Программа забыла FILE_FLAG_OVERLAPPED при открытии. Операции стали синхронными. ERROR_IO_PENDING никогда не возникает.
  • Программа забыла ResetEvent перед операцией. Ожидание мгновенно «проходит». Данные ещё не готовы.
  • Программа забыла задать Offset/OffsetHigh. Чтение идёт с нулевого или мусорного смещения.
  • Программа проверила только readRet == FALSE и решила, что это ошибка. Программа «падает» на первом же нормальном чтении.
  • Программа не проверила возвращаемое значение GetOverlappedResult. При сбое чтения bytesTransferred может содержать старое значение. Программа этого не заметит. Задача 1 показывает этот случай.

Мини-пример: чтение одного блока

WaitForSingleObject(hEvent, INFINITE); DWORD n = 0; GetOverlappedResult(h, &ov, &n, FALSE); // n — реально прочитано

2. NTFS MFT и атрибуты $DATA: резидентные и нерезидентные

Что это

MFT (Master File Table) — главная таблица файлов NTFS. MFT — массив записей фиксированного размера 1024 байта (1 КБ). MFT хранит одну запись на каждый файл и каталог тома. Запись MFT — не сами данные, а «паспорт» файла. Запись хранит заголовок и набор атрибутов.

Важно: порог резидентности — не ровно 1024 и не ровно 700 байт. Запись MFT занята заголовком, $STANDARD_INFORMATION, $FILE_NAME и заголовком самого $DATA. Поэтому свободного места обычно около 700 байт. Точное значение зависит от длины имени файла и наличия других атрибутов. Поэтому файл 200 байт — заведомо резидентный, а файл 2500 байт — заведомо нерезидентный.

Data Runs и экстенты: VCN и LCN

Нерезидентный файл описывается цепочками непрерывных кластеров — экстентами (Data Runs). Каждый экстент имеет два номера. LCN (Logical Cluster Number) — номер первого физического кластера цепочки на томе. NextVCN (Virtual Cluster Number) — логический номер кластера внутри файла, с которого начинается следующая цепочка. Один экстент означает: файл лежит подряд. Много экстентов означает: файл фрагментирован.

Как это проверяется в задаче 2

DeviceIoControl(hFile, FSCTL_GET_RETRIEVAL_POINTERS, …) просит драйвер NTFS вернуть карту кластеров файла. Драйвер возвращает карту в структуру RETRIEVAL_POINTERS_BUFFER. Структура хранит поле ExtentCount и массив Extents[] с Lcn и NextVcn. Для резидентного файла карты нет. Драйвер возвращает ошибку ERROR_HANDLE_EOF (код 38). Программа использует этот код как признак резидентности, а не как сбой: это диагностический сигнал.

Типичные ошибки и заблуждения

  • Не считайте порог резидентности ровно 1024 байта. Часть записи занята служебными данными. Порог ниже и плавает.
  • Не считайте ERROR_HANDLE_EOF сбоем программы. В этом контексте код — ожидаемый ответ «кластеров нет».
  • Не запускайте программу на FAT32/exFAT и не ждите того же поведения. Там нет MFT и нет резидентных атрибутов. Коды ошибок там будут другими.
  • Не думайте, что резидентный файл «не занимает места вообще». Файл занимает место в самой MFT. Запись 1 КБ выделяется под файл в любом случае.
  • Выходной буфер outBuf[1024] в задаче 2 вмещает лишь несколько экстентов. У сильно фрагментированного файла DeviceIoControl вернёт ERROR_MORE_DATA. Код этот случай не обрабатывает.
3. Физический размер файла: кластеры и slack

Что это

У файла два размера. Логический размер — сколько байт данных записано. Это число показывают GetFileSizeEx и проводник в графе «Размер». Физический размер («размер на диске») — сколько байт реально выделено на томе под данные файла вне MFT. Это число возвращают проводник в графе «Размер на диске» и AllocationSize из FILE_STANDARD_INFO. Два размера почти никогда не равны.

Кластер — минимальная единица выделения

NTFS выделяет место кластерами. Кластер — блок обычно по 4096 байт (4 КБ) при стандартном форматировании. Файл занимает целое число кластеров, даже если его данные меньше одного кластера. Неиспользованный остаток последнего кластера называется slack (хвост). Хвост принадлежит файлу, но данных в хвосте нет.

Ловушка GetCompressedFileSizeW — почему старый код врал

Несмотря на слово Compressed в имени, GetCompressedFileSizeW для обычного файла возвращает логический размер. Обычный файл — это несжатый и не разреженный файл. Функция возвращает то же значение, что и GetFileSize. Документация Microsoft подтверждает это: для несжатого и не разреженного файла функция возвращает фактический размер файла, как GetFileSize. Реальный размер на диске функция даёт только для сжатых и разреженных файлов. Поэтому старый вариант задачи 3 печатал 200 и 2000 вместо правильных 0 и 4096.

Это не баг Windows, а задокументированное поведение функции с вводящим в заблуждение именем. Проводник поступает так же. GetCompressedFileSizeW проводник вызывает только для сжатых и разреженных файлов. Для обычных файлов проводник округляет логический размер вверх до кластера. Так описано у Raymond Chen в статье «Just What Is 'Size on Disk?'».

Прямой путь: AllocationSize

Правильный замер — спросить у самой NTFS, сколько места выделено. Программа вызывает GetFileInformationByHandleEx(hFile, FileStandardInfo, &stdInfo, sizeof(stdInfo)) по открытому дескриптору до CloseHandle. Поле FILE_STANDARD_INFO.AllocationSize хранит выделенный размер. Для резидентного файла поле равно 0. Для нерезидентного файла поле равно числу кластеров, умноженному на размер кластера. Пример: 2000 байт дают 4096 при кластере 4 КБ.

Альтернативный прямой путь повторяет путь проводника. Программа узнаёт размер кластера через GetDiskFreeSpace. Программа округляет логический размер вверх до кластера. Программа проверяет резидентность через FSCTL_GET_RETRIEVAL_POINTERS, как в задаче 2. Ошибка ERROR_HANDLE_EOF означает «резидентный», то есть 0 байт.

Функция возвращает младшие 32 бита размера. Старшие 32 бита функция возвращает через второй параметр (highSize). При ошибке функция возвращает INVALID_FILE_SIZE (0xFFFFFFFF). Тогда программа проверяет GetLastError(). Задача 3 теперь содержит эту проверку.

Почему «размер на диске» зависит от тома

  • Размер кластера задаётся при форматировании. 4 КБ — стандарт, но бывает 512 байт, 8 КБ, 64 КБ. Файл 2000 байт на томе с кластером 8 КБ займёт 8192 байта.
  • Сжатие NTFS: на сжатом томе физический размер меньше логического.
  • Разреженные файлы (sparse): нулевые области не занимают кластеры. Физический размер может быть много меньше логического.
  • Резидентность: маленькие файлы на NTFS занимают 0 байт вне MFT. На FAT32 маленький файл занимает целый кластер.

Типичные ошибки

  • Не путайте логический и физический размеры. Фраза «файл 2000 байт» не означает «2000 байт на диске».
  • Не верьте имени GetCompressedFileSizeW. Для обычных файлов функция возвращает логический размер, а не размер на диске.
  • Не забывайте про старшую часть размера (highSize). Для файлов больше 4 ГБ младших 32 бит недостаточно.
  • Не сравнивайте «размер на диске» между разными томами без учёта размера кластера.
  • Не ожидайте 0 байт для маленького файла на любом диске. Это свойство только NTFS.
4. Синхронный и асинхронный вызовы, блокировка потока

Что это

Синхронный вызов (ReadFile без FILE_FLAG_OVERLAPPED) не возвращает управление, пока операция не завершена. Асинхронный вызов возвращает управление сразу. Программа отслеживает завершение отдельно: событие, GetOverlappedResult, IOCP.

Что происходит с потоком при синхронном чтении

  1. Поток вызывает ReadFile и уходит в ядро. Это системный вызов.
  2. Ядро формирует пакет IRP (I/O Request Packet). Ядро передаёт пакет драйверу диска.
  3. Драйвер ставит запрос в очередь устройства. Данных ещё нет. Поток ждёт.
  4. Планировщик переводит поток из состояния Running в Waiting (Blocked). Поток не получает квантов CPU. Поток не выполняет ни одной инструкции.
  5. Контроллер диска по DMA кладёт данные в память. Контроллер генерирует прерывание.
  6. Драйвер завершает IRP. Планировщик переводит поток в Ready, затем в Running. ReadFile возвращает управление.

Почему зависает GUI

Классическое однопоточное GUI-приложение обрабатывает сообщения в том же потоке, где вызывается чтение. Сообщения — это клики, перерисовка и таймеры. Пока поток находится в Waiting, очередь сообщений не разбирается. Окно не перерисовывается. Кнопки не нажимаются. Windows помечает окно как «Не отвечает».

Именно это имитирует задача 4. Тики — это «пульс» потока интерфейса. Замер тиков на 5-м шаге — это момент зависания.

Как решают проблему блокировки на практике

  • Асинхронный I/O (задача 1) не блокирует тот же поток чтением.
  • Отдельный рабочий поток: тяжёлое чтение уходит в фоновый поток. GUI-поток остаётся свободным.
  • Пул потоков / IOCP: много операций идут без привязки потока к каждой.
  • Чтение порциями: программа заменяет один вызов ReadFile на 64 МБ циклом по маленьким блокам. Программа проверяет между блоками, не пора ли обработать сообщения.

Типичные ошибки

  • Не думайте, что «поток завис» означает «программа сломалась». Поток в Waiting находится в нормальном состоянии. Поток проснётся сам, когда данные будут готовы.
  • Не делайте синхронное чтение в потоке GUI «на чуть-чуть». На HDD или при холодном кэше «чуть-чуть» превращается в секунды зависания.
  • Программа не проверила возвращаемое значение ReadFile. В задаче 4 при ошибке чтения bytesRead останется 0. Программа напечатает «Прочитано 0 МБ» как успех.
  • Не ожидайте видимую паузу на любом диске. На NVMe SSD с тёплым кэшем чтение 64 МБ нулей занимает миллисекунды. Пауза почти незаметна.
5. Общие условия запуска всех программ

Что нужно для запуска любой из четырёх программ

  • Только Windows (Windows 10/11, x64): все программы используют Win32 API (windows.h). На Linux/macOS программы не компилируются.
  • Компилятор: MSVC или MinGW-w64. MSVC: cl /EHsc /W4 файл.cpp в Developer Command Prompt for VS. MinGW-w64: g++ -O2 -o файл.exe файл.cpp. Флаги и библиотеки действуют по умолчанию. Дополнительных .lib не требуется. Все вызовы лежат в kernel32.
  • Рабочая папка: все пути в программах относительные. Программа создаёт файлы в текущей папке, откуда запущен exe. Запускайте программу из папки с exe в cmd или PowerShell, а не двойным кликом. При двойном клике окно консоли закроется сразу после завершения. Вывод прочитать не получится.
  • Том NTFS: обязателен для задач 2 и 3. Задачи 2 и 3 используют MFT и резидентные атрибуты. Задачи 1 и 4 работают на любом томе. Файлы разумно держать на NTFS.
  • Русский вывод: программы сами переключают консоль в UTF-8. Программы вызывают chcp 65001 и _setmode. Шрифт консоли должен поддерживать кириллицу. Обычно подходит Consolas.

Какие правила применены (примерно на 60%):

  • Одна мысль — одно предложение.
  • Описание — не больше 25 слов в предложении, инструкция — не больше 20 слов.
  • Действительный залог: пишется, кто что делает («Windows выделяет кластер», а не «кластер выделяется»).
  • Одно понятие — всегда одно и то же слово: «файл» — всегда «файл», «Windows» — всегда «Windows», без синонимов.
  • Сначала ответ, потом подробности: первое предложение — само определение.
  • Один абзац — одна тема, не больше шести предложений.

Что не применено: собственные имена функций из кода (ReadFile, DeviceIoControl, ERROR_HANDLE_EOF) оставлены как есть, названия граф проводника даны в кавычках, а вступление и этот список правил написаны обычным языком — правила действуют на сами определения.

$DATAЗадачи 2, 3

$DATA — это часть записи MFT, которая хранит данные файла. У маленького файла данные лежат в этой части. У большого файла эта часть хранит карту кластеров.

FSCTL_GET_RETRIEVAL_POINTERSЗадача 2

FSCTL_GET_RETRIEVAL_POINTERS — это команда, которая спрашивает у Windows карту кластеров файла. Программа посылает эту команду через DeviceIoControl. Windows отвечает списком экстентов. Если файл резидентный, Windows отвечает ошибкой ERROR_HANDLE_EOF.

IRPЗадача 4

IRP — это пакет, который описывает одну операцию с диском. Программа читает файл. Windows создаёт IRP. Windows передаёт IRP диску. Диск выполняет операцию. Диск возвращает IRP с результатом.

LCNЗадача 2

LCN — это номер кластера на диске. Windows нумерует кластеры тома подряд. Первый кластер имеет номер 0. LCN показывает, где на диске лежит кусок файла.

MFTЗадачи 2, 3

MFT — это главная таблица NTFS. MFT хранит одну запись для каждого файла. Запись хранит имя файла и размеры файла. У маленького файла запись хранит данные файла. У большого файла запись хранит карту кластеров.

OVERLAPPEDЗадача 1

OVERLAPPED — это структура для асинхронного вызова. Программа передаёт OVERLAPPED в ReadFile или WriteFile. OVERLAPPED хранит номер байта для чтения или записи. OVERLAPPED хранит событие hEvent. Windows сообщает через событие о конце операции.

SlackЗадача 3

Slack — это пустой хвост последнего кластера файла. Файл занимает кластер целиком. Данные файла меньше кластера. Остаток кластера принадлежит файлу. Данных в остатке нет.

VCNЗадача 2

VCN — это номер кластера внутри файла. Первый кусок файла имеет номер 0. Второй кусок файла имеет номер 1. VCN показывает порядок кусков файла. LCN показывает место куска на диске.

Асинхронный вызовЗадача 1

Асинхронный вызов — это вызов, который не ждёт конца операции. Программа отдаёт операцию Windows. Программа сразу продолжает работу. Windows сообщает о готовности через событие. Пример: человек отправляет письмо и идёт дальше.

Блокировка потокаЗадача 4

Блокировка потока — это остановка потока до конца операции. Поток — это одна линия выполнения программы. Поток читает большой файл. Поток ждёт конца чтения. Программа замирает на это время.

КластерЗадачи 2, 3

Кластер — это наименьшая единица диска для файла. Windows выдаёт файл кластерами. Обычно кластер равен 4096 байт. Файл занимает целое число кластеров. Данные файла меньше кластера. Файл всё равно занимает целый кластер.

Логический размерЗадача 3

Логический размер — это число байт данных в файле. Проводник показывает это число в графе «Размер». Файл из 2000 байт имеет логический размер 2000.

Нерезидентный атрибутЗадача 2

Нерезидентный атрибут — это часть записи MFT без данных файла. Эта часть хранит карту кластеров файла. Большие файлы имеют нерезидентный атрибут. Данные большого файла лежат на диске.

Резидентный атрибутЗадача 2

Резидентный атрибут — это часть записи MFT с данными файла. Маленькие файлы имеют резидентный атрибут. Данные маленького файла лежат в записи MFT. Файл не занимает кластеры на диске.

Синхронный вызовЗадачи 1, 4

Синхронный вызов — это вызов, который ждёт конца операции. Программа вызывает ReadFile. Программа ждёт, пока Windows прочитает данные. Потом программа продолжает работу. Пример: человек стоит у кассы и ждёт кассира.

СмещениеЗадача 1

Смещение — это номер байта в файле. Смещение показывает, где начинается чтение или запись. Смещение 0 показывает начало файла. Смещение 4096 показывает байт номер 4096.

Событие (hEvent)Задача 1

Событие — это сигнал о конце операции. Программа создаёт событие и кладёт событие в OVERLAPPED. Windows заканчивает чтение и включает событие. Программа проверяет событие. Программа узнаёт, что данные готовы.

Физический размерЗадача 3

Физический размер — это число байт на диске под данные файла. Проводник показывает это число в графе «Размер на диске». Файл из 2000 байт имеет физический размер 4096. Файл занял один кластер.

Экстент (Data Run)Задача 2

Экстент — это один непрерывный кусок файла на диске. Файл имеет один экстент или несколько экстентов. Кластеры файла лежат в разных местах диска. Каждый экстент имеет два числа. Первое число — это LCN. Второе число — это VCN.
