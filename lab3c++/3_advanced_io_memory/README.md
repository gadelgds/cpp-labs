# Раздел 3. Продвинутый ввод-вывод, архитектура памяти и симуляция СУБД

В этом разделе собраны решения сложных системных задач по работе с небуферизированным вводом-выводом, анализу производительности кэширования, накладным расходам сброса TLB при частых отображениях файлов и прямому управлению страницами виртуальной памяти через ядро Windows API.

## Задача №1. Небуферизированный ввод-вывод (`FILE_FLAG_NO_INTERMEDIATE_BUFFERING`)

* **Исходный файл:** [`task1_no_buffering_bench.cpp`](task1_no_buffering_bench.cpp)

### Условие
Написать программу, которая создает тестовый файл 10 МБ и заполняет его случайными данными. Реализовать чтение с флагом `FILE_FLAG_NO_INTERMEDIATE_BUFFERING`. Продемонстрировать возникновение ошибки `ERROR_INVALID_PARAMETER` (код 87) при невыровненном буфере. Исправить ошибку через `VirtualAlloc` с выравниванием по границе страницы/сектора (4096 байт) и размером, кратным 4096. Сравнить скорость чтения с кэшем и без него через `QueryPerformanceCounter`.

### Подробный построчный разбор программы

#### 1. Системные требования флага `FILE_FLAG_NO_INTERMEDIATE_BUFFERING`
При передаче флага `FILE_FLAG_NO_INTERMEDIATE_BUFFERING` драйвер файловой системы Windows обходит системный файловый кэш (System Cache Manager). Передача данных осуществляется контроллером диска напрямую в память вызывающего процесса через **Direct Memory Access (DMA)**.
Аппаратный контроллер диска требует строгого соблюдения трех правил выравнивания:
1. **Указатель буфера в памяти:** адрес начала буфера обязан быть выровнен на границу физического сектора диска (кратен 4096 байтам). Стандартные массивы на стеке (`char buf[1000]`) или `malloc / new` выделяют память без гарантии кратности 4096.
2. **Файловое смещение:** смещение чтения или записи обязано быть кратно размеру сектора (4096 байт).
3. **Объем передаваемых данных:** размер буфера при `ReadFile / WriteFile` обязан быть строго кратен размеру сектора (4096 байт).
* Если хотя бы одно правило нарушено, вызов `ReadFile` немедленно падает с ошибкой **`ERROR_INVALID_PARAMETER` (код 87)**.

#### 2. Демонстрация ошибки (Код 87)
```cpp
HANDLE hDirect = CreateFileW(testFile, GENERIC_READ, FILE_SHARE_READ, NULL, OPEN_EXISTING, 
                             FILE_FLAG_NO_INTERMEDIATE_BUFFERING, NULL);

char unalignedBuf[1000]; // Размер 1000 не кратен 4096, адрес на стеке не кратен 4096!
DWORD bytesRead = 0;
BOOL result = ReadFile(hDirect, unalignedBuf, sizeof(unalignedBuf), &bytesRead, NULL);
// result == FALSE, GetLastError() == ERROR_INVALID_PARAMETER (87)
```

#### 3. Исправление через `VirtualAlloc`
```cpp
const DWORD alignedChunkSize = 64 * 1024; // 64 КБ (кратно 4096)
void* alignedBuffer = VirtualAlloc(
    NULL,
    alignedChunkSize,
    MEM_COMMIT | MEM_RESERVE,
    PAGE_READWRITE
);
```
* `VirtualAlloc` запрашивает память напрямую у диспетчера виртуальной памяти ядра Windows.
* Все адреса, возвращаемые `VirtualAlloc`, **автоматически выровнены по границе страницы памяти (4096 байт)**.
* Размер `alignedChunkSize` (64 КБ = 16 секторов по 4096) идеально удовлетворяет требованиям контроллера DMA.
* Вызов `ReadFile` выполняется успешно.

#### 4. Бенчмарк: Кэшированный vs Прямой ввод-вывод
```cpp
LARGE_INTEGER freq, start, end;
QueryPerformanceFrequency(&freq);
QueryPerformanceCounter(&start);
// ... чтение ...
QueryPerformanceCounter(&end);
double timeMs = (end.QuadPart - start.QuadPart) * 1000.0 / freq.QuadPart;
```
* **Чтение со системным кэшем:** быстрее при повторных чтениях и небольших файлах, так как ОС выполняет агрессивное упреждающее чтение (Read-Ahead) и хранит страницы в оперативной памяти.
* **Чтение без кэша:** быстрее на гигантских файлах (десятки гигабайт) или в базах данных (СУБД), так как не тратит процессорные такты на лишнее копирование байт из кэша ядра в буфер пользователя и не "засоряет" системную память.

## Задача №2. Симуляция СУБД: случайный доступ, проецирование и сброс TLB

* **Исходный файл:** [`task2_dbms_sim_filemapping_tlb.cpp`](task2_dbms_sim_filemapping_tlb.cpp)

### Условие
Создать бинарный файл 16 МБ с последовательностью `int`. Симулировать работу СУБД со случайным доступом и модификацией данных в двух режимах:
* **Режим А (Стандартный I/O):** `ReadFile / WriteFile` с системным кэшем.
* **Режим Б (Ручное проецирование):** Динамическое подключение скользящего окна через `MapViewOfFile`, модификация и принудительное размонтирование `UnmapViewOfFile`.
Замерить время выполнения 10 000 случайных операций записи и объяснить накладные расходы сброса TLB (**TLB Flush**).

### Подробный разбор архитектурных механизмов

#### 1. Режим А: Стандартный I/O
```cpp
SetFilePointerEx(hFileA, offset, NULL, FILE_BEGIN);
ReadFile(hFileA, &value, sizeof(int), &bytesRead, NULL);
value += 1;
SetFilePointerEx(hFileA, offset, NULL, FILE_BEGIN);
WriteFile(hFileA, &value, sizeof(int), &bytesWritten, NULL);
```
* Системный кэш Windows (`System Cache`) удерживает страницы файла в оперативной памяти.
* При вызове `ReadFile` и `WriteFile` ядро быстро находит нужную 4 КБ страницу в кэше и обновляет ее без выгрузки из виртуального пространства.

#### 2. Режим Б: Скользящее окно `MapViewOfFile` + `UnmapViewOfFile`
```cpp
DWORD alignedOffsetLow = (DWORD)((byteOffset / allocGranularity) * allocGranularity);
DWORD offsetWithinWindow = (DWORD)(byteOffset % allocGranularity);

char* pView = static_cast<char*>(MapViewOfFile(hMappingB, FILE_MAP_ALL_ACCESS, 0, alignedOffsetLow, windowSize));
int* pVal = reinterpret_cast<int*>(pView + offsetWithinWindow);
*pVal += 1;

UnmapViewOfFile(pView); // Принудительное размонтирование!
```

#### 3. Физика процесса и почему возникает просадка производительности из-за TLB Flush:
1. **Что такое TLB (Translation Lookaside Buffer):**
   * TLB — это высокоскоростной аппаратный ассоциативный кэш внутри микропроцессора (CPU).
   * Он хранит соответствия между **виртуальными адресами** программы и **физическими адресами** чипов оперативной памяти (Virtual Address $\to$ Physical Page Frame).
2. **Накладные расходы вызова `MapViewOfFile`:**
   * Ядро Windows ищет свободный диапазон виртуальных адресов;
   * Вносит новую запись в каталог страниц (Page Directory) и таблицу страниц (Page Table) процесса;
   * При первом обращении к памяти генерируется аппаратное исключение **Page Fault**, и ядро связывает физическую страницу с процессом.
3. **Накладные расходы вызова `UnmapViewOfFile`:**
   * Ядро обязано стереть записи отображения из таблиц страниц;
   * Процессор обязан удалить устаревшие соответствия адресов из аппаратного кэша TLB. Для этого ядро Windows выполняет специальную инструкцию процессора **`INVLPG` (Invalidate TLB Entry)** или перезаписывает регистр управления `CR3`, что сбрасывает весь кэш TLB текущего процесса (**TLB Shootdown / Flush**).
4. **Итог сравнения:**
   * Выполнение 10 000 повторных циклов "Map $\to$ Unmap" тратит огромное количество тактов процессора на системные вызовы ядра, манипуляции с таблицами страниц и постоянную инвалидацию аппаратного кэша TLB!
   * Поэтому при случайном точечном доступе к разным участкам файла архитектура со постоянным монтированием и размонтированием маленьких окон проигрывает непрерывному маппингу или стандартному кэшированному I/O.

## Задача №3. Прямое выделение памяти у ядра Windows (`VirtualAlloc`)

* **Исходный файл:** [`task3_direct_kernel_memory.cpp`](task3_direct_kernel_memory.cpp)

### Условие
Запросить у пользователя размер массива целых чисел (например, 10 000 элементов). Выделить память напрямую у ядра ОС Windows. Заполнить массив квадратами индексов ($i \times i$) и вывести первые 10 элементов. Освободить память.

### Построчный разбор системных вызовов

#### 1. Запрос размера и расчет байт
```cpp
size_t count = 10000;
size_t sizeInBytes = count * sizeof(int); // 40 000 байт (~39 КБ)
```

#### 2. Прямое выделение памяти у ядра: `VirtualAlloc`
```cpp
int* pArray = static_cast<int*>(VirtualAlloc(
    NULL,                     // 1. Базовый адрес: NULL означает, что ядро выбирает адрес автоматически
    sizeInBytes,              // 2. Требуемый объем в байтах
    MEM_COMMIT | MEM_RESERVE, // 3. Тип операции: резервирование и коммитирование
    PAGE_READWRITE            // 4. Защита страниц: чтение и запись
));
```
* **Чем `VirtualAlloc` отличается от `new` и `malloc`:**
  * `new` и `malloc` работают с "кучей" процесса (CRT Heap / Win32 Heap Manager). Они выделяют память из пула, созданного библиотекой языка Си, что создает накладные расходы на заголовки блоков.
  * `VirtualAlloc` работает **напрямую с ядром ОС Windows (Virtual Memory Manager)**. Память выделяется целыми страницами (обычно кратно 4096 байтам).
* `MEM_RESERVE` — резервирует диапазон виртуальных адресов в адресном пространстве процесса (но пока не привязывает физическую RAM).
* `MEM_COMMIT` — привязывает физическую оперативную память (или страницы в файле подкачки) к зарезервированному виртуальному диапазону.
* `PAGE_READWRITE` — устанавливает атрибуты защиты страниц на уровне контроллера памяти MMU: разрешено чтение и запись.

#### 3. Заполнение и вывод
```cpp
for (size_t i = 0; i < count; ++i) {
    pArray[i] = static_cast<int>(i * i);
}
```
* Заполняет ячейки памяти квадратами индексов ($0, 1, 4, 9, 16, 25, 36, 49, 64, 81...$).

#### 4. Прямое освобождение памяти ядру: `VirtualFree`
```cpp
BOOL freeSuccess = VirtualFree(
    pArray,     // Базовый адрес начала блока страниц
    0,          // Для флага MEM_RELEASE размер ОБЯЗАН быть равен 0!
    MEM_RELEASE // Полный возврат страниц ядру
);
```
* `MEM_RELEASE` — де-коммитирует физические страницы памяти и освобождает зарезервированный диапазон виртуальных адресов обратно ядру Windows.
* **Важное правило Win32 API:** при передаче `MEM_RELEASE` параметр размера *обязан быть строго равен 0*. Ядро Windows автоматически освобождает весь блок, выделенный исходным вызовом `VirtualAlloc`.
