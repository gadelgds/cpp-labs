1. Асинхронный I/O, OVERLAPPED и события (hEvent)

Что это

Синхронный вызов ReadFile возвращает управление только после того, как данные уже лежат в памяти. Асинхронный вызов возвращает управление сразу. Данные дочитываются в фоне: контроллер диска передаёт их по DMA. Поток в это время свободен. Поток делает другую работу или спит в ожидании события.

В Win32 программа включает асинхронность на уровне дескриптора. Программа передаёт флаг FILE_FLAG_OVERLAPPED в CreateFileW. Без флага Windows игнорирует OVERLAPPED, и все операции идут синхронно. Программа включает флаг при открытии файла. Позже добавить флаг нельзя.

Структура OVERLAPPED — поля

ПолеНазначение
Offset / OffsetHighДва поля задают 64-битное смещение операции в файле. Первое поле хранит младшие 32 бита. Второе поле хранит старшие 32 бита. В асинхронном режиме файл не имеет текущего указателя. Программа задаёт смещение явно при каждой операции.
hEventСобытие ядра — это hEvent. Драйвер переводит событие в сигнальное состояние, когда операция завершается. Событие может быть NULL. Тогда программа узнаёт о завершении только через GetOverlappedResult.
Internal / InternalHighПоля Internal и InternalHigh — служебные поля ядра. Internal хранит код завершения операции. InternalHigh хранит число переданных байт. Программа не заполняет эти поля. Их пишет драйвер.
PointerСистема резервирует это поле. Программа не использует это поле.

Как узнать, что операция завершена

СпособКак работаетКогда удобен
WaitForSingleObject(hEvent, INFINITE)Поток засыпает до сигнала события. Поток не тратит CPU. Загрузка CPU — 0%.Этот способ подходит для одной операции и простого ожидания. Задача 1 использует этот способ.
GetOverlappedResult(hFile, &ov, &bytes, TRUE)Вызов сам ждёт завершения операции. Последний аргумент TRUE включает ожидание. Вызов возвращает число переданных байт.Этот способ подходит, когда программа не создавала событие.
GetOverlappedResult(…, FALSE)Вызов не ждёт завершения операции. Вызов возвращает результат уже завершённой операции.Программа вызывает этот вариант после ожидания события. Задача 1 использует этот вариант.
WaitForMultipleObjectsВызов ждёт сразу несколько событий.Этот способ подходит для многих параллельных операций.
Completion Port (IOCP)Ядро само складывает завершённые операции в очередь.Этот способ подходит для серверов с тысячами операций. Он даёт высшую производительность.

События: ручной и автоматический сброс

CreateEventW(NULL, TRUE, FALSE, NULL) создаёт событие с ручным сбросом (manual-reset). После срабатывания событие остаётся сигнальным до явного вызова ResetEvent. Поэтому задача 1 вызывает ResetEvent перед каждым чтением и записью. Без сброса WaitForSingleObject сразу вернулся бы по старому сигналу. Событие с автоматическим сбросом гаснет само, когда один ожидающий поток просыпается. Автоматический сброс включает FALSE вторым аргументом.

Ключевые правила

  • Всегда обнуляйте OVERLAPPED (memset) перед первым использованием. Мусор в полях смещения даёт чтение не оттуда или сбой.
  • FALSE от асинхронного ReadFile/WriteFile — норма. Ошибка возникает только при GetLastError() != ERROR_IO_PENDING (997). Читайте код ошибки сразу после вызова.
  • Буфер нельзя трогать до завершения операции. Пока драйвер пишет в буфер по DMA, чтение из буфера или повторная запись дают гонку данных. Поэтому задача 1 выполняет чтение и запись строго по очереди.
  • Четвёртый аргумент ReadFile/WriteFile — NULL при OVERLAPPED. Программа забирает число байт только через GetOverlappedResult.
  • Один OVERLAPPED — одна операция. Не переиспользуйте структуру, пока операция не завершена.

Типичные ошибки

  • Программа забыла FILE_FLAG_OVERLAPPED при открытии. Операции стали синхронными. ERROR_IO_PENDING никогда не возникает.
  • Программа забыла ResetEvent перед операцией. Ожидание мгновенно «проходит». Данные ещё не готовы.
  • Программа забыла задать Offset/OffsetHigh. Чтение идёт с нулевого или мусорного смещения.
  • Программа проверила только readRet == FALSE и решила, что это ошибка. Программа «падает» на первом же нормальном чтении.
  • Программа не проверила возвращаемое значение GetOverlappedResult. При сбое чтения bytesTransferred может содержать старое значение. Программа этого не заметит. Задача 1 показывает этот случай.

Мини-пример: чтение одного блока

HANDLE hEvent = CreateEventW(NULL, TRUE, FALSE, NULL); OVERLAPPED ov = {}; ov.hEvent = hEvent; ov.Offset = 0; ReadFile(h, buf, 4096, NULL, &ov); // FALSE + ERROR_IO_PENDING — нормально. WaitForSingleObject(hEvent, INFINITE); DWORD n = 0; GetOverlappedResult(h, &ov, &n, FALSE); // n — реально прочитано

2. NTFS MFT и атрибуты $DATA: резидентные и нерезидентные

Что это

MFT (Master File Table) — главная таблица файлов NTFS. MFT — массив записей фиксированного размера 1024 байта (1 КБ). MFT хранит одну запись на каждый файл и каталог тома. Запись MFT — не сами данные, а «паспорт» файла. Запись хранит заголовок и набор атрибутов.

Основные атрибуты записи MFT

АтрибутЧто хранит
$STANDARD_INFORMATIONАтрибут хранит время создания файла и время изменения файла. Атрибут хранит флаги файла: скрытый, системный и другие.
$FILE_NAMEАтрибут хранит имя файла. Атрибут хранит ссылку на родительский каталог.
$DATAАтрибут хранит содержимое файла. Содержимое лежит резидентно или нерезидентно. Подробности — ниже.
$SECURITY_DESCRIPTORАтрибут хранит права доступа (ACL).
$ATTRIBUTE_LISTАтрибут хранит список продолжений. Продолжения нужны, если атрибуты не влезли в одну запись MFT.

Резидентный и нерезидентный $DATA

Резидентный (Resident)Нерезидентный (Non-Resident)
Где данныеДанные файла лежат прямо внутри 1024-байтной записи MFT.Данные файла лежат в отдельных кластерах тома. Кластеры лежат вне MFT.
Что в MFTЗапись MFT хранит сами байты файла.Запись MFT хранит список Data Runs. Data Runs — это цепочки кластеров (экстенты).
КогдаФайл маленький. Заголовок и служебные атрибуты оставляют свободное место в записи. На практике порог — около 700 байт. Порог зависит от длины имени и других атрибутов.Файл не помещается в свободное место записи.
Кластеры на дискеWindows не выделяет кластеры. Проводник показывает размер на диске 0 байт.Windows выделяет кластеры целиком.
Пример из задачи 2200 байт.2500 байт и 500 КБ.

Важно: порог резидентности — не ровно 1024 и не ровно 700 байт. Запись MFT занята заголовком, $STANDARD_INFORMATION, $FILE_NAME и заголовком самого $DATA. Поэтому свободного места обычно около 700 байт. Точное значение зависит от длины имени файла и наличия других атрибутов. Поэтому файл 200 байт — заведомо резидентный, а файл 2500 байт — заведомо нерезидентный.

Data Runs и экстенты: VCN и LCN

Нерезидентный файл описывается цепочками непрерывных кластеров — экстентами (Data Runs). Каждый экстент имеет два номера. LCN (Logical Cluster Number) — номер первого физического кластера цепочки на томе. NextVCN (Virtual Cluster Number) — логический номер кластера внутри файла, с которого начинается следующая цепочка. Один экстент означает: файл лежит подряд. Много экстентов означает: файл фрагментирован.

Как это проверяется в задаче 2

DeviceIoControl(hFile, FSCTL_GET_RETRIEVAL_POINTERS, …) просит драйвер NTFS вернуть карту кластеров файла. Драйвер возвращает карту в структуру RETRIEVAL_POINTERS_BUFFER. Структура хранит поле ExtentCount и массив Extents[] с Lcn и NextVcn. Для резидентного файла карты нет. Драйвер возвращает ошибку ERROR_HANDLE_EOF (код 38). Программа использует этот код как признак резидентности, а не как сбой: это диагностический сигнал.

Типичные ошибки и заблуждения

  • Не считайте порог резидентности ровно 1024 байта. Часть записи занята служебными данными. Порог ниже и плавает.
  • Не считайте ERROR_HANDLE_EOF сбоем программы. В этом контексте код — ожидаемый ответ «кластеров нет».
  • Не запускайте программу на FAT32/exFAT и не ждите того же поведения. Там нет MFT и нет резидентных атрибутов. Коды ошибок там будут другими.
  • Не думайте, что резидентный файл «не занимает места вообще». Файл занимает место в самой MFT. Запись 1 КБ выделяется под файл в любом случае.
  • Выходной буфер outBuf[1024] в задаче 2 вмещает лишь несколько экстентов. У сильно фрагментированного файла DeviceIoControl вернёт ERROR_MORE_DATA. Код этот случай не обрабатывает.
3. Физический размер файла: кластеры и slack

Что это

У файла два размера. Логический размер — сколько байт данных записано. Это число показывают GetFileSizeEx и проводник в графе «Размер». Физический размер («размер на диске») — сколько байт реально выделено на томе под данные файла вне MFT. Это число возвращают проводник в графе «Размер на диске» и AllocationSize из FILE_STANDARD_INFO. Два размера почти никогда не равны.

Кластер — минимальная единица выделения

NTFS выделяет место кластерами. Кластер — блок обычно по 4096 байт (4 КБ) при стандартном форматировании. Файл занимает целое число кластеров, даже если его данные меньше одного кластера. Неиспользованный остаток последнего кластера называется slack (хвост). Хвост принадлежит файлу, но данных в хвосте нет.

Логический размерРезидентностьФизический размер (кластер 4 КБ)Пояснение

0 байт (пустой файл)Резидентный0 байтДанных нет. Кластеры не нужны.

Ловушка GetCompressedFileSizeW — почему старый код врал

Несмотря на слово Compressed в имени, GetCompressedFileSizeW для обычного файла возвращает логический размер. Обычный файл — это несжатый и не разреженный файл. Функция возвращает то же значение, что и GetFileSize. Документация Microsoft подтверждает это: для несжатого и не разреженного файла функция возвращает фактический размер файла, как GetFileSize. Реальный размер на диске функция даёт только для сжатых и разреженных файлов. Поэтому старый вариант задачи 3 печатал 200 и 2000 вместо правильных 0 и 4096.

Это не баг Windows, а задокументированное поведение функции с вводящим в заблуждение именем. Проводник поступает так же. GetCompressedFileSizeW проводник вызывает только для сжатых и разреженных файлов. Для обычных файлов проводник округляет логический размер вверх до кластера. Так описано у Raymond Chen в статье «Just What Is 'Size on Disk?'».

Прямой путь: AllocationSize

Правильный замер — спросить у самой NTFS, сколько места выделено. Программа вызывает GetFileInformationByHandleEx(hFile, FileStandardInfo, &stdInfo, sizeof(stdInfo)) по открытому дескриптору до CloseHandle. Поле FILE_STANDARD_INFO.AllocationSize хранит выделенный размер. Для резидентного файла поле равно 0. Для нерезидентного файла поле равно числу кластеров, умноженному на размер кластера. Пример: 2000 байт дают 4096 при кластере 4 КБ.

Альтернативный прямой путь повторяет путь проводника. Программа узнаёт размер кластера через GetDiskFreeSpace. Программа округляет логический размер вверх до кластера. Программа проверяет резидентность через FSCTL_GET_RETRIEVAL_POINTERS, как в задаче 2. Ошибка ERROR_HANDLE_EOF означает «резидентный», то есть 0 байт.

Функция возвращает младшие 32 бита размера. Старшие 32 бита функция возвращает через второй параметр (highSize). При ошибке функция возвращает INVALID_FILE_SIZE (0xFFFFFFFF). Тогда программа проверяет GetLastError(). Задача 3 теперь содержит эту проверку.

Почему «размер на диске» зависит от тома

  • Размер кластера задаётся при форматировании. 4 КБ — стандарт, но бывает 512 байт, 8 КБ, 64 КБ. Файл 2000 байт на томе с кластером 8 КБ займёт 8192 байта.
  • Сжатие NTFS: на сжатом томе физический размер меньше логического.
  • Разреженные файлы (sparse): нулевые области не занимают кластеры. Физический размер может быть много меньше логического.
  • Резидентность: маленькие файлы на NTFS занимают 0 байт вне MFT. На FAT32 маленький файл занимает целый кластер.

Типичные ошибки

  • Не путайте логический и физический размеры. Фраза «файл 2000 байт» не означает «2000 байт на диске».
  • Не верьте имени GetCompressedFileSizeW. Для обычных файлов функция возвращает логический размер, а не размер на диске.
  • Не забывайте про старшую часть размера (highSize). Для файлов больше 4 ГБ младших 32 бит недостаточно.
  • Не сравнивайте «размер на диске» между разными томами без учёта размера кластера.
  • Не ожидайте 0 байт для маленького файла на любом диске. Это свойство только NTFS.
4. Синхронный и асинхронный вызовы, блокировка потока

Что это

Синхронный вызов (ReadFile без FILE_FLAG_OVERLAPPED) не возвращает управление, пока операция не завершена. Асинхронный вызов возвращает управление сразу. Программа отслеживает завершение отдельно: событие, GetOverlappedResult, IOCP.

Что происходит с потоком при синхронном чтении

  1. Поток вызывает ReadFile и уходит в ядро. Это системный вызов.
  2. Ядро формирует пакет IRP (I/O Request Packet). Ядро передаёт пакет драйверу диска.
  3. Драйвер ставит запрос в очередь устройства. Данных ещё нет. Поток ждёт.
  4. Планировщик переводит поток из состояния Running в Waiting (Blocked). Поток не получает квантов CPU. Поток не выполняет ни одной инструкции.
  5. Контроллер диска по DMA кладёт данные в память. Контроллер генерирует прерывание.
  6. Драйвер завершает IRP. Планировщик переводит поток в Ready, затем в Running. ReadFile возвращает управление.

Таблица состояний потока

СостояниеЧто делает потокПример из задачи 4
RunningПоток выполняется на ядре CPU.Поток печатает тики 1–4.
ReadyПоток готов к выполнению. Поток ждёт свободного ядра.Поток кратко проходит это состояние после завершения чтения.
Waiting (Blocked)Поток спит. Поток не получает CPU, пока не наступит событие.Пауза длится от тика 5 до сообщения о завершении чтения.

Почему зависает GUI

Классическое однопоточное GUI-приложение обрабатывает сообщения в том же потоке, где вызывается чтение. Сообщения — это клики, перерисовка и таймеры. Пока поток находится в Waiting, очередь сообщений не разбирается. Окно не перерисовывается. Кнопки не нажимаются. Windows помечает окно как «Не отвечает».

Именно это имитирует задача 4. Тики — это «пульс» потока интерфейса. Замер тиков на 5-м шаге — это момент зависания.

Синхронный vs асинхронный — сравнение

Как решают проблему блокировки на практике

  • Асинхронный I/O (задача 1) не блокирует тот же поток чтением.
  • Отдельный рабочий поток: тяжёлое чтение уходит в фоновый поток. GUI-поток остаётся свободным.
  • Пул потоков / IOCP: много операций идут без привязки потока к каждой.
  • Чтение порциями: программа заменяет один вызов ReadFile на 64 МБ циклом по маленьким блокам. Программа проверяет между блоками, не пора ли обработать сообщения.

Типичные ошибки

  • Не думайте, что «поток завис» означает «программа сломалась». Поток в Waiting находится в нормальном состоянии. Поток проснётся сам, когда данные будут готовы.
  • Не делайте синхронное чтение в потоке GUI «на чуть-чуть». На HDD или при холодном кэше «чуть-чуть» превращается в секунды зависания.
  • Программа не проверила возвращаемое значение ReadFile. В задаче 4 при ошибке чтения bytesRead останется 0. Программа напечатает «Прочитано 0 МБ» как успех.
  • Не ожидайте видимую паузу на любом диске. На NVMe SSD с тёплым кэшем чтение 64 МБ нулей занимает миллисекунды. Пауза почти незаметна.
5. Общие условия запуска всех программ

Что нужно для запуска любой из четырёх программ

  • Только Windows (Windows 10/11, x64): все программы используют Win32 API (windows.h). На Linux/macOS программы не компилируются.
  • Компилятор: MSVC или MinGW-w64. MSVC: cl /EHsc /W4 файл.cpp в Developer Command Prompt for VS. MinGW-w64: g++ -O2 -o файл.exe файл.cpp. Флаги и библиотеки действуют по умолчанию. Дополнительных .lib не требуется. Все вызовы лежат в kernel32.
  • Рабочая папка: все пути в программах относительные. Программа создаёт файлы в текущей папке, откуда запущен exe. Запускайте программу из папки с exe в cmd или PowerShell, а не двойным кликом. При двойном клике окно консоли закроется сразу после завершения. Вывод прочитать не получится.
  • Том NTFS: обязателен для задач 2 и 3. Задачи 2 и 3 используют MFT и резидентные атрибуты. Задачи 1 и 4 работают на любом томе. Файлы разумно держать на NTFS.
  • Русский вывод: программы сами переключают консоль в UTF-8. Программы вызывают chcp 65001 и _setmode. Шрифт консоли должен поддерживать кириллицу. Обычно подходит Consolas.
